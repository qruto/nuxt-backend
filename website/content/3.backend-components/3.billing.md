`setupBilling(components)` wires subscriptions, discounts, **prepaid credits**, and **gift purchases** via the [Polar](https://www.convex.dev/components/polar) component, linked to your auth users. The reactive **feature + credit cache** and the gift records live inside the all-in-one `backend` component (`components.backend.billing` / `components.backend.gifts`), so **you add nothing to your schema**.

## Server setup

`setupBilling` needs **no config**: the access token, environment, and webhook secret default to the required `BILLING_ACCESS_TOKEN` / `BILLING_ENVIRONMENT` / `BILLING_WEBHOOK_SECRET` env vars, and the billing entity resolves from identity claims — the active workspace by default (`billTo: 'organization'`), or the signed-in user with `billTo: 'user'`.

```ts [backend/billing.ts]
import { setupBilling } from 'nuxt-backend/billing'
import { components } from './_generated/api'

const billing = setupBilling(components)

export const { provider } = billing
export const {
  generateCheckoutLink,
  generateCustomerPortalUrl,
  getConfiguredProducts,
  listAllProducts,
  listAllSubscriptions,
  changeCurrentSubscription,
  cancelCurrentSubscription,
  giftCheckout,
} = billing.api
export const {
  getCurrentSubscription,
  getFeatures,
  getCredits,
  syncEntitlements,
  getReceivedGifts,
  claimGift,
} = billing.functions
export const { webhookEvents } = billing
```

Config is optional — pass it to override the env-var defaults (`accessToken`, `environment`, `webhookSecret`), switch `billTo`, throttle syncs (`rateLimiter`), hook webhook events (`events`), restyle the gift email (`giftEmail`), or override entity resolution (`getUserInfo` / `currentUserId`, consulted with `billTo: 'user'`).

`setupBilling(...)` returns:

::field-group
  :::field{name="api"}
  Checkout / portal / product / subscription functions to re-export, plus `giftCheckout` (a checkout billed to someone else's email).
  :::

  :::field{name="functions"}
  Ready-made reactive functions to re-export so the composables work with zero wiring: `getCurrentSubscription` (→ `useBilling`), `getFeatures` (→ `useFeatures`), `getCredits` (→ `useCredits`), `getReceivedGifts` / `claimGift` (→ `useGifts`), and a `syncEntitlements` action to refresh the cache after checkout/top-up.
  :::

  :::field{name="webhookEvents"}
  Typed billing webhook handlers that keep the cache fresh (subscriptions, benefit grants, credit balances) and fulfil gifts. Mounted at `/billing/events` by [`registerBackendRoutes`](/backend-components/webhooks).
  :::

  :::field{name="spendCredits(ctx, { userId?, name, meterId?, value? })"}
  Spend prepaid credits from your **own** server code. With `meterId` set it throws when the balance is too low, so credits are never billed as overage.
  :::

  :::field{name="getCustomerState / createDiscount / provider"}
  Live customer state, coupon creation, and the underlying billing-provider client (an advanced escape hatch — `provider.polar` is the raw SDK).
  :::
::

## Prepaid credits

Credits are the provider's official model: a credit pack is a one-time product whose *Credits* benefit tops up a meter balance (no backend crediting code needed). The client tops up via `useCredits().topUp(packId)` (a checkout) and the balance is drawn down by `spendCredits`.

## Gifting

A signed-in user can buy credits or a plan **for someone else**, identified only by email:

```vue
<script setup lang="ts">
const { gift } = useCredits()

async function sendGift() {
  await gift('prod_credit_pack', {
    recipientEmail: 'friend@example.com',
    message: 'Happy birthday!',
  })
}
</script>
```

`useBilling().gift(productIds, { recipientEmail, message?, … })` and `useCredits().gift(...)` open a checkout billed to a provider customer keyed by the **recipient's** email — the purchaser pays, the recipient owns the entitlements. On the `order.paid` webhook the package marks the gift paid and:

- **Recipient already has an account** — the gift attaches automatically (in workspace mode, to their personal workspace), and they're notified by email.
- **No account yet** — the recipient gets an email linking to `SITE_URL`; on their first sign-in `useGifts()` claims every paid gift automatically.

```vue
<script setup lang="ts">
// Explicit claiming instead of auto-claim:
const gifts = useGifts({ autoClaim: false })
</script>

<template>
  <GiftClaimBanner />  <!-- or your own UI over gifts.unclaimed / gifts.claim() -->
</template>
```

The notification email is restylable via `giftEmail` in the `setupBilling` config:

```ts
setupBilling(components, {
  giftEmail: ({ recipientEmail, purchaserName, message, claimUrl }) => ({
    to: recipientEmail,
    subject: `${purchaserName ?? 'Someone'} sent you a gift 🎁`,
    html: `…<a href="${claimUrl}">Receive it</a>`,
  }),
})
```

::warning
If the recipient's account already bills through a provider customer under a **different** email, the gift can't attach — entitlements can't move between provider customers. The sender should re-gift to the email the recipient's billing runs under.
::

## Reactive composables

The auto-imported composables read the cache reactively:

```vue
<script setup lang="ts">
// Subscription state + checkout/portal
const billing = useBilling()
// billing.subscription, billing.isSubscribed, billing.checkout(...), billing.gift(...)

// Feature-gating
const { has, hasPlan } = useFeatures()
// has('priority_support'), hasPlan('prod_pro')

// Prepaid credits
const credits = useCredits()
// credits.balance, credits.topUp(packId), credits.gift(...), credits.refresh()

// Gifts addressed to the signed-in user
const gifts = useGifts()
// gifts.received, gifts.unclaimed, gifts.claim(giftId?)
</script>
```

There are also a `<CheckoutLink>` component for launching checkouts, a `<FeatureBoundary feature="…">` / `<FeatureBoundary :plan="…">` component that renders its slot only when the entitlement is active (with `#fallback` / `#placeholder` slots — the billing counterpart of `<RoleBoundary>`), and a `<GiftClaimBanner>` for surfacing unclaimed gifts.

## Feature-gating by a friendly name

`useFeatures().has(feature)` matches a granted benefit by its benefit id, grant id, `type`, **or any value in the benefit's metadata**. So set a stable key on the benefit in the Polar dashboard (e.g. metadata `{ key: 'premium' }`) and gate with `has('premium')` instead of hardcoding a UUID.

::tip
The cache reads the benefit's metadata **live** (not the grant-time snapshot), so changing it takes effect on the next sync — no re-granting.
::

## Environment

Billing is configured by three of the [required env vars](/getting-started/configuration#convex-deployment-variables):

| Variable | Purpose |
|---|---|
| `BILLING_ACCESS_TOKEN` | The provider organization access token |
| `BILLING_WEBHOOK_SECRET` | Verifies webhooks on `/billing/events` |
| `BILLING_ENVIRONMENT` | `sandbox` or `production` |
