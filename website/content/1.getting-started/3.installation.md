## Prerequisites

- A [Convex](https://convex.dev) deployment (`npx convex dev` creates one).
- Node and a package manager. The bundled Convex components ship as dependencies of `nuxt-backend`; the only other package you add is `convex` itself — its peer, and the CLI you run.

::steps{level="3"}

### Install the package

::code-group
```bash [nuxi]
npx nuxi@latest module add nuxt-backend
npm install convex
```

```bash [pnpm]
pnpm add nuxt-backend convex
```

```bash [npm]
npm install nuxt-backend convex
```

```bash [yarn]
yarn add nuxt-backend convex
```
::

::note{to="#using-strict-pnpm"}
The bundled components (`@convex-dev/aggregate`, `migrations`, `polar`, `rate-limiter`, `resend`, `workflow`, `better-auth`) come in transitively — you never add them to your own `package.json`. `convex` is the one peer you declare yourself: a package manager installs it either way, but `npx convex dev` reads your `package.json` and refuses to run until it is listed there (`npx nuxt-backend init` adds it when missing). Strict pnpm needs one extra line; see the note below.
::

### Add the Nuxt module

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-backend'],
})
```

In a fresh `nuxi init` app, `app/app.vue` still renders `<NuxtWelcome />` and no `<NuxtPage />` — the pages this module registers (`/login`, `/pricing`, …) resolve but never render. Replace `<NuxtWelcome />` with `<NuxtPage />` (`npx nuxt-backend init` does it while the file is still the starter; the dev console warns while it is not done).

### Configure environment variables

`npx nuxt-backend init` writes a `.env.example` grouped by what each value is for — copy it to `.env.local`. Nothing in it is required in dev: the backend URLs derive from the deployment slug the platform CLI writes, and `AUTH_SECRET` + `SITE_URL` are provisioned for you on the first run.

```bash [.env.local]
# ── Backend ──────────────────────────────────────────────────────────────────
# Normally derived. Set these only to point at another deployment.
# NUXT_PUBLIC_BACKEND_URL=
# NUXT_PUBLIC_BACKEND_SITE_URL=

# ── Email ────────────────────────────────────────────────────────────────────
# Unset: sends no-op and OTP codes print in the backend dev console.
# EMAIL_API_KEY=
# EMAIL_FROM=
# EMAIL_TEST_MODE=
# EMAIL_WEBHOOK_SECRET=

# ── Billing ──────────────────────────────────────────────────────────────────
# Unset: billing reads return empty and checkout fails on invocation.
# BILLING_ACCESS_TOKEN=
# BILLING_ENVIRONMENT=
# BILLING_WEBHOOK_SECRET=

# ── Dev only ─────────────────────────────────────────────────────────────────
# Also trust the http://localhost:* origin the dev server runs on, in addition
# to SITE_URL. `env push` forwards this to dev deployments, never to production.
# AUTH_TRUST_LOCAL_ORIGINS=1
```

`npx convex dev` adds its own `CONVEX_DEPLOYMENT` line to `.env.local`, under a final **Platform** group. That group belongs to the platform CLI — leave it alone.

#### Deployment environment

The `EMAIL_*` and `BILLING_*` values live on the Convex **deployment**, not in the Nuxt process — `npm run dev` (or `npx nuxt-backend env push`) forwards whatever `.env.local` holds. To set them by hand, via the CLI or the [dashboard](https://dashboard.convex.dev):

```bash
# required — a deploy fails without these two
npx convex env set AUTH_SECRET "$(openssl rand -base64 32)"
npx convex env set SITE_URL https://nuxt-backend.localhost

# optional — email (powered by Resend)
npx convex env set EMAIL_API_KEY re_...
npx convex env set EMAIL_FROM "Acme <hello@yourdomain.com>"
npx convex env set EMAIL_TEST_MODE true
npx convex env set EMAIL_WEBHOOK_SECRET whsec_...

# optional — billing (powered by Polar)
npx convex env set BILLING_ACCESS_TOKEN ...
npx convex env set BILLING_WEBHOOK_SECRET ...
npx convex env set BILLING_ENVIRONMENT sandbox   # or production
```

So the values split like this:

| Location | Variables |
|---|---|
| `.env.local` (Nuxt app) | `NUXT_PUBLIC_BACKEND_URL`, `NUXT_PUBLIC_BACKEND_SITE_URL` — both normally derived, so usually nothing |
| Convex deployment | **Required:** `AUTH_SECRET`, `SITE_URL`. **Optional:** `EMAIL_API_KEY`, `EMAIL_FROM`, `EMAIL_TEST_MODE`, `EMAIL_WEBHOOK_SECRET`, `BILLING_ACCESS_TOKEN`, `BILLING_WEBHOOK_SECRET`, `BILLING_ENVIRONMENT`, and `AUTH_TRUST_LOCAL_ORIGINS` on a dev deployment |

::warning
`AUTH_SECRET` and `SITE_URL` are **required** — a Convex deploy fails until both are set, so misconfiguration surfaces at push time instead of as a silent no-op in production. Everything else is optional and degrades in a designed, observable way until you configure it (`npx nuxt-backend doctor` reports each). See the [configuration reference](/getting-started/configuration#convex-deployment-variables) for what each variable does.
::

### Start the app once to scaffold the backend

```bash
npm run dev
```

On first run the module creates the Convex files that mount the packaged components, register the webhook routes, and re-export each feature's functions. If a Convex functions directory already exists it is reused; otherwise `backend/` is created:

```text
your-project/
├── backend/
│   ├── convex.config.ts   # defineApp + one app.use per component — mounts everything
│   ├── auth.config.ts
│   ├── auth.ts            # setupAuth — passwordless auth + workspaces
│   ├── http.ts            # registerBackendRoutes — auth + webhook routes
│   ├── functions.ts       # authorization + pre-authorized builders
│   ├── billing.ts         # setupBilling — subscriptions, credits, gifts
│   ├── email.ts           # setupEmail — transactional + marketing email
│   ├── rateLimiter.ts
│   ├── workflows.ts
│   ├── migrations.ts
│   ├── aggregates.ts
│   └── search.ts
└── convex.json
```

`convex.json` is only generated when the functions directory is non-standard (anything other than `convex/`).

### Start Convex

```bash
npx convex dev
```

Deploy with `npx convex deploy`.

::

## Optional: override module defaults

Most apps do not need a `backend` block. Add it only to override the env-based defaults or change the auth route:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-backend'],
  backend: {
    url: 'https://your-deployment.convex.cloud',
    siteUrl: 'https://your-deployment.convex.site',
    authRoute: '/api/auth',
  },
})
```

## Using strict pnpm

A flat `node_modules` (npm, yarn, or pnpm with `nodeLinker: hoisted`) exposes the bundled components automatically. pnpm's default isolated linker hides transitive deps, so let Convex's components reach the project root from `pnpm-workspace.yaml` (pnpm 11+ reads its settings there, not from `.npmrc`):

```yaml [pnpm-workspace.yaml]
publicHoistPattern:
  - '@convex-dev/*'
```

(or set `nodeLinker: hoisted`). Without this, the `convex dev` push fails to resolve the component definitions. The Nuxt side needs nothing: `nuxt-convex-module`, `nuxt-security` and the MCP toolkit are installed by the module from its own dependency tree.

pnpm 11 also refuses to install any version published less than 24 hours ago (`minimumReleaseAge`) and asks you to approve build scripts once (`pnpm approve-builds` — `esbuild`, via Nuxt). Both are pnpm's own supply-chain defaults, not this package's.

::warning
The scaffolded `convex.config.ts` imports every component definition directly — the all-in-one `backend` component from `nuxt-backend/component/convex.config` plus the six upstream `@convex-dev/*/convex.config` modules — and Convex builds its component tree from those imports. The `@convex-dev/*` packages therefore must be resolvable from your project root, hence the hoist pattern. You never add them to your own `package.json` — except `@convex-dev/resend` with a [local installation](/tooling/local-installation) under pnpm.
::

## Upgrading

Every release lists what changed, and what a change asks of you, on the
[GitHub Releases](https://github.com/qruto/nuxt-backend/releases) page — the same notes ship in
the package's `CHANGELOG.md`. Which parts of the package a version number promises to keep, and
how upstream releases map onto ours, is [STABILITY.md](https://github.com/qruto/nuxt-backend/blob/main/STABILITY.md).
