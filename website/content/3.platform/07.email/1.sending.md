The `backend` component ships transactional email powered by [Resend](https://www.convex.dev/components/resend) — **nested inside** it, as `backend/resend` in the dashboard — so email works out of the box once the `EMAIL_*` env vars are set. Its component functions are `components.backend.email.send` / `status` / `get` / `cancel` / `handleWebhook`; `setupEmail(components, options?)` from `nuxt-backend/email` is the app-side helper over them, plus the marketing surface (audiences / contacts / broadcasts) via the provider SDK.

## Setup

The scaffolded `backend/email.ts`, as generated:

```ts [backend/email.ts]
import { setupEmail } from 'nuxt-backend/email'
import { v } from 'convex/values'
import { api, components } from './_generated/api'
import { action, internalAction } from './_generated/server'

export const email = setupEmail(components)

// The reactive delivery-status query behind `useEmailStatus`.
export const { getEmailStatus } = email.api

// Send a transactional email (gated: requires a signed-in user).
export const send = action({
  args: { to: v.string(), subject: v.string(), html: v.optional(v.string()), text: v.optional(v.string()) },
  returns: v.union(v.string(), v.null()),
  handler: async (ctx, args) => {
    const user = await ctx.runQuery(api.auth.getAuthUser, {})
    if (!user) throw new Error('Sign in to send email.')
    return email.send(ctx, args)
  },
})

// Marketing — privileged, so internalActions: run from ops or your own server code.
export const createAudience = internalAction({
  args: { name: v.string() },
  handler: async (ctx, { name }) => email.audiences.create({ name }),
})
export const addContact = internalAction({
  args: { audienceId: v.string(), email: v.string(), firstName: v.optional(v.string()), lastName: v.optional(v.string()) },
  handler: async (ctx, args) => email.contacts.add(args),
})
export const createBroadcast = internalAction({
  args: { audienceId: v.string(), from: v.string(), subject: v.string(), html: v.string() },
  handler: async (ctx, args) => email.broadcasts.create(args),
})
export const sendBroadcast = internalAction({
  args: { broadcastId: v.string() },
  handler: async (ctx, { broadcastId }) => email.broadcasts.send(broadcastId),
})
```

## Sending

`email.send(ctx, options)` enqueues a **durable** email through the component and resolves to the email id (or `null` while no transport is configured). Call it from any action, mutation, or workflow step; or reach the component directly:

```ts
const emailId = await email.send(ctx, {
  to: 'user@example.com',
  subject: 'Welcome!',
  html: '<p>Hello</p>',
})

// Equivalent, from a Workflow step or anywhere with `components`:
await ctx.runMutation(components.backend.email.send, { to, subject, html })
```

`SendEmailOptions`: `to` (string or array), `subject?`, `html?`, `text?`, `from?` (defaults to `EMAIL_FROM`), `cc?`, `bcc?`, `replyTo?`, `headers?` (`[{ name, value }]`), and `template?: { id, variables? }` for a provider-hosted template. The validator is exported as `sendArgs` so your own function can mirror it exactly.

The rest of the helper: `email.status(ctx, emailId)` reads delivery status, `email.cancel(ctx, emailId)` cancels a not-yet-sent email, and `email.webhookHandler` is what [`registerBackendRoutes`](/platform/webhooks) mounts at `/email/events`.

Retention is yours to schedule: `email.cleanup(ctx, { olderThanMs? })` prunes finalized records (delivered, bounced, cancelled, failed — default 7 days) and `email.cleanupAbandoned(ctx, { olderThanMs? })` prunes records that never finalized (default 30 days). Both schedule the provider's batched cleanup and return at once, so call them from a cron (`crons.daily(...)` → an `internalMutation` that calls `email.cleanup`).

## Auth emails are automatic

OTP / verification / change-email / delete-account / welcome — and workspace invitation — emails go through the same component path **automatically**; you don't pass an `email` integration to `setupAuth`. Restyle them in [Templates](/platform/email/templates), or take over transport entirely with `integrations.email`.

## Sequences and workflows

For drips, use [`defineEmailSequence`](/platform/workflows) — durable, delivery-tracked steps sleeping their `after` delay through the workflow component. The scaffold starts one on signup (`onSignup`).

## Marketing

`email.audiences` (`create` / `list` / `remove`), `email.contacts` (`add` / `list` / `update` / `remove`), and `email.broadcasts` (`create` / `send(id, payload?)`) wrap the provider SDK with `EMAIL_API_KEY`. They are privileged — a public action would be an open relay on your verified domain — so the scaffold ships them as `internalAction`s; expose one to an admin UI by re-declaring it with the `admin.action` builder from [`functions.ts`](/platform/authorization).

## Environment

| Variable | Effect |
|---|---|
| `EMAIL_API_KEY` | The provider API key — unset, sends no-op (logged) and OTP sign-in throws; `NUXT_BACKEND_LOG_OTP=1` echoes codes to the `convex dev` console instead (dev deployments get it automatically) |
| `EMAIL_FROM` | Sender address, e.g. `Acme <hello@yourdomain.com>` — defaults to the provider's onboarding sender |
| `EMAIL_TEST_MODE` | `true` (the default) delivers only to the provider's test addresses (`delivered@resend.dev`, `+label` aliases); set `false` once your sending domain is verified |
| `EMAIL_WEBHOOK_SECRET` | Verifies delivery events on `/email/events` — see [Delivery tracking](/platform/email/delivery-tracking) |

The component owns these — the scaffolded `convex.config.ts` forwards them by reference from the app env, since components can't read the app's env directly.

::warning
With `EMAIL_TEST_MODE` on, only the provider's test addresses receive mail. Flip it to `false` after verifying a sending domain in the Resend dashboard — `npx nuxt-backend doctor --prod` reminds you.
::
