Authorization sits on top of the bundled Better Auth setup: **app-wide roles** and **permission statements** from the admin plugin, and **workspace membership** from the organization plugin. Reads are claims-first — `role`, `banned`, and `activeOrganizationId` ride on the Convex JWT, so most checks cost no database read. Claims can lag a role change by up to the JWT lifetime (15 minutes); pass `{ fresh: true }` where that matters.

## Server: `setupAuthorization`

The scaffolded `backend/functions.ts` builds the helpers once:

```ts [backend/functions.ts]
import { setupAuthorization } from 'nuxt-backend/authorization'
import { createFunctions } from 'nuxt-backend/functions'
import { components } from './_generated/api'
import { action, internalMutation, mutation, query } from './_generated/server'

export const authorization = setupAuthorization(components, { internalMutation })
export const { setUserRole } = authorization

export const { authed, org, admin, withRole } = createFunctions(
  { query, mutation, action },
  authorization,
)
```

`setupAuthorization(components, options?)` returns:

::field-group
  :::field{name="getUser(ctx)" type="Promise<AuthorizationUser | null>"}
  The signed-in user from identity claims — `id`, `email`, `name`, `role` (`'user'` when unset), `banned`, `activeOrganizationId`, and the raw `claims`. `null` when signed out.
  :::

  :::field{name="requireUser(ctx)"}
  Throws `ConvexError('Unauthenticated')` when signed out, `Forbidden: account is banned` when banned.
  :::

  :::field{name="requireRole(ctx, role | role[], { fresh? })"}
  Require an app-wide role (any match passes; Better Auth stores multiple roles comma-separated). `fresh: true` re-reads the user document past JWT staleness.
  :::

  :::field{name="requirePermission(ctx, { resource: [actions] }, { fresh? })"}
  Require permission statements (e.g. `{ user: ['ban'] }`) against the user's role via the access-control roles — the admin plugin's built-in `admin` / `user` roles by default, or the `roles` map you pass.
  :::

  :::field{name="requireOrganization(ctx)"}
  Require an active workspace on the session; returns `{ user, organizationId }`.
  :::

  :::field{name="requireMember(ctx, { organizationId?, role? })"}
  Require workspace membership — **always a fresh member-table read**. Defaults to the active workspace; `role` also requires a workspace role (`owner` / `admin` / `member` or custom).
  :::

  :::field{name="setUserRole" type="internalMutation"}
  Present when `internalMutation` was supplied: the bootstrap for your first admin.
  :::
::

Mint the first admin from the CLI (an internal mutation, so never callable from the client):

```bash
npx convex run functions:setUserRole '{"email":"you@example.com","role":"admin"}'
```

### Custom roles and permissions

`nuxt-backend/authorization` re-exports Better Auth's building blocks so you never import its internals: `createAccessControl`, `defaultStatements`, `adminAc`, `userAc`. Define statements once, hand the roles to both the admin plugin (so the client's `can()` knows them) and `setupAuthorization` (so `requirePermission` does):

```ts [backend/roles.ts]
import { adminAc, createAccessControl, defaultStatements } from 'nuxt-backend/authorization'

const statement = { ...defaultStatements, project: ['create', 'archive'] } as const
export const ac = createAccessControl(statement)
export const roles = {
  admin: ac.newRole({ ...adminAc.statements, project: ['create', 'archive'] }),
  editor: ac.newRole({ project: ['create'] }),
}
```

```ts [backend/auth.ts]
setupAuth(components, query, {
  admin: { ac, roles },          // the admin plugin's own options
})
```

```ts [backend/functions.ts]
export const authorization = setupAuthorization(components, { internalMutation, roles })
```

## Pre-authorized function builders

`createFunctions({ query, mutation, action }, authorization, options?)` returns drop-in replacements for your `_generated/server` builders, grouped by tier:

```ts [backend/projects.ts]
import { v } from 'convex/values'
import { admin, authed, org, withRole } from './functions'

export const me = authed.query({            // ctx.user — signed in, not banned
  args: {},
  handler: async ctx => ctx.user,
})

export const createProject = org.mutation({  // + ctx.organization { id, role } — fresh membership check
  args: { name: v.string() },
  handler: async (ctx, { name }) =>
    ctx.db.insert('projects', { name, organizationId: ctx.organization.id }),
})

export const purge = admin.action({          // requireRole(adminRoles) — default ['admin']
  args: {},
  handler: async (ctx) => { /* … */ },
})

export const review = withRole('editor').query({ // custom app-wide role tier
  args: {},
  handler: async (ctx) => { /* … */ },
})
```

| Tier | Check | Injects |
|---|---|---|
| `authed` | `requireUser` (claims) | `ctx.user` |
| `org` | `requireMember` — fresh member-table read on **every** call, so a removed member is locked out immediately, not at JWT expiry | `ctx.user`, `ctx.organization` |
| `admin` | `requireRole(adminRoles)` (claims) | `ctx.user` |
| `withRole(role)` | `requireRole(role)` (claims) | `ctx.user` |

Options: `adminRoles` (default `['admin']`), and per-tier write throttling — pass your `setupRateLimiter(...)` as `rateLimiter` and name a limit per tier in `limits` (`{ authed: 'apiWrites' }`); it is consumed on **mutations and actions only**, keyed by user id. Pass your `withTriggers`-wrapped `mutation` to keep [aggregate](/platform/aggregates) triggers composing.

## Client: roles on `useAuth()`

The same claims are readable in the app, synchronously:

```vue
<script setup lang="ts">
const { role, hasRole, can, banned } = useAuth()
</script>

<template>
  <AdminNav v-if="hasRole('admin')" />
  <BanButton v-if="can({ user: ['ban'] })" />
</template>
```

`can()` evaluates permission statements locally through the admin plugin's `checkRolePermission` — no request — against the roles configured on the plugin.

## `<RoleBoundary>`

Renders its default slot only when the signed-in user has the required app-wide role or permission; `placeholder` while the session loads, `fallback` when the check fails. Banned accounts never pass.

```vue
<template>
  <RoleBoundary role="admin">
    <AdminPanel />
    <template #fallback><p>Admins only.</p></template>
  </RoleBoundary>

  <RoleBoundary :permission="{ user: ['ban'] }">
    <BanButton />
  </RoleBoundary>
</template>
```

The billing counterpart is [`<FeatureBoundary>`](/platform/billing/feature-gating); the workspace counterpart is [`<OrganizationBoundary>`](/platform/workspaces#organizationboundary).

::note
Client-side gates are for UI. Every function that matters must check on the server too — that is what the tiers above are for.
