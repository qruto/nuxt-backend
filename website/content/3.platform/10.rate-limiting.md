`setupRateLimiter(components, limits?)` returns a `RateLimiter` pre-seeded with `DEFAULT_LIMITS` — `emailOtp` (OTP / verification sends, per email — 5/minute, keyed by a SHA-256 of the address), `emailOtpGlobal` (OTP sends across the whole deployment — a fixed window of 300/hour, the backstop against address rotation; raise it for a launch that legitimately signs in more), `billingSync` (entitlement syncs, per billing entity), `ai` (metered AI calls, per billing entity), `mcp` (agent token exchanges, per client + user), `admin` (administrator actions on the admin routes — 30/minute per administrator), `invitation` (workspace invitations — 30/hour per inviter) and `invitationGlobal` (invitations across the whole deployment — a fixed window of 200/hour, the ceiling the per-inviter limit cannot be; raise it for a launch that legitimately invites more). Your `limits` are merged on top and can override any of them.

```ts [backend/rateLimiter.ts]
import { setupRateLimiter } from 'nuxt-backend/rate-limit'
import { components } from './_generated/api'

export const rateLimiter = setupRateLimiter(components, {
  // your own limits, merged over DEFAULT_LIMITS
  sendMessage: { kind: 'token bucket', rate: 10, period: 60_000 },
})
```

Pass the limiter into `setupAuth` to throttle OTP sends — see [cross-component wiring](/platform/auth/setup#cross-component-wiring) — and into `setupAi`, whose metered actions use the `ai` limit unless you name another.

## Privileged routes

The same limiter, once it reaches `setupAuth`, also bounds the two routes where one caller acts on *other people*:

| Route | Limit | Keyed by |
| --- | --- | --- |
| `/admin/*` — list, create, update, ban/unban, set role, impersonate, revoke sessions, remove user | `admin` — 30/minute, burst 10 | the administrator's user id |
| `/organization/invite-member` | `invitation` — 30/hour, burst 10 | the inviter's user id |
| …and the same route again | `invitationGlobal` — 200/hour, fixed window | nothing: one ceiling for the deployment |

Better Auth already *authorizes* these routes; the limits bound how fast an authorized caller may go, so one compromised admin session cannot ban a thousand accounts. They are keyed by user id rather than by session, so opening more sessions does not multiply the budget, and a request with no session is left to the route, which answers 401 itself.

A per-caller limit bounds one account and nothing more — thirty invitations an hour each is still a lot of mail from a workspace of fifty. Invitations therefore also spend `invitationGlobal`, an unkeyed ceiling for the whole deployment, because the cost lands on a shared resource: your sending domain's reputation. It is consumed **after** the inviter's own bucket allowed the request, so one account's refused excess never eats everyone else's budget, and a deployment at its ceiling answers 429 with *"Invitations are temporarily unavailable"* rather than blaming the inviter. It is the counterpart of `emailOtpGlobal` on the package's other outbound-email path; admin routes have no such ceiling, because banning a user spends nothing anyone else shares.

`/admin/stop-impersonating` and `/admin/has-permission` are deliberately exempt — the first is the way *out* of an impersonated session and must never be throttled, the second is a read-only check the console calls on render.

Every other Better Auth route is covered by Better Auth's own per-path limiter, which counts per IP and takes its rules from your auth options:

```ts [backend/auth.ts]
setupAuth(components, query, {
  authOptions: {
    rateLimit: {
      storage: 'database',
      customRules: { '/organization/create': { window: 60, max: 5 } },
    },
  },
})
```

::note
There are no password limits (`signIn`, `signUp`, `passwordReset`): the package is passwordless, and per-code brute force is Better Auth's own `allowedAttempts` guard. `DEFAULT_LIMITS` is also exported from `nuxt-backend/rate-limit` if you want to inspect or extend the defaults directly.
::
