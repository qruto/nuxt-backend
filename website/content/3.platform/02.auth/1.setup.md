The `nuxt-backend/auth` entrypoint runs in your **Convex backend** (`backend/`), not the Vue app. It exposes the same two client-code patterns described in the Convex component authoring docs — a simple wrapper via `createAuth(ctx, component, options?)` and a ready-made API remount via `makeAuthApi(component, query)` — plus `setupAuth(...)`, a convenience helper that composes both for the common scaffolded case.

## The scaffolded files

If you let the module scaffold the files, you can keep them as generated. If you create them manually, they look like this:

```ts [backend/convex.config.ts]
import { defineApp } from 'convex/server'
import { backendEnv } from 'nuxt-backend/app'
import backend from 'nuxt-backend/component/convex.config'
import aggregate from '@convex-dev/aggregate/convex.config'
import migrations from '@convex-dev/migrations/convex.config'
import persistentTextStreaming from '@convex-dev/persistent-text-streaming/convex.config'
import polar from '@convex-dev/polar/convex.config'
import rateLimiter from '@convex-dev/rate-limiter/convex.config'
import workflow from '@convex-dev/workflow/convex.config'

const app = defineApp({ env: backendEnv })

// Components are isolated from the app env — forward the email config by
// reference so the deployment's values reach the backend component (auth,
// email, billing cache, gifts — the email provider is nested inside).
app.use(backend, {
  env: {
    EMAIL_API_KEY: app.env.EMAIL_API_KEY,
    EMAIL_FROM: app.env.EMAIL_FROM,
    EMAIL_TEST_MODE: app.env.EMAIL_TEST_MODE,
    EMAIL_WEBHOOK_SECRET: app.env.EMAIL_WEBHOOK_SECRET,
  },
})
app.use(aggregate)
app.use(migrations)
app.use(persistentTextStreaming)
app.use(polar)
app.use(rateLimiter)
app.use(workflow)

export default app
```

::note
The module scaffolds `convex.config.ts` for you (so does `npx nuxt-backend init`). Convex discovers components from the `convex.config` imports it meets while bundling this file, and current Convex backends crash the push (`start_push 500`) when such an import is reached through an intermediate module or `app.use` runs in a loop — so the definition is deliberately explicit: every component imported and mounted in the root file, one `app.use` per component. `backendEnv` (from `nuxt-backend/app`) is the typed env contract — `AUTH_SECRET` + `SITE_URL` required, the rest optional with designed fallbacks.
::

```ts [backend/auth.ts]
import { setupAuth } from 'nuxt-backend/auth'
import { components, internal } from './_generated/api'
import { query } from './_generated/server'
import { rateLimiter } from './rateLimiter'
import { workflow } from './workflows'

export const {
  authComponent,
  createAuthOptions,
  options,
  createAuth,
  getAuthUser,
  authConfig,
  listWorkspaces,
  listWorkspaceMembers,
  updateProfile,
  // The agent token exchange (mounted at /mcp/exchange by http.ts) — the
  // app's OAuth-protected MCP endpoint calls Convex through it. Disable
  // the whole agent surface with `mcp: false`.
  mcp,
} = setupAuth(components, query, {
  // Roles/permissions (admin plugin) and workspaces (organization plugin)
  // are on by default, including a personal workspace per user and emailed
  // workspace invitations with an /accept-invitation page. Customize or
  // disable: `admin: false`, `organization: { personal: false }`, ...
  integrations: {
    // Email (OTP / verification / invitations) is delivered automatically
    // through the backend component — configured by the EMAIL_* env vars.
    // Throttle OTP sends and other auth-sensitive flows.
    rateLimiter,
    // The onboarding sequence below sends its own welcome, so skip the
    // packaged welcome email (new users would get two otherwise).
    welcomeEmail: false,
    // Kick off a durable welcome workflow when a user signs up.
    onUserCreated: async (ctx, user) => {
      await workflow.start(ctx, internal.workflows.onSignup, {
        userId: user.id,
        email: user.email,
        name: user.name,
      })
    },
  },
})
```

```ts [backend/http.ts]
import { registerBackendRoutes } from 'nuxt-backend/http'
import { httpRouter } from 'convex/server'
import { authComponent, createAuth, mcp } from './auth'
import { billing } from './billing'
import { email } from './email'
import { ai } from './ai'

// Mounts every inbound route the backend handles: the auth routes, the
// billing events endpoint (/billing/events), the email events endpoint
// (/email/events), the metered AI stream endpoint (/ai/stream), and the
// agent token exchange (/mcp/exchange). Each option takes the instance the
// matching setup* helper returns.
const http = httpRouter()
registerBackendRoutes(http, {
  auth: { authComponent, createAuth },
  billing,
  email,
  ai,
  mcp,
})

export default http
```

That setup mounts the packaged all-in-one `backend` component (plus the upstream components), configures Convex to trust its tokens, registers the auth, [webhook, AI stream, and agent exchange routes](/platform/webhooks), and exposes `api.auth.getAuthUser` for app queries. The scaffolded `backend/auth.ts` re-exports everything `setupAuth` returns — `authComponent`, `createAuthOptions`, `options`, `createAuth`, `getAuthUser`, `authConfig`, `listWorkspaces`, `listWorkspaceMembers`, `updateProfile`, and `mcp` — for app Convex functions (and `http.ts`) to import. The `rateLimiter` / `workflow` imports come from the scaffold's sibling files (`rateLimiter.ts`, `workflows.ts`).

## `setupAuth(...)`

```ts
function setupAuth<DM, Schema>(
  components: AuthSetupComponents,  // the whole generated `components` object — uses `auth` + optional `email`
  queryBuilder: QueryBuilder<DM, 'public'>,
  options?: SetupAuthOptions<Schema>,
): {
  authComponent: AuthComponent
  createAuthOptions: (ctx) => BetterAuthOptions
  options: BetterAuthOptions
  createAuth: (ctx) => BetterAuthInstance
  getAuthUser: RegisteredQuery           // the signed-in user (null when signed out)
  authConfig: AuthConfig                 // what auth.config.ts re-exports
  listWorkspaces: RegisteredQuery        // the caller's workspaces
  listWorkspaceMembers: RegisteredQuery  // members of the active workspace
  updateProfile: RegisteredMutation      // name / image edits
  mcp: McpExchange                       // the agent token exchange for registerBackendRoutes({ mcp })
}
```

The lower-level pieces — `createAuth`, `createAuthOptions`, `makeAuthApi`, `createBetterAuth`, `createBetterAuthOptions` — are also exported from `nuxt-backend/auth` for when you want to compose them yourself.

## Cross-component wiring

OTP / verification / reset — and workspace invitation — emails are routed through the `backend` component (`components.backend.email.send`) **automatically** — you don't pass an `email` integration. `integrations` accepts `{ rateLimiter, canSignIn, onUserCreated, onUserDeleted, welcomeEmail?, email?, emailTemplates? }`:

- `rateLimiter` throttles OTP sends — per address (`emailOtp`, keyed by a SHA-256 of the email) and deployment-wide (`emailOtpGlobal`, 300/hour); a closed limit answers `TOO_MANY_REQUESTS`
- `canSignIn(ctx, { email, isNewUser, purpose })` gates sign-in and sign-up — an invite-only launch, an allow-list, a closed beta. Return `true` or `{ allowed: false, message? }`. It is asked before an OTP is sent for a sign-in request (`purpose: 'sign-in'`, with `isNewUser` from the auth tables), before any account is created (`'user-create'`), and before a session is created for an existing account (`'session'` — passkey sign-in included). A refusal is a `FORBIDDEN` `APIError` carrying the message, which `useLoginFlow().error` shows; the default message is "Sign-in is by invitation right now."
- `onUserCreated(ctx, user)` runs on signup (the ctx is a full mutation/action ctx, so it can start a Workflow)
- `onUserDeleted(ctx, user)` runs after an account is deleted — erase the app's own rows, forget the billing cache (`billing.forgetEntity(ctx, user.id)`). It chains after any `user.deleteUser.afterDelete` you pass in `authOptions`, and the emailed delete confirmation stays on
- `welcomeEmail?` (default `true`) sends the packaged welcome email right after signup — set `false` when the app owns onboarding (the scaffold does: its `onSignup` sequence sends the welcome), so new users don't get two
- `email?` is an optional override to bypass the automatic transport
- `emailTemplates?` restyles any of the default auth emails (`welcome` / `otp` / `verify` / `changeEmail` / `deleteAccount` / `invite`) without replacing the transport

```ts [backend/auth.ts]
export const { authComponent, createAuth, getAuthUser } = setupAuth(components, query, {
  integrations: {
    // email is automatic via the `backend` component (the EMAIL_* env vars)
    rateLimiter,
    welcomeEmail: false, // the onSignup sequence sends the welcome
    onUserCreated: async (ctx, user) => {
      await workflow.start(ctx, internal.workflows.onSignup, {
        userId: user.id, email: user.email, name: user.name,
      })
    },
  },
})
```

Any `databaseHooks` you pass in `authOptions` **compose** with the package's own: per model and operation, the package hook runs first and yours second — a `before` hook receives the entity as the package left it (a new session already carries its `activeOrganizationId`), and a `false` from either side aborts the write.

Billing links provider customers to auth users, and its reactive feature/credit cache lives **inside** the `backend` component — so subscriptions, discounts, feature-gating, prepaid credits, and gifts work out of the box with nothing added to your schema.

::note
Email delivery is configured by the optional `EMAIL_*` env vars — until `EMAIL_API_KEY` is set, sends no-op and OTP sign-in throws. During local dev, `NUXT_BACKEND_LOG_OTP=1` (which `npm run dev` sets on a dev deployment without a transport) echoes OTP codes to the `convex dev` console instead.
::
