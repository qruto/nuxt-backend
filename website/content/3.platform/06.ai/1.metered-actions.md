`nuxt-backend/ai` is the rails for selling metered AI features. `setupAi(components, { billing, rateLimiter })` composes the billing spend reservation, the rate limiter, and the upstream persistent-text-streaming component, and hands back two builders: `meteredAction` (this page) and `stream` ([Streaming](/platform/ai/streaming)). Usage recording **is** the provider event, so per-customer usage shows up in the provider's own portal and dashboard with no extra tables.

::note
`nuxt-backend/ai` is in the experimental tier (see STABILITY.md): the reserve → settle metering model over provider meter events may change shape in a minor release.
::

## Setup

The scaffolded `backend/ai.ts`:

```ts [backend/ai.ts]
import { setupAi } from 'nuxt-backend/ai'
import { v } from 'convex/values'
import { components } from './_generated/api'
import { billing } from './billing'
import { rateLimiter } from './rateLimiter'

export const ai = setupAi(components, { billing, rateLimiter })

// A metered action — swap the echo for your model call. Costs 1 credit
// from the 'credits' meter per call (see billing.catalog.ts).
export const transform = ai.meteredAction({
  meter: 'credits',
  args: { prompt: v.string() },
  handler: async (ctx, { prompt }) => {
    // const completion = await yourModel(prompt)
    return { echo: prompt.toUpperCase(), chargedTo: ctx.usage.entityId }
  },
})
```

`setupAi` config:

::field-group
  :::field{name="billing" type="Billing" required}
  Your `setupBilling(...)` instance — supplies entity resolution and the credit spend.
  :::

  :::field{name="rateLimiter" type="AiRateLimiter"}
  Your `setupRateLimiter(...)` instance. Metered actions/streams check their named limit (default `'ai'`, seeded in `DEFAULT_LIMITS`) per billing entity before reserving. Omit to leave them unthrottled.
  :::

  :::field{name="cors.origin" type="string"}
  CORS origin for the stream endpoint. Defaults to the `SITE_URL` env var (`*` if unset).
  :::

  :::field{name="budget" type="AiBudget"}
  A per-entity credit cap on top of the call-rate limit — `{ units, period, limit? }`: `units` credits per `period` ms (`HOUR` / `DAY` from `nuxt-backend/rate-limit`), so `{ units: 500, period: DAY }` is "500 credits a day per workspace", not 500 calls. Enforced through the rate limiter as a fixed window over spend value (requires `rateLimiter`; the window is recorded under `limit`, default `'aiBudget'` — name your own to keep separate budgets per feature). A cap, not a ledger: like every rate limit, consumption is never given back, so a run that fails or finalizes under its estimate still spent the estimate against the window. A call whose cost exceeds `units` is refused outright — it could never fit.
  :::

  :::field{name="credits" type="AiCreditsConfig"}
  Low-balance reactions fired after a spend settles: `lowBalanceThreshold`, plus `onCreditsLow(ctx, event)` (the balance just crossed the threshold downwards) and `onCreditsExhausted(ctx, event)` (it just went from positive to zero or below). Both fire on the **crossing** only — a second spend that stays below the line is silent — so they are safe to wire straight to a notification. The event carries `entityId`, `userId`, `meter` / `meterId`, `balance`, `previousBalance`, `spent` and `threshold`. A hook that throws is logged; the spend stays settled. Keep them thin — record or hand off; sending belongs to the lifecycle emails.
  :::

  :::field{name="streamTimeout" type="number | false"}
  How long a started stream may hold its reservation before it is released automatically, in ms. Default 5 minutes; `false` disables the timer. See [Streaming](/platform/ai/streaming).
  :::
::

```ts [backend/ai.ts]
// Replaces the `ai` declaration above: the same call with the optional budget
// and credits hooks. Imports as above, plus:
import { DAY } from 'nuxt-backend/rate-limit'

export const ai = setupAi(components, {
  billing,
  rateLimiter,
  budget: { units: 500, period: DAY },   // 500 credits a day per workspace, on top of the `ai` call-rate limit
  credits: {
    lowBalanceThreshold: 50,
    onCreditsLow: async (ctx, { entityId, balance }) => {
      // record it, or hand it off — the lifecycle emails own the sending
    },
  },
})
```

The stream endpoint needs `persistentTextStreaming` mounted in `convex.config.ts` (the scaffold does) and `registerBackendRoutes({ ai })` in `http.ts`.

## `ai.meteredAction(config)`

A drop-in replacement for `action`: it rate-limits, reserves prepaid credits, runs your handler, then settles the spend. Failed runs release the reservation — nothing charged.

```ts
export const generate = ai.meteredAction({
  meter: 'credits',
  cost: args => args.long ? 5 : 1,
  limit: 'ai',
  charge: 'success',
  args: { prompt: v.string(), long: v.optional(v.boolean()) },
  handler: async (ctx, { prompt, long }) => {
    // ctx is the full action ctx plus ctx.usage
    return runModel(prompt, { maxTokens: long ? 4000 : 800 })
  },
})
```

::field-group
  :::field{name="meter" type="string | false" required}
  The catalog credit meter to charge — or `false` for a rate-limit-only action (no reservation, no event).
  :::

  :::field{name="cost" type="MeteredCost"}
  Credits per call: a number, `(args) => number`, or `{ estimate, finalize }` to reserve an estimate and settle what the run actually used — see [Token pricing](#token-pricing). Default `1`. On a `count` meter the value must be `1`.
  :::

  :::field{name="limit" type="string | false"}
  Named rate limit checked per billing entity through the configured `rateLimiter`. Default `'ai'`; `false` disables the check.
  :::

  :::field{name="allowOverage" type="boolean"}
  Let this spend take the balance negative instead of refusing it — for a pay-as-you-go meter with no credit benefit behind it, where every unit is overage the provider invoices at the end of the cycle. Off by default: credits stay strictly prepaid.
  :::

  :::field{name="charge" type="'success' | 'start'"}
  When to charge. `'success'` (default) settles after the handler returns — a failed run consumes nothing. `'start'` settles before running, for work that is irrevocably consumed upstream the moment it starts (no refund on failure). A finalized cost needs the result, so it only applies to `'success'`.
  :::

  :::field{name="args / handler"}
  Convex validators and `(ctx & { usage: MeteredUsage }, args) => Promise<unknown>`.
  :::
::

`ctx.usage` carries `entityId` (the workspace or user charged), `userId` (the signed-in caller), `meter`, and `cost` (the estimate, for a finalized cost).

### What happens on each call

1. **Identity** — an unauthenticated call throws `Sign in to use this feature.`; the billing entity resolves from claims (`No billing entity` if none — a personal workspace normally guarantees one).
2. **Rate limit** — the named limit is checked, keyed by the entity; over the limit throws `Rate limit reached. Try again in Ns.`
3. **Budget** — with `budget` configured (it needs `rateLimiter`) and the action metered, the call's cost is counted against the entity's window; over it throws `Credit budget reached — N credits per window. Resets in Ns.`
4. **Reserve** — `billing.reserveCredits` decrements the cached balance atomically by the cost (the estimate, for a finalized cost); too little balance throws `Insufficient credits — balance N, need M` unless `allowOverage` is set.
5. **Run** — your handler.
6. **Settle or release** — success ingests the usage event at the final cost, hands any unspent remainder of the estimate back to the balance, and fires the `credits` hooks if the balance crossed a threshold; a throw releases the reservation and rethrows. With `charge: 'start'` the settle happens before the run instead.

## Token pricing

A model call's cost is only known once it returns. `cost: { estimate, finalize }` reserves the estimate, runs the handler, then settles what `finalize` computes from the result and hands the remainder back to the balance in the same transaction. `priceTokens` is the arithmetic — a price table the app owns (no provider knows what a model costs you; rates change weekly and only your margin decides the credit price), applied to the token usage the SDK reports:

```ts [backend/ai.ts]
import { priceTokens, type TokenPriceTable, type TokenUsage } from 'nuxt-backend/ai'

// Credits per million tokens, per model id.
const prices: TokenPriceTable = {
  'fast-1': { input: 3, output: 15, per: 1_000_000 },
  'deep-1': { input: 15, output: 75, cachedInput: 1.5, per: 1_000_000 },
}

export const generate = ai.meteredAction({
  meter: 'credits',
  cost: {
    estimate: 200,   // the ceiling: reserved up front, refunded down to the final cost
    finalize: (result: { usage: TokenUsage }) => priceTokens(result.usage, prices, { round: 'up' }),
  },
  args: { prompt: v.string() },
  handler: async (ctx, { prompt }) => {
    const completion = await yourModel(prompt)
    // Return the usage — `finalize` prices what the handler returns.
    return { text: completion.text, usage: { model: 'fast-1', input: completion.inputTokens, output: completion.outputTokens } }
  },
})
```

- **The estimate is the ceiling.** A final amount above it is clamped down and logged (`Raise the estimate.`): the reservation is what made the spend safe against a concurrent one, so settling beyond it would be a second, unguarded debit. Estimate high — an over-estimate costs nothing once it settles, though it must fit the balance to reserve and counts in full against a `budget` window.
- **Sum meters only.** The finalized amount rides in the ingested event's metadata; a `count` meter can only ever count 1 per event.
- **`charge: 'success'` only.** A finalized cost needs the result.
- `estimate` may also be `(args) => number`; `finalize(result, usage)` receives `ctx.usage` as its second argument. `result` is typed from what `handler` returns — annotate it, as above, or list `handler` before `cost` so inference has seen it.

`priceTokens(usage, table, options?)` takes a `TokenUsage` (`model`, `input`, `output`, `cachedInput?`) and a `TokenPriceTable` (model id → `{ input, output, cachedInput?, per? }`, rates in credits per `per` tokens — default 1; `options.per` sets a table-wide default). `cachedInput` tokens bill at the entry's own rate when it has one, as ordinary input otherwise. `options.round` (`'up'` | `'nearest'` | `'none'`, the default) and `options.minimum` shape the result. A model missing from the table **throws** — a silent 0 would be a revenue leak, and an unpriced model is a deployment mistake worth surfacing.

```ts
priceTokens({ model: 'fast-1', input: 12_000, output: 800 }, prices) // → 0.048
```

## Calling it from the app

```vue
<script setup lang="ts">
import { api } from '#backend/api'

const credits = useCredits('credits')
const transform = useAction(api.ai.transform)
const result = ref<string>()

async function run(prompt: string) {
  try {
    result.value = (await transform({ prompt })).echo
  }
  catch (error) {
    // "Insufficient credits…", "Rate limit reached…", or your model's error — nothing was charged
  }
}
</script>

<template>
  <p>{{ credits.balance.value }} credits</p>
</template>
```

The balance updates live: the cache is debited on reserve and the provider webhook confirms the consumed units.

## Rate limits

`DEFAULT_LIMITS.ai` (30 per minute per billing entity, burst 10) is the package default; override it or add your own in [`setupRateLimiter`](/platform/rate-limiting) and name it in `limit`. `DEFAULT_LIMITS.aiBudget` is the window a `budget` records under — the `units` / `period` you pass to `setupAi` are what it enforces:

```ts [backend/rateLimiter.ts]
export const rateLimiter = setupRateLimiter(components, {
  ai: { kind: 'token bucket', rate: 30, period: 60_000 },
  imageGen: { kind: 'fixed window', rate: 5, period: 60_000 },
})
```
