`setupMigrations(components, options?)` from `nuxt-backend/migrations` returns `{ migrations, run }` — the migrations instance and a generic runner. Define migrations with `migrations.define({ table, migrateOne })`.

```ts [backend/migrations.ts]
import { setupMigrations } from 'nuxt-backend/migrations'
import { components } from './_generated/api'
import schema from './schema'

export const { migrations, run } = setupMigrations(components, { schema })

export const setDefaultStatus = migrations.define({
  table: 'messages',
  migrateOne: async (ctx, doc) => {
    if (doc.status === undefined) {
      await ctx.db.patch(doc._id, { status: 'sent' })
    }
  },
})
```

`migrateOne` runs inside a mutation, one document at a time, a batch per transaction. It can write through `ctx.db` as above, or return a partial document and the component applies the patch — `migrateOne: (_ctx, doc) => (doc.status === undefined ? { status: 'sent' } : undefined)`. A migration is also how you backfill an [aggregate](/platform/aggregates) for rows that predate its trigger: `migrateOne: (ctx, doc) => messagesCount.insertIfDoesNotExist(ctx, doc)`.

## Options

| Option | Effect |
|---|---|
| `schema` | Your database schema. Recommended — it types `doc` in `migrateOne` and enables `customRange` |
| `defaultBatchSize` | Documents processed per transaction batch (default `100`) |
| `migrationsLocationPrefix` | Prefix added to `fn` names when running from the CLI — with `'bar/baz:'`, a migration in `backend/bar/baz.ts` runs as `{ "fn": "foo" }` |

`migrations.define` also takes `batchSize` (this migration's batch size), `customRange` (narrow the pass to an index range — `q => q.withIndex('userId', q => q.eq('userId', id))` — which needs `schema`) and `parallelize` (process each batch's documents in parallel).

## Running

`run` is the generic runner: an internal mutation that starts — or resumes — any defined migration by name and schedules the batches that follow.

```bash
# Start, or resume where it stopped. A finished migration is a no-op.
npx convex run migrations:run '{ "fn": "migrations:setDefaultStatus" }'

# Dry run: one batch, then roll back — see what it would do without committing.
npx convex run migrations:run '{ "fn": "migrations:setDefaultStatus", "dryRun": true }'

# Restart from the beginning.
npx convex run migrations:run '{ "fn": "migrations:setDefaultStatus", "reset": true }'

# A series, one after another.
npx convex run migrations:run '{ "fn": "migrations:setDefaultStatus", "next": ["migrations:backfillMessagesCount"] }'
```

| Argument | Effect |
|---|---|
| `fn` | The migration to run, as `file:export` |
| `cursor` | Where to start — `null` for the beginning; omitted, it resumes where the last run stopped |
| `batchSize` | Batch size for this run — overrides the migration's own |
| `dryRun` | Run one batch and throw, so nothing commits |
| `next` | Migrations to run after this one, in order — a failure or cancel stops the series |
| `reset` | Restart from the beginning (also resets `next`) |

The same instance drives migrations from code: `migrations.runOne(ctx, internal.migrations.setDefaultStatus, { dryRun?, batchSize?, cursor?, reset? })` from a mutation or action, `migrations.runSerially(ctx, [internal.migrations.a, internal.migrations.b])` for a post-deploy series, `migrations.getStatus(ctx, { migrations?, limit? })` for the live state (a query can expose it to a page — the playground's status table does), and `migrations.cancel(ctx, ref)` / `migrations.cancelAll(ctx)` to stop an in-flight run, which resumes when run again without a cursor.
