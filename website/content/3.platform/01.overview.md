`nuxt-backend` ships one [Convex component](https://www.convex.dev/components) of its own — the all-in-one **`backend`** component — and bundles six upstream `@convex-dev/*` components, all wired into Better Auth and configured by the [required env vars](/getting-started/configuration#convex-deployment-variables).

| Capability | Component | Entrypoint | Setup helper |
|---|---|---|---|
| Auth | `backend` (this package — Better Auth tables + adapter) | `nuxt-backend/auth` | `setupAuth` |
| Email | `backend` (nests [`@convex-dev/resend`](https://www.convex.dev/components/resend)) | `nuxt-backend/email` | `setupEmail` — `components.backend.email.send` |
| Billing | [`@convex-dev/polar`](https://www.convex.dev/components/polar) + `backend` (entitlement/credit cache, gifts) | `nuxt-backend/billing` | `setupBilling` |
| Webhooks | — (HTTP routes over auth + billing + email) | `nuxt-backend/http` | `registerBackendRoutes` |
| Rate limiting | [`@convex-dev/rate-limiter`](https://www.convex.dev/components/rate-limiter) | `nuxt-backend/rate-limit` | `setupRateLimiter` |
| Metered AI | [`@convex-dev/persistent-text-streaming`](https://www.convex.dev/components/persistent-text-streaming) + `backend` (credits) | `nuxt-backend/ai` | `setupAi` |
| Migrations | [`@convex-dev/migrations`](https://www.convex.dev/components/migrations) | `nuxt-backend/migrations` | `setupMigrations` |
| Aggregates | [`@convex-dev/aggregate`](https://www.convex.dev/components/aggregate) | `nuxt-backend/aggregate` | `TableAggregate`, `withTriggers` |
| Workflows | [`@convex-dev/workflow`](https://www.convex.dev/components/workflow) | `nuxt-backend/workflows` | `setupWorkflows` |
| Search | Convex native full-text search | `nuxt-backend/search` | `search`, `defineSearch` |

## The scaffolded `convex.config.ts` mounts everything

The module scaffolds `backend/convex.config.ts` for you (so does `npx nuxt-backend init`). It mounts the all-in-one `backend` component plus every bundled upstream component, declares the typed env contract (`backendEnv` from `nuxt-backend/app` — `AUTH_SECRET` + `SITE_URL` required, the rest optional), and forwards the `EMAIL_*` refs to the `backend` component — so you set the env vars and auth OTP / verification / invitation email just works:

```ts [backend/convex.config.ts]
import { defineApp } from 'convex/server'
import { backendEnv } from 'nuxt-backend/app'
import backend from 'nuxt-backend/component/convex.config'
import aggregate from '@convex-dev/aggregate/convex.config'
import migrations from '@convex-dev/migrations/convex.config'
import persistentTextStreaming from '@convex-dev/persistent-text-streaming/convex.config'
import polar from '@convex-dev/polar/convex.config'
import rateLimiter from '@convex-dev/rate-limiter/convex.config'
import workflow from '@convex-dev/workflow/convex.config'

const app = defineApp({ env: backendEnv })

// Components are isolated from the app env — forward the email config by
// reference so the deployment's values reach the backend component (auth,
// email, billing cache, gifts — the email provider is nested inside).
app.use(backend, {
  env: {
    EMAIL_API_KEY: app.env.EMAIL_API_KEY,
    EMAIL_FROM: app.env.EMAIL_FROM,
    EMAIL_TEST_MODE: app.env.EMAIL_TEST_MODE,
    EMAIL_WEBHOOK_SECRET: app.env.EMAIL_WEBHOOK_SECRET,
  },
})
app.use(aggregate)
app.use(migrations)
app.use(persistentTextStreaming)
app.use(polar)
app.use(rateLimiter)
app.use(workflow)

export default app
```

::note
**Why not a one-call helper?** Convex discovers components from the `convex.config` imports it meets while bundling this file, and current Convex backends crash the push (`start_push 500`) when such an import is reached through an intermediate module or `app.use` runs in a loop — so the definition is deliberately explicit: every component imported and mounted in the root file, one `app.use` per component. Keeping the imports and `use` calls in the root file is what makes the push work — and it keeps the component tree obvious.
::

::tip
Need to add env vars, swap in your own definition, or skip an upstream component? Edit the file:

```ts
import { v } from 'convex/values'
import backend from './components/backend/convex.config'   // a local install — swap the import

const app = defineApp({
  env: { ...backendEnv, STRIPE_SECRET_KEY: v.optional(v.string()) },   // extend the declared env
})
// … and leave out the import + app.use(...) of a component nothing in backend/ uses
```

`backend` is the package's core — keep it mounted. Drop an upstream component only when nothing in `backend/` depends on it (`setupAuth` uses `rateLimiter`, `setupAi` needs `persistentTextStreaming` and `rateLimiter`, `setupBilling` needs `polar`, …). The env proxy throws on undeclared vars, so declare every var you read.
::

## One `backend` component — plus the upstream components

The package ships **one Convex component of its own**, with flat function modules split by concern:

- **`adapter`** — the Better Auth tables + adapter (`components.backend.adapter.*`). Better Auth itself is *not* mounted as a component; it runs as app-level code over the component's adapter (the hybrid pattern).
- **`email`** — transactional email, with [`@convex-dev/resend`](https://www.convex.dev/components/resend) nested inside the component: `components.backend.email.send` / `status` / `get` / `cancel` / `cleanup` / `cleanupAbandoned` / `handleWebhook`. The component owns the `EMAIL_*` env.
- **`billing`** — the reactive entitlement / credit cache: `components.backend.billing.getByUser` / `upsert` / `userByCustomer` / `deleteByUser` / `clear`.
- **`gifts`** — gift purchases (the `billingGifts` table): `components.backend.gifts.*`, driven by [`setupBilling`](/platform/billing/gifts).

Resend is the one component nested **inside** another (it's self-contained, so `backend` re-exposes it through its `email` functions). The upstream components mount at the **app level** — a nested component is sandboxed from the parent app, and polar, rateLimiter, workflow, migrations, aggregate, and persistentTextStreaming all operate over **your** tables, functions, auth, and HTTP routes.

The dashboard component tree looks like this:

```text
app
├─ backend
│  └─ backend/resend
├─ polar
├─ rateLimiter
├─ workflow
│  └─ workflow/workpool
├─ migrations
├─ aggregate
└─ persistentTextStreaming
```

Because [components are isolated from the app's env](https://docs.convex.dev/components), the scaffolded `convex.config.ts` declares the deployment env vars with typed validators (`backendEnv`) and **forwards** `EMAIL_API_KEY`, `EMAIL_FROM`, `EMAIL_TEST_MODE`, and `EMAIL_WEBHOOK_SECRET` to the `backend` component by reference — the scaffold writes that wiring for you.

## Server helpers vs. composables — two halves, not duplicates

The `nuxt-backend/*` entrypoints are **server** code: you import them *inside your Convex functions* to construct and configure each component client (with sensible defaults baked in — auth rate limits, workflow retries, etc.). The auto-imported `useSearch` / `useCount` / `useBilling` / `useWorkflowStatus` composables are **client** code: thin Vue-reactive wrappers over `useQuery` that subscribe to the queries those functions expose.

You need both — the helper builds the server endpoint; the composable consumes it reactively in your components.

::note
Each helper lives on its **own** entrypoint (rather than one barrel) so a Convex function only bundles the component it actually imports — the same reason the underlying `@convex-dev/*` packages are split, and what keeps `better-auth` out of a file that only does rate limiting.
::
