`setupWorkflows(components, options?)` from `nuxt-backend/workflows` returns a `WorkflowManager` with sensible defaults — a workpool of `maxParallelism: 10` and `defaultRetryBehavior: { maxAttempts: 3, initialBackoffMs: 250, base: 2 }`, both overridable through `options.workpoolOptions`. Define durable functions with `workflow.define({ args, handler })`, start them with `workflow.start(ctx, internal.x.y, args)` (it returns a `WorkflowId`), and read or stop a run with `workflow.status(ctx, id)` and `workflow.cancel(ctx, id)`.

## Email sequences

The scaffolded `backend/workflows.ts` — as generated, with its commented second step filled in — is an onboarding drip built with `defineEmailSequence(workflow, components, { args, steps })`:

```ts [backend/workflows.ts]
import { defineEmailSequence, setupWorkflows } from 'nuxt-backend/workflows'
import { v } from 'convex/values'
import { components } from './_generated/api'

export const workflow = setupWorkflows(components)

// Runs once on signup (started from auth.ts's onUserCreated).
export const onSignup = defineEmailSequence(workflow, components, {
  args: { userId: v.string(), email: v.string(), name: v.string() },
  steps: [
    {
      after: 0,
      email: ({ email, name }) => ({
        to: email,
        subject: 'Welcome!',
        html: `<p>Welcome aboard, ${name}! We're glad you're here.</p>`,
      }),
    },
    {
      after: 3 * 24 * 60 * 60 * 1000, // three days later
      email: ({ email }) => ({ to: email, subject: 'Getting the most out of it', text: '…' }),
    },
  ],
})
```

Each step is `{ after, email }`. `after` is the delay in milliseconds from the previous step, slept durably through the workflow component — it survives restarts and deploys. `email(data)` receives the workflow's args and returns `{ to, subject, html?, text? }`, or `null` to skip the step (the user already activated, the nudge is moot). Every message goes through the backend component's email module, so it is delivery-tracked like any other [send](/platform/email/sending). Cancel a running sequence with `workflow.cancel(ctx, id)`; `EmailSequenceStep<Data>` is exported for steps you build elsewhere.

## Your own workflows

`workflow.define` is the general form. Each step is retried independently and survives restarts; the handler's `step` runs queries, mutations and actions, and sleeps:

```ts [backend/workflows.ts]
// Below the `workflow` defined above; `v` and `components` are already imported there.
export const provisionAccount = workflow.define({
  args: { email: v.string() },
  handler: async (step, { email }) => {
    await step.runMutation(components.backend.email.send, {
      to: email,
      subject: 'Your account is ready',
      text: 'Everything is set up.',
    })
    await step.sleep(60 * 60 * 1000)
    // more durable steps — step.runQuery / runMutation / runAction
  },
})
```

## Welcome-email flow

The scaffolded `backend/auth.ts` starts the sequence from the `onUserCreated` integration hook and turns the packaged welcome email off, so a new user gets one welcome, not two:

```ts [backend/auth.ts]
import { workflow } from './workflows'

export const { authComponent, createAuth, getAuthUser /* … */ } = setupAuth(components, query, {
  integrations: {
    rateLimiter,
    // The sequence sends its own welcome — skip the packaged one.
    welcomeEmail: false,
    onUserCreated: async (ctx, user) => {
      await workflow.start(ctx, internal.workflows.onSignup, {
        userId: user.id, email: user.email, name: user.name,
      })
    },
  },
})
```

::tip
The `ctx` passed to `onUserCreated` is a full mutation/action ctx, so it can start a Workflow directly. See [cross-component wiring](/platform/auth/setup#cross-component-wiring).
::

## Reactive status

`useWorkflowStatus(query, workflowId)` subscribes to a query that takes `{ workflowId }` and wraps `workflow.status`. The scaffold doesn't ship one, so add it next to your workflows — `WorkflowId` is a branded string, so cast the validated arg back:

```ts [backend/workflows.ts]
// Below the `workflow` defined above — merge these imports with the file's.
import { type WorkflowId } from 'nuxt-backend/workflows'
import { query } from './_generated/server'

export const getWorkflowStatus = query({
  args: { workflowId: v.string() },
  handler: (ctx, { workflowId }) => workflow.status(ctx, workflowId as WorkflowId),
})
```

The subscription pauses while the id is `null`/`undefined`. The value is the component's `WorkflowStatus`: `type` is `'inProgress'` (with the `running` steps), `'completed'` (with `result`), `'failed'` (with `error`) or `'canceled'`:

```vue
<script setup lang="ts">
import { api } from '#backend/api'

const workflowId = ref<string | null>(null)
const status = useWorkflowStatus(api.workflows.getWorkflowStatus, workflowId)
// status.value?.type: 'inProgress' | 'completed' | 'failed' | 'canceled'
</script>
```

::note
`useWorkflowStatus` is in the experimental tier (see STABILITY.md): it tracks the upstream workflow component's pre-1.0 status shape, which may change in a minor release.
::
