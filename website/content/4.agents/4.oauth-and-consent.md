An agent never gets an API key. It runs the OAuth authorization-code flow against **your** app, a human signs in and consents to a set of scopes, and from then on every tool call happens as that user, with those scopes, through a Convex JWT that lives five minutes.

## The flow, end to end

::steps{level="3"}

### The agent hits `/mcp` with no token

The gate answers `401` with the RFC 9728 challenge — a JSON-RPC error body mirroring Better Auth's own shape, plus the header MCP clients look for:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://your-app.com/.well-known/oauth-protected-resource"
Access-Control-Expose-Headers: WWW-Authenticate
Content-Type: application/json

{"jsonrpc":"2.0","error":{"code":-32000,"message":"Unauthorized: authentication required",
 "www-authenticate":"Bearer resource_metadata=\"…\""},"id":null}
```

That is the handshake, not a failure. A client that stops here doesn't implement the flow.

### It reads the two discovery documents

`/.well-known/oauth-protected-resource` names the app origin as the protected `resource`, advertises the [scopes](#scope-semantics), and points at the authorization server — the auth base on the app origin (`/api/auth` by default), which the base module proxies to Convex. `/.well-known/oauth-authorization-server` then returns Better Auth's own RFC 8414 document (proxied from the Convex site URL and cached for five minutes) with the authorize, token, registration and JWKS endpoints.

### It registers itself and sends the user to sign in

The OAuth provider is Better Auth's **`mcp` plugin**, enabled by default inside `setupAuth`. Agents obtain access through dynamic client registration plus the authorization-code flow. The user lands on your app's login page (`/login` by default — the package is passwordless, and the OTP/passkey sign-in resumes the flow through the `oidc_login_prompt` cookie), then sees the consent screen listing the scopes the client asked for.

### It exchanges its token on every request

The agent now holds an **opaque** Bearer. Convex functions authenticate with JWTs, so the Nitro gate bridges the two: it POSTs the Bearer to `POST {CONVEX_SITE_URL}/mcp/exchange`, which

1. looks the token up in the provider's token store (unknown or expired → `401`),
2. spends one token of the `mcp` rate limit, keyed `clientId:userId` (over budget → `429`),
3. loads the user — a deleted or banned account fails like an invalid token,
4. resolves the user's workspace the way a fresh session would (first membership), so agent spend lands on the same billing entity as the web app's,
5. mints a Convex JWT whose claims mirror a session JWT: `name`, `email`, `emailVerified`, `role`, `activeOrganizationId`, `scopes`, `clientId`, `sub`, `iss` (the Convex site URL), `aud: 'convex'`, and a **five-minute** `exp`.

```json
{ "token": "<jwt>", "expiresIn": 300,
  "session": { "userId": "…", "clientId": "…", "scopes": ["profile", "billing:read"] } }
```

### Tools run as that user

The gate attaches the resolved session to `event.context.backendMcp`; [`useBackendMcp()`](/agents/custom-tools) hands tool handlers Convex fetchers bound to the JWT. Every claims-first consumer — authorization, workspace resolution, billing-entity resolution — reads the call exactly like a web session.

::

## The exchange cache

One round trip per token per JWT lifetime. The gate keeps resolved sessions in an in-memory TTL + LRU cache keyed by the opaque Bearer:

| Property | Value |
|---|---|
| Entry TTL | The minted JWT's lifetime **minus a 30 s margin**, so a cached JWT is never handed out moments before it lapses |
| Capacity | 500 entries, least-recently-used evicted first |
| Scope | Per Nitro instance, in memory — nothing is persisted or shared |

That TTL is also the **revocation bound**: because the JWT lives five minutes and the cache expires with it, revoking an agent's OAuth token cuts its Convex access within minutes, with no distributed invalidation to build or operate.

Failures are deliberately separated, so a client is never told to re-authenticate over an infrastructure problem:

| From the exchange | The gate answers |
|---|---|
| `401` (unknown / expired / revoked token, banned or deleted account) | `401` with the discovery challenge |
| `429` (the `mcp` limit) | `429 Too many agent requests — try again shortly.` |
| No Convex site URL configured | `503 Agent endpoint unavailable` |
| Any other non-2xx (route not mounted, deployment unreachable) | `502 Agent token exchange failed (<status>)` |
| `404 mcp_disabled` — the provider is off (`setupAuth({ mcp: false })`) | `502` (the exchange isn't there to serve) |

## Scope semantics

The provider offers a fixed catalogue plus anything you add. Reads never need more than a `*:read` scope, and no scope in the set authorizes an irreversible action:

| Scope | Grants |
|---|---|
| `openid` · `profile` · `email` | Identity — the OIDC scopes the provider always grants |
| `profile:write` | The display **name** only. Email changes stay in the verified web flow, so an agent can never move an account to an unproven address |
| `billing:read` | Plans, the current subscription, credit balances — reads |
| `billing:checkout` | Checkout and portal **links only**. The human opens them in a browser; no tool executes a payment, and success/return paths must be app-relative |
| `workspace:read` | The workspace list and member lists |

Enforcement is two-layered: a tool whose scope is missing is hidden from `tools/list`, **and** the handler re-checks and refuses with `403`. Add your own scopes with `setupAuth({ mcp: { scopes: [...] } })` — see [custom tools](/agents/custom-tools#custom-scopes).

## Rate limiting the exchange

`DEFAULT_LIMITS.mcp` is a token bucket of **60 exchanges per minute per client + user, burst 20**. It guards the endpoint agents call on the app's behalf; pass the limiter into `setupAuth` for it to apply:

```ts [backend/auth.ts]
export const { authComponent, createAuth, mcp /* … */ } = setupAuth(components, query, {
  integrations: { rateLimiter },   // from backend/rateLimiter.ts
})
```

Override it like any other named limit — see [Rate limiting](/platform/rate-limiting).

## Consent

The `mcp` plugin renders the consent screen; `setupAuth`'s `mcp` options shape the rest of the experience:

```ts [backend/auth.ts]
setupAuth(components, query, {
  mcp: {
    loginPage: '/login',              // where the user signs in mid-OAuth
    consentPage: '/oauth/consent',    // your own screen instead of the built-in one
    trustedClients: [/* first-party agents, optionally skipConsent */],
    scopes: ['todos:write'],          // extra scopes on top of the built-in catalogue
    oidcConfig: { /* advanced passthrough — the options above win over it */ },
  },
})
```

::warning
`trustedClients` with `skipConsent` bypasses the consent screen entirely. List **first-party** agents only — a client there can obtain a user's tokens without the user ever approving it.
::

::note
`loginPage` defaults to the built-in login path. If you moved or replaced it (`backend.pages.login`, `backend.loginPath`), point `loginPage` at the same route — otherwise agents' users land on a 404 mid-flow.
::

## What production needs

- **`SITE_URL`** on the deployment set to the public app origin. It is the only trusted browser origin for auth, and the OAuth redirects, discovery documents and checkout links are all built on that origin.
- **A Convex site URL on the Nuxt side** (`NUXT_PUBLIC_CONVEX_SITE_URL`, `backend.siteUrl`, or derived from `CONVEX_DEPLOYMENT`) — without it the gate answers `503`.
- **The exchange route mounted**: `registerBackendRoutes(http, { auth: { authComponent, createAuth }, mcp })`. Missing → `502` on every agent call.
- **The rate limiter wired** into `setupAuth`'s integrations, so the `mcp` limit actually applies.
- **A decision on the built-in tools** — disable the ones you don't want with [`tools.builtin`](/agents/built-in-tools#disabling-tools).
- **HTTPS**, and a publicly reachable origin: a remote client cannot reach `localhost`. See [Connect a client](/agents/connect-a-client).
- Remember that rotating **`AUTH_SECRET`** invalidates sessions *and* the stored signing keys — agents must re-run the OAuth flow. Treat it as incident response, not routine ([Troubleshooting](/production/troubleshooting)).

Not ready to expose any of it? `backend: { mcp: false }` removes the endpoint and the discovery routes, and `setupAuth({ mcp: false })` drops the provider and the exchange. The [production checklist](/production/checklist) carries both decisions.
