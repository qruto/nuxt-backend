Every app built on `nuxt-backend` exposes an **MCP endpoint** at `/mcp`, served by Nitro through [`@nuxtjs/mcp-toolkit`](https://mcp-toolkit.nuxt.dev) (a declared module dependency — you never install or configure it yourself). An agent that connects there signs in through OAuth as one of **your users** and can call the [built-in tools](/agents/built-in-tools) — and [your own](/agents/custom-tools) — with the scopes that user consented to.

It is **on by default**, in dev and in production: everything the built-in tools expose is already reachable through the product UI under the same user auth, and OAuth adds per-client consent on top. `backend: { mcp: false }` removes the whole surface.

## What an agent connects to

| URL | Serves |
|---|---|
| `https://your-app.com/mcp` | The MCP endpoint (streamable HTTP transport). Requires a Bearer token; answers `401` with a discovery challenge otherwise |
| `https://your-app.com/.well-known/oauth-protected-resource` | RFC 9728 protected-resource metadata — points the client at the authorization server |
| `https://your-app.com/.well-known/oauth-authorization-server` | RFC 8414 authorization-server metadata — the Better Auth OAuth provider's own document |

That is the entire handshake: a client hits `/mcp`, gets the challenge, follows the two documents, registers itself, runs the authorization-code flow against your app's login page, and comes back with a token. See [OAuth & consent](/agents/oauth-and-consent) for the flow end to end, and [Connect a client](/agents/connect-a-client) for the commands.

::note
The endpoint lives on your **app origin**, not on the Convex site URL. Discovery documents, checkout links, and OAuth redirects are all built from that origin, which is why `SITE_URL` must be the public app URL in production.
::

## What the module mounts

Three server middleware, registered globally and matched in-handler (each one early-returns on every other path, so the global hop is one string compare):

| Middleware | Owns | Behaviour |
|---|---|---|
| `mcp/gate` | `mcp.route` and everything under it | Reads the `Authorization: Bearer …` header, exchanges the token for a Convex-authenticated session, and attaches it to `event.context.backendMcp`. No/invalid Bearer → `401` with `WWW-Authenticate: Bearer resource_metadata="…"` |
| `mcp/protected-resource` | `/.well-known/oauth-protected-resource` (+ the path-suffix form) | Serves the RFC 9728 document locally, with `resource` set to the app origin, `authorization_servers` pointing at the auth proxy base, `jwks_uri`, `scopes_supported`, `bearer_methods_supported: ["header"]`, `RS256`. Cached 5 minutes, CORS-open |
| `mcp/authorization-server` | `/.well-known/oauth-authorization-server` (+ the path-suffix form) | Proxies Better Auth's own RFC 8414 document, fetched straight from the Convex site URL and cached 5 minutes. A stale copy is served over an upstream outage; `503` when no Convex site URL is configured, `502` when it is unreachable and nothing is cached |

The gate deliberately lets four things through unchallenged, so agents and humans both get sensible behaviour:

- `OPTIONS` preflights.
- A browser `GET` that asks for `text/html` — a human visiting `/mcp` gets the toolkit's page, and because no session is attached, **every tool stays hidden**.
- `{route}/deeplink` and `{route}/badge.svg` — the toolkit's IDE install deeplink and badge.
- Sibling routes: the gate re-checks the full path, so a route like `/mcp-status` is never gated.

The module also enables Nitro's `asyncContext` (the toolkit's helpers, and `useBackendMcp()` inside a tool handler, read the current request from it) and publishes a **server-only** runtime config:

```ts
runtimeConfig.backendMcp = {
  route: '/mcp',                    // the route the gate owns
  authBase: '/api/auth',            // backend.authRoute — used by the discovery documents
  exchangePath: '/mcp/exchange',    // the deployment route Bearers are exchanged at
  scopes: [                         // advertised by the protected-resource document
    'openid', 'profile', 'email',
    'profile:write', 'billing:read', 'billing:checkout', 'workspace:read',
  ],
  tools: {},                        // per-tool disables from `mcp.tools.builtin`
  functions: {},                    // Convex function overrides from `mcp.functions`
}
```

Nothing of it reaches the client bundle. When the surface is disabled the key is absent, and every reader (gate, discovery documents, tool guards) is inert.

### nuxt-security relaxations

`nuxt-security` chains in through the base module. Left alone it would throttle long agent sessions with its IP rate limiter, reject tool arguments that look like markup, and take over CORS on the discovery documents — so the module adds route rules that turn exactly those three off for the agent surface, which has its own guards (OAuth, plus the deployment's `mcp` rate limit):

| Route rule | Relaxes |
|---|---|
| `mcp.route`, `{mcp.route}/**` | `security.rateLimiter`, `security.xssValidator`, `security.corsHandler` |
| `/.well-known/oauth-protected-resource(/**)`, `/.well-known/oauth-authorization-server(/**)` | `security.corsHandler` |

They are `defu`-merged, so your own route rules win, and they are inert when `nuxt-security` isn't installed.

## The Convex side

The Nuxt endpoint is only half of it. The OAuth provider and the token mint live in your deployment:

```ts [backend/auth.ts]
export const { authComponent, createAuth, getAuthUser, mcp /* … */ } = setupAuth(components, query, {
  integrations: { rateLimiter },   // seeds the `mcp` limit that guards the exchange
})
```

```ts [backend/http.ts]
registerBackendRoutes(http, {
  auth: { authComponent, createAuth },
  mcp,   // mounts POST /mcp/exchange
})
```

Both are in the scaffolded files already — see [auth setup](/platform/auth/setup) and [webhooks & routes](/platform/webhooks). Without the exchange route, the gate answers `502`.

## Configuration

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-backend'],
  backend: {
    mcp: {
      route: '/mcp',                       // default; trailing slashes are stripped
      name: 'Acme',                        // server name/description/instructions,
      description: 'Acme account agent',   //   forwarded to the MCP toolkit
      instructions: 'Prefer billing-plans before creating a checkout link.',
      sessions: false,                     // stateful transport sessions, default off
      tools: { builtin: { 'billing-portal-link': false } },
      functions: { getCredits: 'myBilling:getCredits' },
    },
  },
})
```

`name`, `description`, `instructions`, `sessions` and `route` are forwarded to `@nuxtjs/mcp-toolkit` as **defaults** — your own top-level `mcp` config in `nuxt.config.ts` wins over them, the same contract as the `convex.*` forwarding. `tools.builtin` and `functions` are read by this package: see [Built-in tools](/agents/built-in-tools). The full option types are in [Module options](/api-reference/module-options).

`name` and `description` are what the server reports in the MCP `initialize` handshake (a client shows them in its server list); `instructions` is the guidance a client typically injects into the model's system prompt. `sessions` turns on the toolkit's **stateful transport** — session ids, SSE streaming and server-to-client notifications; off, every request stands alone and the OAuth gate is the only state. `true` takes the defaults, an object sizes it:

| Key | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Stateful transport on or off |
| `maxDuration` | `1_800_000` — 30 minutes, in milliseconds | A session inactive for longer is cleaned up |
| `maxSessions` | `1000` | Concurrent sessions; past it the endpoint answers `503` |

Sessions are kept in Nitro storage (`mcp:sessions` and `mcp:sessions-meta`, the in-memory driver unless you mount another), so they are per instance and gone on restart — for more than one instance, mount a shared driver on both keys.

### Changing the route

```ts
backend: { mcp: { route: '/agent' } }
```

The gate follows the route, and so do the toolkit's conveniences (`/agent/deeplink`, `/agent/badge.svg`). The discovery documents stay on their `/.well-known/…` paths — `resource` is the **origin**, not the endpoint URL, so a client requesting any path under it (the moved endpoint included) passes its sub-path resource check.

### Turning it off

```ts
backend: { mcp: false }   // or: backend: { mcp: { enabled: false } }
```

No MCP endpoint, no OAuth discovery routes, no built-in tools, no runtime config. `defineBackendMcpTool` / `useBackendMcp` stay importable and auto-imported, so your own tool files keep compiling — they simply never authenticate anything.

::warning
Disabling the Nuxt side leaves the OAuth provider and `POST /mcp/exchange` mounted in Convex. For the conservative posture, also pass `setupAuth(…, { mcp: false })` — the provider is dropped and the exchange route answers `404 mcp_disabled`.
::

::note
The agent surface is **experimental**: the MCP authorization profile it implements (OAuth 2.1 + protected-resource metadata) and `@nuxtjs/mcp-toolkit` are both still moving, so `nuxt-backend/mcp` may change shape in a minor release. The rest of the package holds the stability promise.
::
