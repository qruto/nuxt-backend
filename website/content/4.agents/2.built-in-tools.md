With the [agent surface](/agents/mcp-server) enabled, nine tools are contributed to the MCP endpoint. Each one calls a scaffolded Convex function **as the signed-in user** (through the short-lived JWT the token exchange mints), so `ctx.auth`, workspace resolution and billing-entity resolution behave exactly as they do for a web session.

Every tool declares an OAuth scope. A tool whose scope the agent didn't get is **hidden from `tools/list`**, and a direct call to it is refused with `403` — list-time hiding is only advisory, so the handler re-checks.

## The tools

| Tool | Scope | Arguments | Returns |
|---|---|---|---|
| `profile-get` | `profile` | — | The signed-in user's profile: name, email, verification state (`{ error: 'No profile found for this session.' }` when there is none) |
| `profile-update` | `profile:write` | `name` (1–256 chars) | `{ ok: true, name }` — the new display name. **Name only**: email changes stay in the verified web flow |
| `billing-plans` | `billing:read` | — | The configured billing products (plans and credit packs) with live pricing |
| `billing-subscription` | `billing:read` | — | `{ subscription }` for the billing entity (active workspace, or the user) — `null` when there is none |
| `credits-balance` | `billing:read` | — | The prepaid credit balances per meter (`{ meters: [] }` when none) |
| `billing-checkout-link` | `billing:checkout` | `productIds` (≥ 1, from `billing-plans`), `successPath?` (app-relative) | `{ url, note }` — a checkout **link** for the user to open |
| `billing-portal-link` | `billing:checkout` | `returnPath?` (app-relative) | `{ url, note }` — a customer-portal **link** for managing subscription, invoices and payment methods |
| `workspace-list` | `workspace:read` | — | `{ workspaces }` — the user's workspaces with role, and which one is active |
| `workspace-members` | `workspace:read` | `organizationId?` (from `workspace-list`, default: the active workspace) | The workspace's members (`{ error: 'Not a member of this workspace.' }` otherwise) |

The scopes come from the package's fixed catalogue (`BACKEND_MCP_SCOPES`): `openid`, `profile`, `email` (the OIDC identity scopes the provider always grants), plus `profile:write`, `billing:read`, `billing:checkout` and `workspace:read`. Reads never ask for more than a `*:read` scope — see [scope semantics](/agents/oauth-and-consent#scope-semantics).

::warning
**The checkout tools return links, never payments.** `billing-checkout-link` and `billing-portal-link` hand back a URL for the human to open in their browser — no tool in this package executes a payment, and both carry `destructiveHint: false`. The `successPath` / `returnPath` arguments must be **app-relative** (they are validated against `/^\//`) and are appended to the request origin, so a prompt-injected agent cannot bounce a paying user to an attacker's origin.
::

::note
The read tools are annotated `readOnlyHint`, `profile-update` is `idempotentHint`, and the two link tools are `openWorldHint` — hints MCP clients use to decide when to ask the human for confirmation.
::

## Disabling tools

`backend.mcp.tools.builtin` takes a map of per-tool switches. A tool set to `false` is hidden from every agent, whatever their scopes:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  backend: {
    mcp: {
      tools: {
        builtin: {
          'billing-portal-link': false,
          'profile-update': false,
        },
      },
    },
  },
})
```

`builtin: false` drops the whole set — the module stops contributing its tool directory to the toolkit's definition scan, so the built-ins are not even in the build:

```ts
backend: { mcp: { tools: { builtin: false } } }
```

Your own tools under `server/mcp/tools/` are unaffected either way — see [Custom tools](/agents/custom-tools).

::tip
The **Agents (MCP)** card in the [Backend DevTools panel](/tooling/devtools) lists the route and the built-in tools that survived your config — the quickest way to confirm a toggle landed.
::

## Repointing the Convex functions

Each tool calls a scaffolded function by `module:export` reference. Rename the scaffolded `auth.ts` / `billing.ts` files (or their exports) and the tools need to be told where the functions went — that is what `backend.mcp.functions` is for:

| `functions` key | Default ref | Used by |
|---|---|---|
| `getAuthUser` | `auth:getAuthUser` | `profile-get` |
| `updateProfile` | `auth:updateProfile` | `profile-update` |
| `getConfiguredProducts` | `billing:getConfiguredProducts` | `billing-plans` |
| `getCurrentSubscription` | `billing:getCurrentSubscription` | `billing-subscription` |
| `getCredits` | `billing:getCredits` | `credits-balance` |
| `generateCheckoutLink` | `billing:generateCheckoutLink` | `billing-checkout-link` |
| `generateCustomerPortalUrl` | `billing:generateCustomerPortalUrl` | `billing-portal-link` |
| `listWorkspaces` | `auth:listWorkspaces` | `workspace-list` |
| `listWorkspaceMembers` | `auth:listWorkspaceMembers` | `workspace-members` |

```ts [nuxt.config.ts]
backend: {
  mcp: {
    functions: {
      getCredits: 'myBilling:getCredits',
      generateCheckoutLink: 'myBilling:generateCheckoutLink',
    },
  },
}
```

Only the keys you pass are overridden; the rest keep their defaults.

::note
`doctor`'s `function-contract` finding lists any `module:export` name the deployment is missing — the same names the composables and these tools bind to. See [Troubleshooting](/production/troubleshooting).
::
