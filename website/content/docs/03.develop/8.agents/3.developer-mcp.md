`npx nuxt-backend mcp` starts one MCP server for the coding agent that builds your app. It answers three kinds of question an agent asks while it works: what state the project is in, what the docs say, and what a provider holds. For the last, it passes the agent through to Convex, Polar, Resend and Vercel, on the logins and keys your project already has, so there is one server to connect rather than five. It runs on your machine over stdio, acts on the deployment your project points at, and asks you before any tool changes something.

## Connect it

`npx nuxt-backend init` writes it into the project's `.mcp.json`, which Claude Code and most agents read ([Agent files](/docs/develop/agents/agent-files)). The server runs on the MCP SDK, `@modelcontextprotocol/sdk`, an optional peer of `nuxt-backend`, so apps that never start it don't install it. `init` adds it to your `devDependencies`. If you add the server by hand, install the SDK first:

```bash
npm install -D @modelcontextprotocol/sdk
```

To add the server by hand in Claude Code:

```bash
claude mcp add --scope project nuxt-backend -- npx nuxt-backend mcp
```

In Cursor, `.cursor/mcp.json`:

```json [.cursor/mcp.json]
{
  "mcpServers": {
    "nuxt-backend": {
      "command": "npx",
      "args": ["nuxt-backend", "mcp"]
    }
  }
}
```

In VS Code, `.vscode/mcp.json`, for Copilot's agent mode:

```json [.vscode/mcp.json]
{
  "servers": {
    "nuxt-backend": {
      "type": "stdio",
      "command": "npx",
      "args": ["nuxt-backend", "mcp"]
    }
  }
}
```

The [agent plugin](/docs/develop/agents/plugin) brings it with the skills, for every project at once.

## Tools

Each tool answers as data, not as the text a command prints. The names of a group share a prefix, named for what it does rather than for the provider behind it.

### Project state

| Tool | What it answers | Built on |
|---|---|---|
| `doctor` | Every finding with its fix, for one capability or all | [`doctor --json`](/docs/develop/doctor) |
| `status` | Each [capability](/docs/start/concepts/capabilities)'s state: `live`, `test` or `missing` | `status` |
| `env` | The env names the app and its deployment need, which are set, and what a missing one turns off. Never a value | The [env registry](/docs/reference/configuration/environment-variables) |
| `catalog` | Your billing catalog, and what `billing sync` would create, change or leave as drift | [`billing sync --dry-run`](/docs/build/billing/catalog) |
| `functions` | Every function the scaffold exports: whether the deployment has it, and what a call takes (a recent sign-in, no administrator acting as the account, the limits it spends) | The function contract `doctor` checks |

### Docs

| Tool | What it answers |
|---|---|
| `search-docs` | The docs sections that match a query, written-by-hand sections first |
| `get-page` | A docs page as Markdown, by its path |

They answer from the [docs MCP](/docs/develop/agents/docs-mcp)'s index, so an agent with this server needs no second one. The docs describe the current release line: when your project installed another, each answer says so, and points at the skills in `node_modules/nuxt-backend/skills`, which match the installed version.

### Providers

| Group | Provider | Signs in with | What it covers |
|---|---|---|---|
| `data-*` | Convex | Your Convex CLI login (`npx convex login`) | Tables and documents, a one-off query, running a function, the logs, the names of the deployment's env vars, insights |
| `billing-*` | Polar | `BILLING_ACCESS_TOKEN` from `.env.local`: your sandbox | Products, customers, subscriptions, usage events and webhook deliveries |
| `email-*` | Resend | `EMAIL_API_KEY` from `.env.local` | Sent emails and their last events, the [dev inbox](/docs/develop/dev-inbox)'s sign-in codes, domains, contacts and segments, and a test email to a test address |
| `hosting-*` | Vercel | Your Vercel CLI login (`vercel login`), on the project `vercel link` linked | Deployments, their build logs, the names of the env vars and the firewall rules |

The tools of each group:

- **`data-*`:** `data-tables`, `data-documents`, `data-functions`, `data-query`, `data-run`, `data-logs`, `data-insights`, `data-env`, `data-env-set` and `data-env-remove`.
- **`billing-*`:** `billing-products`, `billing-customers`, `billing-subscriptions`, `billing-events` and `billing-webhook-deliveries`.
- **`email-*`:** `email-sent`, `email-get`, `email-inbox`, `email-domains`, `email-contacts`, `email-segments` and `email-send-test`.
- **`hosting-*`:** `hosting-deployments`, `hosting-logs`, `hosting-env` and `hosting-firewall`.

The `data-*` tools are the Convex CLI's own MCP tools (`npx convex mcp start`), run for this project and passed through with two changes: the env tools answer names, never values, and the tables of the package's component, which hold sessions, codes and tokens, stay out of reach, since the tools read the app's own tables and no argument the Convex tool does not declare reaches it. The deployment is the one your project points at, so an agent never picks one. The rest call each provider's API with the key or login named here: the hosting tools go through the Vercel CLI's own `vercel api`, so no token passes through the server. A provider you have not signed in to keeps its tools listed, and each answers with the command that signs you in.

## What it changes, and where

- **Every write asks first.** A tool that changes something, `data-run`, `data-env-set`, `data-env-remove` and `email-send-test`, asks you to confirm before it runs, through the client's MCP elicitation prompt. The prompt names what it passes: the function and its arguments for `data-run`, the variable's name but never its value for `data-env-set`. A client that cannot show one gets the write refused, with the command to run it yourself. `email-send-test` sends only to the provider's test addresses.
- **A one-off query asks too.** `data-query` changes nothing, but a query can read the deployment's env values as well as its tables. It shows you the query and runs it only once you accept.
- **Development by default.** The tools act on your dev deployment, your Polar sandbox and Resend's test addresses. Started with `npx nuxt-backend mcp --prod`, the project, billing, email and hosting tools read production, the `data-*` tools read only its logs and insights, and no tool that writes is listed. Polar's production needs a production token in the env the server starts with, as `billing sync --env production` does. One Resend key usually serves both, so without `--prod` the email tools answer only the emails sent to Resend's test addresses and the contacts that are one, and `--prod` reads every one.
- **Sign-in codes stay in development.** `email-inbox` reads codes only on a deployment whose `BACKEND_ENVIRONMENT` is `development`, and refuses anywhere else ([Environments](/docs/start/concepts/environments)).
- **Secrets never leave.** No tool returns a key, a token or an env value on its own: `env` and `data-env` say which names are set, never what they hold. Only a one-off query you accept could read one.
- **Local and over stdio.** Nothing listens on a port, and only the agent that started the server reaches it.
