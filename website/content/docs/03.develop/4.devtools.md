With Nuxt DevTools enabled, the module adds a **Backend** tab to the Server group. It shows your backend as it runs: each capability's state, the findings, the account, billing, email and webhook deliveries. It is dev-only, on whenever DevTools is (never under a test runner), and off with `backend: { devtools: false }`. It is built for Nuxt DevTools 3, the version Nuxt 4 installs. The connection's details, live queries, the auth-state timeline and function logs live in `nuxt-convex-module`'s own tab, which the Backend tab links to.

Two data paths feed it:

- **Dev-server facts** come over the DevTools RPC: the deployment, the checks, which env names are set, the pages, the catalog. The dev server pushes fresh facts to an open panel when `.env`, `.env.local` or the codegen changes. Only env **names** cross, never values: secrets stay in the Node process.
- **Live app state** comes from the inspected page: a dev-only client plugin runs the package's own composables (`useAuth`, `useBilling`, `useFeatures`, `useWorkspace`, the credit and delivery queries) and mirrors their state into a plain-JSON bridge on `window.__NUXT_BACKEND_DEVTOOLS__`. What the page already holds (the session, the content config, the connection) is mirrored from page load. The queries on top (the subscription, granted features, every credit meter, the active workspace, webhook deliveries) start the first time the tab opens, so a page nobody inspects pays nothing for them. Sessions, passkeys, gifts and email lookups load only when a tab asks for them. If the panel says the bridge is missing, reload the inspected page.

Colour means one thing everywhere in the tab: green is fine, amber needs attention, red is broken, grey is off or not applicable.

## Overview

| Part | Shows |
|---|---|
| Header | The backend connection, the deployment's kind and id (dev, local, production, …), a link to its dashboard for cloud deployments, **Connection & queries** (the base module's tab), and the installed versions of `nuxt-backend`, `nuxt-convex-module`, `convex` and `nuxt` |
| Capabilities | A console of the [capabilities](/docs/start/concepts/capabilities), one channel each: a light for its state (green live, amber test, grey missing, red failing), what it is built on and why it is in that state, the env names it lacks, its most pressing finding, and links to its own tab and its docs. It reads the dev-server checks, the deployment env names and the **Run doctor** results since an env file last changed, as [`npx nuxt-backend status`](/docs/reference/cli#status) does. It reads no value off the deployment, so a `BACKEND_ENVIRONMENT` set there and not in `.env.local` shows its safe mode, the providers' test modes, and says so |
| Missing modules | A warning when a scaffolded function module the composables bind to (`auth.ts`, `billing.ts`, `email.ts`) is not deployed |
| Health | The same checks the dev server prints on start, problems first with a **copyable fix**. **Run doctor** adds [`nuxt-backend doctor`](/docs/reference/cli#doctor)'s deployment-side checks, run in the dev server against the dev deployment: codegen, deployed functions, the invitation route, webhook route probes, the billing catalog. **Copy doctor JSON** then copies the run as `doctor --json` prints it, for an issue or a coding agent |
| Env | Every variable of the [env contract](/docs/reference/configuration), twice: set in this dev server (`.env`, `.env.local`, its process env) and set on the deployment (read with `convex env list`, names only, cached for a minute). A variable that is set on the deployment counts as set, so `AUTH_SECRET` and `SITE_URL` provisioned by the dev server stop warning |
| Mounts | Every component the scaffold mounts in `convex.config.ts`, and any of your own, amber when one is missing, with the route groups `http.ts` does not register. [`doctor --fix`](/docs/reference/cli/diagnostics#convex-config) adds them |
| Maintenance | The backend component's [maintenance](/docs/build/data/jobs/scheduled#the-maintenance-the-component-runs): each task's last pass and the rows it deleted, read from the dev deployment with `convex run` (cached for a minute) |
| Pages | Every ready-made page: its path, whether it needs a session, and whether the module or your own page renders it |
| Wiring | The module options that change what runs: the backend URL, the auth route, the pages, the redirects and DevTools itself |

The panel reads only a dev deployment. For production, run `npx nuxt-backend doctor --prod`.

## Account

The signed-in user (name, email, id), the active workspace with your role, its members and pending invitations, and this account's device sessions (the current browser marked) and passkeys. A session's token and a passkey's credential never reach the panel. Buttons open `auth.ts` and `functions.ts` in your editor.

## Billing

The subscription's state (status, product, cancel at period end, paused, trial end, a plan change scheduled for the next period), the granted feature keys `useFeatures().has()` matches, each [plan quota](/docs/build/billing/subscriptions/quotas) with its use and limit as `useFeatures().quota()` reads it (the **Quotas** card, its catalog `description` on hover), every credit meter (balance, credited, consumed), and gifts waiting for this account (read only, never claimed from the panel). The **Catalog as code** card lists what `billing.catalog.ts` declares and whether `billing sync` has written ids for the sandbox and production, and warns when `appConfig.backend.billing` lists a plan or pack the catalog does not declare. Outside production, the tab says billing runs in [Polar's sandbox](/docs/develop/sandboxes#billing-on-polars-sandbox) and links to its dashboard.

## Email

What the transport has (`EMAIL_API_KEY`, `EMAIL_FROM`, `EMAIL_WEBHOOK_SECRET`), with what each one's absence means, and whether `BACKEND_ENVIRONMENT` keeps it in test mode; recent delivery events; and a lookup of one email's delivery status by the id `send` returned.

**Templates** previews every email the package sends, rendered with sample data by your dev deployment, so what you see is what it sends: your `templates`, `messages` and `brand` from `email.ts`. Pick a language your messages cover, light or dark, and wide or phone width; the text version is under the preview. **Send to delivered@resend.dev** sends the one in view to Resend's test address, where the [dev inbox](/docs/develop/dev-inbox) reads it back, and its id looks up above. The tab runs the two internal functions the scaffolded `email.ts` re-exports (`export const { previewEmails, sendEmailPreview } = email.devtools`) with the Convex CLI, on a dev deployment only; without them it shows the line to add. [Customize email templates](/docs/build/email/templates#previewing) has the rest.

## Webhooks

The last event received per service with its outcome, both webhook secrets, and the delivery log: the last 50 deliveries the deployment verified or refused, filterable by service and to problems only. Refused requests of one kind share a row, with a ×count. The log is for admins: signed in as anyone else, the tab says so and gives the command that makes an account an admin. Outcomes: `ok` is green, `duplicate` (already handled) is grey, an unknown event type is amber, and a refused delivery (`invalid_signature`, `missing_secret`, …) is red. To send one again, replay it from the provider's dashboard.

## Monitoring

The [monitoring capability](/docs/ship/operate/monitoring) on the dev server: its state and why, the app's health as `/api/backend/health` answers it (each capability's state, and on a dev deployment why), and the **local error log**: what an error-reporting service would receive from this dev server. Each entry is a failed backend call from the browser or the server, with the function it ran and its error code, or a crash, newest first; the last 200 are kept, and **Clear** forgets them. A refusal from the error catalog (nobody signed in, a missing role) is the app working as designed, and is left out. The tab reads both every five seconds while it is open: they are same-origin reads of the app's own routes, so they work only in dev.

## Activity

What changed while the page was open, newest first: sign-ins, sign-outs and account switches; workspace and role changes; a subscription's status, plan, scheduled cancellation and pause; features granted and removed; each credit meter's balance; every new webhook delivery, a refused one in red; the delivery status of the email looked up on the Email tab; the connection dropping and coming back. Changes are compared between settled values, so a sign-in still counts though the session reloads on the way, and a section's first settled value is the baseline: a session that already existed when the page loaded is not a sign-in, and connecting at page load is not news. The last 200 entries are kept. When an amber or red entry arrives while another tab is open, the Activity tab shows how many.

The same entries go to a **Backend** layer on the Vue DevTools timeline, beside route changes and component events, so a backend change lines up with what the page did.

## Bundles

What `npx nuxt-backend analyze` measured last, from `node_modules/.cache`: the backend's bundle and, once the command has built the app, the Nuxt client and server bundles. Each bundle shows its size, who brings it (`nuxt-backend`, your code, everything else), its largest packages and its insights. Opening the tab reads the last run and measures nothing. **Refresh** runs `analyze --only convex`, which bundles the functions again and takes a few seconds, so nothing else starts it. A run that can't happen, for lack of `backend/_generated/`, says why in the tab ([See what is inside your bundles](/docs/develop/analyze)).

## Open in editor

The panel's file buttons resolve a backend source file (`billing.ts`, `auth.ts`, …) to its path under the functions directory and open it through the dev server's editor launcher. Only plain relative names inside the functions directory resolve: a path segment like `..` is refused.

## Options

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-backend'],
  devtools: { enabled: true },   // Nuxt DevTools itself
  backend: {
    devtools: false,             // drop only the Backend tab
  },
})
```
