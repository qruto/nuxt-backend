Test a query, a mutation or an action in Vitest, with no deployment and no provider.

- **What powers it natively:** [`convex-test`](https://docs.convex.dev/testing/convex-test), Convex's mock of a deployment, which runs your functions against an in-memory database.
- **What the package adds:** `nuxt-backend/test`. It mounts the packaged `backend` component and every component the scaffold mounts, and signs callers in with the claims a real session carries.

## Your app under test

Install `convex-test` beside Vitest and Convex's edge runtime. `convex-test` is an optional peer of the package, so an app with no tests never installs it:

```bash
npm install -D vitest convex-test @edge-runtime/vm
```

Give the backend tests a Vitest project that runs in the edge runtime, as the deployment does:

```ts [vitest.config.ts]
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    projects: [{
      test: {
        name: 'backend',
        include: ['backend/**/*.test.ts'],
        environment: 'edge-runtime',
      },
    }],
  },
})
```

`defineBackendTestApp(schema, modules)` returns a function that builds a fresh instance. Every component the scaffold mounts is registered under the name `convex.config.ts` gives it: `backend`, and the official components beside it, such as `polar`, `rateLimiter` and `workflow` ([What the scaffold mounts](/docs/start/concepts/how-it-works#the-scaffolded-convexconfigts)). Call it once per test, so no test sees another's rows.

`asUser(t, options)` creates an account in the component's auth tables and returns the instance signed in as it. The caller looks the way a real sign-in leaves one: the role `'user'`, and a personal workspace it owns and has active.

```ts [backend/todos.test.ts]
import { asUser, defineBackendTestApp, seedWorkspace } from 'nuxt-backend/test'
import { expect, test } from 'vitest'
import { api } from './_generated/api'
import schema from './schema'

const testApp = defineBackendTestApp(schema, import.meta.glob('./**/*.ts'))

test('a member adds a todo to their workspace', async () => {
  const ada = await asUser(testApp())
  await ada.mutation(api.todos.create, { text: 'Ship it' })
})

test('everyone in the workspace is listed', async () => {
  const t = testApp()
  const workspace = await seedWorkspace(t)
  const owner = await asUser(t, { workspace, workspaceRole: 'owner' })
  await asUser(t, { workspace })
  const workspaceMembers = await owner.query(api.auth.listWorkspaceMembers, {})
  expect(workspaceMembers?.members).toHaveLength(2)
})
```

`asUser` takes these options:

::field-group
  :::field{name="email / name" type="string"}
  The account. Default: a fresh `user-<n>@example.com`, named after it.
  :::

  :::field{name="role" type="string"}
  The app-wide role, such as `'admin'`. Default: `'user'`, the role every new account gets.
  :::

  :::field{name="workspace" type="boolean | string"}
  The active workspace. Default: a personal one the user owns, made the way sign-in makes it. A workspace id (from `seedWorkspace(t)` or another `asUser`) adds them to that one instead; `false` leaves them in none, as after leaving every workspace.
  :::

  :::field{name="workspaceRole" type="string"}
  Their role there. Default: `'owner'` of their own, `'member'` of another.
  :::

  :::field{name="impersonatedBy" type="string"}
  The admin's user id, for a session an admin opened as this user.
  :::
::

The caller is `t.withIdentity(...)` with the claims a real session token carries: the account's fields, `role` included, plus the active workspace, `sessionId` and `impersonatedBy`. The issuer is `CONVEX_SITE_URL` when the test sets it, so `tokenIdentifier` reads as in production. The function tiers, the billing entity and `listSessions` resolve exactly as they do for a real caller, and a contract test in the package keeps the claims in step with the real tokens. The caller also carries `userId`, `email`, `workspaceId` and `sessionId` for your assertions.

::note
The three helpers are experimental ([Stability](/docs/ship/releases/stability#the-experimental-tier)): the claims follow the auth flows, which may still move.
::

## Assert a refusal

A tier refuses with a code from the error catalog, so a test never matches a message. Read the code with `getBackendError`:

```ts [backend/todos.test.ts]
import { getBackendError } from 'nuxt-backend/functions'

test('a visitor cannot add a todo', async () => {
  const error = await testApp().mutation(api.todos.create, { text: 'Ship it' }).catch(e => e)
  expect(getBackendError(error)?.code).toBe('unauthenticated')
})

test('someone outside every workspace cannot add one either', async () => {
  const loner = await asUser(testApp(), { workspace: false })
  const error = await loner.mutation(api.todos.create, { text: 'Ship it' }).catch(e => e)
  expect(getBackendError(error)?.code).toBe('no_workspace')
})
```

[Errors](/docs/reference/backend/errors) lists every code, with what a page shows for each.

## Test AI calls

Under `defineBackendTestApp`, every `provider/model` id answers from a mock of the AI SDK's `ai/test`, so a test needs no key and makes no network call. A model repeats the prompt (`Test reply to: …`) at a fixed cost. A safety classifier, any id with `llama-guard` or `safeguard` in it, answers as Llama Guard does: `unsafe` and `S1` when the text it checks contains `[[unsafe]]`, and `safe` otherwise. So a test of `ai.requireSafe`, or of `moderate` on a call, passes or refuses on purpose:

```ts [backend/captions.test.ts]
test('a flagged prompt is refused before anything is spent', async () => {
  const ada = await asUser(testApp())
  const error = await ada.action(api.captions.write, { prompt: 'A fox [[unsafe]]' }).catch(e => e)
  expect(getBackendError(error)).toMatchObject({ code: 'invalid_input', data: { reason: 'content_blocked' } })
})
```

The mock reads text only: an image checked under test is always `safe`.

## Mount a component of your own

A component your app mounts itself, beside the scaffold's, registers through its own test helper under the same name. For `@convex-dev/aggregate`, that is `aggregate.register(t)`, with `aggregate` from `@convex-dev/aggregate/test`.

## Register the component yourself

For a harness you build by hand, `register(t)` mounts the `backend` component alone:

```ts [backend/billing.test.ts]
import { convexTest } from 'convex-test'
import backendTest from 'nuxt-backend/test'
import { components } from './_generated/api'
import schema from './schema'

const modules = import.meta.glob('./**/*.ts')

const t = convexTest(schema, modules)
backendTest.register(t)

// Your own functions, and the component's, through the boundary:
await t.query(components.backend.billing.getByUser, { userId: 'user_1' })
```

`register(t)` mounts the all-in-one `backend` component the way `app.use(backend)` does. It registers it under its name, with its real schema, so every index and document validator applies. Its two children come with it: the email provider at `backend/resend` and the package's migrations at `backend/migrations`. Functions that read auth tables, send email or call into `components.backend` resolve under test.

```ts
function register(
  t: TestConvex<SchemaDefinition>,
  name?: string, // the mount name from convex.config.ts, default 'backend'
): void
// default export: { register, schema, modules }
```

The helper has the shape every `@convex-dev/*` component ships, so `convex-test` needs nothing extra. It uses `import.meta.glob`, so it runs under Vitest only.

::note
The email provider's own children (its send workpools and API rate limiter) are not registered: they only run from the batch job a send schedules. Emails sent under test stay `waiting`, which is the state `cancel` and delivery-status assertions need.
::

## What it does not cover

- **Pages and components:** render them over a mock backend ([Test pages over a mock backend](/docs/develop/testing/pages)).
- **The providers:** no test here calls Polar or Resend. A run that crosses one is an [end-to-end test](/docs/develop/testing/e2e).
- **Webhook signatures:** `convex-test` runs HTTP actions through `t.fetch`, but it can't sign a request the way a provider does. Test the handler's logic as a function.
