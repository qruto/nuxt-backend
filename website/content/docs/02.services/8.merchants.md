Polar is the provider the billing layer is built on. Three other merchants of record sell through the provider-neutral adapters in `nuxt-backend/billing`: Stripe Managed Payments, Dodo Payments and Creem. Each one is the seller in its own name, so it collects and remits sales tax and VAT and emails the receipts, as Polar does.

::warning
**Early support.** The adapters cover checkout, the customer portal, plan changes, cancellation, refunds, invoices and the webhook. `setupBilling`'s cached reads (`useBilling`, credits, quotas, gifts, passes, discounts sync) still run on Polar alone. With another provider, your backend keeps its own subscription and order rows from the webhook events, as shown below.
::

## What each one offers

Checked against each provider's docs on 2026-11-24.

| | Stripe Managed Payments | Dodo Payments | Creem |
|---|---|---|---|
| One-time purchases and subscriptions | Yes | Yes | Yes |
| Customer portal | Yes | Yes | Yes |
| Plan changes, with proration | Yes | Yes | Yes |
| Cancel at period end, and take it back | Yes | Yes (taking it back is untested) | Yes |
| Pause and resume | No | Yes | Yes |
| Refunds through the API | Yes | Yes | No: refund in its dashboard |
| Invoice or receipt link | Yes | Yes (the PDF itself) | No: Creem emails each one |
| Signed success redirect | No | No | Yes: `verifyCheckoutRedirect` |
| Webhook signature | `Stripe-Signature` | Standard Webhooks | `creem-signature` |
| API version | `2026-04-22.dahlia`, pinned | Unversioned | `/v1` |

Stripe Managed Payments sells digital products only: software, SaaS and digital content. Each product needs a tax code that Stripe marks "Eligible for Managed Payments" ([set up](https://docs.stripe.com/payments/managed-payments/set-up)).

## Keys

The same env names Polar uses, plus the provider's name:

```dotenv
BILLING_PROVIDER=stripe          # stripe, dodo or creem; polar when unset
BILLING_ACCESS_TOKEN=sk_test_... # the provider's secret API key
BILLING_WEBHOOK_SECRET=whsec_... # the signing secret of the webhook endpoint
```

Use the test-mode key outside production and the live key on it. Dodo and Creem have a separate host for each mode, and the adapter picks it from `BACKEND_ENVIRONMENT`.

## The webhook

Point the provider's webhook endpoint at `https://<your deployment>.convex.site/billing/events`. Subscribe to these events:

- **Stripe:** `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `invoice.paid`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `refund.created`, `refund.updated`, `charge.dispute.created`. Set the endpoint's API version to `2026-04-22.dahlia`.
- **Dodo:** `payment.succeeded`, every `subscription.*` event, `refund.succeeded`, `refund.failed`, `dispute.opened`.
- **Creem:** `checkout.completed`, every `subscription.*` event, `refund.created`, `dispute.created`.

`BILLING_PROVIDER` does not mount the handler by itself: pass it to `registerBackendRoutes` as `billing.webhookHandler`, in place of the Polar one. `createCommerceWebhookHandler` runs each delivery through the same guarded route Polar's take: it answers 503 without a secret and 413 over 1 MB, skips a delivery it already handled, and logs each one. It then hands your handler one neutral event: `order.paid`, `order.refunded`, `order.disputed` or `subscription.updated`. Your handler must be idempotent, because providers retry until they get a 2xx.

```ts [backend/http.ts]
import { commerceProviderFromEnv, createCommerceWebhookHandler, webhookSecretsFromEnv } from 'nuxt-backend/billing'
import { registerBackendRoutes } from 'nuxt-backend/http'
import { httpRouter } from 'convex/server'
import { components, internal } from './_generated/api'
import type { ActionCtx } from './_generated/server'
import { ai } from './ai'
import { authComponent, createAuth } from './auth'
import { billing } from './billing'
import { email } from './email'

const provider = commerceProviderFromEnv(process.env, process.env.BACKEND_ENVIRONMENT === 'production' ? 'production' : 'sandbox')

const http = httpRouter()
registerBackendRoutes(http, {
  auth: { authComponent, createAuth },
  billing: {
    ...billing,
    // Mounted at /billing/events in place of the Polar handler.
    webhookHandler: createCommerceWebhookHandler<ActionCtx>({
      provider: provider!,
      secrets: webhookSecretsFromEnv(process.env),
      webhookLog: components.backend.webhooks,
      onEvent: (ctx, event) => ctx.runMutation(internal.purchases.apply, { event: JSON.stringify(event) }),
    }),
  },
  email,
  ai,
})

export default http
```

Every checkout stores the billing entity in its metadata as `entity_id`, and `order.paid` and `subscription.updated` carry it back as `entityId`, with the checkout's metadata. `order.refunded` and `order.disputed` carry only the order's id and, for a renewal, the subscription's: look the entity up in the rows you stored from `order.paid`. On Stripe both name the same order id `order.paid` did, the invoice for a subscription and the PaymentIntent for a one-time purchase. Grant access when `order.paid` arrives, never on the success page.

## Account review

Each provider reviews your business before it pays out. Start a week or two before launch:

- **Stripe:** activate the account, then turn on Managed Payments in the Dashboard. Keep the support email current: Stripe may refund a customer itself after 48 hours without your answer ([how it works](https://docs.stripe.com/payments/managed-payments/how-it-works)).
- **Dodo:** verify the business and the owner's identity, add a payout account, and list your website with its terms, privacy and refund pages.
- **Creem:** verify the store, and check that the product you sell is allowed.

Every review reads your site. Have the pricing, the terms, the privacy notice and the refund policy public before you apply, with the company name and address. [Legal pages](/docs/ship/compliance/privacy) prints them from `appConfig.backend.legal`.
