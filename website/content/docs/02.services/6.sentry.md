Sentry collects errors and log lines from the browser, the Nuxt server and the backend's actions, replays what led to an error for visitors who allowed it, takes feedback, watches the backend's crons, receives the backend's alerts, and checks that the app is up. It is optional. Turn it on before launch.

| You need | Time | Cost to start |
|---|---|---|
| A Sentry account | 15 minutes | Free for one person: 5,000 errors a month |

## What it powers

| Capability | What Sentry gives | Pages |
|---|---|---|
| `monitoring` | Error reports from every side, tagged with the function and the error code | [Monitor errors and uptime](/docs/ship/operate/monitoring) |
| `monitoring` | Cron monitors: the backend's maintenance pass, and the jobs you check in | [Check jobs in](/docs/ship/operate/monitoring#check-jobs-in) |
| `monitoring` | Log lines, session replay after consent and the feedback widget, with personal data scrubbed | [What the preset does](/docs/ship/operate/monitoring#what-the-preset-does) |
| `monitoring` | The backend's alerts: the email quota and the day's AI spend | [Alerts](/docs/ship/operate/monitoring#alerts) |
| `monitoring` | An uptime check on the health endpoint | [The health endpoint](/docs/ship/operate/monitoring#the-health-endpoint) |
| `jobs` | The backend's own exception reports, through Convex's integration on Professional | [Background work](/docs/build/data/jobs) |

Without a DSN in development, the dev server keeps a local error log that DevTools lists, so you see the same reports before you sign up.

## Create the account

::steps{level="3"}

### Sign up and pick the data region

At [sentry.io/signup](https://sentry.io/signup), create an organization. Choose where its data lives, the US (Iowa) or the EU (Frankfurt), at that step: the choice is final, and moving means a new organization ([Data storage location](https://docs.sentry.io/organization/data-storage-location/)).

### Create the project

**Projects**, **Create Project**, platform **Nuxt**. One project serves the app and the backend: each report carries `backend.source` (`browser`, `server` or `backend`) to tell them apart.

### Copy the DSN

**Project Settings**, **Client Keys (DSN)**. The DSN is public by design: it lets a client send reports, nothing more.

### Install the SDK

```bash
npm install @sentry/nuxt
```

The module wires it once a build sees a DSN. Skip Sentry's setup wizard: the package passes the SDK its own config files, and a `sentry.client.config.ts` of yours replaces the package's whole ([Customize the SDK](/docs/ship/operate/monitoring#customize-the-sdk)).

::

**Who should own it.** The person on call owns the organization and its alert rules. On the free plan the organization holds one person; Team adds as many as you need.

## Sandbox and test mode

Sentry has no test mode. Every report names the deployment's `BACKEND_ENVIRONMENT` as its environment, so one alert rule scoped to `production` ignores the rest:

| `BACKEND_ENVIRONMENT` | Reports | Cron check-ins |
|---|---|---|
| `development` | The local error log, or Sentry once a DSN is set | No |
| `preview` | Sentry, under `preview` | No |
| `sandbox` | Sentry, under `sandbox` | Yes |
| `production` | Sentry, under `production` | Yes |

A dev deployment that sleeps with a laptop, or a preview deleted with its branch, would read as a missed run, so only `sandbox` and `production` check in.

## Keys and environment

| Variable | Where to find it | Dev | Prod | Secret |
|---|---|---|---|---|
| `MONITORING_DSN` | **Project Settings**, **Client Keys (DSN)** | Optional | On the Convex deployment, and in the app host's env | No |
| `SENTRY_AUTH_TOKEN` | **Settings**, **Auth Tokens**, or set by Sentry's Vercel integration | Not needed | In the app host's build env, to upload source maps | Yes |
| `SENTRY_ORG`, `SENTRY_PROJECT` | The organization's and the project's slugs, or set by the integration | Not needed | In the app host's build env | No |

Sentry's Vercel integration sets the three source-map names, and the DSN as `NEXT_PUBLIC_SENTRY_DSN`, a name meant for Next.js ([Vercel integration](https://docs.sentry.io/organization/integrations/deployment/vercel/)). The package reads it as it is: the app reports to it when `MONITORING_DSN` is unset, and `npx nuxt-backend env push` forwards it to the deployment as `MONITORING_DSN` (after `vercel env pull .env.local`), so the integration alone is enough. Set `MONITORING_DSN` yourself to report to another project.

## Link it

::steps{level="3"}

### Give the deployment the DSN

```bash
npx convex env set --prod MONITORING_DSN
```

It asks for the value. `env push --prod` forwards it from `.env.local` instead, when you keep it there.

### Give the app the DSN

Add `MONITORING_DSN` to the host's production env. On Vercel, also install Sentry's integration from the Vercel Marketplace and link it to the project, for source maps and releases.

### Watch the health endpoint

In Sentry, open **Monitors**, **Add Monitor**, **Uptime**. Point it at `https://app.example.com/api/backend/health`, every minute. Sentry opens an issue after three failures in a row ([Uptime monitoring](https://docs.sentry.io/product/monitors-and-alerts/monitors/uptime-monitoring/)).

### Turn on the backend's exception reports

On Convex Professional, open the production deployment's **Settings**, **Integrations**, and add Sentry with a DSN of a **Node.js** project. Convex then reports the exceptions of queries and mutations with their real message, which callers only see as `Server Error` ([Exception reporting](https://docs.convex.dev/production/integrations/exception-reporting)).

::

The backend's maintenance cron creates its own monitor, `backend-maintenance`, on its first check-in.

## Go to production

::steps{level="3"}

### Set the DSN on both sides

The deployment and the app host, as in [Link it](#link-it).

### Scope your alerts

Create an alert rule for new issues in the `production` environment, sent where the person on call reads it, and one for issues tagged `backend.alert`: the backend's quota and spend alerts, one issue per kind ([Alerts](/docs/ship/operate/monitoring#alerts)).

### Deploy and check

```bash
npx nuxt-backend doctor --prod
```

::

## Costs and limits

Checked on 2026-10-25 against [Sentry pricing](https://sentry.io/pricing/):

| | Developer | Team | Business |
|---|---|---|---|
| Price | $0 | $26 a month, billed yearly | $80 a month, billed yearly |
| People | 1 | Unlimited | Unlimited |
| Errors | 5,000 a month | 50,000 a month | 50,000 a month |
| Logs | 5 GB | 5 GB | 5 GB |
| Session replays | 50 | 50 | 50 |
| Cron monitors | 1 | 1 | 1 |
| Uptime monitors | 1 | 1 | 1 |

- **Cron monitors:** the backend's `backend-maintenance` uses the one included. Each job you check in adds a monitor at $0.78 a month. The backend's alerts are issues, not monitors.
- **Session replays:** the preset sends a replay only once an error happens, and only for visitors who allowed it, so the 50 included go to errors.
- **Logs** cost $0.50 per GB past the 5 GB.
- **Spike protection** stops a flood of one error from eating the month's quota. It is on per project.
- **Past the quota,** Sentry answers `429` and the SDK drops reports. `reportError` never throws for it.

## Data and compliance

- **What it holds:** error messages, stack traces, log lines, feedback, and the URL and browser of each report. The package's preset scrubs personal data before anything leaves (addresses, credentials, secret parameters, cookies, bodies; of a user only the id), and Sentry scrubs common secrets again on its servers by default.
- **Region:** the US or the EU, chosen when you created the organization. Cron check-ins, DSN keys and organization settings stay in the US either way.
- **Session replay** runs only in a browser whose visitor allowed the `replay` purpose, and only when the app lists it: after an error, the minute before it and the rest of that visit, every text, input and image masked. Withdrawing stops it, and what it still held is not sent.
- **Role:** Sentry processes data on your behalf. Accept its [DPA](https://sentry.io/legal/dpa/) in the organization's legal settings; it lists its [subprocessors](https://sentry.io/legal/subprocessors/) and holds SOC 2 Type II ([Security](https://sentry.io/security/)).
- **Erasure:** in `0.2.0`, once an account is deleted, errors stop naming it. The package does not yet delete what Sentry already holds for that person: whether Sentry offers an API for one user's data is still being checked, and until then its retention period removes old events ([Export and delete an account](/docs/build/auth/accounts/data#what-an-erasure-removes)).

Name Sentry in your privacy policy as a processor ([Privacy, GDPR and cookies](/docs/ship/compliance/privacy)). This is not legal advice.
