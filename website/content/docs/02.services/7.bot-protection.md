Bot protection checks that a person, not a script, asks for a sign-in code or creates an account. On Vercel it runs as BotID and needs no account. On any other host it runs as a Cloudflare Turnstile challenge.

| You need | Time | Cost to start |
|---|---|---|
| On Vercel: one secret. Elsewhere: a free Cloudflare account | 5 minutes | Free |

## What it powers

| Capability | What it gives | Build pages |
|---|---|---|
| `protection` | A check before the auth route that sends a sign-in code, which sign-up starts with too | [Stop bots](/docs/build/auth/sign-in/bots) |
| `protection` | `useHumanCheck` and `verifyHuman`, for a public form or vote of your own | [Protect your own calls](/docs/build/auth/sign-in/bots#protect-your-own-calls) |

The rate limits bound how fast one address or client can go; the bot check decides whether a person asks at all ([Tune rate limits](/docs/ship/security/rate-limits)). A request that fails it is refused as `forbidden` with reason `bot_check`.

## Create the account

**On Vercel, BotID:**

::steps{level="3"}

### Nothing to sign up for

BotID's basic check is part of every Vercel plan. Install its package, an optional peer of nuxt-backend:

```bash
npm install botid
```

A build on Vercel with `botid` installed turns it on in the browser and on the Nuxt server, with no module of yours to add: the package wires BotID's client and the server's `checkBotId()` itself, and Vercel's own `botid/nuxt` module is not needed. A Vercel build without it says so in its log, and runs no bot check on the app's server. Deep Analysis, on Pro, is a setting under the project's **Firewall**, **Rules**.

### Generate the proof secret

Once BotID passes, the Nuxt server signs a short-lived proof the deployment checks, so a bot that calls the deployment's own URL is refused too. Both sides share one secret:

```bash
openssl rand -base64 32
```

::

**Elsewhere, a Turnstile challenge:**

::steps{level="3"}

### Sign up at Cloudflare

At [dash.cloudflare.com/sign-up](https://dash.cloudflare.com/sign-up). Your site does not need to run through Cloudflare.

### Create a widget

**Turnstile**, **Add widget**. Name it, add your app's hostnames, and choose **Managed** or **Invisible**: the package shows it only when Cloudflare asks for a click. Copy the site key and the secret key ([Get started](https://developers.cloudflare.com/turnstile/get-started/)).

::

**Who should own it.** Whoever owns the host owns the check: the Vercel team, or the Cloudflare account that holds the widget.

## Sandbox and test mode

The dev server's check answers human without asking, as BotID itself does in development, so sign-in never stalls on your machine. The deployment checks nothing until a secret is set.

| Where the app runs | What checks for bots |
|---|---|
| `npx nuxt-backend dev` | Nothing: the check answers human. With `PROTECTION_PROOF_SECRET` in `.env.local`, the dev server signs proofs and the dev deployment checks them |
| A build on Vercel | BotID, then the proof |
| A build elsewhere, with a site key | The Turnstile challenge |

To see a challenge on your machine, use Cloudflare's test keys:

| Site key | Secret key | Result |
|---|---|---|
| `1x00000000000000000000AA` | `1x0000000000000000000000000000000AA` | Always passes |
| `2x00000000000000000000AB` | `2x0000000000000000000000000000000AA` | Always fails, so you see `bot_check` |

`doctor --prod` fails a production that runs on the test keys ([Testing](https://developers.cloudflare.com/turnstile/troubleshooting/testing/)).

## Keys and environment

| Variable | Where to find it | Dev | Prod | Secret |
|---|---|---|---|---|
| `PROTECTION_PROOF_SECRET` | Generate it. On Vercel only: the same value on the deployment and in the Vercel project | Optional, in `.env.local` | Production's own, never `.env.local`'s | Yes |
| `NUXT_PUBLIC_BACKEND_CHALLENGE_SITE_KEY` | The Turnstile widget's site key, in the app host's env | A test key, optional | The widget's key | No: the page needs it |
| `PROTECTION_CHALLENGE_SECRET_KEY` | The Turnstile widget's secret key, on the deployment | A test key, optional | The widget's key | Yes |

## Link it

### On Vercel

```bash
SECRET=$(openssl rand -base64 32)
printf %s "$SECRET" | npx convex env set --prod PROTECTION_PROOF_SECRET
printf %s "$SECRET" | vercel env add PROTECTION_PROOF_SECRET production
```

Then deploy. A proof is valid for one minute, for one route, one address and one deployment ([Why the deployment checks a proof](/docs/build/auth/sign-in/bots#why-the-deployment-checks-a-proof)).

### Elsewhere

Set the site key in the app host's env as `NUXT_PUBLIC_BACKEND_CHALLENGE_SITE_KEY`, then the secret key on the deployment:

```bash
npx convex env set --prod PROTECTION_CHALLENGE_SECRET_KEY
```

The module lets `https://challenges.cloudflare.com` into the security headers' `script-src` and `frame-src`. Off Vercel, set `PROTECTION_PROOF_SECRET` only beside the challenge keys: nothing signs a proof there.

## Check it

```bash
npx nuxt-backend doctor --only protection
```

| Finding | What it checks |
|---|---|
| [`bot-protection`](/docs/reference/cli/diagnostics#bot-protection) | What the deployment checks. Under `--prod`, it warns when nothing does |
| [`protection-proof`](/docs/reference/cli/diagnostics#protection-proof) | A proof signed with your secret passes on the deployment. It sends no mail and spends no limit |
| [`protection-challenge-keys`](/docs/reference/cli/diagnostics#protection-challenge-keys) | The app shows a widget whenever the deployment asks for an answer, and production runs on real keys |
| [`deployment-protection-proof-secret`](/docs/reference/cli/diagnostics#deployment-protection-proof-secret), [`deployment-protection-challenge-secret-key`](/docs/reference/cli/diagnostics#deployment-protection-challenge-secret-key) | The deployment holds the secret it needs |

## Go to production

Give production its own secret or keys, as in [Link it](#link-it), deploy, then run:

```bash
vercel env pull
npx nuxt-backend doctor --prod
```

`doctor` reads the app's env only from your shell, so pull it first. To rotate the proof secret without downtime, set `new,old` on the deployment, move the app to the new value and redeploy, then set the new value alone ([Rotate secrets](/docs/ship/security/secrets)).

## Costs and limits

Checked on 2026-10-25:

- **BotID:** the basic check is free on every Vercel plan. Deep Analysis costs $1 per 1,000 checks, on Pro ([BotID](https://vercel.com/docs/botid)). It runs only on a Vercel deployment.
- **Turnstile:** free, with unlimited challenges, up to 20 widgets per account and 10 hostnames per widget ([Plans](https://developers.cloudflare.com/turnstile/plans/)). A token is valid for 300 seconds, once.
- **Proofs:** each is accepted for a minute, so a slow network never fails a person, and a stolen one is worth little.

## Data and compliance

- **BotID:** Vercel checks signals from the browser and the request, under its [DPA](https://vercel.com/legal/dpa).
- **Turnstile:** Cloudflare processes the visitor's IP address, TLS fingerprint and user agent to tell people from bots, and reads no form input. It acts as your processor under its [DPA](https://www.cloudflare.com/cloudflare-customer-dpa/) ([Turnstile privacy](https://www.cloudflare.com/turnstile-privacy-policy/)).
- **Cookies:** Turnstile sets a cookie only when you turn on its pre-clearance option.

Name the service you use in your privacy policy ([Privacy, GDPR and cookies](/docs/ship/compliance/privacy)). This is not legal advice.
