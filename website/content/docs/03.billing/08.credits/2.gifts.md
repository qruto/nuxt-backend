A signed-in user can buy credits or a plan **for someone else**, identified only by email. The purchaser pays; the recipient owns the entitlements. Gift records live in the `backend` component's `billingGifts` table — nothing to add to your schema.

## Sending a gift

```vue
<script setup lang="ts">
const { products } = useBilling()
const { gift } = useCredits()

async function sendGift() {
  await gift(products.value!.credits500!.id, {
    recipientEmail: 'friend@example.com',
    message: 'Happy birthday!',
  })
}
</script>
```

`useBilling().gift(productIds, { recipientEmail, message?, metadata?, successUrl?, redirect? })` and `useCredits().gift(...)` both call the `giftCheckout` action: a checkout for the provider customer that carries the **recipient's** email — the one that already exists, or a new one for a recipient the provider has never seen. The checkout itself carries only that email, never the customer: a checkout bound to a customer pre-fills its name, billing address and tax id, and would show them to whoever pays. The provider settles the paid order on the customer that carries the email. With a `rateLimiter` configured, `giftCheckout` counts against the `billingSync` limit (10/min), keyed by the purchaser.

On the `order.paid` webhook the package checks the order landed on the recipient's customer, marks the gift paid, and:

- **Recipient already has an account** — the gift attaches automatically (in workspace mode, to their personal workspace), and they're notified by email.
- **No account yet** — the recipient gets an email linking to `SITE_URL`; on their first sign-in `useGifts()` claims every paid gift automatically.

The purchaser can still change the email on the checkout before paying. The order then belongs to whoever that email is, so the gift is not delivered: it stays `pending`, nobody is emailed, and the deployment logs `billing.gift_attach_failed`.

## Who can receive a gift

Every address is accepted by default. To limit recipients — your own domain only, say, or sandbox addresses on a public demo — pass `canGift` to `setupBilling`. `giftCheckout` asks it before it creates anything for the recipient:

```ts [backend/billing.ts]
export const billing = setupBilling(components, {
  catalog,
  email,
  canGift: (ctx, { recipientEmail, purchaserUserId }) =>
    recipientEmail.endsWith('@example.com') || { allowed: false, message: 'Gifts go to teammates only.' },
})
```

`recipientEmail` arrives lower-cased, and `ctx` is the action's, so the check can read your own tables. A refusal is `forbidden` with reason `gift_refused`, carrying the message (default: "This address can't receive gifts."), so it reaches the purchaser even where production hides other errors.

## Receiving gifts

```vue
<script setup lang="ts">
// Auto-claim is the default: the first authenticated load holding paid-but-unclaimed
// gifts claims them all. Disable it to show an explicit "receive" action instead.
const gifts = useGifts({ autoClaim: false })
</script>

<template>
  <GiftClaimBanner />  <!-- or your own UI over gifts.unclaimed / gifts.claim() -->

  <div v-for="g in gifts.unclaimed.value" :key="g.id">
    🎁 from {{ g.purchaserName ?? 'someone' }}: {{ g.message }}
    <button :disabled="gifts.isClaiming.value" @click="gifts.claim(g.id)">Receive</button>
  </div>
</template>
```

::field-group
  :::field{name="received" type="ComputedRef<ReceivedGift[] | undefined>"}
  Every gift addressed to the signed-in user's email — `id`, `recipientEmail`, `purchaserUserId` / `purchaserEmail` / `purchaserName`, `productIds`, `message`, `status` (`'pending'` → `'paid'` → `'claimed'`), `createdAt`, `paidAt`, `claimedAt`.
  :::

  :::field{name="unclaimed" type="ComputedRef<ReceivedGift[]>"}
  The `paid` ones — claimable now.
  :::

  :::field{name="isLoading / isClaiming" type="ComputedRef<boolean>"}
  `isLoading` is `true` until the gift list has loaded (always `false` when signed out); `isClaiming` while an auto- or manual claim is in flight.
  :::

  :::field{name="claim(giftId?)" type="Promise<number>"}
  Claim one gift or every claimable gift; resolves with the number attached. Entitlements and credits refresh reactively right after. The server checks the gift is addressed to the signed-in identity's email.
  :::
::

## The notification email

It goes out through `email`, the `setupEmail` instance `setupBilling` takes, once per gift. The package sends first and stamps the gift after, with the key `nuxt-backend:gift:<id>`:

- A send that throws — a template override, test mode refusing the address, a transient failure — leaves no stamp, so the provider's redelivery of `order.paid` sends it again.
- A run that sent but failed before stamping is absorbed by the key while the first email's record exists.
- Once stamped, a replay emails nobody, however late it comes.

The default is a minimal, dependency-free template linking to `SITE_URL`. Restyle it as the `gift` [template](/docs/email/templates), with the rest of the package's email:

```ts [backend/email.ts]
export const email = setupEmail(components, {
  templates: {
    gift: ({ recipientEmail, purchaserName, message, claimUrl }) => ({
      to: recipientEmail,
      subject: `${purchaserName ?? 'Someone'} sent you a gift 🎁`,
      html: `…<a href="${claimUrl}">Receive it</a>`,
    }),
  },
})
```

::warning
If the recipient's account already bills through a provider customer under a **different** email, the gift can't attach — entitlements can't move between provider customers. The sender should re-gift to the email the recipient's billing runs under.

A gift is paid to the customer of the recipient's email. When that customer already pays for another of the recipient's workspaces, the gift's plan or credits are there, and a claim from a different workspace is refused: open that workspace to receive it. See [One email, one billing profile](/docs/billing/subscriptions#one-email-one-billing-profile).
::
