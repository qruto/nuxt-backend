Every email the package sends on your behalf comes from a template that returns `{ to, subject, html?, text? }`, an `EmailMessage`. The templates live in one place, the `setupEmail` instance in `backend/email.ts`: `setupAuth` and `setupBilling` take that instance as their `email` option and send through it, so one override restyles an email wherever it goes out. The defaults are minimal, dependency-free HTML and text.

## The templates

| Name | Sent when | Data |
|---|---|---|
| `otp` | A one-time code: to sign in, to verify an address (`email-verification`, which with `reason: 'email-change'` confirms the current address at the start of an email change, in its own words), and for the new address of an email change (`change-email`) | `{ email, otp, type: 'sign-in' \| 'email-verification' \| 'forget-password' \| 'change-email', reason?: 'email-change' }` |
| `emailChanged` | An email change went through: to the old address, so whoever holds it hears of a change they didn't make | `{ email, newEmail }` |
| `welcome` | Once, right after a user is created | `{ email, name }` |
| `deleteAccount` | Confirmation link for account deletion | `{ email, url }` |
| `invite` | Workspace invitation with an accept link | `{ email, url, inviterName, inviterEmail, organizationName, role }` |
| `gift` | A gift is paid, to its recipient (see [Gifts](/docs/billing/credits/gifts#the-notification-email)) | `{ recipientEmail, purchaserName?, purchaserEmail?, message?, claimUrl }` |

Each template also gets a render context:

- `t(key, params?)` reads the package's labels, the words the defaults are made of: `t('email.invite.subject', { workspace: 'Acme' })` is `Join Acme`.
- `locale` is the recipient's locale, `'en'` until accounts carry one.
- `brand` is `{ name, url }`: `url` is `SITE_URL`, and `name` is `setupEmail`'s `brand.name`, or the site's host without one. Every packaged email signs off with the name, linked to `url`.

## Overriding

Pass any subset as `templates` on `setupEmail`. The transport stays the component's; only the message changes. Each override gets the data, the render context, and `byDefault`, the packaged template bound to the same context:

```ts [backend/email.ts]
import { setupEmail } from 'nuxt-backend/email'
import { components } from './_generated/api'

export const email = setupEmail(components, {
  brand: { name: 'Acme' },
  templates: {
    otp: ({ email, otp, type }) => ({
      to: email,
      subject: type === 'sign-in' ? `${otp} is your Acme sign-in code` : 'Your Acme verification code',
      text: `Your code: ${otp}. It expires in 5 minutes.`,
      html: renderOtpEmail({ otp }),   // your own renderer
    }),
    invite: (data, { byDefault }) => ({
      ...byDefault(data),    // keep the default body…
      subject: `${data.inviterName} wants you on ${data.organizationName}`,   // …change the subject
    }),
  },
})
```

Render however you like: a string builder, `@vue-email`, `@react-email`, anything that returns HTML and text. An override may be `async`, so a renderer that returns a promise works as is; `byDefault` stays synchronous. The [advanced example](/docs/start/templates#example-advanced) overrides `otp`, `invite` and `gift` this way.

Some fields hold text a user typed: a name, a workspace name, a gift message. Escape them when you write your own HTML, or that user can put markup into an email your domain sends. `escapeHtml` from `nuxt-backend/email` is the one the packaged templates use:

```ts
import { escapeHtml } from 'nuxt-backend/email'

gift: (data, { byDefault }) => ({
  ...byDefault(data),
  html: `<p>${escapeHtml(data.message ?? '')}</p>`,
}),
```

::note
`backend/auth.ts` imports `email` from `backend/email.ts`, so `email.ts` must not import `auth.ts` back: the import cycle leaves `email` undefined while `setupAuth` runs. To read the signed-in user in `email.ts`, use `ctx.auth.getUserIdentity()`.
::

### The welcome email

`welcome` goes out once, right after signup, on every app. Onboarding that follows it belongs in an [email sequence](/docs/email/engagement/sequences): the scaffold's `onSignup` sequence starts three days later. Restyle the welcome itself through `templates.welcome`.

### Taking over the invitation

The workspace plugin's own `organization.sendInvitationEmail` on `setupAuth` replaces the invitation email entirely, delivery included. It bypasses the component's delivery tracking.

## Sent once

The welcome email, the email-change notice and a gift notification carry an idempotency key under the package's own prefix: `nuxt-backend:welcome:<user>`, `nuxt-backend:email-changed:<user>:<address>` and `nuxt-backend:gift:<id>`. While the first email is on record (finalized records are pruned after a week), a second send with the same key returns its id and delivers nothing, so a retried request or a redelivered webhook doesn't email twice. An invitation carries none: every send of it, a resend included, goes out. Your own sends take the same option, `email.send(ctx, { …, idempotencyKey })`; keep the `nuxt-backend:` prefix for the package's.

## Previewing

`email.render(name, data)` resolves a template in effect, override included, without sending it. The playground's email-templates page renders each one with sample data:

```ts [backend/emailTemplates.ts]
import { query } from './_generated/server'
import { email } from './email'

export const otpPreview = query({
  args: {},
  // { to, subject, html, text }
  handler: () => email.render('otp', { email: 'you@example.com', otp: '482913', type: 'sign-in' }),
})
```

`email.sendTemplate(ctx, name, data, { idempotencyKey? })` renders and sends in one call, the way auth and billing do.
