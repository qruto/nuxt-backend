A preview build can have a backend of its own: a Convex **preview deployment** per branch, made by the same build command as production. The package gives each one the env its first push needs, with `BACKEND_ENVIRONMENT=preview`, so every provider stays in its test mode there. A preview never mails a real person or charges a real card.

Convex creates the preview deployment when the host's preview environment holds a *preview* deploy key. The package does not create one per pull request for you: it fills in the one Convex creates.

## The build command

Put a preview deploy key in the host's **preview** environment as `CONVEX_DEPLOY_KEY`. It comes from the Convex dashboard's project settings ([Convex](/docs/services/convex#keys-and-environment)). On Vercel, that is the project's **Preview** environment ([Vercel](/docs/services/vercel#sandbox-and-test-mode)). The production build command then creates, or reuses, a preview deployment named after the branch:

```bash
npx convex deploy --cmd 'npm run build' --cmd-url-env-var-name NUXT_PUBLIC_BACKEND_URL --preview-run 'billing:syncProducts'
```

`--preview-run` runs a function on the preview after the push, and only on a preview. Loading the products is the usual one, so the pricing page shows the sandbox catalog.

## Give each preview its env

A new preview starts with nothing but the project's preview env defaults, and its first push fails without `AUTH_SECRET` and `SITE_URL`. Two ways to have them there, which work together:

- **In the build, exactly.** `convex deploy` runs `--cmd` once the preview exists and before it pushes, so `env push --preview` can fill the env there, with the branch's own origin as `SITE_URL`. On Vercel, `VERCEL_BRANCH_URL` is the branch's stable URL, and the same build command also runs for production:

  ```bash
  npx convex deploy --cmd-url-env-var-name NUXT_PUBLIC_BACKEND_URL \
    --cmd 'if [ "$VERCEL_ENV" = preview ]; then npx nuxt-backend env push --preview --site-url "https://$VERCEL_BRANCH_URL"; fi && npm run build'
  ```

  It generates `AUTH_SECRET` and sets `BACKEND_ENVIRONMENT=preview`. Without a name, it acts on the branch the build names, read as `convex deploy` reads it. It refuses a deploy key that is not a preview key.

- **Project env defaults, once.** Convex copies them into every preview it creates, so a preview built without that step can still push:

  ```bash
  npx nuxt-backend env push --defaults preview --site-url https://preview.example.com
  ```

  It writes a generated `AUTH_SECRET`, the `SITE_URL` you name and `BACKEND_ENVIRONMENT=preview`. A default already set is kept unless `--force` names it. Every preview created from the defaults shares their one `AUTH_SECRET`.

`SITE_URL` is the one value neither will make up. Auth trusts only that origin, and a preview's origin is its own, one per branch on most hosts. So it has to come from the build, which knows it, or from you. A default cannot be exact for every preview: name a stable preview domain if your host gives you one, and let the build step replace it per branch. `doctor` reports the defaults as `env-defaults`.

## What a preview runs on

| Capability | On a preview |
|---|---|
| Auth | Its own `AUTH_SECRET`, so no session from another deployment signs in there. Sign in with a test address, such as `delivered+you@resend.dev`, and read the code in the [dev inbox](/docs/develop/dev-inbox) |
| Email | Test mode: only Resend's test addresses receive mail, so a preview never writes to a real person |
| Billing | Polar's sandbox, with the sandbox catalog, once the preview holds a sandbox `BILLING_ACCESS_TOKEN`. Add it to the project's default environment variables for previews in the Convex dashboard, and pay with Polar's test card. Point a sandbox webhook at the preview's `/billing/events` only if the preview must see payments land |
| AI | The same models, through the Convex AI Gateway or `AI_GATEWAY_API_KEY` |
| Monitoring | Reports name the `preview` environment, and its jobs never check in, so a preview deleted with its branch never reads as a missed run |

Convex deletes a preview deployment, with its data, 5 days after it was created (14 days on the Professional plan and above). Nothing needs cleaning up on the package's side. A sandbox webhook you pointed at one is yours to remove.
