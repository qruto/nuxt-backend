Vercel is the host the package is built and tested on first: the deploy itself is the one every host shares ([Deploy to production](/docs/ship/deploy)), and on Vercel a few capabilities take what the platform gives. [Vercel](/docs/services/vercel) has the account and the project's setup. Off Vercel each of them keeps working another way ([Vercel first, not Vercel only](/docs/start/concepts/principles#vercel-first-not-vercel-only)).

## What an app gets on Vercel

| Capability | On Vercel | Read |
|---|---|---|
| `protection` | BotID, an invisible bot check before a code is sent or an account created: the Nuxt server runs it and signs a proof the deployment checks, once `botid` (an optional peer) is installed | [Bot protection](/docs/services/bot-protection) |
| `monitoring` | Sentry's integration sets the names a build uploads source maps with. The package reads the DSN the integration sets, `NEXT_PUBLIC_SENTRY_DSN`, as `MONITORING_DSN` | [Sentry](/docs/services/sentry) |
| `ai` | Models by `provider/model` id at their real cost, through the Convex AI Gateway on a paid Convex plan, else the Vercel AI Gateway. The backend's calls run in Convex actions, never on Vercel, so the Vercel AI Gateway needs `AI_GATEWAY_API_KEY` on the deployment | [Choose a model](/docs/build/ai/models#where-a-model-id-goes) |
| `hosting` | The build command and the env split, set in the project's settings. In `0.2.0`, one-command production writes the app's env into the project, and a deploy template starts a new app with Convex through the Marketplace | [One-command production](/docs/ship/deploy/one-command), [Start from the deploy template](/docs/ship/deploy/template) |

### The backend's URL at build

The build bakes in the deployment's URLs, derived from `NUXT_PUBLIC_BACKEND_URL` (or the `CONVEX_DEPLOYMENT` the Convex CLI names) where the build runs. The sign-in proxy at `/api/auth` forwards to the HTTP routes' origin it baked in. When the build knew no backend URL (`NUXT_PUBLIC_BACKEND_URL` set for the runtime only, say), that origin is empty, and every sign-in request answers `500`. Set `NUXT_PUBLIC_BACKEND_URL` for builds too, or set `NUXT_PUBLIC_CONVEX_SITE_URL` to the deployment's `https://<name>.convex.site` URL on the project as well. `npx nuxt-backend doctor --prod` asks the proxy through the live site, and reports it as [`site-auth-proxy`](/docs/reference/cli/diagnostics#site-auth-proxy).

## This site's setup

This site, the docs, the homepage and the playground, is one Nuxt app on Vercel, built and deployed as [Deploy to production](/docs/ship/deploy) describes. Beside hosting it uses a few Vercel features, each through Vercel's own package or integration, and each turns off by itself anywhere else, so a local or CI build behaves as before. Take the parts your app needs:

| Feature | What it gives | How it is turned on |
|---|---|---|
| Web Analytics | Page views and referrers, with no cookies | Its Nuxt module in a Vercel build, and the dashboard toggle |
| Speed Insights | Core Web Vitals from real visits | Its Nuxt module in a Vercel build, and the dashboard toggle |
| Firewall | Rate limits per IP at the edge, held across every server instance | `@vercel/firewall` in a server middleware, and one rule per limit |
| Sentry's integration | Error reports from the browser and the Nuxt server, with source maps | `@sentry/nuxt`, the integration, and the DSN in `MONITORING_DSN` |
| AI Gateway | A model for the docs assistant, with no key on Vercel | The deployment's OIDC token |

## Count visits without cookies

Install Vercel's two packages, and add their Nuxt modules for a build on Vercel only:

```bash
npm install @vercel/analytics @vercel/speed-insights
```

```ts [nuxt.config.ts]
// A deployment's build, not a machine that loaded what `vercel env pull`
// wrote: that file sets VERCEL too, beside VERCEL_ENV=development.
const onVercel = Boolean(process.env.VERCEL) && process.env.VERCEL_ENV !== 'development'

export default defineNuxtConfig({
  modules: [
    'nuxt-backend',
    ...(onVercel ? ['@vercel/analytics/nuxt', '@vercel/speed-insights/nuxt'] : []),
  ],
})
```

Then turn on **Analytics** and **Speed Insights** in the project's dashboard before the next deploy. Each module adds a client plugin that loads its script from the site's own origin, `/_vercel/insights/script.js` and `/_vercel/speed-insights/script.js`, which only Vercel serves, and only once the feature is on. That is why the modules are left out elsewhere: another host answers those paths with `404`, and in dev each module loads a debug script from Vercel's CDN.

Neither sets a cookie or stores anything on the visitor's device. Web Analytics tells visitors apart by a hash of the request that it discards after a day, and Speed Insights sends only the page's timings. The Content Security Policy the package sets through `nuxt-security` lets both scripts load: each plugin inserts its script from code the page already trusts (`'strict-dynamic'`).

## Rate-limit at the edge

A per-IP limit in the Nuxt server, such as `nuxt-security`'s, counts in each server instance's memory, and Vercel runs as many instances as traffic needs. The Vercel Firewall counts at the edge, once for the whole deployment. This site checks it from a server middleware with `@vercel/firewall`, for three endpoints, each against a rule of its own:

| Rule id | What it counts | Budget per IP |
|---|---|---|
| `docs-assistant` | The docs assistant's chat endpoint, `/__docus__/assistant` | 10 requests a minute |
| `docs-mcp` | The [docs MCP](/docs/develop/agents/docs-mcp): `/mcp` on the docs host, and its route on the site, `/api/docs-mcp` | 120 requests a minute |

The docs MCP's budget is the one its route keeps in memory, now held across instances, whichever of its two addresses a caller uses. A request the site makes to itself is not counted again: the docs host hands `/mcp` to the route in the same server, and the assistant reads the docs through it, each already counted as the request that made it. The playground's MCP endpoint signs every agent in, so its edge budget is a ceiling for floods only. It leaves the playground with the end-user MCP, which waits for the next release ([Roadmap](/docs/start/roadmap)).

```ts [server/middleware/0.firewall.ts]
import { checkRateLimit } from '@vercel/firewall'

// Each limited path, and the id of the Firewall rule that counts it.
const RULES: Record<string, string> = {
  '/__docus__/assistant': 'docs-assistant',
  '/api/docs-mcp': 'docs-mcp',
}

// What the check hands the Firewall: the host it asks, the IP it counts.
// It forwards every header it gets, and a rule needs none of the caller's
// cookies or tokens.
const FORWARDED = ['host', 'x-real-ip', 'x-forwarded-for', 'user-agent']

// The Firewall answers only on a deployment (see the config above).
const onVercel = Boolean(process.env.VERCEL) && process.env.VERCEL_ENV !== 'development'

export default defineEventHandler(async (event) => {
  if (!onVercel) return
  // The router ignores a trailing slash, so the lookup does too.
  const id = RULES[event.path.split('?')[0]!.replace(/\/+$/, '') || '/']
  if (!id) return
  const headers = new Headers()
  for (const name of FORWARDED) {
    const value = event.headers.get(name)
    if (value) headers.set(name, value)
  }
  let verdict
  try {
    verdict = await checkRateLimit(id, { headers })
  }
  catch {
    // Fail open: an outage of the limiter must not take the endpoint down.
    return
  }
  if (!verdict.rateLimited) return
  // A deny rule blocked the caller outright: not a budget to wait out.
  if (verdict.error === 'blocked') {
    setResponseStatus(event, 403)
    return { error: 'forbidden', message: 'This request was blocked.' }
  }
  setResponseStatus(event, 429)
  setResponseHeader(event, 'retry-after', '60')
  return { error: 'rate_limited', message: 'Too many requests. Try again in 60 seconds.' }
})
```

The `0.` keeps it first: Nitro runs a project's middleware in file-name order, and the middleware modules add after them, so the request is counted before the package's own handlers see it. `checkRateLimit` throws when the Firewall answers with anything it does not expect, so the `try` matters: without it, a hiccup of the limiter answers `500` on every limited path. The site's version also tells the docs host's `/mcp` from its own, skips the requests it makes to itself, and gives up after a second.

`checkRateLimit` asks the Firewall only when `NODE_ENV` is `production`, as it is in Vercel's functions; anywhere else it answers "not limited" and logs a warning. To see a rule work, deploy, then send the endpoint more requests in a minute than its budget: the one past it answers `429`.

Create each rule in the project's dashboard, under **Firewall**, **Configure**, then **New Rule**:

1. **If** `@vercel/firewall` (the rate limit id) equals the rule's id, `docs-assistant` for the first.
2. **Then** **Rate Limit**, fixed window, 60 seconds, the budget from the table, counted by IP, answering `429`.
3. **Save**, then **Publish**.

Until its rule exists, the Firewall answers that it does not know the id, and the request goes on. Off Vercel the middleware does nothing, and the per-IP limits in the Nuxt server hold alone: 10 a minute for the assistant, 120 for the docs MCP.

## Report errors

Install `@sentry/nuxt` and add Sentry's Vercel integration, which sets the names a build needs to upload its source maps (`SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT`). It sets the DSN as `NEXT_PUBLIC_SENTRY_DSN`, a Next.js name the package reads as it is (set `MONITORING_DSN` to report to another project). The package's monitoring capability wires the SDK once a build sees the DSN: the site's own code never names it, and nothing in the repository holds one. [Monitoring](/docs/ship/operate/monitoring) has what each side reports, and how the backend reports through `MONITORING_DSN`, which `npx nuxt-backend env push --prod` sets on the deployment.

The SDK loads on every page. This site reports errors only, as Speed Insights already measures its pages, and leaves the SDK's tracing code out at build, some 22 kB of each page's initial JavaScript:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  sentry: { bundleSizeOptimizations: { excludeTracing: true, excludeDebugStatements: true } },
})
```

## Reach a model with no key

The site's docs assistant, Docus's own, reaches its model through the AI Gateway. On Vercel the deployment's OIDC token authenticates it, so the project holds no key; a local build turns the assistant on only with `AI_GATEWAY_API_KEY` in `.env.local`, and without either credential nothing of it renders. A token `vercel env pull` wrote into `.env.local` does not count: it expires within hours. It reads these docs through the [docs MCP](/docs/develop/agents/docs-mcp)'s route, in the same server, as the visitor.

Its endpoint is public and every question is a billed model call, so the site serves it from a route of its own, Docus's handler built from Docus's own helpers, with checks in front. It answers a JSON `POST` from the site's own pages only, so another site cannot spend the budget from its visitors' browsers. And it reads the conversation the chat sends as text alone: the question, at most 4,000 characters, and the newest turns before it, so a client cannot hand the model a `system` message, a page it claims a tool read, or a megabyte of history. A [budget](https://vercel.com/docs/ai-gateway/observability-and-spend/budgets) on the project caps what the gateway spends in a month.

The token belongs to code running in Vercel's functions, the Nuxt server. Your app's own model calls run in the backend, which reads `AI_GATEWAY_API_KEY` from the deployment's env instead: [Models](/docs/build/ai/models).

## Check the dashboard

Once per project, before the deploy that brings these in:

- **Analytics** and **Speed Insights** are on.
- **Settings**, **Security**: "Secure backend access with OIDC federation" is on (the default for a new project), and the team can use the AI Gateway.
- **Firewall**: the two rules above are published.
- **AI Gateway**, **Budgets**: a project budget, so a flood of questions stops at a sum you chose (`vercel ai-gateway budgets set project <name> --limit <usd> --refresh-period monthly`).
- **Integrations**: Sentry's integration is installed and linked to the project, and `MONITORING_DSN` holds the project's DSN.
- **Settings**, **Environment Variables**: "Enable access to System Environment Variables" is on, so the functions see `VERCEL` and `VERCEL_ENV` and check the Firewall.
