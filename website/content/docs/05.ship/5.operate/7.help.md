Most answers are a command away: `npx nuxt-backend doctor` names what is wrong with its fix, [Troubleshooting](/docs/ship/operate/troubleshooting) indexes fixes by symptom and by log code, and the docs assistant on this site answers from these pages. When none of them does, ask.

## Where to ask

| You have | Where | Why there |
|---|---|---|
| A question, an idea or a "how do I" | [GitHub Discussions](https://github.com/qruto/nuxt-backend/discussions) | Answers stay findable for the next person |
| A bug: something the docs promise that the package does not do | [A GitHub issue](https://github.com/qruto/nuxt-backend/issues/new/choose), from the bug template | It asks for what a fix needs |
| A vulnerability | [A private security advisory](https://github.com/qruto/nuxt-backend/security/advisories/new), never a public issue | Only you and the maintainers see it until a fix ships |
| A problem in Convex, Better Auth or a provider | That project's own channel | The package reports upstream what it finds, but cannot fix it there |

## What to include

Everything below is free of secrets: none of it prints a value of your env.

```bash
npx nuxi info                       # Nuxt, Nitro and your modules
npx nuxt-backend doctor --json      # the package's version and every finding, by capability
```

- **The kind of deployment.** Local, a cloud dev deployment, a preview or production, and self-hosted or not. Add `--prod` to `doctor` when the problem is in production.
- **The host.** Vercel, a Node server or another; the Nitro preset if you set one.
- **What you did, what you expected, what happened.** A minimal repository or the steps from a fresh `create nuxt` with the starter is worth more than any description.
- **The log line.** A `[nuxt-backend] <code>` line from the Convex dashboard's logs, or a Sentry event's `backend.code` and `backend.function` tags. They name no person, so they are safe to paste.

Leave out what is not safe to paste: `.env.local`, a deploy key, a provider token, a session cookie, or a person's address.

## A bug report and a security report

A bug report is public and asks for a fix. A security report is private and asks for a fix before anyone else learns of the problem. If what you found lets one person read or change what belongs to another, spend credits they did not buy, or get past a guard on the [security model](/docs/ship/security), it is a security report: use the advisory, even when you are not sure. SECURITY.md in the repository says what happens next and how fast.
