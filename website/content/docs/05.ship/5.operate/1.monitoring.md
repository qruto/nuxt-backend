The monitoring capability tells you what goes wrong in production, wherever it goes wrong: a crash in the browser, a failed request on the Nuxt server, an action that threw on the backend, a cron job that stopped running, an email quota or an AI bill that is about to run away. It is built on [Sentry](https://sentry.io), with a preset that scrubs personal data before anything leaves. With a DSN set, it reports to Sentry. In development without one, the dev server keeps a local error log that DevTools lists. Its state is detected, never configured: `npx nuxt-backend status` shows it as `live`, `test` or `missing`.

## Turn it on

[Sentry](/docs/services/sentry) walks the account, the project and its data region. Then install the SDK, and give the app and the backend the project's DSN:

```bash
npm install @sentry/nuxt
```

`@sentry/nuxt` is an optional peer dependency. The module wires it only once it is installed and a DSN is set when the app builds, so an app without either never bundles it and never imports it. Then:

| Where | Name | What it reports |
|---|---|---|
| The Nuxt app | `MONITORING_DSN` in the host's env. On Vercel, [Sentry's integration](https://vercel.com/integrations/sentry) sets the DSN as `NEXT_PUBLIC_SENTRY_DSN`, which the app reads when `MONITORING_DSN` is unset | The browser and the Nuxt server |
| The deployment | `MONITORING_DSN`, pushed with `npx nuxt-backend env push --prod` (from `MONITORING_DSN` in `.env.local`, else the integration's `NEXT_PUBLIC_SENTRY_DSN` there) | The backend's actions, and its cron check-ins |

The module reads the DSN into runtime config (`runtimeConfig.public.backend.monitoring`), so your app code never names the service. Both halves may use the same DSN; the reports say which side they came from.

## What gets reported

Every report about a failed backend call carries its error code and the side that sent it, and the function it ran wherever that side can tell, so one search in Sentry finds a failure from every angle:

| Tag | What it says |
|---|---|
| `backend.function` | The function the call ran, `billing:checkout`, or the webhook it came in on, `billing webhook` |
| `backend.code` | Its [error code](/docs/reference/backend/errors), or `none` for a crash or your own error |
| `backend.reason` | For `unavailable`, which service failed and why: `billing/provider_refused` |
| `backend.source` | Where it was reported from: `browser`, `server` or `backend` |

What each side reports:

- **The browser.** Unhandled errors and Vue errors, through the SDK. A composable's failed action (the [`backend:error` hook](/docs/reference/backend/hooks)) is reported too, even when your page handles it.
- **The Nuxt server.** Errors in server routes and rendering, through the SDK, and every failed backend call the server makes through [`backendAuth(event)`](/docs/reference/nuxt/server-utilities#backendauthevent) (`fetchAuthQuery`, `fetchAuthMutation`, `fetchAuthAction`, `preloadAuthQuery`) with the function it ran. A call through the plain `fetchQuery`, `fetchMutation` or `fetchAction` reaches the SDK only when it is left to fail the route, without its function (and with its code when it carries one).
- **The backend's actions.** An action defined with [`createFunctions`](/docs/build/auth/access/functions) (`authed`, `workspace`, `admin`, `withRole`, `withFeature`) reports what its handler throws, with its code and its stack; an action cannot read its own name, so that report carries no `backend.function` (the caller's report of the same failure does). A webhook handler that fails reports why, as `billing webhook` or `email webhook`. Actions post straight to the DSN with `fetch`: no SDK runs in the backend.
- **Queries and mutations.** They cannot fetch, so they are reported where they are called, by the browser or the Nuxt server, with the function and its code. In production a crash in one reaches its caller as `Server Error`: for the backend's own report of every exception, with its real message, turn on exception reporting in the Convex dashboard (a Pro plan setting).

A refusal from the error catalog (nobody signed in, a role the caller lacks, credits that ran out) is the app working as designed, and is never reported, whichever handler caught it: an event about one is dropped even when the SDK's own handler caught a call a page left unhandled. Only a crash, your own error and an `unavailable` service are.

## What the preset does

The package passes the SDK one preset, on the browser and the Nuxt server alike, and the backend's own reports follow the same rules:

- **Personal data stays out.** Before an event, a span, a breadcrumb, a log line or a feedback report leaves, email addresses become `[email]`, bearer and basic credentials `[Filtered]`, and so does the value of every parameter or field whose name says it is a secret (`token`, `invite_token`, `accessToken`, `code`, `api_key`, `signature`, …). That holds inside a URL carried percent-encoded in another, such as a `?redirect=`, and inside the objects a console call logs. A request's cookies and its body are dropped, and of a user only the id is kept. The SDK collects no user, cookie, request or response body, model input or output, or local variable of its own. The package sets no user on a report.
- **Log lines.** The browser and the Nuxt server send `console.warn` and `console.error` as log lines, scrubbed the same way, and Sentry shows them beside the trace and the error they came with. The backend's logs stay in Convex: a log stream (a Pro plan setting) carries them to a log service.
- **Session replay, only after consent.** List `replay` in `appConfig.backend.consent.purposes`, and [`<ConsentPrompt>`](/docs/build/auth/accounts/consents#ask-before-optional-storage) asks for it. Replay starts only in a browser that allowed it, and sends nothing until an error. Then it sends the minute before the error and records the rest of that visit, until 15 idle minutes or an hour end it. Every text, input and image is masked. When the person withdraws, it stops at once and sends nothing it still held. An app that does not list the purpose never records.
- **The feedback widget.** Set `appConfig.backend.monitoring.feedback` to `true`, and a **Report a problem** button opens a form whose report reaches Sentry beside the errors. It asks for no name, address or screenshot. Its words are the `feedback` [labels](/docs/reference/configuration/labels#feedback).

```ts [app/app.config.ts]
export default defineAppConfig({
  backend: {
    consent: { purposes: ['replay'] },
    monitoring: { feedback: true },
  },
})
```

Sentry counts replays and log volume against the plan ([Sentry](/docs/services/sentry#costs-and-limits)).

## Report from your own actions

An action of your own reports what it catches with `reportError`. Give it the function's name, since an action cannot read its own, and any tags you search by:

```ts [backend/covers.ts]
import { reportError } from 'nuxt-backend/monitoring'
import { v } from 'convex/values'
import { internalAction } from './_generated/server'

export const renderCover = internalAction({
  args: { storyId: v.id('stories') },
  handler: async (ctx, { storyId }) => {
    try {
      await renderAndStore(ctx, storyId)
    }
    catch (error) {
      // Reported, and the next story goes on.
      await reportError(error, { function: 'covers:renderCover', tags: { story: storyId } })
    }
  },
})
```

`reportError` and `checkIn` (below) resolve whether the report was sent, and never reject, so a report never fails what it reports on. One the service has not taken within three seconds is given up, so a slow service never holds an action up. Without `MONITORING_DSN` on the deployment, both do nothing. `nuxt-backend/monitoring` is [experimental](/docs/ship/releases/stability): its options may change in a minor release, while the tags above stay.

## Check jobs in

A cron monitor expects a check-in on schedule and alerts when one is missed, which is how a job that failed or stopped shows. The backend component's own maintenance cron checks in to the monitor `backend-maintenance` once its hourly pass has finished every task: `ok`, or `error` when a task failed. A pass that never finishes, or a cron that stops, sends nothing, which the monitor reports as missed. The component reads the DSN through the `backend` mount's `env` in `convex.config.ts`, which the scaffold forwards; an older project gets the forward from `npx nuxt-backend doctor --fix` (the `convex-config` finding).

A job of yours checks in with `checkIn` from an action. Pass its schedule, and the first check-in creates the monitor:

```ts [backend/digest.ts]
import { checkIn } from 'nuxt-backend/monitoring'
import { internalAction } from './_generated/server'

export const send = internalAction({
  args: {},
  handler: async (ctx) => {
    await deliverDigests(ctx)
    await checkIn('send weekly digest', { schedule: { cron: '15 8 * * 1' } })
  },
})
```

The job named `send weekly digest` checks in to the monitor `send-weekly-digest`. `checkingIn` wraps an action's handler and does both ends of it: `ok` with how long the run took, or `error` with the error reported, then rethrown:

```ts [backend/digest.ts]
import { checkingIn } from 'nuxt-backend/monitoring'
import { internalAction } from './_generated/server'

export const send = internalAction({
  args: {},
  handler: checkingIn('send weekly digest', { cron: '15 8 * * 1' }, async (ctx) => {
    await deliverDigests(ctx)
  }),
})
```

A job that is a mutation cannot fetch: its last step schedules an action that checks in, inside its own transaction, so a run that throws takes the check-in with it:

```ts [backend/drafts.ts]
import { checkIn } from 'nuxt-backend/monitoring'
import { internal } from './_generated/api'
import { internalAction, internalMutation } from './_generated/server'

export const prune = internalMutation({
  args: {},
  handler: async (ctx) => {
    await pruneOldDrafts(ctx)
    // Last: scheduled only when everything above succeeded, and committed with it.
    await ctx.scheduler.runAfter(0, internal.drafts.pruneCheckIn, {})
  },
})

export const pruneCheckIn = internalAction({
  args: {},
  handler: async () => {
    await checkIn('prune drafts', { schedule: { every: { hours: 1 } } })
  },
})
```

## Alerts

Three things can run out before anything breaks. The package watches two of them itself, and Convex the third. The package also raises an alert when AI hits its own daily ceiling:

| What | Who watches | When it alerts |
|---|---|---|
| The email plan's quota | The hourly `backend alerts` cron, through the email provider's usage endpoint | The daily or the monthly quota, once 80% of it is used, and again once it is used up |
| AI spend | The same cron, from what every AI run recorded | The day's AI spend (UTC) passes twice the daily average of the seven days before, and $5 |
| The AI spend limit | The cost record that reaches `setupAi({ spendLimit })`, at once | The day's AI spend (UTC) reaches the limit, and `pause_ai` turns on until the day ends ([Cap the daily spend](/docs/build/ai/models#cap-the-daily-spend)) |
| Convex usage | Convex's own usage limits | A `warning` limit you set is passed: Convex emails the team |

Each package alert fires once for its period: the UTC day, or for the monthly quota the plan's billing month as the email provider reports it. Each is a `monitoring.alert` [log line](/docs/ship/operate/troubleshooting), and with `MONITORING_DSN` on the deployment an issue in Sentry, one per kind, tagged `backend.alert` (`email_quota`, `ai_spend` or `ai_spend_limit`). Create an alert rule on that tag, sent where the person on call reads it. Like check-ins, the hourly `backend alerts` cron runs only on a `production` or `sandbox` deployment; the spend limit's alert fires wherever the limit is reached. The quota check needs an `EMAIL_API_KEY` with full access: a key restricted to sending cannot read usage, and `monitoring.alert_unread` says so.

A deployment cannot read its own Convex usage, so set the warning in Convex, in the metric's own units:

```bash
npx convex deployment usage-limits set --prod --metric functionCalls --window month --type warning --limit 1000000
npx convex deployment usage-limits set --prod --metric aiGatewayCostDollars --window day --type warning --limit 50
```

`doctor --prod` reads them back ([`monitoring-usage-alerts`](/docs/reference/cli/diagnostics#monitoring-usage-alerts)), and asks for the gateway's dollars when models go through the Convex AI Gateway. A `warning` only tells; a `disable` limit pauses the whole deployment, so keep it above the warning ([Cap what the gateway spends](/docs/build/ai/models#cap-what-the-gateway-spends)).

## AI cost per person

The admin console's **Costs** tab shows what AI cost over the last 7, 30 or 90 days: the total, and the 100 people whose calls cost the most, with their runs and tokens. A run is a queued job, a metered action, a stream, a chat reply, or a knowledge document or search.

Each run's cost is recorded as the gateway reports it, against the member who made it and the workspace that paid. A job's steps are recorded in the same transaction as the job's own usage. Any other run is recorded once it ends. A failed run's calls count too, since you paid for them. A run whose calls never reached a model records nothing, and a call through a key of your own reports no cost. Visitors' jobs are listed as one row, and a chat reply or a document the app pays for under `app`. Each person's day is kept 90 days; an erasure keeps the figures under the account's pseudonym.

The tab reads once: when it opens, when you pick another window, and on **Refresh**. A live view would read again every time a run ends. Each day's total is kept apart, in a few rows a day, so the total stays whole however many people spent. The list of people reads each person's days, up to 10,000 rows. Past that, the tab says the list covers the newest days.

The tab appears once `backend/ai.ts` re-exports `getCosts` from `ai.api`, as the scaffold does. `getCosts({ since })` answers administrators only. Polar's Cost Insights holds what each job cost per customer, beside revenue and margin ([Report what each job cost you](/docs/build/ai/jobs/credits#report-what-each-job-cost-you)).

## Where reports come from

The backend cannot tell production from a dev or a preview deployment by itself. Its reports name the deployment's `BACKEND_ENVIRONMENT` as their environment: `development`, `preview`, `sandbox` or `production`, which `env push` sets for each kind of deployment ([Environments](/docs/start/concepts/environments#backend_environment)). The app's own reports use the same names: `BACKEND_ENVIRONMENT` where the app's host sets it too (set `sandbox` on a demo's host), else Vercel's own (`production`, `preview`), so one alert rule scoped to `production` covers every side, and a demo's errors stay apart under `sandbox`.

Only a `production` or `sandbox` deployment checks its jobs in. A dev deployment that sleeps with a laptop, or a preview deleted with its branch, would read as a missed run.

## The health endpoint

`GET /api/backend/health` answers with the app's health: a summary and every [capability's](/docs/start/concepts/capabilities) state, detected on the deployment from the env it holds. Point an uptime check at it, such as Sentry's uptime monitoring ([Sentry](/docs/services/sentry#link-it)):

```json
{
  "status": "degraded",
  "capabilities": {
    "auth": "live", "data": "live", "jobs": "live", "billing": "live", "email": "live", "notifications": "live",
    "ai": "missing", "protection": "live", "monitoring": "live", "flags": "live", "analytics": "live", "hosting": "live"
  }
}
```

| `status` | When | HTTP |
|---|---|---|
| `ok` | every capability is live, or in a provider's test mode | `200` |
| `degraded` | a capability is missing | `200` |
| `failing` | a capability's env is set but unusable (a `MONITORING_DSN` that is not a DSN), or the backend cannot be reached (then only `data` is reported) | `503` |

The states come from the env the deployment holds, by name, with nothing probed: the endpoint says whether a capability is configured, not whether its provider answers right now. The public sees the states and nothing else: no env name, no error. Signed in as an admin (the `admin` role, or the roles `registerBackendRoutes` takes as `adminRoles`), or on a deployment whose `BACKEND_ENVIRONMENT` is `development`, the answer adds `detail`: per capability, why it is in its state, the env names it lacks and the finding that fails it, if one does. The app asks the backend's own route, `/backend/health` on the deployment's site origin, which `registerBackendRoutes` mounts at that fixed path. [HTTP routes](/docs/reference/backend/http-routes) lists both.

`npx nuxt-backend doctor --prod` asks production's endpoint the way an uptime check does, anonymously, and fails it when it shows the detail to anyone ([`monitoring-health`](/docs/reference/cli/diagnostics#monitoring-health)).

## On Vercel

A Vercel function cannot take Node's `--import` flag, so the Nuxt server's SDK starts from inside the server bundle, as the server starts: Sentry's top-level import, its default since `@sentry/nuxt` 11. Requests are traced, and so are the libraries Sentry instruments when it builds; a library outside that list is not traced on the server. The browser is traced in full.

Releases and source maps follow Sentry's Vercel integration: it sets `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` and `SENTRY_PROJECT` on the project, and each deploy uploads its source maps and names its release after the commit. A Vercel build without them says so in its log, and `doctor` reports it as `monitoring-source-maps`.

## Customize the SDK

The module passes the SDK its own config files: a client and a server `Sentry.init` with the DSN, the environment, [the preset](#what-the-preset-does), and traces at every request in dev and one in ten in production. The server reads its DSN from its env when it starts, and falls back to the one the build wired, so a server started with `node` and no `.env` still reports. A `sentry.client.config.ts` or `sentry.server.config.ts` at your app's root replaces the package's whole, the preset with it, and the SDK module's own options stay yours in `nuxt.config` under `sentry`. Replay after consent and the feedback widget come from a plugin of the package, which reads the app config either way; a client config of your own sets `replaysOnErrorSampleRate` for replay to record anything.

## Develop without a DSN

In dev without a DSN, the dev server's local error log stands in for Sentry: failed backend calls from the browser and the server, with their function and code, and crashes, as a report would carry them. [DevTools](/docs/develop/devtools#monitoring) lists it on its Monitoring tab beside the app's health, and the capability reads as `test`. The log lives in the dev server's memory and is never part of a build. With a DSN set in dev, reports go to Sentry and the log keeps listing them too.

## Check it

`npx nuxt-backend doctor --only monitoring` checks the capability: `deployment-monitoring-dsn` warns when production has no DSN; `monitoring-app` when the app has a DSN but no SDK, or under `--prod` when no DSN is visible to the app at all; `monitoring-source-maps` when a Vercel deploy would upload no source maps; `monitoring-backend-exceptions` reminds you of the dashboard setting; and under `--prod`, `monitoring-usage-alerts` warns when production has no Convex usage warning. [Diagnostics](/docs/reference/cli/diagnostics#monitoring) explains each.
