Every flow that sends mail, spends money or acts on someone else is rate-limited by default. The limits run on Convex's official rate-limiter component, which the scaffold mounts, so you tune them in one file. `setupRateLimiter(components, limits?)` returns a `RateLimiter` pre-seeded with `DEFAULT_LIMITS`:

- sign-in codes sent and checked per address, with a ceiling for the whole deployment;
- email changes and account deletions per account;
- entitlement syncs and metered AI calls per billing entity, with a credit budget per day;
- administrator actions;
- invitations per inviter and for the deployment, and new workspaces per member;
- passkey challenges per client address and for the deployment.

[Limits and retention](/docs/reference/backend/limits#rate-limits) lists each one with its rate, burst and key, read from the code. Your `limits` merge on top and can override any of them. A launch most often raises the two deployment-wide ceilings, `emailOtpGlobal` and `invitationGlobal` ([Launch from a waitlist](/docs/ship/checklist#launch-from-a-waitlist)).

```ts [backend/rateLimiter.ts]
import { setupRateLimiter } from 'nuxt-backend/rate-limit'
import { components } from './_generated/api'

export const rateLimiter = setupRateLimiter(components, {
  // your own limits, merged over DEFAULT_LIMITS
  sendMessage: { kind: 'token bucket', rate: 10, period: 60_000 },
})
```

Pass the limiter into `setupAuth` to throttle sending and checking codes ([cross-component wiring](/docs/build/auth/setup#cross-component-wiring), [Security](/docs/ship/security#passwordless-sign-in-and-its-rate-limits)). Pass it into `setupAi` too, whose metered actions use the `ai` limit unless you name another, and into `setupEmail`, whose contact form and inbound mail spend `contact`, `contactGlobal`, `inboundMail` and `inboundMailGlobal`.

## Privileged routes

Once the limiter reaches `setupAuth`, it also bounds the auth routes where one caller acts on *other people* or on an address they typed. It bounds the route that makes a billing entity, the route that deletes an account, and the route anyone may call without a session too:

| What it limits | Limit | Keyed by |
| --- | --- | --- |
| `/admin/*`: list, create, update, ban/unban, set role, impersonate, revoke sessions, remove user | `admin`: 30/minute, burst 10 | the administrator's user id |
| Inviting someone to a workspace | `invitation`: 30/hour, burst 10 | the inviter's user id |
| …and the same invitation again | `invitationGlobal`: 200/hour, fixed window | nothing: one ceiling for the deployment |
| Creating a workspace, which is a billing entity (with a free plan in the catalog, a provider customer and the plan's credits) | `workspaceCreate`: 10/hour, burst 5 | the member's user id |
| `/email-otp/request-email-change`: the code to an email change's new address | `emailChange`: 5/hour | the user's id |
| `/delete-user`: an account's own deletion, which also takes a recent sign-in | `accountDelete`: 3/hour | the user's id |
| …and the same route again | `emailOtpGlobal`: 300/hour, fixed window | nothing: the ceiling every code send spends |
| `/passkey/generate-authenticate-options`: the challenge every passkey sign-in starts with | `passkeySignIn`: 30/minute, burst 30 | an HMAC of the client's address under the auth secret, as Better Auth reads the address |
| …and the same route again | `passkeySignInGlobal`: 3000/hour, fixed window | nothing: the ceiling behind the per-address bucket |

Better Auth already *authorizes* these routes; the limits bound how fast an authorized caller may go, so one compromised admin session cannot ban a thousand accounts. They are keyed by user id rather than by session, so opening more sessions does not multiply the budget. The caller is the session the route runs with, whether its token came in a cookie or as `Authorization: Bearer`; a request with no credential is left to the route, which answers 401 itself, and one whose credential matches no session is refused with 401 before it runs.

A per-caller limit bounds one account and nothing more: thirty invitations an hour each is still a lot of mail from a workspace of fifty. Invitations therefore also spend `invitationGlobal`, an unkeyed ceiling for the whole deployment, because the cost lands on a shared resource: your sending domain's reputation. It is consumed **after** the inviter's own bucket allowed the request, so one account's refused excess never eats everyone else's budget, and a deployment at its ceiling answers 429 with *"Invitations are temporarily unavailable"* rather than blaming the inviter. It is the counterpart of `emailOtpGlobal` on the package's other outbound-email path; admin routes have no such ceiling, because banning a user spends nothing anyone else shares.

A passkey sign-in has no caller yet either, but it serves people, so its challenge route spends a bucket per client address first. A tap on a passkey button spends one, and so does every sign-in page that offers passkeys in the email field's [autofill](/docs/build/auth/sign-in#passkey-autofill). Better Auth reads the address from `x-forwarded-for` (its `advanced.ipAddress` options: `ipAddressHeaders`, `trustedProxies`), and only a proxy in front of the deployment makes that header true: anyone calling the deployment directly writes it themselves. That bucket is a best effort, then, and `passkeySignInGlobal` is the ceiling an address-rotating caller meets, spent only after the address's own bucket allowed the request. A request whose headers name no address Better Auth trusts (several hops and no `trustedProxies`) spends the ceiling alone. Sign-in requests reach the deployment through your Nuxt app's auth proxy, which passes the browser's headers on: check which address arrives there once deployed. If it is your server's own, every visitor shares one bucket; point `ipAddressHeaders` at a header your host sets to the visitor's address (`x-real-ip` on Vercel), or raise `passkeySignIn`. At the ceiling, the passkey prompt answers 429, autofill offers no passkey, and sign-in codes still sign people in. The answer (`/passkey/verify-authentication`) uses its challenge up, so it spends nothing of its own. Raise `passkeySignInGlobal` when more sign-in pages than that open in an hour.

`/admin/stop-impersonating` and `/admin/has-permission` are exempt. The first is the way *out* of an impersonated session and must never be throttled, and the second is a read-only check an admin UI calls on render.

Better Auth's own per-path limiter is off by default: it keeps its counters in memory, which on Convex lasts one function call, so it would limit nothing. To throttle another route through it, turn it on (`enabled: true`) with durable storage. It counts per IP and takes its rules from your auth options:

```ts [backend/auth.ts]
setupAuth(components, query, {
  email,
  authOptions: {
    rateLimit: {
      enabled: true,
      storage: 'database',
      customRules: { '/sign-in/email-otp': { window: 60, max: 10 } },
    },
  },
})
```

## What the user sees

Every 429 the package raises is an `APIError('TOO_MANY_REQUESTS')` whose body carries `code: 'rate_limited'`, the `limit` it spent and `retryAfter`, the milliseconds until the limit lets the caller through again. That covers the code limits (`emailOtp`, `emailOtpGlobal`, `emailOtpAttempt`, `emailChange`), the passkey challenge (`passkeySignIn`, `passkeySignInGlobal`) and the privileged routes above. `useLoginFlow()` and `useEmailChange()` keep it in `error` as `{ code: 'rate_limited', data: { limit, retryAfter }, message }`, where `data.retryAfter` is still in milliseconds, and expose the same wait as `retryAfter`, in whole seconds rounded up. The body carries no sentence of its own, so `message` is the `errors.rate_limited_for` label, *"Too many requests. Try again in N seconds."*, in the person's language, and `<AuthForm>` and `<ProfileSettings>` show it (see [the authentication guide](/docs/build/auth/sign-in)).

Better Auth's own per-path limiter, once you turn it on, answers 429 too, but it sends the wait only as an `X-Retry-After` header. The auth client's `{ data, error }` result drops headers, so those refusals read *"Try again in a moment."* with `retryAfter` left `null`.

Outside the auth routes, the package's limits (`billingSync`, `ai`, `aiBudget`) throw the limiter's own error, and `getBackendError(error)` reads it, like the 429 above, as `rate_limited` with `limit` and `retryAfter` ([Handle errors](/docs/build/data/read-write/errors)).

::note
There are no password limits: the package has no passwords. Guessing at one code is bounded by Better Auth's own `allowedAttempts` (three wrong guesses), and guessing at one address by `emailOtpAttempt`. `DEFAULT_LIMITS` is exported from `nuxt-backend/rate-limit`, to read or extend the defaults.
::
