A security review starts from an inventory: everything an outsider can reach. This page is that inventory for an app built on the package. The [security model](/docs/ship/security) says how each part is guarded. For `0.2.0`, the whole surface was reviewed as one checkpoint once the release's features had landed, and the repository's `SECURITY.md` carries the same list with what each review found.

## What it covers

| Kind | What is listed | Where each is documented |
|---|---|---|
| Routes | Every HTTP route on the deployment and on the Nuxt server: the auth routes, the webhooks, the AI stream, the health checks, the unsubscribe and file routes, the push worker | [HTTP routes](/docs/reference/backend/http-routes) |
| Public functions | Every query, mutation and action of the scaffold and of the setups an app turns on, with who it answers | [Component functions](/docs/reference/backend/component#functions) |
| Env names | Every name the app and the deployment read, and what its absence does | [Environment variables](/docs/reference/configuration/environment-variables) |
| Webhooks | Every inbound route a provider signs, and its fail-closed outcomes | [Register webhooks](/docs/ship/security/webhooks) |
| Public pages | Every page the module adds that a visitor reaches signed out | [Pages](/docs/build/ui/pages) |
| Uploads and links | What an upload is checked for, and what a share link lets an anonymous visitor read | [Files](/docs/build/data/files) |
| Services | Each provider the app sends data to, what it holds and where | [Service map](/docs/services) |

## What 0.2.0 adds

Everything below is new since `0.1`. Who a function answers is said in the words of the probe suite's policies: *anyone*; *signed in*; a *member* of the active workspace; a *billing manager* (its owner or admin); an *administrator* (the app-wide admin role). Each is read fresh on every call, not from the session token. *In person* means an administrator impersonating the account is refused. *Recent sign-in* means a session signed in more than ten minutes ago is refused until the person signs in again. *Own ids only* means someone else's ids are refused.

### Routes

| Route | Where | Guarded by |
|---|---|---|
| `/email/unsubscribe` | Deployment, `GET` and `POST` | The signed token of the email's `List-Unsubscribe` link (RFC 8058); it can only take mail away |
| `/backend/health` | Deployment, `GET` | Public: each capability's state; the detail only for an administrator's session, or on a deployment named `development` |
| `/storage/<id>` | Deployment, `GET`, with `setupStorage` | A signature under the app's secret that expires; anything but a raster image downloads, under a sandboxing content security policy |
| `/api/backend/health` | App | The same as the deployment's health |
| `/api/human-proof` | App, `POST` | The bot check: it signs a proof for one call, for one target, that lasts a minute |
| `/api/backend/visitor-ip` | App, `GET` | Public, never cached: the caller's own address, which nothing keeps |
| `/_backend/push/worker.js` | App, `GET` | Public: the push service worker, the same file for everyone |
| `/manifest.webmanifest` | App, `GET` | Public: the web app manifest, once the app has its icons and brand |
| `/api/backend/_monitoring` | App, `nuxt dev` only | Same site; never in a build |

The webhook routes are the same two as in `0.1`, `/billing/events` and `/email/events`. What `/email/events` does with an authentic delivery grew: inbound mail (`email.received`) files contact replies and support threads, and bounces and complaints mirror the provider's suppression list.

The backend component's own functions, such as `access.rekeyInvite` (an invitation code moved to the current auth secret's hash) and `notifications.channelOpen` (whether a person lets one kind of message through one channel), are no public surface: only the app's own functions can call a component's.

### Env names

New: `BACKEND_ENVIRONMENT`, `EMAIL_MARKETING_FROM`, `EMAIL_REGION`, `EMAIL_DEV_INBOX`, `AI_GATEWAY_API_KEY`, `PROVENANCE_PRIVATE_KEY`, `PROVENANCE_CERTIFICATE`, `PUSH_PUBLIC_KEY`, `PUSH_PRIVATE_KEY`, `PROTECTION_PROOF_SECRET`, `PROTECTION_CHALLENGE_SECRET_KEY`, `MONITORING_DSN` and `NUXT_PUBLIC_BACKEND_CHALLENGE_SITE_KEY`. `AUTH_SECRET` can now hold a versioned list, which [rotating it](/docs/ship/security/secrets) writes.

Gone: `AUTH_TRUST_LOCAL_ORIGINS`, `EMAIL_TEST_MODE`, `BILLING_ENVIRONMENT` and `NUXT_BACKEND_LOG_OTP`, which `BACKEND_ENVIRONMENT` replaced, and `NUXT_PUBLIC_BACKEND_SITE_URL`.

### Public pages

New pages a visitor reaches signed out: `/legal/privacy`, `/legal/terms`, `/legal/subprocessors`, `/legal/accessibility`, `/report`, `/unsubscribe`, `/invite`, `/waitlist`, `/r/:code` and `/account/keep`. The ones a link opens (`/unsubscribe`, `/invite`, `/waitlist`, `/r/:code`, `/account/keep`, and an appeal on `/report`) take the link's token as their only authorization, and all but `/report`, a public form, are kept out of search indexes. New signed-in pages: `/admin`, hidden from anyone without the role, `/gifts` and `/welcome`.

### Tools that change a deployment

`npx nuxt-backend env rotate` writes the deployment and, for the webhook secrets, the provider accounts, with every value on `convex env set`'s stdin. `doctor --fix` applies the provider settings the billing findings recommend and turns a webhook endpoint back on, each change only once it is confirmed. Both run on the developer's machine, with the developer's own credentials.

### Removed since 0.1

The hosted agent endpoint is gone, and with it its whole surface: `/mcp`, `/mcp/exchange`, the OAuth routes (`/mcp/authorize`, `/mcp/token`, `/mcp/register`, `/oauth2/consent`) and the consent page. The starter no longer exports `auth:listWorkspaces`, `auth:listWorkspaceMembers`, `billing:createDiscount`, the email admin actions (`sendAsAdmin`, `addContact`, `createSegment`, `createBroadcast`, `sendBroadcast`), the echo stream or `migrations:run`.

## How it is checked

- **Every public function, probed.** The package's test suite calls each public function of the scaffold, and of every setup an app may turn on, the way an attacker would. It calls signed out, as someone else, as someone who no longer belongs, as another workspace's manager, through an administrator's visit, with an old sign-in, and with inputs only the server may choose. Each must refuse exactly what its policy refuses. A setup that adds a public function fails the suite until the function has a policy. A known gap would sit on a list with the unit that closes it. For `0.2.0` that list is empty, and the suite fails on any new gap.
- **The repository's own checks.** `pnpm test:security` and fallow's security pass run over the whole repository on every change, as `SECURITY.md` describes. At this checkpoint they report no candidate.
- **A deeper review before the release.** The maintainer runs deepsec, an AI-assisted review, over the release candidate, as a step of the release's last phase.
