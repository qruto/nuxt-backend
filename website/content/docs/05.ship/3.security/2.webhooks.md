One call mounts every route your backend answers over HTTP, so billing and email events reach it, signed, with nothing else to wire. `registerBackendRoutes(http, options)` from `nuxt-backend/http` mounts them on your Convex HTTP router: the auth routes, the two webhooks, the metered AI stream and the health check. Both webhooks verify their signature once, at one edge, with one verifier ([Webhooks: fail closed](/docs/ship/security#webhooks-fail-closed)). Each option takes the instance its `setup*` helper returns. This is the scaffolded `http.ts`, its comment left out:

```ts [backend/http.ts]
import { registerBackendRoutes } from 'nuxt-backend/http'
import { httpRouter } from 'convex/server'
import { ai } from './ai'
import { authComponent, createAuth } from './auth'
import { billing } from './billing'
import { email } from './email'

const http = httpRouter()
registerBackendRoutes(http, {
  auth: { authComponent, createAuth },
  billing,
  email,
  ai,
})

export default http
```

## What gets mounted

| Route | What it does | Verified with |
|---|---|---|
| Auth routes | The Better Auth HTTP endpoints (same as `authComponent.registerRoutes`) | Auth's own signing |
| `/billing/events` (POST) | Refreshes the reactive entitlement cache (subscriptions, benefit grants, credit balances) and fulfils [gift purchases](/docs/build/growth/offers/gifts) | `BILLING_WEBHOOK_SECRET` |
| `/email/events` (POST) | Tracks delivery status (delivered / bounced / complained) behind `useEmailStatus` | `EMAIL_WEBHOOK_SECRET` |
| `/ai/stream` (POST + OPTIONS) | Runs an `ai.stream(...)` handler and streams its chunks to `useAiStream`. The OPTIONS route answers the browser's CORS preflight for the app origin (`SITE_URL`) | The `streamId` the signed-in `start` action handed the caller (its credits are already reserved) |
| `/backend/health` (GET) | The [health check](/docs/ship/operate/monitoring#the-health-endpoint) the app's `/api/backend/health` asks, at a fixed path | Public for each capability's state; the detail for an administrator |

Both webhooks share one fail-closed policy: missing secret → `503`, invalid signature → `403`, oversized body → `413`, authentic-but-unknown event type → `202`, handler throw → `500` (so the provider retries), redelivery of a processed id → `200`. Every delivery's outcome lands in the component's [delivery log](#the-delivery-log) (the Backend tab in Nuxt DevTools and the admin console's Webhooks tab read it). Both routes run through one edge, so the policy cannot drift between them. The size cap is 1 MiB, counted in bytes: a `Content-Length` over it is refused before the body is read. A refused request also leaves a `webhook.rejected` line in the deployment log, with the route, the outcome and the status, once per isolate for each route and outcome so junk traffic cannot flood the log; a missing secret leaves `webhook.secret_missing` instead. [Troubleshooting](/docs/ship/operate/troubleshooting#log-codes) says what to do about each.

## Point the provider dashboards at them

Webhooks arrive on your backend's **site** URL: the `.convex.site` domain, not `.convex.cloud` (inside the deployment the platform runtime exposes it as `CONVEX_SITE_URL`):

- **Billing ([Polar](/docs/services/polar#link-it)).** `npx nuxt-backend billing sync` (with `--env production` for production) provisions the endpoint at `https://your-deployment.convex.site/billing/events`, subscribed to every event the package handles, and stores its secret on the deployment as `BILLING_WEBHOOK_SECRET`. By hand: the provider's dashboard, Settings, Webhooks, with the same secret on the deployment.
- **Email ([Resend](/docs/services/resend#link-it)).** `npx nuxt-backend email sync` (with `--prod` for production) points a webhook at `https://your-deployment.convex.site/email/events` and stores its secret as `EMAIL_WEBHOOK_SECRET`. By hand: the provider's dashboard, Webhooks, subscribed to the `email.*` events.

A local deployment has no public URL, so no provider reaches it. Develop on a cloud dev deployment, or run a tunnel to the local one ([Develop on real sandboxes](/docs/develop/sandboxes)). Resend's test addresses then send real delivery events, and Polar's sandbox real billing events. [Service map](/docs/services#provider-setup) has both providers per environment, with the findings that check them.

## Reacting to events

The built-in handlers keep state fresh; your hooks run on top of them, per event.

Billing hooks go on `setupBilling` and run after the built-in entitlement refresh: see [React to billing events](/docs/build/billing/events).

Email hooks go on [`setupEmail`](/docs/build/email/sending), keyed by the provider's event names too (`'email.delivered'`, `'email.bounced'` and the rest of the catalog on [Delivery tracking](/docs/build/email/delivery#reacting-to-events)), and fire after the event is verified and the status recorded:

```ts [backend/email.ts]
export const email = setupEmail(components, {
  events: {
    'email.delivered': async (ctx, event) => { /* … */ },
    'email.bounced': async (ctx, event) => { /* suppress future sends to event.data.to */ },
    'email.complained': async (ctx, event) => { /* alert an admin */ },
  },
})
```

## The delivery log

Redelivery dedupe reads the log, and how it keeps an outcome depends on whether the request proved who sent it:

- A delivery whose signature verified (`ok`, `unknown_type`, `handler_error`) gets a row of its own. The newest 200 are kept: older rows are trimmed in the background, at most once an hour, so recording a delivery never reads the rest of the log and concurrent deliveries never wait on each other.
- A request answered before any signature verified (`missing_secret`, `oversized`, `invalid_signature`, or a `duplicate` of a processed id) is counted per route and outcome instead, under the latest one's delivery id. Anyone can POST to these routes, so a flood of junk can neither grow the log nor push out the verified rows that dedupe relies on. A count starts afresh after a day without one.

Delivery ids and event types are kept to their first 128 characters, a handler's error note to its first 500.

The log spans every account on the deployment, so `getWebhookDeliveries` (re-exported by the scaffolded `webhooks.ts`, from `setupWebhooks`) is admin-tier: it answers an administrator in person (an account with the `admin` role, read fresh, or one `adminUserIds` names) and `null` to anyone else, signed out included. The DevTools Backend tab and the admin console's Webhooks tab say so instead of showing an empty log.

A delivery that failed is sent again by its provider, which retries on a `5xx`. After a fix, [Replay a webhook delivery](/docs/ship/operate/replay) asks the provider to send it again from the log, in the admin console and in DevTools. [Respond to incidents](/docs/ship/operate/runbooks#webhooks-fail) says what to check first.

## Custom paths

Change where the routes mount with `billingPath`, `emailPath` and `aiPath`, and point the provider dashboards at the new paths:

```ts [backend/http.ts]
registerBackendRoutes(http, {
  auth: { authComponent, createAuth },
  billing,
  email,
  ai,
  billingPath: '/hooks/billing',
  emailPath: '/hooks/email',
})
```

::note
Every part is required. A route left out would answer `404` the first time a provider or a client calls it, so the type refuses the call instead. For fully custom routing, skip `registerBackendRoutes` and mount each part on your own router: `authComponent.registerRoutes(http, createAuth)` for the auth routes; each instance's `webhookHandler` (`billing`, `email`), wrapped in `httpActionGeneric` from `convex/server`; and `ai.httpHandler`, already an HTTP action, beside an `OPTIONS` route that answers its CORS preflight.
::
