`0.2.0` is the first release of the package: `0.1.0` on npm was a throwaway test publish. So an app has nothing to migrate from, and no codemod rewrites its code. From `0.2.0` on, every release moves your app forward the same way:

```bash
npm install nuxt-backend@latest
npx nuxt-backend upgrade --dry-run   # what it would repair and migrate; nothing written
npx nuxt-backend upgrade             # the scaffold and the dev deployment's data
```

- **Scaffold.** It makes the repairs `npx nuxt-backend doctor --fix` makes: the scaffold files, mounts and routes the new version adds. The rest of `backend/` stays as it is.
- **Data.** It runs the package's own data migrations on the dev deployment, once that runs the new backend: start `npx nuxt-backend dev` once. Production's migrations run after its deploy, with `npx nuxt-backend upgrade --prod --yes`.

`upgrade` rewrites none of your code. A release that renames or removes a public name says so in the [changelog](/docs/ship/releases/changelog), with the edit to make, and keeps the old name working for at least one minor release ([Stability](/docs/ship/releases/stability#deprecation)). After the upgrade, run `npx nuxt-backend doctor`, which names any scaffolded function your `backend/` files no longer export, then your type check.

An app built on a preview of `main` before `0.2.0` (`npm install https://pkg.pr.new/qruto/nuxt-backend@main`) makes each edit by hand: `upgrade` repairs the scaffold and migrates the data, and rewrites none of the app's code. The sections below list each change between those previews, newest first, with the edit to make. They leave this page once `0.2.0` is published.

## One way to do each thing

`0.2.0` keeps one API per action. Where two did the same thing, one goes: one `createFunctions` call builds every function tier, one `<Gate>` gates a region, one `<BackendNotices>` holds every app-wide notice, `definePageMeta({ auth })` is the one page guard, and `useAuth` only reads the session. The thin wrappers over Convex's own components go: an app imports the component it uses. Each `setupX` returns its functions in one bag, `.api`. Both webhooks verify through one verifier, which also takes Polar's older key, so a billing webhook secret created before 2026-09-08 keeps working.

| Gone | Instead |
|---|---|
| `setupAuthorization` | `createFunctions({ query, mutation, action }, { components, billing, rateLimiter })`, called once in `backend/functions.ts`: it builds the roles and returns `authed`, `workspace`, `admin`, `withRole`, `withFeature` and `setUserRole` |
| `nuxt-backend/authorization` | `nuxt-backend/functions`, which also exports `RECENT_SIGN_IN_SECONDS` and `SENSITIVE_ACTIONS` |
| `requirePermission` | An app-wide role: the `withRole(role)` tier, or `admin` |
| `createAccessControl` | Nothing: a role is a name. Custom permissions wait for a later release |
| `functionOptions` | `createFunctions`' options, in its one call |
| `setupMigrations` | `new Migrations(components.migrations, { schema })` from `@convex-dev/migrations` |
| `setupWorkpool` | `new Workpool(components.workpool, options)` from `@convex-dev/workpool` |
| `setupCounter` | `new ShardedCounter(components.shardedCounter)` from `@convex-dev/sharded-counter` |
| `defineCache` | `new ActionCache(components.actionCache, { action })` from `@convex-dev/action-cache` |
| `setupCrons` | `new Crons(components.crons)` from `@convex-dev/crons` |
| `defineBackendCrons` | Convex's own `cronJobs()` in `crons.ts` |
| `withTriggers` | `customMutation(mutation, customCtx(triggers.wrapDB))` from `convex-helpers` |
| `billing.functions` | `billing.api`, which now holds every function the billing composables call |
| `email.devtools` | `email.api`: `previewEmails` and `sendEmailPreview` sit beside `getEmailStatus` |
| `account.functions` | `account.api` |
| `listWorkspaces` and `listWorkspaceMembers` of `setupAuth` | `useWorkspace()`, which reads them through the auth routes |
| `<RoleBoundary>` | `<Gate role>`. Its `permission` prop has no counterpart |
| `<OrganizationBoundary>` | `<Gate workspace>`, whose default slot still receives `{ workspace }` |
| `<FeatureBoundary>` | `<Gate feature>`. Its `plan` prop has no counterpart: gate on a feature the plan grants |
| `<QuotaBoundary>` | `<Gate quota>`, with the same `amount`, `name` and `labels` |
| `<ImpersonationBanner>` | The `impersonation` notice of `<BackendNotices>` |
| `<MaintenanceBanner>` | The `maintenance` notice of `<BackendNotices>` |
| `<CreditsLowBanner>` | The `low-credits` notice of `<BackendNotices>`, with `threshold` on the region |
| `<GiftClaimBanner>` | The `gift` notice of `<BackendNotices>` |
| `definePageMeta({ middleware: 'auth' })` | `definePageMeta({ auth: true })` |
| `auth: { permission }` | `auth: { role }` |
| `auth: { workspaceRole }` | `auth: { workspace }`, which also takes `true` for any member |
| `useAuthState` | `useAuth()`'s `isSignedIn` and `isLoading` |
| `useAccountData` | `useAccount`, which also saves the profile |
| `useFlags` | `useFlagAdmin` |
| `useAggregate` | `useQuery` over the aggregate's own query |
| `describeUserAgent` | A session's `device` label, from `useSessions()` |
| `unwrapAuth` | Nothing: every composable resolves with its data or rejects |
| `useAuth().updateUser` | `useAccount().updateProfile` |
| `useAuth().deleteAccount` | `useAccount().deleteAccount` |
| `useAuth().registerPasskey` | `usePasskeys().add` |
| `useAuth().stopImpersonating` | `useAdmin().stopImpersonating` |
| `useAuth().lastSignInMethod` | `useLoginFlow().lastMethod` |
| `useAuth().isAuthenticated` | `useAuth().isSignedIn` |
| `useAuth().isImpersonating` | `useAuth().impersonating` |
| `useAuth().can` | `useAuth().hasRole`: a role is a name |
| `useAuth().client` | Nothing: sign in with `useLoginFlow`, and reach the rest through the composables |

**What to do**

- Rewrite `backend/functions.ts` as one `createFunctions` call with `components`, `billing` and `rateLimiter` in its options ([Project files](/docs/reference/configuration/project-files)), and import `withFeature` from it instead of from `billing.ts`. `billing.ts`, and every file it imports (`email.ts`, `audit.ts`), must not import `functions.ts`: move a function they build on a tier into a file of its own.
- In `backend/billing.ts`, `backend/email.ts` and `backend/account.ts`, re-export from `.api`.
- Install and import each Convex component you used through a removed subpath, and mount it in `convex.config.ts`: `doctor` names a mount a backend file needs.
- Replace each boundary with `<Gate>` and the four banners with one `<BackendNotices>` in your layout.
- Replace `middleware: 'auth'` with `auth: true`, keeping any other middleware of a list, and the `permission` and `workspaceRole` page rules with `role` and `workspace`. `nuxt-backend upgrade` rewrites none of your code.
- Point each removed `useAuth` member at its composable above.

[Protect backend functions](/docs/build/auth/access/functions), [Gate](/docs/build/ui/gate), [Notices](/docs/build/ui/notices) and [Protect pages](/docs/build/auth/access/pages) show each one.

## One variable says what kind of deployment this is

`0.2.0` replaces five variables that each said one part of the same thing (email's test mode, the billing environment, the local origins auth trusts, the sign-in codes in the logs and the environment a report names) with one, `BACKEND_ENVIRONMENT`: `development`, `preview`, `sandbox` or `production`. Only `production` takes mail and billing out of their test modes. `npx nuxt-backend env push` derives it from the deployment, and sets `development` on a dev one, `preview` on a preview and `production` on production. An app built on a preview of `main` that set the five by hand keeps working only on a deployment that holds the new one: until it does, every provider stays in its test mode, and nothing local is trusted.

| Gone | Instead |
|---|---|
| `EMAIL_TEST_MODE` | `BACKEND_ENVIRONMENT`: test mode everywhere but `production`. `EMAIL_TEST_MODE=false` becomes `BACKEND_ENVIRONMENT=production` |
| `BILLING_ENVIRONMENT` | `BACKEND_ENVIRONMENT`: the billing provider's sandbox everywhere but `production`. `BILLING_ENVIRONMENT=production` becomes `BACKEND_ENVIRONMENT=production` |
| `MONITORING_ENVIRONMENT` | `BACKEND_ENVIRONMENT`, which names the environment a report carries |
| `AUTH_TRUST_LOCAL_ORIGINS` | `BACKEND_ENVIRONMENT=development`, which trusts the local origins |
| `NUXT_BACKEND_LOG_OTP` | `BACKEND_ENVIRONMENT=development`, which logs the sign-in codes |
| `NUXT_PUBLIC_BACKEND_SITE_URL` | Derived from `NUXT_PUBLIC_BACKEND_URL`. A custom domain or a self-hosted backend sets `NUXT_PUBLIC_CONVEX_SITE_URL`, the base module's own variable |
| `SENTRY_DSN` | `MONITORING_DSN`, or the `NEXT_PUBLIC_SENTRY_DSN` that Sentry's Vercel integration sets, which the package reads as it is |
| `backend.siteUrl` | Derived from `backend.url`: the module refuses the option and names this section |
| `backend.autoEnv` | `npx nuxt-backend dev` provisions a new dev deployment's env once, and `env push` forwards the rest: the module refuses the option |
| `backend.scaffold` | `npx nuxt-backend init` scaffolds the backend, and `dev` scaffolds an app with no functions directory: the module refuses the option |
| `setupBilling({ environment })` | Nothing: the billing environment follows `BACKEND_ENVIRONMENT` |
| The `deployment-auth-trust-local-origins`, `deployment-email-test-mode`, `deployment-billing-environment` and `deployment-monitoring-environment` findings of `doctor` | `deployment-backend-environment`, which fails production when it is unset, `development` or `preview`, and warns on `sandbox`. `deployment-removed-env` names any variable above that a deployment still holds |

**What to do**

- Run `npx nuxt-backend env push` on the dev deployment and `npx nuxt-backend env push --prod` on production: each sets `BACKEND_ENVIRONMENT` where it is missing. A demo or staging deployment that kept `EMAIL_TEST_MODE=true` or `BILLING_ENVIRONMENT=sandbox` on purpose sets `sandbox` first, by hand: `npx convex env set --prod BACKEND_ENVIRONMENT sandbox` ([Deploy a demo or staging app](/docs/ship/deploy/staging)).
- Delete the variables above from `.env.local`, your host's env and the deployment (`npx convex env remove NAME`; `doctor` names each one it still finds).
- In `backend/convex.config.ts`, forward `BACKEND_ENVIRONMENT` to the `backend` component and delete the `EMAIL_TEST_MODE` and `MONITORING_ENVIRONMENT` lines: `doctor --fix` adds the first, and the `convex-config` finding names the others, which the push fails on.
- Remove `siteUrl`, `autoEnv` and `scaffold` from `backend` in `nuxt.config.ts`, and `environment` from `setupBilling`.
- If the app reads `SENTRY_DSN` for the package, set `MONITORING_DSN` or install Sentry's Vercel integration, which sets `NEXT_PUBLIC_SENTRY_DSN`.

[Environments and deployments](/docs/start/concepts/environments) says what each value decides, and [Environment variables](/docs/reference/configuration/environment-variables) lists every name.

## Development runs on the providers' sandboxes, with nothing simulated

`0.2.0` has no billing simulator, no simulated email events and no stand-in model. An app built
on a preview of `main` that billed on the simulator, or answered models from the stand-in, bills in
Polar's sandbox and calls real models instead ([Develop on real sandboxes](/docs/develop/sandboxes)).
The suites keep working: `nuxt-backend/test` answers every `provider/model` id with the AI SDK's
mock, and `createBackendMock` renders your pages with no network.

| Gone | Instead |
|---|---|
| `nuxt-backend simulate serve`, and the simulator `nuxt-backend dev` started on a local deployment with no `BILLING_ACCESS_TOKEN` | A Polar sandbox token in `.env.local`, then `npx nuxt-backend env push` and `npx nuxt-backend billing sync`. Pay with the test card |
| `nuxt-backend simulate email` | Send to `delivered@resend.dev`, `bounced@resend.dev` or `complained@resend.dev` (any with a `+label`): Resend posts the real event to a deployment it can reach |
| `BILLING_SIMULATOR_URL` | Nothing: delete it from `.env.local` and the deployment (`npx convex env remove BILLING_SIMULATOR_URL`) |
| `NUXT_BACKEND_SIMULATE_MODELS` | Nothing: a call with no route is refused in development as in production. Set `AI_GATEWAY_API_KEY`, or use a paid Convex plan's AI Gateway |
| `npx nuxt-backend billing sync --env simulated`, and the `simulated` map of `billing.generated.ts` | `billing sync` writes `sandbox` and `production` only: delete the `simulated` map, then sync |
| The `billing-simulator` finding of `doctor`, and the `billing.simulator_refused` and `ai.model_simulated` log codes | Nothing |
| The `simulated` state of a capability, in `status --json`, the health route and `labels.admin.system.states.simulated` | The `test` state, and `labels.admin.system.states.test` |
| `getSandboxInbox` as a query, and the `sandboxInbox` table of the `backend` component | `getSandboxInbox` is a public action that reads Resend's log of sent email with the deployment's `EMAIL_API_KEY`: keep the re-export in `backend/email.ts`. It answers only once the deployment opts in with `EMAIL_DEV_INBOX=1`, which `npx nuxt-backend dev` sets on a dev deployment; set it by hand on a preview or a deliberate sandbox. A send with no key sends nothing, so a keyless demo has no inbox to read |

**What to do**

- Delete the variables above from `.env.local` and the deployment, and the `simulated` map from
  `backend/billing.generated.ts`.
- Put the providers' sandbox keys in `.env.local` (a Polar sandbox token, a Resend key with full
  access) and run `npx nuxt-backend env push`, then `npx nuxt-backend billing sync`.
- The `sandboxInbox` table is gone from the component: a deployment that still holds rows in it
  refuses the push until they are deleted in the dashboard (they expire within the hour).

## The MCP endpoint for your users' agents waits for the next release

`0.2.0` ships no MCP endpoint for your users' agents, and nothing that only served it. An app built
on a preview of `main` that served `/mcp` loses the route, the consent page and everything an
agent's token touched ([Roadmap](/docs/start/roadmap), [MCP endpoint](/docs/develop/agents/mcp)).
The agents that build your app are not affected: the skills, the agent files, the docs MCP and the
developer MCP server stay.

| Gone | Instead |
|---|---|
| `nuxt-backend/mcp`, `useBackendMcp` and `defineBackendMcpTool`, and the `/mcp` and `/mcp/exchange` routes | Nothing: delete your tool files. A Nuxt server route or a Convex HTTP action can serve an MCP server of your own |
| `backend.mcp` in `nuxt.config.ts` | Nothing: the module refuses the option and names this section |
| `<AgentConsent>`, `useAgentConsent` and the page at `backend.pages.agentConsent` (`/oauth/consent`) | Nothing |
| `setupAuth({ mcp })`, and `registerBackendRoutes(http, { auth: { authComponent, createAuth, mcp } })` taking the `mcp` it returns | Nothing: leave `mcp` out of `backend/auth.ts`, and call `registerBackendRoutes(http, { auth: { authComponent, createAuth }, billing, email, ai })`. Its `mcpExchangePath` option goes with the route |
| `scope` beside `args`, as in `authed.query({ scope })` on every tier of `createFunctions`, on `requireUser`, `requireMember` and the other checks, on `billing.requireEntity` and on `setupAi`'s metered actions and streams | Nothing: no function takes an agent's token, so every one is a person's own |
| `AuthorizationUser.agentClientId` and `agentScopes`, and `asUser({ agent })` | Nothing |
| The `forbidden` reasons `agent_token` and `insufficient_scope`, the `agent.authorized` and `agent.revoked` events, the `mcp` and `agentRegistrationGlobal` rate limits, and the `labels.agents` labels | Nothing |
| The `agents` capability, so `doctor --only agents`, with its findings `mcp`, `agent-login-path`, `agent-consent-path`, `mcp-challenge` and `agent-discovery`, and DevTools' Agents tab | `doctor --only data`: `agent-files` and `agent-docs` are `data` findings now |

**What to do**

- Delete the keys and exports above from `nuxt.config.ts`, `backend/auth.ts` and `backend/http.ts`,
  and drop any `scope` from your own functions.
- The `backend` component no longer has the OAuth tables (`oauthApplication`, `oauthAccessToken`
  and `oauthConsent`). A deployment that still holds rows in them refuses the push until they are
  deleted in the dashboard.

## Every public name says workspace, never organization

A workspace was the auth library's organization under its own name in the docs, and under the
library's name in the code. The code now says workspace too: the composable, the function tier,
the `setupAuth` option, the billing default, the invitation email's data and every field a
member or an invitation carries. Better Auth's own `organization`, `member` and `invitation`
tables, its routes and its session claim keep their names, inside the `backend` component. The
CLI and DevTools say capability where they said layer, and the admin console's System tab labels
follow ([Capabilities](/docs/start/concepts/capabilities)).

| Gone | Instead |
|---|---|
| `useOrganization()` | `useWorkspace()`, which also lists the active workspace's pending `invitations` and changes members with `updateMemberRole` and `removeMember` |
| `useOrganization().organizations` | `useWorkspace().workspaces` |
| `UseOrganizationReturn` | `UseWorkspaceReturn` |
| `organizationId`, `organizationName` and `organizationSlug` on a member or an invitation, and the `organizationId` that `invite`, `setActive` and `leave` take | `workspaceId`, `workspaceName` and `workspaceSlug` |
| `organizationName` in the `invite` email's data | `workspaceName` |
| The `org` tier of `createFunctions`, `ctx.organization` (`{ id, role }`) and `limits.org` | The `workspace` tier, `ctx.workspace` (`{ id, slug, name, role }`) and `limits.workspace` |
| `requireOrganization` resolving `{ user, organizationId }` | `requireWorkspace`, resolving `{ user, workspace }`, the workspace as `ctx.workspace` has it |
| `requireMember({ organizationId })`, its result's `organizationId`, and `activeOrganizationId` on the user `getUser` reads | `workspaceId` and `activeWorkspaceId` |
| `setupAuth({ organization })` | `setupAuth({ workspaces })`, the same options |
| `billTo: 'organization'` | `billTo: 'workspace'`, still the default |
| `listWorkspaceMembers({ organizationId })` and the `organizationId` it resolves | `workspaceId` |
| A Better Auth refusal reason with the word in it (`user_is_not_a_member_of_the_organization`) | `not_member`; any other says workspace |
| `labels.admin.system.layers` and `labels.admin.system.layer` | `labels.admin.system.capabilities` and `labels.admin.system.capability` |

- Rename the composable, its `workspaces` member and the `setupAuth` option: `upgrade` does
  these three for you.
- In `backend/functions.ts`, destructure `workspace` where you destructured `org`, then read
  `ctx.workspace` in its functions.

## Deleting an account is immediate, and erases it everywhere

An account's deletion no longer waits for a link from its inbox. It happens at once, behind a
sign-in from the last ten minutes and the account's address typed to confirm it, and it is
refused to the only owner of a workspace others belong to. Then an erasure runs every place the
package keeps something of the person, the billing customer, the email contact and your own
tables included, retried until it is done. Each person can also download everything in one file.
`backend/account.ts` sets both up with `setupAccount`, and `/security` offers them through
`<AccountData>`. [Export and erase account data](/docs/build/auth/accounts/data) has the details, and the
[Privacy and data inventory](/docs/ship/compliance/privacy) lists what each part holds.

| Gone | Instead |
|---|---|
| `useAuth().deleteAccount()` emailing a confirmation link | `useAuth().deleteAccount(confirmation)` deletes now: `confirmation` is the address the person typed (`invalid_input`, field `confirmation`, when it differs), the call takes a recent sign-in, and the only owner of a workspace others belong to is refused (`forbidden`, reason `sole_owner`). `useAccountData()` holds the whole flow |
| `/delete-user` with an empty body | `/delete-user` with `{ confirmation }`, under its own `accountDelete` limit (three an hour per account); `/admin/remove-user` refuses an only owner the same way |
| The `deleteAccount` email: `DeleteAccountEmailData`, `setupEmail({ templates: { deleteAccount } })` and its `email.deleteAccount.*` labels | Nothing: deleting an account sends no email |
| `user.deleteUser.sendDeleteAccountVerification`, set by the package | Not set. One your `authOptions` pass still sends its link, and the link still deletes |
| `<SecuritySettings @delete-requested>`, the `requestDeletion` slot prop and the `security.dangerNote`, `security.deleteAccount`, `security.deleting`, `security.deleteConfirm` and `security.deleteSent` labels | `<AccountData>`, which `/security` renders below `<SecuritySettings>`: the export, and the deletion with its typed confirmation. The `danger` section signs this browser out, under `security.danger`, now "This device" |
| `onUserDeleted` as the place to erase your tables | `setupAccount({ sources })`: each source exports its rows and erases them in batches, retried, also when server code deletes an account. `onUserDeleted` still runs, for side effects |
| The `audit.erasure_failed` and `flags.erasure_failed` log lines | `account.erasure_failed`, once a participant failed five times (`account.erasure_retried` before each retry) |

**What to do**

- Run `npx nuxt-backend upgrade` (or `doctor --fix`): it adds `backend/account.ts`, which exports
  `exportAccountData`, `getAccountExport` and `eraseAccountData`. `doctor` names them while they
  are missing. A `backend/account.ts` from before `0.2.0` also needs the consent functions
  (`getConsents`, `getConsentTerms`, `grantConsent`, `withdrawConsent` and `chooseStorage`), which
  `account.api` holds: destructure them beside the others, as [Record consents](/docs/build/auth/accounts/consents#declare-your-consents) shows.
- Pass the instance to `setupAuth` in `backend/auth.ts`, so a deletion erases the providers'
  records and your own tables too: `import { account } from './account'`, then `account` beside
  `audit`. Without it, the backend's own tables are erased and the only-owner refusal holds.
- A page of yours that deleted the account asks for the address and passes it:
  `withReauthentication(() => deleteAccount(typed))`, or renders `<AccountData />`.
- Move the erasure of your own tables from `onUserDeleted` into a source of `setupAccount`, as
  [Join your own tables](/docs/build/auth/accounts/data#join-your-own-tables) shows.
- Drop a `deleteAccount` template override, and an alert on `audit.erasure_failed` or
  `flags.erasure_failed`: watch `account.erasure_failed` instead.
- Optional: pass `audit` to `setupBilling` and `setupEmail` too, so billing's events and bounces
  reach your `onEvent`; without it they are recorded on the backend's own trail.

## The free plan is a subscription, and prices come in the visitor's currency

A catalog plan priced `{ month: 0 }` is now a real free plan: every workspace the auth layer
makes (every account, with `billTo: 'user'`) is subscribed to it at the provider, so its credits, features
and quotas are granted like a paid plan's, a checkout of a paid plan upgrades it in place, and a
paid plan that ends puts the workspace back on it. A plan or a pack can also be priced per
currency, and the pricing page and checkout follow the visitor's. [The free plan](/docs/build/billing/catalog#the-free-plan)
and [Currencies](/docs/build/billing/catalog#currencies) have the details.

| Gone | Instead |
|---|---|
| `useBilling().subscription` `null` on the free plan | The free plan's subscription, marked `free: true`, its `productKey` the free plan's key; `useBilling().isFree` stays `true` on it, `isSubscribed` `false`, and `useBilling().plan` names it |
| `useBilling().status` `null` on the free plan | The free subscription's status, `active`; `null` only without any subscription |
| `useBilling().subscriptions` listing paid plans only | The free plan's subscription among them, marked `free: true` (and in `getCurrentSubscription`'s array with `multipleSubscriptions`): filter on `!free` for the paid plans |
| `getOrders` listing every order | The subscription orders that charged nothing (a free plan's cycle, a trial's start, a cycle a full discount brought to nothing) left out of the history: `useOrders` and `<BillingHistory>` list charges. The provider's `total` and `pageCount` still count them, so a page may list fewer than `limit` |
| `billing.functions` without the free plan's action | `startFreePlan` among them, exported from `backend/billing.ts`: the workpool runs `billing:startFreePlan` by that name |

**What to do**

- Export it from `backend/billing.ts`, beside `syncProducts`:
  `export const { …, syncProducts, startFreePlan } = billing.functions`. `npx nuxt-backend doctor`
  names it while it is missing; with no free plan in the catalog it does nothing.
- Code that reads `subscription === null` (or `!subscription`) as "on the free plan" reads
  `isFree` instead, and code that shows "a plan" for any subscription reads `isSubscribed`, or
  `plan` for its key.
- To give your workspaces a free plan, add one to `billing.catalog.ts` and run
  `npx nuxt-backend billing sync`; then put the workspaces that exist on it once per deployment:
  `npx convex run billing:startFreePlan '{}'` (`--prod` for production). A workspace your own
  code writes outside the auth layer (a migration, an adapter write) is not announced: call
  `billing.startFreePlan(ctx, id)` for it, or run the backfill again.
- Code that counts or walks `useBilling().subscriptions` to mean paid plans filters on `!free`.
- A new workspace is a provider customer from the start, and `/organization/create` spends the
  new `workspaceCreate` limit (five at once, then ten an hour per member).
- A test that answers `billing:getPricing` may answer `currency` and `currencies` beside `plans`
  and `packs`, and a plan `free: true`; the query now takes an optional `currency`.

## Emails share one layout, and speak their recipient's language

Every email the package sends renders into one layout: the brand's header (a logo, or the name),
the message in a card, a footer that says who sent it, light and dark. The brand is named after
the display name of `EMAIL_FROM` before the host of `SITE_URL`, and Better Auth's `appName`,
which a passkey prompt shows, follows it. Each account has a language, `user.locale`, set at
sign-up from the request (`useLoginFlow` sends the app's `@nuxtjs/i18n` locale) and on every
language switch, and each email is written in its recipient's language when
`setupEmail({ messages })` has it. [Send email in each reader's language](/docs/build/email/templates/languages) has the details.

| Gone | Instead |
|---|---|
| The packaged emails' HTML as one `<div>`, signed "— Acme" | A whole document in the shared layout, its footer "Sent by Acme"; the text ends with "— Sent by Acme" |
| The brand named after the `SITE_URL` host when `setupEmail` names none | `brand.name`, else the display name of `EMAIL_FROM`, else the host; `brand.logo` shows in the header |
| Better Auth's own `appName` | The same name as the emails', unless `authOptions.appName` sets one |
| `EmailRenderContext` as `{ t, locale, brand }`, `locale` always `'en'` | `{ t, locale, brand, link }`: `locale` and `t` in the recipient's language, `link(url)` for a localized link |

**What to do**

- Look at your emails once: the DevTools **Email** tab renders every one of them, light and dark.
  A test that compares a packaged email's `html` or `text` with a fixed string needs the new
  one; `renderEmail` from `nuxt-backend/test-utils` renders it without a deployment. An
  override that spreads `byDefault(data)` keeps the layout; one that writes its own `html`
  keeps its own.
- Give the email the name you want: a display name in `EMAIL_FROM` (`Acme <hello@acme.com>`),
  or `setupEmail(components, { brand: { name, logo } })`, the same as `appConfig.backend.brand`.
- Running `defineEmailSequence` runs carry on: an email a run sent stays sent, and its next ones
  go out in the layout. From now on a step's copy, a translation or the brand can change under a
  running run; adding, dropping or moving a step still fails it, as
  [Change a sequence that is running](/docs/build/growth/engage/lifecycle-emails#change-a-sequence-that-is-running) says.
- Add the DevTools tab's functions to `backend/email.ts`:
  `export const { previewEmails, sendEmailPreview } = email.devtools`.
- To write your emails in other languages, pass your i18n files:
  `setupEmail(components, { messages: { de, fr } })`.
- A hand-built `EmailRenderContext` (in a test) needs `link`, a function from a URL to a URL.

## An impersonation lasts thirty minutes, and never visits an administrator

An administrator acts inside an account only by impersonating it, and the visit is now short and
never of another administrator. Better Auth's admin plugin kept an impersonation an hour, and let an
administrator impersonate another one where the app's roles granted `impersonate-admins` or set
`allowImpersonatingAdmins`. A visit now lasts at most thirty minutes
(`IMPERSONATION_SESSION_SECONDS` in `nuxt-backend/admin`), and the auth layer refuses an
impersonation of any account that holds an administrator role, the caller's own included and
whoever asks, as `forbidden` with reason `admin_target`. The admin console is new beside it: `/admin`
(`pages.admin`), `backend/admin.ts` with `setupAdmin`, `useAdmin`, `<AdminUsers>`,
`<AdminWorkspaces>` and `<ImpersonationBanner>` ([Run the admin console](/docs/build/auth/admin)).

| Gone | Instead |
|---|---|
| `admin.impersonationSessionDuration` longer than thirty minutes, and Better Auth's default hour | At most thirty minutes: a longer `impersonationSessionDuration` is held to `IMPERSONATION_SESSION_SECONDS`, a shorter one kept |
| A role granting `impersonate-admins` letting one administrator impersonate another | Nothing: an administrator's account is never impersonated. Help an administrator from your own account |
| `allowImpersonatingAdmins: true` | Nothing: it no longer lets an administrator's account be impersonated |
| Better Auth's `YOU_CANNOT_IMPERSONATE_ADMINS` reading as `forbidden` with reason `you_cannot_impersonate_admins` | `forbidden` with reason `admin_target`, as the package's own refusal reads |

**What to do**

- Drop `impersonate-admins` from your roles and `allowImpersonatingAdmins` from `setupAuth({ admin })`,
  and shorten `impersonationSessionDuration` if you set it longer: none of them changes anything now.
- Search the app for `you_cannot_impersonate_admins` and read `admin_target` instead.
- An app page at `/admin` keeps its path, and the console mounts nowhere: move the console with
  `backend.pages.admin` to mount it beside yours.
- Run `npx nuxt-backend doctor --fix`: it adds `backend/admin.ts` to an older scaffold, and asks for
  the first administrator's address when the deployment has none.

## Feature gates match one key, and the server enforces them

`useFeatures().has(feature)` and `<FeatureBoundary feature>` matched a granted benefit by its
benefit id, its grant id, its provider type or any value in its metadata, so `has('nuxt-backend')`
was true for every benefit `billing sync` made. A gate now knows a benefit by one name: the `key`
in its metadata (the catalog key), else its benefit id when it has no key. The server makes the
same match: `billing.requireFeature(ctx, key)`, `billing.hasFeature(ctx, key)` and the new
`withFeature(key)` tier of `createFunctions` read the entitlement cache and refuse with the new
`feature_required` code, whose `plans` are the catalog plans on sale that include the feature.
`<UpgradePrompt>` offers those plans, and `getPricing` lists each plan's `featureKeys`.
[Feature gating](/docs/build/billing/subscriptions/feature-gating) has the details.

| Gone | Instead |
|---|---|
| `useFeatures().has()` matching a grant id, a provider type (`feature_flag`, `meter_credit`) or any metadata value | The benefit's `key` metadata, else its benefit id for a benefit without one: `has('premium')` for the catalog's `premium` feature |
| `<FeatureBoundary feature>` matching the same way | The same one name as `useFeatures().has()` |
| A function gated by reading `getFeatures` itself and throwing `forbidden` | `await billing.requireFeature(ctx, 'premium')`, or a function built with `withFeature('premium')`: refused with `feature_required` and the `plans` that include it |
| A `PricedPlan` without `featureKeys`, in a test's `getPricing` answer | `featureKeys` beside `features`: the plan's benefit keys, or `[]` |

**What to do**

- Search the app for `has(` on `useFeatures()` and `<FeatureBoundary feature=`: a check by a grant
  id, a type or a metadata value other than `key` now says no. Gate on the catalog key, or set a
  `key` in the metadata of a benefit made in the dashboard.
- Enforce each gated function on the server. A new scaffold ships the tier; `doctor --fix` adds
  files, never lines to yours, so add it by hand. In `backend/functions.ts`, export the options
  your tiers take as `functionOptions` (`export const functionOptions = {} satisfies
  CreateFunctionsOptions`, passed to `createFunctions` there). In `backend/billing.ts`, after
  `setupBilling`: `export const { withFeature } = createFunctions({ query, mutation, action },
  authorization, { ...functionOptions, billing })`. Build the function with
  `withFeature('premium')`.
- Give each plan of a test's `getPricing` answer its `featureKeys`.

## Plans have a monthly and a yearly price, and pricing renders on the server

A plan in `billing.catalog.ts` had one `interval` and one `price`. It now has `prices: { month, year }`,
and `billing sync` makes one product per price, tagged with the plan's key and the interval: the
monthly one keeps the plan's key in the generated map, the yearly one is `<plan>:year`. A plan's
`credits` are a month's allowance, granted twelve-fold once a year on the yearly price. A plan
marked `retired: true` is archived: its subscribers keep it, nobody new buys it. The sync now
pushes a plan's trial when it changed, and reports a credit benefit whose units or rollover moved.
`<PricingTable>` and `/pricing` read one new public query, `getPricing`, through `usePricing()`,
rendered on the server, with a monthly / yearly switch, packs compared per credit and a contact
card; the credits a card shows come from the live benefit, so app config keeps only the copy. A
switch from a yearly price to a monthly one waits for the paid year's end.
[Customize the pricing page](/docs/build/billing/pricing-page) and
[Define and sync your catalog](/docs/build/billing/catalog) have the details.

| Gone | Instead |
|---|---|
| `interval: 'month', price: 2900` on a catalog plan (`CatalogPlan.interval`, `CatalogPlan.price`) | `prices: { month: 2900 }` (`CatalogPlan.prices`), and a yearly price beside it if you sell one: `prices: { month: 2900, year: 29000 }`. `billing sync` refuses the old shape and prints the line to write. `CatalogPlan` has `prices` and `retired` |
| A plan's `credits.units` as the grant of each cycle it is billed at, a year's on a yearly plan (`CatalogPlan.credits`) | A month's allowance, granted twelve-fold on the yearly price. A plan billed yearly keeps its grant as `units: { year: <units> }`; `billing sync` checks the benefit its product carries against it and reports drift, never a second benefit |
| `products.<plan>` naming a plan billed yearly, in `billing.generated.ts` | `products['<plan>:year']`: `products.<plan>` names a plan's monthly price only, and `plans.<plan>` holds both. `useBilling().products` and the generated `catalog` read by key follow the same keys |
| `credits` in `appConfig.backend.billing.plans` and `packs` (`PricingPlan.credits`, `CreditPack.credits`) | Nothing to write: a card shows the credits of the live benefit, per cycle at its interval. `appConfig.backend.billing.contact` is new |
| `<PricingTable>`'s `period` prop and the `pricing.period` label | The `pricing.period.month` and `pricing.period.year` labels |
| The `pricing.credits` label | `pricing.credits.month` and `pricing.credits.year` |
| `<PricingTable>` reading names and prices from `useBilling().products` | `usePricing()`, from the scaffolded `getPricing`. A slot's `ResolvedPlan` has `offer`, `interval`, `priceAt` and `credits` where `product` was; `ResolvedPack` has `offer` and its per-credit figures. `useBilling().products` itself is unchanged |
| A sign-in link back to the page's path alone | The page's whole address, `useRoute().fullPath`: a campaign link's discount and UTM survive the sign-in, and `<PricingTable>` passes them to checkout through `useCampaign()` |
| `<CreditsLowBanner>` without `pack` always linking to the pricing page | For a member who manages billing, a `<button data-pack>` (`credits.topUpPack`, "Buy {pack}") that buys the smallest pack covering the shortfall: `need`, else the threshold. The link stays for everyone else, and while the pricing loads |
| `changePlan` and `updateSubscription` from a yearly price to a monthly one switching at once | The switch waits for the paid year's end (`next_period`), whatever `proration` says, and reads back as `pendingChange`: the yearly price granted the year's credits up front |
| `useCredits().expiresAtCycleEnd` `true` when a plan's allowance lapses though a pack's credits on the meter keep | `true` only when every benefit crediting the meter lapses |
| `billing sync` never writing to a product it found | It pushes a changed trial to a plan's products and archives a retired plan's; prices and grants are still reported as drift, never rewritten |

**What to do**

- Write each plan's `interval` and `price` as `prices: { <interval>: <price> }` in
  `backend/billing.catalog.ts`, then run `npx nuxt-backend billing sync`: it finds the products
  it made before (by key and interval), creates any yearly ones, and writes `plans` into the id map.
- For a plan billed yearly, write its `credits.units` as `{ year: <units> }`, and search the app
  for its key in `products`: after the sync it is `products['<plan>:year']`.
- Export `getPricing` from `backend/billing.ts` with the rest of `billing.api`;
  `npx nuxt-backend doctor` names it until you do.
- Drop `credits` from `appConfig.backend.billing.plans` and `packs`, and move overrides of
  `labels.pricing.period` and `labels.pricing.credits` to their `month` and `year` keys.
- A test that answers `billing:getConfiguredProducts` for `<PricingTable>` answers
  `billing:getPricing` instead ([Testing](/docs/develop/testing/pages#write-a-test)).

## Sensitive actions ask for a recent sign-in

Saving or removing a passkey, asking to delete the account, deleting a workspace, inviting,
removing or changing the role of a workspace member, and an administrator's
writes now take a sign-in from the last ten minutes. An older session is refused with `reauthentication_required` before anything happens;
the person confirms it is them with a passkey or a code to their own address, which opens a new
session (the old one is signed out, the active workspace kept), and the action runs again.
`<SecuritySettings>` and the `/security` page do this on their own.
[Require a recent sign-in](/docs/build/auth/access/step-up) lists every action that asks.

| Gone | Instead |
|---|---|
| Better Auth's `session.freshAge` of a day, or the one in your `authOptions.session` | Ten minutes, `RECENT_SIGN_IN_SECONDS` from `nuxt-backend/authorization`, which the package sets: Better Auth's own checks (the passkey routes, its session list `/list-sessions`, which `useSessions()` replaces at any age) and every row of the sensitive-action table count in it |
| `/delete-user`, `/organization/delete`, `/organization/invite-member`, `/organization/remove-member`, `/organization/update-member-role`, `/passkey/delete-passkey`, `/unlink-account`, `/link-social`, `/change-password` and the administrator writes (`/admin/create-user`, `/admin/update-user`, `/admin/set-role`, `/admin/ban-user`, `/admin/unban-user`, `/admin/impersonate-user`, `/admin/set-user-password`, `/admin/remove-user`) taking any session | A sign-in from the last ten minutes, or `reauthentication_required` (403) |
| The `admin` tier's mutations and actions taking any session | A recent sign-in by default (`recentSignIn: false` on a routine one). `refundOrder` and the scaffolded `sendAsAdmin` ask too |
| Better Auth's `SESSION_NOT_FRESH` read as `forbidden` with reason `session_not_fresh`, and its `SESSION_EXPIRED` read as no code | Both read as `reauthentication_required` |

**What to do**

- Mount `<ReauthenticateDialog />` once, in `app.vue` or your layout, and wrap your own calls to
  the routes and admin functions above in `useReauthentication().withReauthentication(...)`: it
  asks the person to confirm when the server refuses, then runs the call once more. That includes
  `useOrganization().invite`. With no dialog mounted, the call is refused as it came.
- An admin function that is routine and should not ask says `recentSignIn: false` beside its
  `args`.
- Code that compared `getBackendError(error).data.reason` with `'session_not_fresh'` checks
  `code === 'reauthentication_required'` instead.
- Tests that call these as a person: `asUser` signs in just now, so they pass as before. A
  hand-made identity needs a `sessionId` and an `authTime` (epoch milliseconds) claim.
- Nothing for revoking sessions: signing devices out never asks.

## The billing section follows the subscription, and cancelling takes one step

The billing section of `<WorkspaceSettings>`, and so the ready-made `/settings` page, showed
the plan's name, whether it renews, and a "Cancel plan" button that cancelled at once. It now

plan grants, and cancelling takes one step, there and on `<PricingTable>`'s current plan: what

has the states.

  `[data-pricing="confirm-cancel"]` after it.
- Code that retried a refused cancellation on `unavailable` reads `invalid_input` and its
  `reason` instead: there is nothing to retry.
- Nothing more for a return URL: a `checkout_id={CHECKOUT_ID}` of your own stays on the

## Passkey sign-ins spend a limit, and the sign-in form opens on the last way in

Every passkey sign-in starts with a challenge the server stores, and the route that issues it had
no limit. It now spends `passkeySignIn` per client address and `passkeySignInGlobal` for the
deployment. Every sign-in records how it was made, on the account (`user.lastLoginMethod`) and in
a cookie, and `<AuthForm>` reads it: it opens on the email step after a code sign-in, marks the
last method "Last used", and offers saved passkeys in the email field's autofill, whose
`autocomplete` is now `username webauthn`.

**What to do**

- If you passed `rateLimiter` from a limiter of your own that lists limits by name, add
  `passkeySignIn` and `passkeySignInGlobal`, the two names `AuthRateLimitName` gained; one built
  with `setupRateLimiter` over `DEFAULT_LIMITS` already has them. Without them, a passkey sign-in
  fails.
- An end-to-end test that clicks "Continue with email code" right after opening `/login` finds
  the email step already open once the browser signed in by code: go straight to the email field,
  or clear the `better-auth.last_used_login_method` cookie first.
- If you replaced `<AuthForm>`'s `request-code` slot, set `autocomplete="username webauthn"` on
  your email input, so the browser offers saved passkeys there.
- Every sign-in now writes `user.lastLoginMethod`: your `databaseHooks.user.update` hooks and
  user-update triggers run on every sign-in, and `user.updatedAt` moves to its time. If something
  of yours syncs on a user update (a CRM, a copy of the user) or shows `updatedAt` as "profile
  changed", skip the writes whose only change is `lastLoginMethod`, or pass Better Auth's
  `lastLoginMethod` with `storeInDatabase: false` and `customResolveMethod: resolveSignInMethod`
  from `nuxt-backend/auth`: the "Last used" mark then reads the cookie alone.
- Nothing else: the account's new field arrives with the component, and a page of your own on
  `useLoginFlow()` behaves as before until you pass `autofill` or `preferLastMethod`.

[Passkey autofill](/docs/build/auth/sign-in#passkey-autofill) and
[Rate limiting](/docs/ship/security/rate-limits#privileged-routes) describe both.

## The backend cleans up after itself, and secret emails leave no record

Sessions, codes, AI request records and email records used to stay
until you deleted them. The `backend` component now runs its own maintenance every hour, in
batches, and prunes the email records itself, by windows `setupEmail({ retention })` can change.
The scaffold gains `backend/crons.ts`, on `defineBackendCrons`. Sign-in codes and
account-deletion links go out through `email.sendSecret` and leave no email record: their
`sendTemplate` resolves with `null`, and they have no status.

**What to do**

- Run `npx nuxt-backend doctor --fix`. It writes `backend/crons.ts`, and leaves the rest of
  your backend as it is.
- Drop a cron of your own that calls `email.cleanup` or `email.cleanupAbandoned`: the component
  prunes the records now. To keep them longer or shorter than the defaults, pass
  `setupEmail(components, { retention: { finalizedMs, abandonedMs } })`
  ([How long records are kept](/docs/build/email/sending#how-long-records-are-kept)). Jobs for your own
  tables can stay as they are, or move onto `defineBackendCrons`
  ([Schedule jobs](/docs/build/data/jobs/scheduled#your-own-jobs)).
- On a deployment with data, the first pass deletes everything already past its window, a batch
  at a time. [Limits and retention](/docs/reference/backend/limits#windows-and-lifetimes) lists
  the windows.
- Code that read the id `sendTemplate` returned for an `otp` or `deleteAccount` email gets
  `null` now; nothing in the package reads it.
- A hand-written `components` object for `setupEmail` (in a test) needs
  `backend.email.sendSecret`, which secret emails go through. The generated one has it.

## Billing is managed by a workspace's owner and admins

Billing trusted the session token: its active workspace for every read, spend and AI call, and
its role for the admin functions. A member you removed, or an admin you demoted, kept both until
the token expired, and any member of a workspace could buy, change the plan, open the portal and
read its invoices. Every billing call now reads the account and the caller's membership
and role fresh; the workspace's owner and admins manage its billing, and other members read it
and spend its credits. An administrator impersonating someone may read but not spend or change
billing. [Decide who manages billing](/docs/build/billing/setup#who-may-buy-for-a-workspace) has
the whole table.

| Gone | Instead |
|---|---|
| Any member of a workspace checking out, opening the portal, changing, cancelling, pausing or resuming the plan, and reading orders and invoices | Its owner and admins only; another member is `forbidden` (reason `not_billing_manager`). The new scaffolded `getBillingAccess` query says which, behind `useBilling().canManage`; `<PricingTable>`, `<WorkspaceSettings>`, `<BillingCheckoutLink>` and `<BillingPortalLink>` show a non-manager no buttons (`labels.pricing.managed` is the note in their place) |
| A removed member, or an account banned since its token was minted, keeping the workspace's plan, credits, usage and metered AI until the token expired | Refused on the next call: a reactive read answers `null`, an action or a spend is `forbidden` (reason `not_member` or `banned`) |
| An administrator impersonating someone checking out, opening the portal, changing the plan, spending credits, buying or claiming a gift, or signing their devices out through `revokeSession` | `forbidden` (reason `impersonating`). Reads still work |
| An impersonated session reaching every auth route but the few the package refused | An allowlist: reads, the Convex token, signing out and `/admin/stop-impersonating`, the profile's name and image (no other field of the user), switching, creating or renaming a workspace, withdrawing or declining an invitation. Every other route is `forbidden` (reason `impersonating`): signing devices out, leaving, joining or deleting a workspace, removing a member, a sign-in method, the password, the provider token routes, every other `/admin/*` route, and any route a plugin of yours adds. [Roles and permissions](/docs/build/auth/admin/impersonation) lists them |
| A ban taking up to the token's 15 minutes to reach a write | The mutations and actions of every `createFunctions` tier, `updateProfile`, `revokeSession`, every billing call and the gift functions read the account fresh: a banned account is `forbidden` (reason `banned`), a deleted one `unauthenticated`. Queries of the `authed` and `withRole` tiers still read the token's claims |
| `refundOrder`, `getWebhookDeliveries` and the `admin` builder of `createFunctions` reading the role from the token | The role read fresh from the user table: a demoted admin is refused at once. `refundOrder` and the `admin` builder's mutations and actions refuse impersonated sessions too, and a signed-out caller is `unauthenticated` |
| `requireOrganization` reading the active workspace from the token alone | A fresh member read, like `requireMember`: someone removed is `forbidden` (reason `not_member`). It takes the same `impersonation`, `scope` and `reread` options |
| `setupAi` resolving the paying workspace with `billing.resolveEntity` | `billing.requireEntity(ctx, rule)`, which your own functions can call with the access they need. A hand-built `billing` object handed to `setupAi` in a test needs `requireEntity` |
| A `resolveEntity` of your own returning something other than a workspace, with the default `billTo: 'organization'` | Refused as `not_member`, since the caller is no member of it: set `billTo: 'user'`, where your resolver decides who acts for the entity. A checking call hands it the rule as a second argument (a gift checkout or claim asks for `access: 'manage'`), so it can refuse a caller who may only read; a refusal it throws is kept, and a read answers `null` for it. Treat a missing rule as the strictest case |
| `getOrders`, `getInvoiceUrl` and `getUsageHistory` answering a signed-out caller `null` when billing is not configured | `unauthenticated`, configured or not |
| A workspace admin's portal refused as `not_billing_manager` | `forbidden` with the new reason `provider_owner_only`: the provider lists only the owner as a member who manages the customer for now |
| `BillingComponents` without the auth tables | `setupBilling` reads accounts, members and roles through `components.backend.adapter`, which the generated `components` already has |

**What to do**

- Export `getBillingAccess` from `backend/billing.ts` beside `getCredits`;
  `npx nuxt-backend doctor` names it until you do.
- Nothing more, where only a workspace's owner and admins buy for it. Make anyone else who
  should buy for a workspace one of its admins.
- Handle `not_billing_manager`, `not_member`, `banned` and `impersonating` where you show a
  refusal.
- Where your own functions decided who may act for the billing entity with
  `billing.resolveEntity`, call `billing.requireEntity(ctx, { access: 'manage' })` (or
  `'member'`) instead: `resolveEntity` checks nobody.
- A hand-built `components` object in a test of `setupBilling` needs
  `backend.adapter.findOne` (answering the user and member reads), and a hand-built `billing`
  for `setupAi` needs `requireEntity`.

  `billing.customer_mapping_shared`: on a sandbox, start from a fresh organization, or delete
  those customers in the provider's dashboard and clear the deployment's `customers` table of the
  billing provider's component and the `backend` component's `billingEntitlements` cache.
- Issue a new organization access token with the `members:write` and `customer_sessions:write`
  scopes besides the ones it has, and turn on customer members (the member model) for the
  organization. `npx nuxt-backend doctor` reports both as `billing-team-customers`, and each pack's
  gift product as `billing-gift-twins`.
- Run `npx nuxt-backend billing sync`, so each pack gets its private gift product.
- Replace `useGifts({ autoClaim })` with `useGifts()` and a claim button (or `<GiftClaimBanner>`
  without `auto-claim`), and pass the gift's id to `claim`.
- Drop the base module's props from `<BillingCheckoutLink>` and `<BillingPortalLink>`; listen for
  `error` to show a refusal.
- Read `item` instead of `message` and `purchaserEmail` in a `gift` template override.

## Checkout sells only your catalog, and returns only to your site

A checkout, a plan change and a gift used to take what the browser sent: any product the
provider sells, a trial of any length, a discount by id, metadata keys the package reads back,
and any URL to send the buyer to afterwards. The server decides each of them now, and refuses
the rest as `invalid_input` with the field it refuses. [What the server
decides](/docs/build/billing/subscriptions/checkout#what-the-server-decides) has the rules:

| Gone | Instead |
|---|---|
| `generateCheckoutLink` with any product id | Products of your catalog only (`billing.generated.ts`, or `setupBilling({ products })`); `updateSubscription` and `changePlan` too |
| A `successUrl`, `origin` or portal `returnUrl` on any site | `SITE_URL`'s origin, or one listed in the new `setupBilling({ trustedOrigins })` |
| `trialInterval` and `trialIntervalCount` from the browser (`checkout(id, { trialInterval })`) | The plan's own trial (the catalog's `trial`); a different one, 1 to 30 days in days or weeks, or none (`trial: false`), from server code through the new `billing.checkout(ctx, options)` |
| `discountId` from the browser | `discountCode` for a code a customer or a campaign link carries; a discount by id through `billing.checkout(ctx, { discountId })` |
| Metadata with any key | Your own keys; `userId`, `gift`, `giftId`, `recipientEmail`, `purchaserUserId`, `giftRecipient` and `utm_*` are the package's, at most 20 keys |
| Campaign UTM parameters as hand-made metadata | `checkout(id, { utm: { source, medium, campaign, term, content } })`, stored as `utm_*` metadata |
| `gift(productIds, …)` on `useBilling` and `useCredits`, for a plan or a pack | `useGifts().send(item, …)`: a pack by its catalog key (`'credits500'`), or a plan as a one-time pass with its `months` (`send('pro', { months: 3, … })`), never a plan that renews on the purchaser's card. `giftCheckout` takes `pack`, or `plan` and `months`, in place of `productIds` |
| A plan change to any product, a credit pack included | A recurring plan of the catalog only |
| A webhook resolving the billing entity from an order's or a subscription's `userId` metadata | Only the customer's own metadata (`customer.*` events, or the customer on the payload), then the synced cache: checkout metadata is the buyer's |
| `gift(...)` with a one-time product the catalog does not list as a pack | Run `billing sync`: it writes the catalog's pack keys into `billing.generated.ts` as `packs`, and only those gift |
| `listAllProducts`, `changeCurrentSubscription` and `cancelCurrentSubscription` on `billing.api` | Gone: `getConfiguredProducts` is the price list, and `updateSubscription` and `cancelSubscription` (`changePlan`, `cancel`) change and cancel. `useBilling` no longer falls back to the removed pair |

**What to do**

- Remove `listAllProducts`, `changeCurrentSubscription` and `cancelCurrentSubscription` from
  the `billing.api` exports in `backend/billing.ts`.
- Run `npx nuxt-backend billing sync` again, so the catalog has your products and lists its packs,
  and add any other origin the app runs on to `setupBilling({ trustedOrigins })`, with its scheme.
- Move a trial you set in the browser to the plan's `trial` in `billing.catalog.ts`, or to an
  action of your own that calls `billing.checkout(ctx, { trial })`. Do the same with a
  `discountId`, or pass the code as `discountCode`.
- Rename metadata keys that clash with the reserved ones, and pass UTM parameters as `utm`.
- Call `gift` with the pack's catalog key instead of its product id.

## Refusals carry a code, and survive production

Every refusal a person can meet now has a stable code. A package function throws it as a
`ConvexError` whose data is `{ code, ...fields }`, which Convex sends to the client in production.
Most refusals used to be plain `Error`s, which production shows as "Server Error". An auth route
puts the same code and fields in its error body. `getBackendError(error)`, auto-imported and also
exported from `nuxt-backend/functions`, reads either one, and `backendError()` throws one from
your own functions. The English sentences stay as each error's `message` for the log.
[Errors](/docs/reference/backend/errors) lists the codes:

| Gone | Instead |
|---|---|
| A string in `error.data` from `requireUser`, `requireRole`, `requirePermission`, `requireOrganization`, `requireMember` and `setUserRole` (`'Unauthenticated'`, `'Forbidden: …'`, `'No active organization …'`) | `unauthenticated`, `forbidden` with a `reason` (`banned`, `role`, `permission`, `not_member`, `workspace_role`), `no_workspace`, and `invalid_input` for `setUserRole` |
| A string in `error.data` from checkout and the gift claim (one email, another workspace), `canGift` and `revokeSession` | `forbidden` (reason `customer_taken` or `gift_refused`) and `invalid_input` (field `sessionId`), with the sentence in `data.message`; `revokeSession` signed out is `unauthenticated` |
| Plain `Error`s from billing, credits, gifts, `setupAi` and `updateProfile`: signed out, no workspace, admin-only, not the caller's order or subscription, no subscription, missing `BILLING_ACCESS_TOKEN`, a balance that cannot cover a spend | `unauthenticated`, `no_workspace`, `forbidden` (`admin_only`, `not_owner`, `not_recipient`, `no_email`), `invalid_input`, `unavailable` (`not_configured`), `not_ready` (`no_customer`, `not_synced`: nothing a retry changes), `insufficient_credits` with `balance` and `need`. A signed-out caller is `unauthenticated` before anything says billing is not configured, `spendCredits` and `refundCredits` included |
| `getInvoiceUrl` for an order id the provider does not know: the provider's error | `forbidden` (reason `not_owner`), the same as another account's order |
| "Too many …", "Rate limit reached" and "Credit budget reached" `Error`s from the `billingSync`, `ai` and `aiBudget` limits | The limiter's own error (`throws: true`), read as `rate_limited` with `limit` and `retryAfter` |
| The provider's own error, body included, from `syncEntitlements`, `billing.getCustomerState`, `generateCustomerPortalUrl`, `changeCurrentSubscription`, `cancelCurrentSubscription`, `discounts.*`, a usage report and the email marketing calls | `unavailable` with reason `provider_refused`. The provider's words go to the deployment log only |
| `generateCustomerPortalUrl`, `changeCurrentSubscription` and `cancelCurrentSubscription` on `billing.api` from the provider's client | The package's own, with the same arguments: the portal checks the token and spends one token of the `billingSync` limit, like every live provider call, and the two subscription actions run `updateSubscription` and `cancelSubscription` and resolve `null` |
| `cancelCurrentSubscription` refused a `past_due` or `paused` subscription ("Subscription is not active") | It cancels any running subscription, as `cancelSubscription` does |
| `changeCurrentSubscription` and `cancelCurrentSubscription` threw the provider client's own error when the entity held several running subscriptions | `invalid_input` (field `subscriptionId`): call `updateSubscription` or `cancelSubscription` with the `subscriptionId` |
| `changeCurrentSubscription` to the current product refused with a plain `Error`; `updateSubscription` sent it to the provider | Both refuse with `invalid_input` (field `productId`) before the provider is asked |
| Auth route refusals with `{ message, retryAfter? }` in the body | The same, plus `code` and its fields: `rate_limited` with `limit`, `forbidden` with `reason` (`sign_in_refused`, `impersonating`, …), `unauthenticated`, `invalid_input` |
| A code or an invitation refused as undeliverable with `400` | `503`, `unavailable` with service `email` and reason `test_mode` or `unconfigured` |
| `useAiStream().start()` refused, with `status` left at `'pending'` | `status` ends in `'error'`, and `error` holds the refusal |

**What to do**

- Replace checks on `error.data` as a string, or on an error's `message`, with
  `getBackendError(error)`: branch on `code`, and show `message`.
- A rate limiter you pass to `setupBilling` or `setupAi` that is not `setupRateLimiter`'s
  is now called with `throws: true`. It may throw the limiter's `RateLimited` error or keep
  answering `{ ok: false }`; both refuse as `rate_limited`.
- In your own functions, throw `backendError(code, data)` from `nuxt-backend/functions` where you
  threw a `ConvexError` with a string, so one reader handles every refusal.

[Handle errors](/docs/build/data/read-write/errors) shows the reader and the thrower in use.

- Delete `export const { provider } = billing` from `backend/billing.ts`, as the scaffold no
  longer writes it.
- Rename the auto-imports, components and middleware in the table. `npx nuxi typecheck` names

  for the old names before you ship.
- If `billing.ts` passed `getUserInfo` or `currentUserId`, replace both with one
  `resolveEntity`. With `billTo: 'organization'`, the default, they were never consulted: delete
  them.
- `/billing/events` and `/email/events` answer as before, with one difference: the 1 MiB cap
  counts bytes, and a `Content-Length` over it is refused with `413` before the body is read. A
  refused delivery also leaves a `webhook.rejected` line in the deployment log, once per isolate

## One-time codes are checked per address, and the unused routes are off

A code now gets at most a few guesses per address an hour, and a new code replaces the one before
it. Codes are stored as a hash keyed by `AUTH_SECRET`. Routes the package never calls are off,
and so is password reset until you turn passwords on. An email change says so in its first code,
and once it goes through, the old address hears of it:

| Gone | Instead |
|---|---|
| `/email-otp/check-verification-otp` | Nothing: it answers 404. The code routes check a code as they consume it |
| `/send-verification-email`, `/verify-email`, `/change-email` | Nothing: they answer 404. Verification and an email change go by code |
| `/email-otp/request-password-reset`, `/forget-password/email-otp`, `/email-otp/reset-password` and `type: 'forget-password'` codes, on a passwordless app | Nothing: 404 and 400. They come back with `emailAndPassword.enabled` |
| `setupAuth` with `email` undefined, or with `integrations` | Nothing: both throw at setup, the first naming the import cycle that usually causes it |

**What to do**

- If you list or implement rate limits by name, add `emailOtpAttempt`; one built over
  `DEFAULT_LIMITS` already has it.
- A `canSignIn` that switches on `purpose` gets `'email-change'` too, for the new address of
  an email change.
- Codes minted before the upgrade stop verifying, and so do codes in flight when you rotate
  `AUTH_SECRET`: ask for a new one.
- The old address of an email change now gets the `emailChanged` notice; restyle it like any
  other template.

`useOrganization()`'s actions used to resolve the auth client's `{ data, error }` result, so a

| Gone | Instead |
|---|---|
| `const { error } = await invite({ email })`, and the same for `setActive`, `create`, `leave`, `acceptInvitation`, `declineInvitation` and `cancelInvitation` | `try { await invite({ email }) } catch (error) { … }`; on success each still resolves the client's result |

**What to do**

- Where you read `error` from one of these results, catch the rejection instead. A call you never

  leaves `email` undefined while `setupAuth` runs.
- In `backend/http.ts`, pass `billing`, `email` and `ai` beside `auth`.
- A preview page that read `emailTemplates` from `./auth` renders with `await email.render(name, data)`:
  `render` resolves, so a template may be `async`.

An email change no longer sends links: the person enters a code from the current address, then one
from the new address. Verification is a code too, so the verification email and its section are

| Gone | Instead |
|---|---|
| `setupAuth(components, query, { integrations: { rateLimiter, canSignIn, onUserCreated, onUserDeleted, email, emailTemplates } })` | The same keys at the top level: `setupAuth(components, query, { rateLimiter, … })` |

## The welcome email and both sign-in methods are always on

Every new account gets the packaged welcome email, and the sign-in form always offers a passkey
and an email code. The switches are gone:

| Gone | Instead |
|---|---|
| `setupAuth({ integrations: { welcomeEmail } })` | Nothing: restyle the welcome with the `welcome` template on `setupEmail` |
| `<AuthForm :passkeys>`, `<AuthForm :otp>` | Nothing: build your own page on `useLoginFlow()` for a different set of steps |
| `useLoginFlow({ offerPasskey })` | Nothing: after a code, the flow offers to save a passkey; `skipPasskey()` moves past it |

**What to do**

- Delete those keys and props. A leftover `:passkeys` or `:otp` on `<AuthForm>` no longer does
  anything but land on its root element as an attribute.
- A sign-in page of your own built on `useLoginFlow()` must handle the `passkey-offer` step (it was
  `add-passkey`, and so was `<AuthForm>`'s slot): render it, or call `skipPasskey()` when `step` reaches it. A flow left there never calls `onSuccess`, and
  the person, signed in already, stays on the page.
- If an onboarding sequence of yours sent its own welcome, drop that step: the packaged one
  always goes out. The scaffold's `onSignup` sequence now starts three days after sign-up.
- Mind the sequences already running when you deploy. The workflow component replays each run
  against your code and fails one whose steps changed under it when it next wakes
  ([Change a sequence that is running](/docs/build/growth/engage/lifecycle-emails#change-a-sequence-that-is-running)).
  Two changes here do that, and they need different handling:
  - **The upgrade itself.** `defineEmailSequence` now reads the account before each email of a
    run started with a `userId`, as the scaffold's `onSignup` is (a deleted account gets nothing,
    a changed address gets the email). Every such run that has already sent an email fails at its
    next wake, whatever you do with your own export. Let those runs finish before you upgrade,
    cancel them (`workflow.listByName` finds them, `workflow.cancel` stops each), or keep them
    on a copy of the old loop, with no account read, under the export name they were started on,
    and start new sign-ups on a new export:

    ```ts [backend/workflows.ts]
    // The runs started before the upgrade, on the loop they recorded
    export const onSignup = workflow.define({
      args: { userId: v.string(), email: v.string(), name: v.string() },
      handler: async (step, data) => {
        for (const [index, { after, email }] of oldSteps.entries()) {
          if (after > 0) await step.sleep(after, { name: `email-sequence-wait-${index}` })
          const message = email(data)
          if (message) await step.runMutation(components.backend.email.send, message)
        }
      },
    })
    // New sign-ups: start this one from onUserCreated
    export const onSignupV2 = defineEmailSequence(workflow, components, { args, steps })
    ```

    `oldSteps` is your steps array exactly as it was. The scaffold's own `onSignup` had a single
    step at sign-up, so its runs have all finished: this is for a sequence you extended.
  - **Dropping your welcome step.** A run without a `userId` that already sent it fails as well.
    Keep the old export as it was for those runs, and start new sign-ups on a new one
    (`onSignupV2`).

  Starting a cancelled run again sends every step again, the welcome included, so change its
  steps first.

[Sign in](/docs/build/auth/sign-in) and [Email sequences](/docs/build/growth/engage/lifecycle-emails) describe both.

| `getWebhookDeliveries` for any signed-in caller | Admins only, the role read fresh; anyone else reads `null`, and DevTools says so |
| `billing.api.getWebhookDeliveries` | `webhooks.api.getWebhookDeliveries`, re-exported from the scaffold's `backend/webhooks.ts` (`setupWebhooks`, from `nuxt-backend/admin`) beside `replayWebhookDelivery`, for the email log as much as the billing one. A `billing.ts` that still re-exports it from `billing.api` fails its type check; DevTools and the admin console read the new one |

**What to do**

- Delete those keys. Where you turned every page off, set `false` on each key instead; where you set
  `loginPath`, set `pages.login` to the same path. `css: false` still loads no package CSS.
- Where you passed a path to the backend (`basePath`, `invitationPath`, `keepPath`), set it in
  `nuxt.config` instead, then pass the generated `paths` on as the scaffold does:
  `defineBackendAuthConfig({ paths })`, `setupAuth(components, query, { paths, … })` and
  `setupAccount(components, { paths, … })`, with `import { paths } from './paths.generated'`.
  `npx nuxt-backend upgrade` writes the file; commit it ([The paths file](/docs/reference/configuration/module-options#the-paths-file)).
- If you imported a stylesheet from the package, drop the import. The module adds the tokens and
  each component's styles in the `nuxt-backend` cascade layer, which `@layer theme, base, reset, nuxt-backend;` puts after Tailwind's and before yours.
- If your CSS has a reset or element rules outside a cascade layer (`* { margin: 0 }`,
  `button { background: none }`), move them into `@layer reset { … }`, or import the file into it:
  `@import './reset.css' layer(reset);`. A rule outside any layer beats every layered one, so an
  unlayered reset strips the packaged buttons and inputs. Tailwind's own reset already sits in
  `base`.
- Every module page now carries route rules: none is prerendered, and the private ones are kept
  out of caches and indexes at their paths. A rule you set for the same path wins key by key. Keep
  an app-wide `swr`, `isr` or `cache` rule off them; the module warns at startup when one covers
  them ([Caches](/docs/build/ui/pages#caches)).
- A leftover 0.1 value (a page set to `true`, `backend.pages: false` or `loginPath`) now stops
  the build with an error that names each one and links here.
- Move `getWebhookDeliveries` from `backend/billing.ts` to a `backend/webhooks.ts` that re-exports
  `setupWebhooks(components).api` (`npx nuxt-backend upgrade` writes the file); DevTools and the admin
  console's Webhooks tab read it there.
- A page of yours that showed `getWebhookDeliveries` to everyone now gets `null` for non-admins.
  To show the log more widely, serve it from a query of your own over
  `components.backend.webhooks.listRecent`.

[Replace a page](/docs/build/ui/customize/parts#replace-a-page) and [Restyle with tokens](/docs/build/ui/customize/tokens) describe both.

## Workspaces and admin are always on

Every app gets workspaces (with a personal workspace per user) and roles. The switches that
turned them off are gone:

| Gone | Instead |
|---|---|
| `backend.workspaces` in `nuxt.config.ts`, and `runtimeConfig.public.backend.workspaces` | Nothing: the organization endpoints always exist |
| `setupAuth({ admin: false })`, `{ organization: false }` | Pass an options object to configure a plugin, or leave the key out |
| `organization: { personal: false }` | Every user gets a personal workspace on first sign-in |
| `setupAuth({ verbose })` | Nothing |

**What to do**

- Delete those keys from `nuxt.config.ts` and `backend/auth.ts`.
- If your app ran without workspaces, run `npx nuxt-backend doctor`: `listWorkspaces` and
  `listWorkspaceMembers` are part of the function contract again, so `backend/auth.ts` must
  re-export them.
- Then run `npx nuxt-backend upgrade`, and `npx nuxt-backend upgrade --prod --yes` after the
  production deploy. Its data migrations give each signed-in user without a workspace the
  personal one their sign-in would have made, and activate it on their live sessions, so nobody
  has to sign in again for it. Anyone else gets theirs at their next sign-in, after `canSignIn`.

[Workspaces](/docs/build/auth/workspaces) describes them.

## Local installation is gone

`installation: 'local'` copied the `backend` component into `backend/components/backend/` so an
app could change its schema. Every app now mounts the packaged component, which owns its schema. The
option, `init --installation`, the `schema` option of `setupAuth` and the six
`nuxt-backend/component/*` subpaths are gone.

**What to do**

- Back up the deployment first: `npx convex export --path backup.zip`.
- In `backend/convex.config.ts`, import the packaged component instead of the local one:

  ```ts [backend/convex.config.ts]
  import backend from 'nuxt-backend/convex.config'
  ```

- In `backend/auth.ts`, remove `schema: authSchema` from `setupAuth` and its import.
- Delete `backend/components/backend/`, and `installation` from the `backend` options in
  `nuxt.config.ts`.
- Remove `@convex-dev/better-auth` and `@convex-dev/resend` from your `package.json` unless your
  own code imports them; the package brings both.
- Run `npx nuxt-backend doctor`.

The packaged component mounts under the same name, `backend`, so the data in its tables stays where
it is. What you added to the component schema needs a new home first:

- **An extra table** becomes an app table in `backend/schema.ts`. Empty it in the component
  (`npx convex import --component backend --table <name> --replace -y empty.jsonl`, with an empty
  file), switch, then load its rows from the backup into the app table
  (`npx convex import --table <name> <file>`).
- **An extra field** on an auth table has no place in the packaged schema. Move the value to an app
  table keyed by the user id, then clear the field before you switch, or start a dev deployment
  fresh.

[Auth setup](/docs/build/auth/setup) lists what the packaged schema covers.

## The scaffolded `send` is internal

`api.email.send` in the scaffolded `backend/email.ts` was a public action that only checked for a
sign-in, so anyone who could sign in could send mail from your verified domain to any address. It
is an `internalAction` now, and the welcome step of the onboarding sequence sends plain text.

**What to do**

- Call `send` from your own server code: `ctx.runAction(internal.email.send, { to, subject, text })`
  from an action, a scheduled function, or `npx convex run email:send`. Take the address from data
  you trust: the signed-in user's own record, a workspace invitation, an order.
- If a person types the address (an admin tool), use the scaffold's `sendAsAdmin`, built with
  `admin.action`, or build your own the same way.
- If you kept your own `backend/email.ts`, make the same change: replace `action` with
  `internalAction` for any function that takes a recipient.

[Sending email](/docs/build/email/sending) shows the new scaffold.

## Sessions are listed and revoked by id

The device-session list on `/security` failed for anyone who signed in more than a day ago, because
Better Auth's own `/list-sessions` refuses an older session. The list now comes from two functions
`setupAuth` returns, which work for sessions of any age and never send a session token to the
browser.

**What to do**

- Re-export the two functions from `backend/auth.ts`:

  ```ts [backend/auth.ts]
  export const {
    // …the exports you already have
    listSessions,
    revokeSession,
  } = setupAuth(components, query, { /* … */ })
  ```

- In your own code, `useSessions().revoke(id)` takes a session id instead of a token, and each
  session is `{ id, userAgent, createdAt, updatedAt, expiresAt, current }` with dates as epoch
  milliseconds. The list is live, so `refresh()` and the `immediate` option are gone.
- A `<SecuritySettings>` listener on `session-revoked` receives the session id.

[Auth setup](/docs/build/auth/setup) lists every function `setupAuth` returns.
