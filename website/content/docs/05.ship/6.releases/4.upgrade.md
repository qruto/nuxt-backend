`0.2.0` is the first release of the package: `0.1.0` on npm was a throwaway test publish. So an app has nothing to migrate from, and no codemod rewrites its code. From `0.2.0` on, every release moves your app forward the same way:

```bash
npm install nuxt-backend@latest
npx nuxt-backend upgrade --dry-run   # what it would repair and migrate; nothing written
npx nuxt-backend upgrade             # the scaffold and the dev deployment's data
```

- **Scaffold.** It makes the repairs `npx nuxt-backend doctor --fix` makes: the scaffold files, mounts and routes the new version adds. The rest of `backend/` stays as it is.
- **Data.** It runs the package's own data migrations on the dev deployment, once that runs the new backend: start `npx nuxt-backend dev` once. Production's migrations run with its deploy, when that is `npx nuxt-backend deploy` or `deploy --build`; a deploy that runs `convex deploy` itself leaves them to `npx nuxt-backend upgrade --prod --yes` after it.

`upgrade` rewrites none of your code. A release that renames or removes a public name says so in the [changelog](/docs/ship/releases/changelog), with the edit to make, and keeps the old name working for at least one minor release ([Stability](/docs/ship/releases/stability#deprecation)). After the upgrade, run `npx nuxt-backend doctor`, which names any scaffolded function your `backend/` files no longer export, then your type check.

A release that renames, reshapes or removes a public name adds a section here, newest first, with the edit to make. The upgrade skill carries the same names in its rename map, so a coding agent finds the new name in the installed package.

An app built on a preview of `main` before `0.2.0` (`npm install https://pkg.pr.new/qruto/nuxt-backend@main`) makes each edit by hand, from the [Upgrade page as `0.2.1` published it](https://github.com/qruto/nuxt-backend/blob/v0.2.1/website/content/docs/05.ship/6.releases/4.upgrade.md). It lists every change between the previews, newest first: start at the first section newer than the build and work up.

## `billing sync` prices every product in the organization's currency, and attaches the benefits a product lacks

The provider now makes no product without a price in the organization's default presentment currency, whatever currency the catalog pins. 0.2 created every price in the catalog's `currency`, and a new product on an organization that defaults to another currency failed on the provider's raw refusal. 0.3 reads the organization's currency first and refuses, in one line before it creates anything, a catalog with a paid plan or pack that has no price in it. The free plan's product and a plan's pass are priced at nothing in it by the sync itself. And a plan's product the sync finds by its key no longer keeps only the benefits it was made with: the sync attaches the catalog's credit grant or feature it lacks, and the provider grants it to the product's current subscribers too. A pack's product is left as it is and reported as `drift`, since the provider would credit everyone who ever bought it.

**What to do**

- **A catalog priced in its pinned `currency` alone**, on an organization that defaults to another: add that currency to every paid plan's and pack's prices (`prices: { usd: { month: 1200 }, eur: { month: 1100 } }`), or change the organization's default currency in the provider dashboard. `npx nuxt-backend doctor` names each one ([`billing-currency`](/docs/reference/cli/diagnostics#billing-currency)).
- **A benefit attached to an existing product by hand**, or one you meant to leave off: run `npx nuxt-backend billing sync --dry-run` first. Each `would-attach` line is a benefit the sync attaches, and its subscribers are granted. A product that grants other credits on the same meter is reported as `drift` and left as it is ([`billing-plan-benefits`](/docs/reference/cli/diagnostics#billing-plan-benefits)).

## The Better Auth client loads on first use, and a failed server call names its function

The package now runs on `nuxt-convex-module` 0.14 (`nuxt-convex-module@^0.14.0`), which loads the Better Auth client the first time something needs it instead of with every page. A signed-in visitor gets it at startup, beside the page; a page a signed-out visitor only reads downloads none of it, and the starter's entry is about 11 kB (gzip) smaller. An app that reads the session with `useAuth()` and signs in through `useLoginFlow` or the packaged pages changes nothing.

- **An auth client module of your own** (`convex.betterAuth.authClient`) evaluates on first use: keep its top level to creating the client.
- **Code that imports the client from `nuxt-convex-module/better-auth/client`.** Until the client has loaded, `useBetterAuth().client` forwards: a call (`$fetch` included), a `use*` hook and a store's `listen` work as before, but a value read without a call, such as `$store.atoms` or a plugin's atom, is a stand-in. Read `useBetterAuth().client.$store` as `(await loadAuthClient()).$store` instead.
- **A test of your own against the real client** (`nuxt-backend/test-utils` loads its mock for you) that signs in and reads the session a `nextTick` later: `await loadAuthClient()` in a `beforeAll` first.
- **To load it at startup as before,** set `NUXT_PUBLIC_CONVEX_DEFER_AUTH_CLIENT=false`. A webpack or rspack build always does.
- **A failed `fetchQuery`, `fetchMutation` or `fetchAction` on the server** puts the function in front of its message, `[CONVEX Q(module:fn)] …`, as the browser client always has, and error reports now carry it. The error is the one that was thrown, with its class and `data`: code that compared a server failure's `message` reads `getBackendError(error)` instead.

## The upload field retries a failure, and prepares a file before it uploads

`<UploadField>` and `useUploadField` run on the base module's `useUploadQueue`, one file at a time. A refusal (your `claim` throwing `invalid_input`, `quota_exceeded`, …) leaves the field `refused`, and the picker asks for another file. A failure on the way leaves it `error` with a Try again button, which picks up where the file stopped: the claim alone once the file is stored, the transfer otherwise.

- **`useUploadField({ claim, prepare })`** and `<UploadField :prepare>` take a function that turns the picked file into what is sent (a photo shrunk or re-encoded in the browser). Drop a wrapper that did that before calling `pick`.
- **Markup of your own** from `useUploadField` gets `retry` and `bind.retry`, for its own Try again button, and the `error` slot's scope adds `refused` and `retry`.
- **Translations.** The `upload` label group adds `retry`; the package's own locales have it, and a locale of yours shows the English until you add it.

## Emails and notifications read the labels app config sets

0.2 worded the emails, a notification's email and its push from `setupEmail`'s messages alone: a label set in app config (`backend.labels`) changed the pages and the inbox, not what the backend sent, so an app wrote the same copy twice, once in app config and once in `messages`. 0.3 carries app config's labels to the backend as `labels.generated.ts`, a new scaffold file the module rewrites on every start, as it does `brand.generated.ts`, and `setupEmail` reads them before its messages, as the pages do ([Labels reach the backend](/docs/build/ui/customize/labels#labels-reach-the-backend)).

- **Pass the labels on.** `npx nuxt-backend upgrade` writes `backend/labels.generated.ts`, but never edits `backend/email.ts`: add `import { labels } from './labels.generated'`, and turn setupEmail({ paths, brand }) into setupEmail({ paths, brand, labels }). Then drop what your `messages` repeated from app config, and the copy file both imported, if that was all it was for. `doctor` warns while the file is missing or out of date (`labels-file`).
- **The `email` group joins app config.** `labels.email` rewords the package's emails like any other group.
- **The credit words say `{unit}`.** The `billing.credits_low` and `billing.credits_exhausted` notifications, the low-credits email, a received gift and the cancel flow name what the credits count, from the `credits` group's `unit`, where they said "credits". An override of yours keeps its own words; one written for the old English leaves `{unit}` out, and development says so.

## Moderation verdicts name shared categories

`ai.moderate` answered `categories` with the classifier's own codes, such as Llama Guard's `S12`. It now answers the shared categories every provider maps onto (`sexual`, `hate`, `minors_sexual`…) in `categories`, and the codes in `codes`, beside `scores` and `providers`. `block` and `escalate` take either, so a policy written in codes keeps working.

**What to do**

- Read `verdict.codes` where you read Llama Guard's codes from `verdict.categories`, or move to the shared names ([Choose moderation providers](/docs/build/ai/content-safety/providers#read-the-categories)).
- `moderation.model` is now also `moderation.text`: name the classifier one way or the other.

## A production checkout waits for billing to launch, and welcome credits come from the catalog

A production deployment with no `BILLING_ACCESS_TOKEN`, or no production catalog, is [not launched](/docs/build/billing/setup#before-billing-launches): its pricing reads "Plans open soon", and a checkout, a gift checkout or a switch to a paid plan is refused before anything reaches Polar. 0.2 refused that sale as `unavailable` (reason `not_configured`) from a production checkout, or, with a token but no production catalog, as `not_ready` (reason `no_catalog`) from a production checkout; 0.3 refuses both as `unavailable` (reason `not_launched`), whose label reads "Plans open soon". Every other deployment, and every other provider call, keeps `not_configured` and `no_catalog`.

- **A switch of your own for when sales open goes.** An app that hides its pricing and gift links behind a flag of its own (`salesOpen` in app config, say) reads `usePricing().launched` instead, and the packaged pricing table and gifts page follow it with no change.
- **Welcome credits move to the catalog.** An app that grants them itself, with billing.refundCredits in onUserCreated, declares them on the free plan instead, `credits: { meter, units, once: true }`, then runs `billing sync`. The package grants them once per person (the owner's address, as the reverse trial counts it) on a first start, as soon as the reverse trial begins rather than when it ends, under the key `welcome:<entityId>`. Accounts that already hold a plan get nothing new. Delete the hand-rolled grant in the same change.
- **The package counts people from the upgrade on.** It never reads the grants your code made, so a person one reached can get the package's as well, once: with the first workspace they make after the upgrade (`billTo: 'workspace'`), or with an account they make again. A start that runs again within an hour of a free plan's start, a retry or the `billing:startFreePlan` backfill, takes it for a first start whose answer was lost and grants too: Polar drops that grant only when yours used the same key, as an app that keyed `welcome:<userId>` with `billTo: 'user'` did. Run the backfill no sooner than an hour after the deploy.
- **A refund under a key Polar holds credits the cached balance once.** `refundCredits` with an `externalId` Polar already took no longer credits the cached balance a second time, and a refund for an entity never synced reads it from Polar first, so the cache holds the credit.
- **`PricedPlan.gift`** lists a giftable plan's lengths at their live prices: an app that priced a pass as months times the monthly price reads `plan.gift.lengths` instead.

## A job step stops its model calls at its timeout

A job step's model calls ran until the stall sweep failed the job. `jobs.step` now aborts them at the step's `timeout`: by default 3 minutes, or 80% of the queue's `stallAfter` when that is less. The step is tried again, as after a provider's timeout, and a `timeout` at or above `stallAfter` is refused where the step is defined.

**What to do**

- Give a step whose calls legitimately run longer its own `jobs.step({ timeout })`, below `stallAfter` ([Model limits](/docs/build/ai/jobs/model-limits)).
- Pass `ctx.callSettings` to `generateText` and `generateImage`, or `ctx.signal` as `abortSignal`, for a call the step makes outside `ctx.model()` and `ctx.image()`.

## Members bring friends with a ticket of their own, and the waitlist records the campaign

- **Member tickets come from the package.** An app that minted an access link for each member itself, with access.invites.create with a label per member and a table of its own to read it back, re-exports `access.memberTickets({ uses, lifetime })` from `backend/access.ts` instead, and reads it with `useMemberTicket()` ([Let members bring friends](/docs/build/growth/launch/invites#let-members-bring-friends)). Its links keep working until they expire: they are access links like any other. The package does not read the app's table, so a member who asks again gets a ticket of the package's; revoke the old links in the Access tab if a member should not hold both. An account a member ticket admitted holds none of its own unless you pass `chain: true`, and a switch of your own goes in `enabled`.
- **The waitlist records the campaign.** useWaitlist({ source }) now records the page address's `utm_source` and `utm_campaign` after the source, as `landing:newsletter/launch`. Drop a helper that built that source yourself and pass the form's alone, or pass useWaitlist({ source, campaign }) with `campaign: false` to record the source as before.

## A job joins on a balance never read

`jobs.enqueue` refused a job with `not_ready` (reason `not_synced`) whenever the credit balance was not in this deployment's cache. Only a balance this deployment has never read now lets the job join: it holds nothing yet, and its first step reads the balance and takes the hold, or fails the job `insufficient_credits` before any model is called. A balance that was read and holds no credit meter is still refused `not_ready` at enqueue.

**What to do**

- Drop a `try`/`catch` around `jobs.enqueue` that only waited out `not_synced` for a new account's first credits: the job joins.
- Keep handling `not_ready` from `enqueue` for an owner with no credit meter, and `insufficient_credits` on a job that failed short of credits ([Credits and jobs](/docs/build/ai/jobs/credits)).

## Report forms send notices, and the legal pages fill your own

The report form you build into your pages is a notice the law asks a host to accept, and the legal pages' facts reach a Content page of yours ([Moderation](/docs/ship/compliance/moderation#build-the-report-form-into-your-own-pages), [Privacy](/docs/ship/compliance/privacy#write-your-own-pages-in-content)).

- **Reports.** Replace a hand-rolled `useMutation(api.admin.reportContent)` with `useReportForm(subject)`, which sends a notice (DSA Art. 16) through `sendNotice` with every field it requires, a receipt and the decision by email, or with `useReportForm(subject, { mode: 'quick' })` for a signed-in person's one-click report. `reportContent({ website })` and `sendNotice({ website })` take an optional honeypot, and `getConsentTerms` also returns `documents`: deploy the backend.
- **Six component names are global.** `LegalProcessors`, `LegalStorage`, `LegalDetail`, `LegalVersion`, `LegalContactPoints` and `LegalModeration` are registered globally, so Markdown renders them. A component of yours under one of these names replaces the package's everywhere, the packaged legal pages included: rename yours unless that is what you mean.
- **The terms page says more.** Once the report page is on, a section says how content is moderated; the Contact section lists your DSA points of contact; a mediator gets a Disputes section; the privacy policy and the terms print their version once `setupAccount({ consents })` declares it. In development, the terms page names `legal.contactPoints.authorities` and `legal.contactPoints.languages` while they are unset.
- **The manifest.** `backend.installable` is checked as the module starts; an app whose `public/` holds RealFaviconGenerator's `web-app-manifest-192x192.png` and `web-app-manifest-512x512.png`, and no manifest of its own, now gets the module's.

## Browser error reports go through a tunnel on the app's own origin

The package's Sentry configs send the browser's reports through Sentry's managed tunnel, a path on the app's own origin that the Nuxt server forwards to the ingest, so ad blockers don't drop them. It needs `@sentry/nuxt` 11.10, and the peer range is now `^11.10.0`.

- **Upgrade the SDK:** `npm install @sentry/nuxt@^11.10.0`. An older one still builds and reports, straight to the ingest as before, and the build and `doctor` (`monitoring-app`) warn.
- **An app with only its own `sentry.server.config.ts`:** the package's browser config reports straight to the ingest, and the build says so. For the tunnel, add `Sentry.serveTunnelIntegration()` to your server config first, then a `sentry.client.config.ts` with `tunnel: true`: a client that posts to the tunnel before your server answers it loses every report ([Customize the SDK](/docs/ship/operate/monitoring#customize-the-sdk)).
- **An app with its own `sentry.client.config.ts`:** nothing to change; the ingest's origin stays in `connect-src`. Add `tunnel: true` to report through the tunnel, once a server config answers it: the package's, or yours with `Sentry.serveTunnelIntegration()`.
- **On Vercel,** every page view now invokes the server function, prerendered pages included, and the tunnel is outside nuxt-security's rate and size limits ([What the tunnel costs](/docs/ship/operate/monitoring#what-the-tunnel-costs)).

## The packaged UI reads its faces, lines and shadows from tokens

Seven tokens take the packaged components past colour: `--bk-font`, `--bk-font-heading` and `--bk-font-control` (the faces), `--bk-border-width` (every outline) and `--bk-shadow`, `--bk-shadow-control` and `--bk-shadow-overlay` ([Restyle with tokens](/docs/build/ui/customize/tokens#faces-lines-and-shadows)). The outermost element of every packaged component and page carries `data-backend`, so one selector reaches them all: replace a list of families in your CSS, such as `[data-auth='form'], [data-pricing='table'], [data-admin]`, with `[data-backend]`. `<AppShell>` frames your own pages, so its root carries none.

With no token set, most of the UI looks as it did. What changes:

- **Dialogs float.** The confirm, re-authentication and consent dialogs, the AI label's details and the admin drawer cast `--bk-shadow-overlay`, a black shadow. The account menu, the workspace switcher and the inbox panel move to the same shadow, which no longer glows on a dark page, and the storage question's darker shadow becomes it too.
- **Multi-line fields have card corners.** The contact message and the cancellation comment use `--bk-radius` instead of a pill.
- **Every packaged button takes the page's font.** The buttons of `<CancelFlow>`, `<WithdrawalButton>`, `<AccessDenied>`, the past-due notice and the workspace switcher's create button used the browser's button font; they take `font: inherit` like the others.
- **The current plan's ring is an outline.** It is drawn with `outline` instead of `box-shadow`, so the card keeps `--bk-shadow`; a rule of yours that restyled that ring's `box-shadow` styles `outline` now.

A heading or a root face rule of yours, in any layer, wins over the face tokens: they sit in `nuxt-backend-tokens`, below every layer.

## Passkeys check the person, and a ban says when it ends

0.2 asked a passkey's device to check the person (a fingerprint, a face or the device's PIN) as `preferred`, and took a passkey that skipped it. 0.3 requires it (`userVerification: 'required'`): at registration, at every sign-in and in `useReauthentication().withPasskey`, the server refuses a passkey whose device did not check the person ([Limits](/docs/build/auth/sign-in#limits)).

- **A security key with no PIN.** A passkey a security key with no PIN set saved under 0.2 is refused from now on. The passkey's row keeps no verification flag, so those accounts can't be found in advance: the person reads `invalid_input` on `passkey`, whose label names the PIN, or `passkey_cancelled` when the browser gives up on the key. They set a PIN on the key (Chrome offers to) or sign in with an email code; a passkey-only account uses its recovery code, or an administrator's `allowSignInCodes`.
- **Your own `passkey(...)`** in `authOptions.plugins`: add `authenticatorSelection: { userVerification: 'required' }` to it. Without it, a passkey that never checked the person still signs in.
- **`resolveSignInMethod` is deprecated.** Better Auth 1.7 names a code sign-in `email-otp` itself: drop `customResolveMethod: resolveSignInMethod` from a `lastLoginMethod(...)` of your own. It keeps working until a later minor release removes it.
- **A ban names its end.** A banned account's refusal (`forbidden`, reason `banned`) carries `until`, and the person reads the new `errors.forbidden_banned_until` label. An `admin.bannedUserMessage` of your own changes nothing the person sees and drops `until`: delete it, and word the refusal with the `errors.forbidden_banned` and `errors.forbidden_banned_until` labels ([What an administrator may do](/docs/build/auth/admin#what-an-administrator-may-do)). A locale of yours shows the English of the new label until you add it.

## Better Auth 1.7, and a deploy for the backend's schema

The package runs Better Auth 1.7 (`better-auth@>=1.7.16 <1.8.0`) on `@convex-dev/better-auth` 0.13, which closes the security advisories every Better Auth 1.6 release carries.

- **A Better Auth plugin you add through `authOptions`** must support 1.7. Code of yours that imports `getIp` from `better-auth/api` imports `getIP`.
- **Deploy the backend.** The `backend` component's schema gains the `jwks` fields `alg` and `crv`, an `account` index and the tables behind welcome credits and moderation flags; existing rows stay valid. Start `npx nuxt-backend dev` once, then run `npx nuxt-backend upgrade`; in production, `npx nuxt-backend upgrade --prod --yes` after the deploy. Its data half now also runs the workpool's backfill (`migrations:backfillPendingStartIds`) in every pool, which the workpool's 0.5 line needs: run it before a later release moves there.
- **Pending email-change codes.** A code requested before the deploy no longer matches: the person asks for a new one.
