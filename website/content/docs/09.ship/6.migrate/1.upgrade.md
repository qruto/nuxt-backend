`0.1.0` on npm was a throwaway test publish, so most apps start on 0.2 directly. This page is for
apps built on a preview of `main` (`npm install https://pkg.pr.new/qruto/nuxt-backend@main`): it
lists every change that needs an edit in your app, newest first, with the edit to make. Run
`npx nuxt-backend doctor` after upgrading; it names any scaffolded function your `backend/` files
no longer export.

## Data composables take options and report failures in `error`

`useSearch`, `useAggregate`, `useWorkflowStatus`, `useEmailStatus`, `useSandboxInbox` and
`useSessions` follow [Composable conventions](/docs/reference/nuxt/conventions): inputs come in an
options object, each returns a plain object with `isLoading` and `error`, a read never throws, and
an action rejects. `error` is `{ code, data, message } | null`, the shape `getBackendError` reads;
a failure with no catalog code reads as `unavailable` with reason `unexpected`.

| Gone | Instead |
|---|---|
| `useSearch(query, term, { debounce, args })` | `useSearch(query, { term, debounce, args })`, which also returns `error`. A whitespace-only term pauses it too |
| The `UseSearchResult` type | `UseSearchReturn` |
| `useAggregate(query, args)` as a `ComputedRef<number>`, `0` while loading | `{ data, isLoading, error }`: `data` is `undefined` until the first read lands |
| `useCount` | `useAggregate`, the same composable |
| `useWorkflowStatus(query, workflowId)` as a `ComputedRef` of the status | `useWorkflowStatus(query, { workflowId })`, returning `{ data, isLoading, error }` |
| `useEmailStatus(emailId, { api })` | `useEmailStatus({ emailId, api })` |
| `useEmailStatus().isError` | `isFailed`; `error` now means the status could not be read |
| `useSandboxInbox(address, { api })` | `useSandboxInbox({ address, api })`, which also returns `error` |
| `useSessions().error` as `Ref<string \| null>` | `ComputedRef<BackendError \| null>`: show `error.message`, branch on `error.code`. It holds a failed read of the list too |
| `useSessions().revoke` and `revokeOthers` rejecting with a new `Error` carrying the message | They reject with what the call threw; `isPending` is `true` while one runs |
| `describeUserAgent()` returning `'unknown device'` for no user agent, and `'Browser'` for one it could not read (`curl/8.4.0`) | `null` for both: word an unknown device yourself |
| A failed query in these composables throwing out of the render | Nothing thrown: the failure is in `error` |

**What to do**

- Move the second argument into the options object: `{ term }`, `{ workflowId }`, `{ emailId }`,
  `{ address }`.
- Read `.data` from `useAggregate` and `useWorkflowStatus`
  (`const { data: count } = useAggregate(api.aggregates.countMessages)`), and rename `useCount` to
  `useAggregate`. Where a template bound the count straight to a number, write `count ?? 0`.
- Rename `isError` to `isFailed` on `useEmailStatus`.
- Where you showed `useSessions().error`, show `error.message`, and replace
  `describeUserAgent(ua)` with `describeUserAgent(ua) ?? 'Unknown device'`.

## Checkout sells only your catalog, and returns only to your site

A checkout, a plan change and a gift used to take what the browser sent: any product the
provider sells, a trial of any length, a discount by id, metadata keys the package reads back,
and any URL to send the buyer to afterwards. The server decides each of them now, and refuses
the rest as `invalid_input` with the field it refuses. [What the server
decides](/docs/billing/subscriptions/checkout#what-the-server-decides) has the rules:

| Gone | Instead |
|---|---|
| `generateCheckoutLink` with any product id | Products of your catalog only (`billing.generated.ts`, or `setupBilling({ products })`); `updateSubscription` and `changePlan` too |
| A `successUrl`, `origin` or portal `returnUrl` on any site | `SITE_URL`'s origin, or one listed in the new `setupBilling({ trustedOrigins })` |
| `trialInterval` and `trialIntervalCount` from the browser (`checkout(id, { trialInterval })`) | The plan's own trial (the catalog's `trial`); a different one, 1 to 30 days in days or weeks, or none (`trial: false`), from server code through the new `billing.checkout(ctx, options)` |
| `discountId` from the browser | `discountCode` for a code a customer or a campaign link carries; a discount by id through `billing.checkout(ctx, { discountId })` |
| Metadata with any key | Your own keys; `userId`, `gift`, `giftId`, `recipientEmail`, `purchaserUserId`, `giftRecipient` and `utm_*` are the package's, at most 20 keys |
| Campaign UTM parameters as hand-made metadata | `checkout(id, { utm: { source, medium, campaign, term, content } })`, stored as `utm_*` metadata |
| `gift(productIds, …)` on `useBilling` and `useCredits`, for a plan or a pack | `gift(pack, …)` with the pack's catalog key (`'credits500'`): gifts are credit packs only, since a plan gift renews on the purchaser's card. `giftCheckout` takes `pack` in place of `productIds` |
| A plan change to any product, a credit pack included | A recurring plan of the catalog only |
| A webhook resolving the billing entity from an order's or a subscription's `userId` metadata | Only the customer's own metadata (`customer.*` events, or the customer on the payload), then the synced cache: checkout metadata is the buyer's |
| `gift(...)` with a one-time product the catalog does not list as a pack | Run `billing sync`: it writes the catalog's pack keys into `billing.generated.ts` as `packs`, and only those gift |
| `listAllProducts`, `changeCurrentSubscription` and `cancelCurrentSubscription` on `billing.api` | Gone: `getConfiguredProducts` is the price list, and `updateSubscription` and `cancelSubscription` (`changePlan`, `cancel`) change and cancel. `useBilling` no longer falls back to the removed pair |

**What to do**

- Remove `listAllProducts`, `changeCurrentSubscription` and `cancelCurrentSubscription` from
  the `billing.api` exports in `backend/billing.ts`.
- Run `npx nuxt-backend billing sync` again, so the catalog has your products and lists its packs,
  and add any other origin the app runs on to `setupBilling({ trustedOrigins })`, with its scheme.
- Move a trial you set in the browser to the plan's `trial` in `billing.catalog.ts`, or to an
  action of your own that calls `billing.checkout(ctx, { trial })`. Do the same with a
  `discountId`, or pass the code as `discountCode`.
- Rename metadata keys that clash with the reserved ones, and pass UTM parameters as `utm`.
- Call `gift` with the pack's catalog key instead of its product id.

## Refusals carry a code, and survive production

Every refusal a person can meet now has a stable code. A package function throws it as a
`ConvexError` whose data is `{ code, ...fields }`, which Convex sends to the client in production.
Most refusals used to be plain `Error`s, which production shows as "Server Error". An auth route
puts the same code and fields in its error body. `getBackendError(error)`, auto-imported and also
exported from `nuxt-backend/functions`, reads either one, and `backendError()` throws one from
your own functions. The English sentences stay as each error's `message` for the log.
[Errors](/docs/reference/backend/errors) lists the codes:

| Gone | Instead |
|---|---|
| A string in `error.data` from `requireUser`, `requireRole`, `requirePermission`, `requireOrganization`, `requireMember` and `setUserRole` (`'Unauthenticated'`, `'Forbidden: …'`, `'No active organization …'`) | `unauthenticated`, `forbidden` with a `reason` (`banned`, `role`, `permission`, `not_member`, `workspace_role`), `no_workspace`, and `invalid_input` for `setUserRole` |
| A string in `error.data` from checkout and the gift claim (one email, another workspace), `canGift` and `revokeSession` | `forbidden` (reason `customer_taken`, `billing_profile_mismatch` or `gift_refused`) and `invalid_input` (field `sessionId`), with the sentence in `data.message`; `revokeSession` signed out is `unauthenticated` |
| Plain `Error`s from billing, credits, gifts, `setupAi` and `updateProfile`: signed out, no workspace, admin-only, not the caller's order or subscription, no subscription, missing `BILLING_ACCESS_TOKEN`, a balance that cannot cover a spend | `unauthenticated`, `no_workspace`, `forbidden` (`admin_only`, `not_owner`, `not_recipient`, `no_email`), `invalid_input`, `unavailable` (`not_configured`), `not_ready` (`no_customer`, `not_synced`: nothing a retry changes), `insufficient_credits` with `balance` and `need`. A signed-out caller is `unauthenticated` before anything says billing is not configured, `spendCredits` and `refundCredits` included |
| `getInvoiceUrl` for an order id the provider does not know: the provider's error | `forbidden` (reason `not_owner`), the same as another account's order |
| "Too many …", "Rate limit reached" and "Credit budget reached" `Error`s from the `billingSync`, `ai` and `aiBudget` limits | The limiter's own error (`throws: true`), read as `rate_limited` with `limit` and `retryAfter` |
| The provider's own error, body included, from `syncEntitlements`, `billing.getCustomerState`, `generateCustomerPortalUrl`, `changeCurrentSubscription`, `cancelCurrentSubscription`, `discounts.*`, a usage report and the email marketing calls | `unavailable` with reason `provider_refused`. The provider's words go to the deployment log only |
| `generateCustomerPortalUrl`, `changeCurrentSubscription` and `cancelCurrentSubscription` on `billing.api` from the provider's client | The package's own, with the same arguments: the portal checks the token and spends one token of the `billingSync` limit, like every live provider call, and the two subscription actions run `updateSubscription` and `cancelSubscription` and resolve `null` |
| `cancelCurrentSubscription` refused a `past_due` or `paused` subscription ("Subscription is not active") | It cancels any running subscription, as `cancelSubscription` does |
| `changeCurrentSubscription` and `cancelCurrentSubscription` threw the provider client's own error when the entity held several running subscriptions | `invalid_input` (field `subscriptionId`): call `updateSubscription` or `cancelSubscription` with the `subscriptionId` |
| `changeCurrentSubscription` to the current product refused with a plain `Error`; `updateSubscription` sent it to the provider | Both refuse with `invalid_input` (field `productId`) before the provider is asked |
| Auth route refusals with `{ message, retryAfter? }` in the body | The same, plus `code` and its fields: `rate_limited` with `limit`, `forbidden` with `reason` (`sign_in_refused`, `impersonating`, …), `unauthenticated`, `invalid_input` |
| A code or an invitation refused as undeliverable with `400` | `503`, `unavailable` with service `email` and reason `test_mode` or `unconfigured` |
| `useAiStream().start()` refused, with `status` left at `'pending'` | `status` ends in `'error'`, and `error` holds the refusal |

**What to do**

- Replace checks on `error.data` as a string, or on an error's `message`, with
  `getBackendError(error)`: branch on `code`, and show `message`.
- A rate limiter you pass to `setupBilling` or `setupAi` that is not `setupRateLimiter`'s
  is now called with `throws: true`. It may throw the limiter's `RateLimited` error or keep
  answering `{ ok: false }`; both refuse as `rate_limited`.
- In your own functions, throw `backendError(code, data)` from `nuxt-backend/functions` where you
  threw a `ConvexError` with a string, so one reader handles every refusal.

[Handle errors](/docs/data/errors) shows the reader and the thrower in use.

## The surface says backend, never a provider

The public names no longer say the platform or a provider. The base module's brand-named
auto-imports are hidden in an app that uses nuxt-backend, each with a neutral name in its place.
`setupBilling` takes an explicit option set with one entity resolver, and its result no longer
hands out the provider's client:

| Gone | Instead |
|---|---|
| `useConvex()` | `useBackendClient()` |
| `useConvexQuery`, `useConvexQueries`, `useConvexMutation`, `useConvexAction`, `useConvexPaginatedQuery`, `useConvexAsyncQuery`, `useConvexAsyncPaginatedQuery`, `useConvexUpload`, `useConvexUploadQueue`, `useConvexStorageUrl` | The same name without `Convex`: `useQuery`, `useQueries`, … |
| `useConvexAuth()` · `useConvexConnectionState()` | `useAuthState()` · `useConnectionState()` |
| `useBetterAuth()` | `useAuth()`, which extends it |
| `provideConvexAuth`, `provideConvexApi`, `useConvexApi`, `useConvexNamespace` as auto-imports | An explicit import from `nuxt-convex-module/client` |
| `<ConvexImage>` | `<StorageImage>`, the same component |
| `<CheckoutLink>` · `<CustomerPortalLink>` | `<BillingCheckoutLink>` · `<BillingPortalLink>` |
| `<ConvexProviderWithClerk>` and `provideConvexAuthFromClerk` · `<ConvexProviderWithAuth0>` and `provideConvexAuthFromAuth0`, as auto-imports | An explicit import from `nuxt-convex-module/clerk/vue` · `nuxt-convex-module/auth0/vue` |
| `definePageMeta({ middleware: 'convex-auth' })` | `definePageMeta({ middleware: 'auth' })` |
| `convexAuth(event)` in Nitro · `convexBetterAuthNuxt` | `backendAuth(event)` · an explicit import from `nuxt-convex-module/better-auth/server` |
| `export const { provider } = billing` and `billing.provider` | Nothing: the provider's client stays inside `setupBilling`. Its functions are on `billing.api` and `billing.functions` |
| `setupBilling({ getUserInfo, currentUserId })` | `setupBilling({ resolveEntity })`: one `(ctx) => Promise<{ userId, email } \| null>` for queries and actions alike, consulted whatever `billTo` says |
| Provider options `setupBilling` passed through untyped | Only the options `SetupBillingConfig` lists; anything else is a type error |
| `BILLING_REFRESH_EVENTS` · `BILLING_WEBHOOK_PROVISION_EVENTS` from `nuxt-backend/billing` | Nothing: `billing sync` registers the webhook events itself. `ALL_BILLING_EVENTS` stays |
| `sendArgs` from `nuxt-backend/email` | Nothing: the scaffolded `send` is internal and takes its own validator |
| The optional `clearPendingSpends`, `deleteByUser`, `cleanup`, `cleanupAbandoned` and `inbox` component refs | Required, as the generated `components` object already has them; only a hand-written component object needs them added |

**What to do**

- Delete `export const { provider } = billing` from `backend/billing.ts`, as the scaffold no
  longer writes it.
- Rename the auto-imports, components and middleware in the table. `npx nuxi typecheck` names
  every auto-import and middleware name left, since the hidden names leave the generated types.
  It cannot see a component name in a template: in development, `<ConvexImage>`,
  `<CheckoutLink>` and `<CustomerPortalLink>` still render their replacement and warn once in
  the console, naming it, while a production build no longer knows them. Search your templates
  for the old names before you ship.
- If `billing.ts` passed `getUserInfo` or `currentUserId`, replace both with one
  `resolveEntity`. With `billTo: 'organization'`, the default, they were never consulted: delete
  them.
- `/billing/events` and `/email/events` answer as before, with one difference: the 1 MiB cap
  counts bytes, and a `Content-Length` over it is refused with `413` before the body is read. A
  refused delivery also leaves a `webhook.rejected` line in the deployment log, once per isolate
  for each route and outcome.

[Queries and mutations](/docs/data/queries-and-mutations), [Files](/docs/data/files) and
[Subscriptions](/docs/billing/subscriptions) show the neutral names in use.

## One-time codes are checked per address, and the unused routes are off

A code now gets at most a few guesses per address an hour, and a new code replaces the one before
it. Codes are stored as a hash keyed by `AUTH_SECRET`. Routes the package never calls are off,
and so is password reset until you turn passwords on. An email change says so in its first code,
and once it goes through, the old address hears of it:

| Gone | Instead |
|---|---|
| `/email-otp/check-verification-otp` | Nothing: it answers 404. The code routes check a code as they consume it |
| `/send-verification-email`, `/verify-email`, `/change-email` | Nothing: they answer 404. Verification and an email change go by code |
| `/email-otp/request-password-reset`, `/forget-password/email-otp`, `/email-otp/reset-password` and `type: 'forget-password'` codes, on a passwordless app | Nothing: 404 and 400. They come back with `emailAndPassword.enabled` |
| `setupAuth` with `email` undefined, or with `integrations` | Nothing: both throw at setup, the first naming the import cycle that usually causes it |

**What to do**

- If you list or implement rate limits by name, add `emailOtpAttempt`; one built over
  `DEFAULT_LIMITS` already has it.
- A `canSignIn` that switches on `purpose` gets `'email-change'` too, for the new address of
  an email change.
- Codes minted before the upgrade stop verifying, and so do codes in flight when you rotate
  `AUTH_SECRET`: ask for a new one.
- The old address of an email change now gets the `emailChanged` notice; restyle it like any
  other template.

[Sign in](/docs/auth/sign-in), [Rate limits](/docs/ship/production/rate-limits) and
[Templates](/docs/email/templates) describe the rules.

## Workspace actions reject when they are refused

`useOrganization()`'s actions used to resolve the auth client's `{ data, error }` result, so a
refused call looked like a success unless you read `error`. Each now rejects with the server's
reason, and a rate-limited call rejects with the wait in `retryAfter`:

| Gone | Instead |
|---|---|
| `const { error } = await invite({ email })`, and the same for `setActive`, `create`, `leave`, `acceptInvitation`, `declineInvitation` and `cancelInvitation` | `try { await invite({ email }) } catch (error) { … }`; on success each still resolves the client's result |

**What to do**

- Where you read `error` from one of these results, catch the rejection instead. A call you never
  checked now throws on refusal, so show its message where your form reports success.

[Workspaces](/docs/auth/workspaces) describes the actions.

## Every email comes from one registry, and every route is required

The app's `setupEmail` instance holds the templates of every email the package sends. `setupAuth`
and `setupBilling` take it as a required `email` option and send through it, so one override
restyles an email wherever it goes out. `registerBackendRoutes` takes every part, the agent token
exchange inside `auth`:

| Gone | Instead |
|---|---|
| `emailTemplates` on `setupAuth`, and the set it returned as `emailTemplates` | `templates` on `setupEmail`; `await email.render(name, data)` for a preview |
| The default as an override's second argument: `(data, byDefault)` | `byDefault` in the second argument, beside `t`, `locale` and `brand`: `(data, { byDefault }) => …` |
| `email` on `setupAuth` as a transport, `(ctx, message) => …` | `email`, the `setupEmail` instance, required |
| `giftEmail` on `setupBilling`, and `defaultGiftEmail`, `GiftEmailData` and `GiftEmailMessage` from `nuxt-backend/billing` | The `gift` template on `setupEmail`; `GiftEmailData` from `nuxt-backend/email` |
| `setupBilling(components)` with no options | `setupBilling(components, { email })` |
| `AuthEmailSender`, `AuthEmailMessage`, `AuthEmailTemplates`, `AuthEmailTemplateOverrides` | `AuthEmail`; `EmailMessage`, `EmailTemplates` and `EmailTemplateOverrides` from `nuxt-backend/email` |
| `registerBackendRoutes(http, { auth: { authComponent, createAuth }, mcp, … })`, every part but `auth` optional | `registerBackendRoutes(http, { auth: { authComponent, createAuth, mcp }, billing, email, ai })`, every part required |
| `setupMcp`, `McpExchange` and `SetupMcpOptions` from `nuxt-backend/http` | Nothing: `setupAuth` returns the exchange as `mcp`, typed `McpExchange` from `nuxt-backend/auth` |
| The `billing.gift_email_unsent` log line | Nothing: the gift email goes through the email instance |

The welcome email, the email-change notice and a gift notification carry an idempotency key, so
a repeated send of the same one delivers nothing while the first is on record. An invitation
carries none: every send of it goes out.

**What to do**

- In `backend/email.ts`, move the auth `emailTemplates` and the billing `giftEmail` overrides into
  `setupEmail(components, { templates })`. An override that used its second argument as the
  default takes `byDefault` from it instead.
- In `backend/auth.ts` and `backend/billing.ts`, import `email` from `./email` and pass it to
  `setupAuth` and `setupBilling`. Keep `backend/email.ts` free of imports from `./auth`: the cycle
  leaves `email` undefined while `setupAuth` runs.
- In `backend/http.ts`, move `mcp` into `auth: { authComponent, createAuth, mcp }` and pass
  `billing`, `email` and `ai`.
- A preview page that read `emailTemplates` from `./auth` renders with `await email.render(name, data)`:
  `render` resolves, so a template may be `async`.

[Templates](/docs/email/templates), [Auth setup](/docs/auth/setup) and
[Webhooks & routes](/docs/ship/production/webhooks) describe the new shapes.

## Email changes take a code from each address, and `setupAuth` is the one factory

An email change no longer sends links: the person enters a code from the current address, then one
from the new address. Verification is a code too, so the verification email and its section are
gone. Codes are stored as a hash keyed by `AUTH_SECRET`. `setupAuth` is the only function of `nuxt-backend/auth`, and its
cross-component options sit at the top level:

| Gone | Instead |
|---|---|
| `setupAuth(components, query, { integrations: { rateLimiter, canSignIn, onUserCreated, onUserDeleted, email, emailTemplates } })` | The same keys at the top level: `setupAuth(components, query, { rateLimiter, … })` |
| `createAuthOptions` and `options` from `setupAuth` (and the scaffold's `backend/auth.ts`) | Nothing: `createAuth` is the factory |
| `createAuth`, `createAuthOptions`, `createBetterAuth`, `createBetterAuthOptions`, `makeAuthApi` exported from `nuxt-backend/auth` | `setupAuth`, which returns `createAuth` and the auth queries |
| `defaultEmailTemplates` | An override receives the default it replaces as `byDefault` (see the section above) |
| The `verify` and `changeEmail` email templates | Nothing: `otp` sends every code (`email-verification` to the current address, `change-email` to the new one) |
| `CreateBetterAuthOptions` | `SetupAuthOptions` |
| `useAuth().changeEmail`, `useAuth().sendVerificationEmail` | `useEmailChange()`: `start`, `confirmCurrent`, `verifyNew` |
| `<ProfileSettings callback-path>`, its `email-change-requested` event, and `newEmail` / `changingEmail` / `requestEmailChange` in its slots | `email-changed(email)`, and `emailChange` (the `useEmailChange()` flow) in its slots |
| `<SecuritySettings callback-path>`, the `verification` section and slot, and its `verification-sent` event | Nothing: the code that signs a person in verifies their address |

Better Auth's own rate limiter is now off unless you turn it on with
`authOptions.rateLimit: { enabled: true, storage: 'database' }`; an object without `enabled: true`
leaves it off. It
counted in memory, which on Convex lasts one function call. A new named limit, `emailChange`,
throttles the code an email change sends to the new address, per account.

**What to do**

- In `backend/auth.ts`, move the members of `integrations` up one level, and drop `createAuthOptions`
  and `options` from the names you export.
- Replace calls to `changeEmail` and `sendVerificationEmail` with `useEmailChange()`, and drop
  `callback-path` from `<ProfileSettings>` and `<SecuritySettings>`.
- A template override that called `defaultEmailTemplates.<key>(data)` takes the default as
  `byDefault` instead (see the section above).
- If you passed `rateLimiter` from a `setupRateLimiter` of your own that lists limits by name, add
  `emailChange`; one built over `DEFAULT_LIMITS` already has it.

[Auth setup](/docs/auth/setup), [Let users edit their profile](/docs/auth/accounts/profile) and
[Templates](/docs/email/templates) describe the new shapes.

## The welcome email and both sign-in methods are always on

Every new account gets the packaged welcome email, and the sign-in form always offers a passkey
and an email code. The switches are gone:

| Gone | Instead |
|---|---|
| `setupAuth({ integrations: { welcomeEmail } })` | Nothing: restyle the welcome with the `welcome` template on `setupEmail` |
| `<AuthForm :passkeys>`, `<AuthForm :otp>` | Nothing: build your own page on `useLoginFlow()` for a different set of steps |
| `useLoginFlow({ offerPasskey })` | Nothing: after a code, the flow offers to save a passkey; `skipPasskey()` moves past it |

**What to do**

- Delete those keys and props. A leftover `:passkeys` or `:otp` on `<AuthForm>` no longer does
  anything but land on its root element as an attribute.
- A sign-in page of your own built on `useLoginFlow()` must handle the `add-passkey` step: render
  it, or call `skipPasskey()` when `step` reaches it. A flow left there never calls `onSuccess`, and
  the person, signed in already, stays on the page.
- If an onboarding sequence of yours sent its own welcome, drop that step: the packaged one
  always goes out. The scaffold's `onSignup` sequence now starts three days after sign-up.

[Sign in](/docs/auth/sign-in) and [Email sequences](/docs/email/engagement/sequences) describe both.

## Pages, the stylesheet and the webhook log are always on

Every module page mounts, the neutral stylesheet always loads, and every webhook delivery is
logged. The switches are gone:

| Gone | Instead |
|---|---|
| `backend.pages: false`, `backend.pages.<key>: false` | Put an app page at the page's path: it replaces the module's |
| `backend.pages.<key>: true` | Leave the key out; a string still moves the page |
| `backend.loginPath` | `backend.pages.login`: the `auth` middleware follows it, whichever page serves it |
| `backend.css: false` | Restyle through the `--bk-*` tokens or the `data-*` hooks: the stylesheet is layered, so your own CSS wins without a fight |
| `nuxt-backend/ui.css`, `nuxt-backend/auth.css`, `nuxt-backend/*.css` | Nothing to import: the module adds the stylesheet |
| `setupBilling({ deliveryLog })`, `setupEmail({ deliveryLog })` | Nothing: the log also dedupes redeliveries |
| `setupBilling({ benefitMetadataTtlMs })` | Nothing: a fixed 15 minutes |
| `getWebhookDeliveries` for any signed-in caller | Admins only, by the gate `refundOrder` uses (`setupBilling({ requireAdmin })`); anyone else reads `null`, and DevTools says so |

**What to do**

- Delete those keys. Where you turned a page off, put your own page at its path; where you set
  `loginPath`, set `pages.login` to the same path.
- If you imported a stylesheet from the package, drop the import. The stylesheet sits in the
  `components.backend` cascade layer, ahead of your CSS.
- If your CSS has a reset or element rules outside a cascade layer (`* { margin: 0 }`,
  `button { background: none }`), move them into `@layer base { … }`, or import the file into it:
  `@import './reset.css' layer(base);`. A rule outside any layer beats every layered one, so an
  unlayered reset strips the packaged buttons and inputs. Tailwind's own reset already sits in
  `base`.
- Every module page now carries route rules: none is prerendered, and the private ones are kept
  out of caches and indexes at their paths. A rule you set for the same path wins key by key. Keep
  an app-wide `swr`, `isr` or `cache` rule off them; the module warns at startup when one covers
  them ([Caches](/docs/ui/pages#caches)).
- A leftover 0.1 value (a page set to `true` or `false`, `backend.pages: false`, `loginPath` or
  `css`) now stops the build with an error that names each one and links here.
- A page of yours that showed `getWebhookDeliveries` to everyone now gets `null` for non-admins.
  To show the log more widely, serve it from a query of your own over
  `components.backend.webhooks.listRecent`, as the playground does.

[Replace a page](/docs/ui/customize/replace-pages) and [Restyle with tokens](/docs/ui/customize/theming) describe both.

## Agents always pass the consent page

An agent used to receive an authorization code without anyone approving it. Every authorization
now stops at a consent page, `/oauth/consent`, where the person approves or denies, and agents
must use PKCE. The options that configured the provider are now paths only:

| Gone | Instead |
|---|---|
| `setupAuth({ mcp: { loginPage } })` | `mcp: { loginPath }` |
| `setupAuth({ mcp: { consentPage } })` | `mcp: { consentPath }`, and the page at `backend.pages.agentConsent` |
| `setupAuth({ mcp: { trustedClients } })` | Nothing: every agent passes the consent page |
| `setupAuth({ mcp: { oidcConfig } })` | Nothing |

**What to do**

- Rename `loginPage` to `loginPath` and `consentPage` to `consentPath`, and delete
  `trustedClients` and `oidcConfig`.
- If you had a consent page of your own, keep its path in `consentPath` and in
  `backend.pages.agentConsent` (or put it at `/oauth/consent`), and build it on
  `useAgentConsent()`. `npx nuxt-backend doctor` checks that both sides agree.
- Agents connected before the upgrade keep their tokens; the next authorization asks the person.

[OAuth & consent](/docs/agents/mcp/oauth-and-consent#consent) describes the page.

## Workspaces, admin and the agent surface are always on

Every app gets workspaces (with a personal workspace per user), roles and the OAuth-protected
agent endpoint at `/mcp`. The switches that turned them off are gone:

| Gone | Instead |
|---|---|
| `backend.workspaces` in `nuxt.config.ts`, and `runtimeConfig.public.backend.workspaces` | Nothing: the organization endpoints always exist |
| `setupAuth({ admin: false })`, `{ organization: false }`, `{ mcp: false }` | Pass an options object to configure a plugin, or leave the key out |
| `organization: { personal: false }` | Every user gets a personal workspace on first sign-in |
| `setupAuth({ verbose })` | Nothing |
| `backend.mcp: false`, `backend.mcp.enabled` | Nothing: `backend.mcp` takes options only |
| `backend.mcp.tools.builtin`, `builtinToolEnabled` from `nuxt-backend/mcp` | An agent sees a built-in tool only with its scope, which the person consents to |

**What to do**

- Delete those keys from `nuxt.config.ts` and `backend/auth.ts`.
- If your app ran without workspaces, run `npx nuxt-backend doctor`: `listWorkspaces` and
  `listWorkspaceMembers` are part of the function contract again, so `backend/auth.ts` must
  re-export them. A user who signs in after the upgrade gets a personal workspace.

[Workspaces](/docs/auth/workspaces) and [MCP server](/docs/agents/mcp) describe both.

## Local installation is gone

`installation: 'local'` copied the `backend` component into `backend/components/backend/` so an
app could change its schema. Every app now mounts the packaged component, which owns its schema. The
option, `init --installation`, the `schema` option of `setupAuth` and the six
`nuxt-backend/component/*` subpaths are gone.

**What to do**

- Back up the deployment first: `npx convex export --path backup.zip`.
- In `backend/convex.config.ts`, import the packaged component instead of the local one:

  ```ts [backend/convex.config.ts]
  import backend from 'nuxt-backend/convex.config'
  ```

- In `backend/auth.ts`, remove `schema: authSchema` from `setupAuth` and its import.
- Delete `backend/components/backend/`, and `installation` from the `backend` options in
  `nuxt.config.ts`.
- Remove `@convex-dev/better-auth` and `@convex-dev/resend` from your `package.json` unless your
  own code imports them; the package brings both.
- Run `npx nuxt-backend doctor`.

The packaged component mounts under the same name, `backend`, so the data in its tables stays where
it is. What you added to the component schema needs a new home first:

- **An extra table** becomes an app table in `backend/schema.ts`. Empty it in the component
  (`npx convex import --component backend --table <name> --replace -y empty.jsonl`, with an empty
  file), switch, then load its rows from the backup into the app table
  (`npx convex import --table <name> <file>`).
- **An extra field** on an auth table has no place in the packaged schema. Move the value to an app
  table keyed by the user id, then clear the field before you switch, or start a dev deployment
  fresh.

[Auth setup](/docs/auth/setup) lists what the packaged schema covers.

## The scaffolded `send` is internal

`api.email.send` in the scaffolded `backend/email.ts` was a public action that only checked for a
sign-in, so anyone who could sign in could send mail from your verified domain to any address. It
is an `internalAction` now, and the welcome step of the onboarding sequence sends plain text.

**What to do**

- Call `send` from your own server code: `ctx.runAction(internal.email.send, { to, subject, text })`
  from an action, a scheduled function, or `npx convex run email:send`. Take the address from data
  you trust: the signed-in user's own record, a workspace invitation, an order.
- If a person types the address (an admin tool), use the scaffold's `sendAsAdmin`, built with
  `admin.action`, or build your own the same way.
- If you kept your own `backend/email.ts`, make the same change: replace `action` with
  `internalAction` for any function that takes a recipient.

[Sending email](/docs/email/sending) shows the new scaffold.

## Sessions are listed and revoked by id

The device-session list on `/security` failed for anyone who signed in more than a day ago, because
Better Auth's own `/list-sessions` refuses an older session. The list now comes from two functions
`setupAuth` returns, which work for sessions of any age and never send a session token to the
browser.

**What to do**

- Re-export the two functions from `backend/auth.ts`:

  ```ts [backend/auth.ts]
  export const {
    // …the exports you already have
    listSessions,
    revokeSession,
  } = setupAuth(components, query, { /* … */ })
  ```

- In your own code, `useSessions().revoke(id)` takes a session id instead of a token, and each
  session is `{ id, userAgent, createdAt, updatedAt, expiresAt, current }` with dates as epoch
  milliseconds. The list is live, so `refresh()` and the `immediate` option are gone.
- A `<SecuritySettings>` listener on `session-revoked` receives the session id.

[Auth setup](/docs/auth/setup) lists every function `setupAuth` returns.
