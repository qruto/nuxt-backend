`0.1.0` on npm was a throwaway test publish, so most apps start on 0.2 directly. This page is for
apps built on a preview of `main` (`npm install https://pkg.pr.new/qruto/nuxt-backend@main`): it
lists every change that needs an edit in your app, newest first, with the edit to make. Run
`npx nuxt-backend doctor` after upgrading; it names any scaffolded function your `backend/` files
no longer export.

## Email changes take a code from each address, and `setupAuth` is the one factory

An email change no longer sends links: the person enters a code from the current address, then one
from the new address. Verification is a code too, so the verification email and its section are
gone. Codes are stored hashed. `setupAuth` is the only function of `nuxt-backend/auth`, and its
cross-component options sit at the top level:

| Gone | Instead |
|---|---|
| `setupAuth(components, query, { integrations: { rateLimiter, canSignIn, onUserCreated, onUserDeleted, email, emailTemplates } })` | The same keys at the top level: `setupAuth(components, query, { rateLimiter, … })` |
| `createAuthOptions` and `options` from `setupAuth` (and the scaffold's `backend/auth.ts`) | Nothing: `createAuth` is the factory |
| `createAuth`, `createAuthOptions`, `createBetterAuth`, `createBetterAuthOptions`, `makeAuthApi` exported from `nuxt-backend/auth` | `setupAuth`, which returns `createAuth` and the auth queries |
| `defaultEmailTemplates` | An override receives the default it replaces: `invite: (data, byDefault) => ({ ...byDefault(data), subject })`; `setupAuth(…).emailTemplates` is the set in effect, for previews |
| The `verify` and `changeEmail` email templates | Nothing: `otp` sends every code (`email-verification` to the current address, `change-email` to the new one) |
| `CreateBetterAuthOptions` | `SetupAuthOptions` |
| `useAuth().changeEmail`, `useAuth().sendVerificationEmail` | `useEmailChange()`: `start`, `confirmCurrent`, `verifyNew` |
| `<ProfileSettings callback-path>`, its `email-change-requested` event, and `newEmail` / `changingEmail` / `requestEmailChange` in its slots | `email-changed(email)`, and `emailChange` (the `useEmailChange()` flow) in its slots |
| `<SecuritySettings callback-path>`, the `verification` section and slot, and its `verification-sent` event | Nothing: the code that signs a person in verifies their address |

Better Auth's own rate limiter is now off unless you turn it on through `authOptions.rateLimit`; it
counted in memory, which on Convex lasts one function call. A new named limit, `emailChange`,
throttles the code an email change sends to the new address, per account.

**What to do**

- In `backend/auth.ts`, move the members of `integrations` up one level, and drop `createAuthOptions`
  and `options` from the names you export.
- Replace calls to `changeEmail` and `sendVerificationEmail` with `useEmailChange()`, and drop
  `callback-path` from `<ProfileSettings>` and `<SecuritySettings>`.
- A template override that called `defaultEmailTemplates.<key>(data)` takes the default as its second
  argument instead.
- If you passed `rateLimiter` from a `setupRateLimiter` of your own that lists limits by name, add
  `emailChange`; one built over `DEFAULT_LIMITS` already has it.

[Auth setup](/docs/auth/setup), [Let users edit their profile](/docs/auth/accounts/profile) and
[Templates](/docs/email/templates) describe the new shapes.

## The welcome email and both sign-in methods are always on

Every new account gets the packaged welcome email, and the sign-in form always offers a passkey
and an email code. The switches are gone:

| Gone | Instead |
|---|---|
| `setupAuth({ integrations: { welcomeEmail } })` | Nothing: restyle the welcome with `emailTemplates.welcome` |
| `<AuthForm :passkeys>`, `<AuthForm :otp>` | Nothing: build your own page on `useLoginFlow()` for a different set of steps |
| `useLoginFlow({ offerPasskey })` | Nothing: after a code, the flow offers to save a passkey; `skipPasskey()` moves past it |

**What to do**

- Delete those keys and props.
- If an onboarding sequence of yours sent its own welcome, drop that step: the packaged one
  always goes out. The scaffold's `onSignup` sequence now starts three days after sign-up.

[Sign in](/docs/auth/sign-in) and [Email sequences](/docs/email/engagement/sequences) describe both.

## Pages, the stylesheet and the webhook log are always on

Every module page mounts, the neutral stylesheet always loads, and every webhook delivery is
logged. The switches are gone:

| Gone | Instead |
|---|---|
| `backend.pages: false`, `backend.pages.<key>: false` | Put an app page at the page's path: it replaces the module's |
| `backend.pages.<key>: true` | Leave the key out; a string still moves the page |
| `backend.loginPath` | `backend.pages.login`: the `auth` middleware follows it, whichever page serves it |
| `backend.css: false` | Restyle through the `--bk-*` tokens or the `data-*` hooks: the stylesheet is layered, so your own CSS wins without a fight |
| `nuxt-backend/ui.css`, `nuxt-backend/auth.css`, `nuxt-backend/*.css` | Nothing to import: the module adds the stylesheet |
| `setupBilling({ deliveryLog })`, `setupEmail({ deliveryLog })` | Nothing: the log also dedupes redeliveries |
| `setupBilling({ benefitMetadataTtlMs })` | Nothing: a fixed 15 minutes |

**What to do**

- Delete those keys. Where you turned a page off, put your own page at its path; where you set
  `loginPath`, set `pages.login` to the same path.
- If you imported a stylesheet from the package, drop the import. The stylesheet sits in the
  `components.backend` cascade layer, ahead of your CSS.
- Every module page now carries route rules: none is prerendered, and the private ones are
  never cached or indexed. A rule you set for the same path wins key by key.

[Replace a page](/docs/ui/customize/replace-pages) and [Restyle with tokens](/docs/ui/customize/theming) describe both.

## Agents always pass the consent page

An agent used to receive an authorization code without anyone approving it. Every authorization
now stops at a consent page, `/oauth/consent`, where the person approves or denies, and agents
must use PKCE. The options that configured the provider are now paths only:

| Gone | Instead |
|---|---|
| `setupAuth({ mcp: { loginPage } })` | `mcp: { loginPath }` |
| `setupAuth({ mcp: { consentPage } })` | `mcp: { consentPath }`, and the page at `backend.pages.agentConsent` |
| `setupAuth({ mcp: { trustedClients } })` | Nothing: every agent passes the consent page |
| `setupAuth({ mcp: { oidcConfig } })` | Nothing |

**What to do**

- Rename `loginPage` to `loginPath` and `consentPage` to `consentPath`, and delete
  `trustedClients` and `oidcConfig`.
- If you had a consent page of your own, keep its path in `consentPath` and in
  `backend.pages.agentConsent` (or put it at `/oauth/consent`), and build it on
  `useAgentConsent()`. `npx nuxt-backend doctor` checks that both sides agree.
- Agents connected before the upgrade keep their tokens; the next authorization asks the person.

[OAuth & consent](/docs/agents/mcp/oauth-and-consent#consent) describes the page.

## Workspaces, admin and the agent surface are always on

Every app gets workspaces (with a personal workspace per user), roles and the OAuth-protected
agent endpoint at `/mcp`. The switches that turned them off are gone:

| Gone | Instead |
|---|---|
| `backend.workspaces` in `nuxt.config.ts`, and `runtimeConfig.public.backend.workspaces` | Nothing: the organization endpoints always exist |
| `setupAuth({ admin: false })`, `{ organization: false }`, `{ mcp: false }` | Pass an options object to configure a plugin, or leave the key out |
| `organization: { personal: false }` | Every user gets a personal workspace on first sign-in |
| `setupAuth({ verbose })` | Nothing |
| `backend.mcp: false`, `backend.mcp.enabled` | Nothing: `backend.mcp` takes options only |
| `backend.mcp.tools.builtin`, `builtinToolEnabled` from `nuxt-backend/mcp` | An agent sees a built-in tool only with its scope, which the person consents to |

**What to do**

- Delete those keys from `nuxt.config.ts` and `backend/auth.ts`.
- If your app ran without workspaces, run `npx nuxt-backend doctor`: `listWorkspaces` and
  `listWorkspaceMembers` are part of the function contract again, so `backend/auth.ts` must
  re-export them. A user who signs in after the upgrade gets a personal workspace.

[Workspaces](/docs/auth/workspaces) and [MCP server](/docs/agents/mcp) describe both.

## Local installation is gone

`installation: 'local'` copied the `backend` component into `backend/components/backend/` so an
app could change its schema. Every app now mounts the packaged component, which owns its schema. The
option, `init --installation`, the `schema` option of `setupAuth` and the six
`nuxt-backend/component/*` subpaths are gone.

**What to do**

- Back up the deployment first: `npx convex export --path backup.zip`.
- In `backend/convex.config.ts`, import the packaged component instead of the local one:

  ```ts [backend/convex.config.ts]
  import backend from 'nuxt-backend/convex.config'
  ```

- In `backend/auth.ts`, remove `schema: authSchema` from `setupAuth` and its import.
- Delete `backend/components/backend/`, and `installation` from the `backend` options in
  `nuxt.config.ts`.
- Remove `@convex-dev/better-auth` and `@convex-dev/resend` from your `package.json` unless your
  own code imports them; the package brings both.
- Run `npx nuxt-backend doctor`.

The packaged component mounts under the same name, `backend`, so the data in its tables stays where
it is. What you added to the component schema needs a new home first:

- **An extra table** becomes an app table in `backend/schema.ts`. Empty it in the component
  (`npx convex import --component backend --table <name> --replace -y empty.jsonl`, with an empty
  file), switch, then load its rows from the backup into the app table
  (`npx convex import --table <name> <file>`).
- **An extra field** on an auth table has no place in the packaged schema. Move the value to an app
  table keyed by the user id, then clear the field before you switch, or start a dev deployment
  fresh.

[Auth setup](/docs/auth/setup) lists what the packaged schema covers.

## The scaffolded `send` is internal

`api.email.send` in the scaffolded `backend/email.ts` was a public action that only checked for a
sign-in, so anyone who could sign in could send mail from your verified domain to any address. It
is an `internalAction` now, and the welcome step of the onboarding sequence sends plain text.

**What to do**

- Call `send` from your own server code: `ctx.runAction(internal.email.send, { to, subject, text })`
  from an action, a scheduled function, or `npx convex run email:send`. Take the address from data
  you trust: the signed-in user's own record, a workspace invitation, an order.
- If a person types the address (an admin tool), use the scaffold's `sendAsAdmin`, built with
  `admin.action`, or build your own the same way.
- If you kept your own `backend/email.ts`, make the same change: replace `action` with
  `internalAction` for any function that takes a recipient.

[Sending email](/docs/email/sending) shows the new scaffold.

## Sessions are listed and revoked by id

The device-session list on `/security` failed for anyone who signed in more than a day ago, because
Better Auth's own `/list-sessions` refuses an older session. The list now comes from two functions
`setupAuth` returns, which work for sessions of any age and never send a session token to the
browser.

**What to do**

- Re-export the two functions from `backend/auth.ts`:

  ```ts [backend/auth.ts]
  export const {
    // …the exports you already have
    listSessions,
    revokeSession,
  } = setupAuth(components, query, { /* … */ })
  ```

- In your own code, `useSessions().revoke(id)` takes a session id instead of a token, and each
  session is `{ id, userAgent, createdAt, updatedAt, expiresAt, current }` with dates as epoch
  milliseconds. The list is live, so `refresh()` and the `immediate` option are gone.
- A `<SecuritySettings>` listener on `session-revoked` receives the session id.

[Auth setup](/docs/auth/setup) lists every function `setupAuth` returns.
