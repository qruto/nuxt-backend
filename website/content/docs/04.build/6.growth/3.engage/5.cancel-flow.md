Keep the subscribers you can keep, and let the rest go in one step. You get `<CancelFlow>`: cancelling takes one step, and where you turn save offers on, one optional step comes first, a question and at most one offer that fits the answer. After the plan ends, a win-back email can follow at 7 and 30 days, to people who opted in.

**What Polar does natively** (checked on 2026-10-25, [Managing subscriptions](https://polar.sh/docs/features/subscriptions/manage)):

- It cancels at the period's end, and the customer keeps the plan until then.
- It records one of eight cancellation reasons with a comment, and counts cancellations per reason in its metrics.
- It pauses a plan at the period's end, and resumes it on a date or by hand.
- Its customer portal always offers "cancel at period end", whatever your portal settings say.

**What the package adds:** the in-app flow, save offers chosen by reason, the rules that keep them lawful, and the events the win-back emails start from. Polar's metrics already count cancellations per reason.

## Turn on save offers

Without save offers, cancelling takes one step. `useBilling().cancel({ reason })` cancels at the period's end ([Cancelling takes one step](/docs/build/billing/subscriptions#cancelling-takes-one-step)). Save offers are opt-in. Declare one per reason on `setupBilling`:

```ts [backend/billing.ts]
import { setupBilling } from 'nuxt-backend/billing'
import { components } from './_generated/api'
import { audit } from './audit'
import { catalog } from './billing.generated'
import { email } from './email'

export const billing = setupBilling(components, {
  catalog,
  email,
  audit,
  lifecycle: {
    saveOffers: {
      too_expensive: { discount: 'stay30' },
      unused: { pause: { months: 2 } },
      missing_features: { downgrade: 'starter' },
    },
  },
})
```

Each key is one of Polar's cancellation reasons: `too_expensive`, `missing_features`, `switched_service`, `unused`, `customer_service`, `low_quality`, `too_complex` or `other`. Each value is one offer:

| Offer | What the customer gets | What it needs |
|---|---|---|
| `{ pause: { months } }` | The plan pauses at the period's end and resumes by itself after 1 to 3 months. Nothing is charged meanwhile. | Nothing more |
| `{ downgrade: '<plan>' }` | A switch to a cheaper plan at the period's end, so this period's price stays earned. | A plan key from the catalog |
| `{ discount: '<key>' }` | A discount on the next cycles, put on the subscription by the server. | A discount in the catalog without a `code` |

Declare the discount in the catalog like any other, with no `code`, so only your server applies it. Then push it with `npx nuxt-backend billing sync`:

```ts [backend/billing.catalog.ts]
discounts: {
  stay30: {
    name: 'Stay with Panels',
    percentOff: 30,
    duration: { months: 3 },
    perCustomer: 1,
    products: { plans: ['pro'], interval: 'month' },
  },
},
```

`perCustomer: 1` is Polar's per-customer redemption limit, so one customer never takes the save discount twice ([Run a promotion](/docs/build/growth/offers#declare-it)). A reason with no entry cancels without an offer.

## Show it in a page

`<CancelFlow>` runs the flow below: the optional step, then the cancellation. Put it behind the "Cancel plan" button of your billing page; the billing section of `/settings` opens it on its own once save offers are on (`useBilling().saveOffers` says so):

```vue [app/pages/settings/plan.vue]
<script setup lang="ts">
definePageMeta({ auth: { workspace: ['owner', 'admin'] } })
const open = ref(false)
</script>

<template>
  <button type="button" @click="open = true">Cancel plan</button>
  <CancelFlow v-if="open" @close="open = false" @canceled="navigateTo('/settings')" />
</template>
```

1. **One question, optional.** "What is the main reason?" with the eight reasons and a comment field, then "Continue". "Cancel my plan" beside it skips the question and cancels at once.
2. **One offer.** The offer for that reason, with its real terms: "Pause Pro for 2 months instead. It resumes by itself on 1 April 2027, and nothing is charged meanwhile.", or "30% off for 3 months". Two buttons of the same size and style: accept it, or "Cancel my plan".
3. **The end.** The date the plan ends, that everything keeps working until then, and a "Keep my plan" button. It emits `canceled` with that date (epoch ms), `kept` when the person keeps the plan, and `close` from its "Close" button or Escape.

Its steps are the parts `CancelFlowQuestion`, `CancelFlowOffer` and `CancelFlowEnd`, each given the flow's state and actions (`CancelFlowPartProps`, from `#backend/parts`); slots named `question`, `offer` and `end` replace them in one place, and its words are the `cancelFlow` labels ([Billing components](/docs/reference/components/billing)).

A page of your own gets the same steps from `useBilling()`:

```vue [app/components/PanelsCancel.vue]
<script setup lang="ts">
import type { CancellationReason, SaveOffer } from 'nuxt-backend/billing'

const billing = useBilling()
const reason = ref<CancellationReason>()
const offer = ref<SaveOffer>()

async function submit() {
  const result = await billing.cancel({ reason: reason.value })
  if ('offer' in result) offer.value = result.offer
}
</script>

<template>
  <form v-if="!offer" @submit.prevent="submit">
    <ReasonPicker v-model="reason" />
    <button type="submit">Continue</button>
  </form>
  <div v-else>
    <OfferCard :offer="offer" />
    <button type="button" @click="billing.acceptOffer(offer)">Keep Panels with this offer</button>
    <button type="button" @click="billing.cancel({ reason, offer: false })">Cancel my plan</button>
  </div>
</template>
```

`ReasonPicker` and `OfferCard` are your components. `cancel({ reason, comment, offer })` returns `{ offer }` when a save offer applies and none was made to the customer in the last 12 months. Otherwise it cancels and returns `{ canceled: true, endsAt }`, with `endsAt` in epoch milliseconds. `offer: false` cancels at once. `acceptOffer(offer)` applies the offer on the server. The browser only names the offer by its `id`: the server checks that it made this offer to this billing entity, that nobody took it yet, and that it is still open, for an hour after it was made.

A `SaveOffer` carries its real terms: `kind: 'pause'` with `months`, `resumesAt` and the current `plan`; `kind: 'downgrade'` with the cheaper `plan` and `appliesAt`; `kind: 'discount'` with the catalog `discount`, its `name`, `percentOff` or `amountOff`, `duration` and `months`. The cancel flow records `billing.save_offer_made` and `billing.save_offer_accepted` on the [activity trail](/docs/build/billing/events#on-the-activity-trail).

## The rules it keeps

A save offer is lawful when it is one honest step on the way out, not a wall. `<CancelFlow>` keeps these rules, and `useBilling()` enforces the ones a server can:

- **One optional step.** At most one question and one offer, both skippable: "Cancel my plan" is on every screen and finishes the cancellation at once.
- **One offer per cancellation,** and one save offer per billing entity in 12 months. Someone who cancels again within the year cancels in one step.
- **The same weight for both choices.** Accept and cancel are buttons of the same size and style. There is no countdown, no "offer ends when you leave", and no guilt in the labels.
- **No offer where it would stand in the way of a right.** None during the EU withdrawal period while the [withdrawal button](/docs/ship/compliance/subscriptions) is on, none on a past-due plan, and none on a trial. An offer goes only to an active plan.
- **The portal stays open.** Polar's portal cancels without any offer, and the package never hides its link.

That is the line between a save offer and the obstruction consumer law forbids. California's automatic renewal law requires cancellation online, and the EU requires a withdrawal button since 2026-06-19. [Follow subscription law](/docs/ship/compliance/subscriptions) covers both. This is not legal advice: check the rules where you sell.

## Pause instead of cancel

A pause suits someone who will be back: a seasonal user, or someone between projects. `useBilling().pause({ resumesAt })` pauses at the period's end, with or without the cancel flow ([Pause and resume](/docs/build/billing/subscriptions#pause-and-resume)). While a plan is paused, Polar revokes its benefits: features close and plan credits stop. Credits from packs stay. Resuming starts a new period and charges the card on file at once.

## Win people back

`setupEmail({ lifecycle: { winBack } })` writes to a former subscriber 7 and 30 days after the plan ended ([Send lifecycle emails](/docs/build/growth/engage/lifecycle-emails#the-ready-made-flows)). The emails go out under a marketing topic, so only people who opted in get them. They stop as soon as the person subscribes again. The 30-day email may carry a discount, shown with its real end date.

The flow starts from `billing.subscription_revoked`, the plan ended, and stops at `billing.subscription_created`. The cancellation reason shapes the message: "Panels now draws team boards" for someone who left for `missing_features`, a pause reminder for `unused`. `billing.subscription_canceled` carries the customer's `reason`, which Polar keeps on the subscription, and the win-back's event carries it on to Resend, for a condition in the flow's automation or for its template.

## What happens when…

| Situation | Result |
|---|---|
| A member who is no billing manager cancels | Refused as `forbidden`, reason `not_billing_manager` ([Who may buy for a workspace](/docs/build/billing/setup#who-may-buy-for-a-workspace)) |
| `acceptOffer` gets an offer the server did not make, or one already used | Refused as [`invalid_input`](/docs/reference/backend/errors#invalid_input), and nothing changes |
| The subscription is already set to cancel | Refused as `invalid_input`, reason `cancel_scheduled`: Polar takes one cancellation per period |
| The plan is past due, on a trial, or inside the withdrawal period | No offer: `cancel` cancels at the period's end |
| Polar is unreachable | Refused as [`unavailable`](/docs/reference/backend/errors#unavailable). The portal link stays as a fallback. |
| The offer's discount was retired, has a code, or does not apply to the plan | That reason cancels without an offer |
| An offer is accepted after an hour, or twice | Refused as `invalid_input` (`offer`): the flow's sitting is over |

## Limits

- **A pause lasts 1 to 3 months.** Longer pauses rarely come back, and Polar needs a resume date after the period's end.
- **A downgrade waits for the period's end.** Polar schedules a change one period ahead at most, so an offer never takes effect mid-cycle.
- **No offer in the portal.** Polar's portal has no save-offer step. Customers who cancel there skip the flow, and that is how it should be.
- **A workspace cancels as a whole.** There are no seats, so no offer shrinks a team.

## Test it

Run the flow on Polar's sandbox after a checkout with the test card:

```ts [tests/e2e/cancel-flow.spec.ts]
import { expect, test } from '@playwright/test'

test('a customer who finds Panels too expensive sees the save discount', async ({ page }) => {
  await page.goto('/settings/plan')
  await page.getByRole('button', { name: 'Cancel plan' }).click()
  await page.getByLabel('Too expensive').check()
  await page.getByRole('button', { name: 'Continue' }).click()
  await expect(page.getByText('30% off for 3 months')).toBeVisible()
  await page.getByRole('button', { name: 'Cancel my plan' }).click()
  await expect(page.getByText(/Your plan ends on/)).toBeVisible()
})
```

[Run end-to-end tests](/docs/develop/testing/e2e) signs a test account in and checks out with `4242 4242 4242 4242` first.
