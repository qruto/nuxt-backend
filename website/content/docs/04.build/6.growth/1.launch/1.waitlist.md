While your app is in [early access](/docs/build/growth/launch), a new address joins a waitlist instead of signing up. Every entry is proven by an email code, so the list holds real people. Each person sees their place and moves up when friends join through their link. Administrators admit people in waves from the console's **Waitlist** tab, then open the doors.

- **Natively:** Resend keeps contacts in Segments and lets them opt in to Topics; Convex's aggregate component ranks rows. Neither runs a waitlist (checked on 2026-10-25).
- **The package adds:** the list in the `backend` component, the join flow on the sign-in code, positions on the aggregate component, the referral boost, waves from the admin console, and a durable mirror of the people who asked for launch news into a Resend segment and topic. The aggregate and the mirror's workpool are nested inside the `backend` component: nothing else is mounted.

## Set it up

`backend/waitlist.ts` adds the waitlist to your launch phases:

```ts [backend/waitlist.ts]
import { setupWaitlist } from 'nuxt-backend/access'
import { components } from './_generated/api'
import { access } from './access'
import { email } from './email'
import { paths } from './paths.generated'

export const waitlist = setupWaitlist(components, {
  access,
  email,
  paths,
  questions: { role: ['Writer', 'Illustrator', 'Reader'] },
})

// The functions behind useWaitlist, <WaitlistForm> and the Waitlist tab.
export const { getWaitlistQuestions, joinWaitlist, waitlistStatus, leaveWaitlist, getWaitlistConsole, admitWaitlist, declineWaitlist, noteWaitlist, getWaitlistCaps } = waitlist.api
```

`paths` comes from the [paths file](/docs/reference/configuration/module-options#the-paths-file) the module writes from `nuxt.config`: the "You're in" email links to its `login` page, so it follows `backend.pages.login`. `questions` are your own, asked beside the address: up to five, each with up to twenty choices. Each answer is checked against its choices and kept with the entry. `getWaitlistQuestions` hands them to the form.

The waitlist is built on [`setupAccess`](/docs/build/growth/launch): the join only works while `early-access` is one of its `phases`, and an admitted entry is a ticket. The Waitlist tab shows once the app has `backend/waitlist.ts`.

## Show it in a page

People join from either of two places, with the same steps:

- **The sign-in page.** In early access, a new address asks for a code as usual. Checking the code records the entry, and the flow moves to its `waitlisted` step, which shows the person's place.
- **Your landing page.** `<WaitlistForm>` asks for the address, your questions and the launch-news box, then the code, then shows the place. `useWaitlist()` runs the same steps for markup of your own: `join`, `verify`, `status`, `leave`, `isPending` and `error`, with `bind` for the fields. `join` passes the [bot check](/docs/build/auth/sign-in/bots), keeps the answers and asks for the sign-in code; `verify` checks it on the same route a sign-in uses.

```vue [app/pages/index.vue]
<script setup lang="ts">
const { phase } = useAccessPhase()
const position = ref<number>()
</script>

<template>
  <WaitlistForm v-if="phase === 'early-access'" @joined="place => (position = place.position)" />
  <p v-if="position">You're number {{ position }}. We'll email you when your wave opens.</p>
</template>
```

What a join does, and what it leaves alone:

- **Proven by the code.** The code is the double opt-in: an entry is made when the code checks, so it is never someone else's address. What a join carries (the answers, the launch-news box, a friend's code) waits for the code for a day at most, and changes nothing about anyone until then.
- **Its own budget.** Join codes spend the deployment-wide `signUpOtpGlobal` limit, so a rush of joins never delays existing people's codes. Each join passes the [bot check](/docs/build/auth/sign-in/bots) first, and an address may join five times an hour (`waitlistJoin`, with `waitlistJoinGlobal` across the deployment).
- **Nothing more.** A person waiting gets no account, no workspace, no welcome email and no billing customer.
- **Their record.** Each entry keeps the address, its status (waiting, admitted, declined or joined), when it was verified, where it came from, the answers, the language and a note. A person can leave with `leave()`. [Erasure by address](/docs/build/auth/accounts/data#someone-without-an-account) removes the entry and its contact.

## Launch news, for those who ask

The join form has a box for launch news, unticked. Only the people who tick it become contacts at the email provider, in a segment of their own, subscribed to your launch topic. The time and the words they agreed to (the label the form showed beside the box) are kept on the [consent ledger](/docs/build/auth/accounts/consents) alone, by a hash of the address, and the sign-up carries them over to the account; the entry keeps only whether its contact is written. Everyone else hears from you once, when they are admitted ([Guardrails on growth features](/docs/start/concepts/principles#guardrails-on-growth-features)).

The mirror runs on Convex's workpool component. It creates the segment (`Waitlist`) and the topic (`Launch news`) on the first contact, then writes each contact in one call. It retries with backoff, flags a contact that could not be written as `drift`, and writes it again in the hourly maintenance pass, so the segment matches the list even when the provider was down. Leaving or erasure removes the contact. In email test mode only the provider's test addresses are written. `waitlist.launchAudience(ctx)` answers the segment and topic ids for a launch announcement.

## Position and referral boost

A person waiting sees "You're #48 of 1,204". The line is ordered by when people were verified, moved up by their boost, and Convex's aggregate component keeps it. Its writes are queued, so a rush of joins never contends on one row, and a place can run a few seconds behind.

- **A status link.** The confirmation email, sent once when the code checks, carries a signed link to the person's status page, `/waitlist#<token>`. Checking a place costs no sign-in email. The link's signature is derived from `AUTH_SECRET`, so nothing is stored for it, and the page keeps the token in the address so it can be bookmarked.
- **A referral boost.** Each person has a share code, the same kind the [referral program](/docs/build/growth/offers/referrals) hands out: the code of a person who is waiting becomes their referral code when their address signs up. A link to your form with `?ref=<code>` carries it. The form reads it once, shows "A friend invited you" with a way to drop it, and sends it with the join; nothing is stored on the device. Each friend who joins and verifies through it moves the sharer up a day in the line, up to ten friends. Nothing counts for the sharer's own mailbox (`+tag` addresses and dots included), for an address already on the list, or for an unknown code. The boost is taken back if the friend leaves, is erased or is removed for abuse. The program-wide codes and rewards are the [referral program's](/docs/build/growth/offers/referrals).
- **Honest words.** The status page, the sign-in page's `waitlisted` step and the confirmation email say "We admit in waves and may also admit by other criteria. Your position can change." The share text says the sharer gains from it. No names and no leaderboards are ever shown.

## Admit in waves

The Waitlist tab lists entries oldest first, filtered by status, domain, source or answer (a filter looks through the oldest thousand of the status), with a count per status and the contacts that drifted. It offers:

- **Approve** the entries ticked, or **the next N** (up to 200 at a time, in the order of the line, boost included). The tab shows "Room for a wave": the sign-in codes left this hour and the email plan's daily quota.
- **Decline**, **remove as abuse** (which takes back what each gave the friend who shared with it), and **add a note**.

Every change asks for a recent sign-in and lands on the [activity trail](/docs/build/auth/admin/audit-log), never with an address. An approved person gets a plain "You're in" email in their language: no token and no promotion, sent once. They sign up with the address they joined with, since an admitted entry is a [ticket](/docs/build/growth/launch#what-admits-a-new-address).

## Launch

When you're ready, move the phase on in the Access tab ([Change the phase](/docs/build/growth/launch#change-the-phase)). Waiting people are not admitted in bulk: each one's entry turns into an account when they next sign in.

To tell them, send a launch announcement to the launch-news segment at the same moment, scheduled ahead or sent now ([Announce product news](/docs/build/growth/engage/announcements#launch-from-a-waitlist)). It goes out at most once. It is refused in email test mode, and without the unsubscribe link and your postal address in its template. An entry whose address signs up turns `joined`.

## What happens when…

- **Someone joins twice:** the second join finds the first entry and shows its place. No duplicate is made.
- **Someone joins with another person's address:** nothing happens to that person. A join's answers, launch-news box and share link wait for a code typed in the same browser that joined (`joinWaitlist` answers a key that `useWaitlist().verify` sends back). The address's owner signing in from anywhere else records a bare entry at most.
- **The code is wrong or expired:** `verify` is refused as [`invalid_input`](/docs/reference/backend/errors#invalid_input) on `otp`, like a sign-in code.
- **An answer is not among its choices:** the join is refused as `invalid_input` on that question's field.
- **The bot check fails:** the join is refused as [`forbidden`](/docs/reference/backend/errors#forbidden) with reason `bot_check`.
- **The email provider is down:** the entry is recorded, and the mirror retries the contact later.
- **The phase is no longer `early-access`:** new joins are refused as `forbidden` with reason `waitlist_closed`, and every existing entry keeps its place.
- **A person leaves:** their entry and contact are removed, and the friends behind them move up. They can join again.

## Limits

- **One list per app.** There is no waitlist per plan or per feature.
- **Your email plan caps a wave.** A free plan of 100 emails a day carries one small wave at most; the Waitlist tab shows the quota beside the approve button. `npx nuxt-backend doctor --prod` warns about a waitlist with no bot check live ([`waitlist-bot-check`](/docs/reference/cli/diagnostics#waitlist-bot-check)).
- **The boost has a cap per person**: ten friends, a day each, so one sharer can't jump the whole list.
- **Sign-up is at the sign-in.** A person admitted from the list signs up with the address they joined with; an address with an account is joined, not admitted.

## Test it

Drive a join end to end: ask for a code, read it from the dev inbox and expect a place ([Run end-to-end tests](/docs/develop/testing/e2e)). In a backend test, check that a waiting person gets no account:

```ts [backend/waitlist.test.ts]
import { defineBackendTestApp } from 'nuxt-backend/test'
import { expect, test } from 'vitest'
import { api } from './_generated/api'
import schema from './schema'

const testApp = defineBackendTestApp(schema, import.meta.glob('./**/*.ts'))

test('a person who never verified has no place', async () => {
  const t = testApp()
  await t.action(api.waitlist.joinWaitlist, { email: 'mo@panels.example', answers: { role: 'Illustrator' } })
  // A status link is signed: nothing names an address that was never verified.
  expect(await t.query(api.waitlist.waitlistStatus, { token: 'mo@panels.example' })).toBeNull()
})
```
