`setupAuth` asks your code at three moments: before anyone signs in or signs up (`canSignIn`), once an account exists (`onUserCreated`), and once it is deleted (`onUserDeleted`). Each one gets the request's full Convex context, so it can read your tables, schedule work or start a workflow. Better Auth's own hooks are open too, and run beside the package's.

## Gate who signs in

`canSignIn(ctx, { email, isNewUser, purpose })` answers `true`, or `{ allowed: false, message? }` to refuse. It is asked at four points, named by `purpose`:

| `purpose` | Asked | `isNewUser` |
|---|---|---|
| `sign-in` | before a sign-in code is sent to `email` | whether the address has no account yet |
| `user-create` | before any account is created, by any route | always `true` |
| `session` | before a session opens for an existing account, a passkey sign-in included | always `false` |
| `email-change` | before a code goes to a signed-in person's new address, and again before the account moves to it | always `false` |

`email` is lower-cased, as Better Auth holds it. A closed beta for one domain refuses new accounts and new addresses elsewhere, and lets every existing account in:

```ts [backend/auth.ts]
export const { authComponent, createAuth, getAuthUser } = setupAuth(components, query, {
  email,
  rateLimiter,
  canSignIn: async (_ctx, { email, purpose }) => {
    if (purpose !== 'user-create' && purpose !== 'email-change') return true
    return email.endsWith('@acme.com')
      ? true
      : { allowed: false, message: 'Acme is open to acme.com addresses for now.' }
  },
})
```

A refusal is a `forbidden` error with reason `sign_in_refused`, and `useLoginFlow().error` shows your `message` as written. Without one, the person reads the `errors.forbidden_sign_in_refused` label ("Sign-in is by invitation right now." in English). To read an allow-list of your own, call it from the gate: `await ctx.runQuery(internal.beta.isAllowed, { email })`.

::warning
**Refuse at `user-create`, not at `sign-in`.** A refusal at `sign-in` answers whoever typed the address, so a gate that refuses new addresses there tells anyone which addresses have an account. Refused at `user-create`, the code goes out either way, and only the person holding the mailbox reads the refusal. The cost is a code email to every address that asks.

At `email-change` the gate answers a signed-in person about an address they typed. With `rateLimiter` passed, each answer costs one of the account's `emailChange` requests (five an hour), so an account cannot probe it for free.
::

A gate that refuses every new address also refuses the people your members invite to a workspace and the recipients of gifts, since both sign up as new accounts. In `0.2.0`, [launch phases](/docs/build/growth/launch) run waitlist and invite-only launches and admit those people themselves, and `canSignIn` stays your extra veto on top.

## Run code when an account is created

`onUserCreated(ctx, user)` runs in the request that created the account, after its welcome email went out. `user` holds `id`, `email` and `name`. The scaffold starts the onboarding sequence there:

```ts [backend/auth.ts]
setupAuth(components, query, {
  email,
  onUserCreated: async (ctx, user) => {
    await workflow.start(ctx, internal.workflows.onSignup, {
      userId: user.id,
      email: user.email,
      name: user.name,
    })
  },
})
```

Better Auth runs a failed after-hook a second time, so the hook can run twice for one account: key what it starts on `user.id`. A second failure fails the sign-up request, and the account stays created. [Email sequences](/docs/build/growth/engage/lifecycle-emails) has the onboarding sequence the scaffold ships.

## Run code when an account is deleted

`onUserDeleted(ctx, user)` runs once an account is deleted, after any `user.deleteUser.afterDelete` you pass in `authOptions`: tell a team channel, stop a workflow. Erasing your own tables does not belong here. A source of [`setupAccount`](/docs/build/auth/accounts/data#join-your-own-tables) runs for every deletion, server code's included, and is retried when it fails.

## Add Better Auth hooks of your own

`databaseHooks` you pass in `authOptions` compose with the package's: per model and operation, the package's hook runs first and yours second. A `before` hook receives the entity as the package left it (a new session already carries its active workspace), and a `false` from either side aborts the write.

To refuse with a message, throw `APIError`, re-exported from `nuxt-backend/auth` so there is no `better-auth` dependency to add. The client gets the status and the message:

```ts [backend/auth.ts]
import { APIError, setupAuth } from 'nuxt-backend/auth'

setupAuth(components, query, {
  email,
  authOptions: {
    databaseHooks: {
      user: {
        update: {
          before: async (user) => {
            if (typeof user.name === 'string' && user.name.trim().length > 60) {
              throw new APIError('BAD_REQUEST', { message: 'Keep your name to 60 characters.' })
            }
          },
        },
      },
    },
  },
})
```

Leave out plugins that add tables or fields: the `backend` component owns the auth schema ([Auth setup](/docs/build/auth/setup#change-the-auth-route)).

## Verify

1. With the closed-beta gate above, sign in with an address of another domain: the code arrives, and checking it shows your message.
2. Sign in with an existing account of another domain: it signs in.
3. Check the `convex dev` console after a sign-up: your `onUserCreated` ran once.
