`setupAuth` builds your app's auth in one call, in your Convex backend (`backend/`), not in the Vue app. It runs Better Auth inside the package's `backend` component and turns on sign-in codes and passkeys. Then it connects them to your email, rate limits, activity trail and erasure. The scaffold calls it for you, so most apps never change this file. Read on when you add a hook, move the auth route or pass Better Auth options of your own.

## The scaffolded files

`npx nuxt module add nuxt-backend` writes them when it installs the module (`npx nuxt-backend init` does the same later), and `nuxt-backend dev` restores any that go missing ([Installation](/docs/start/installation)). Auth needs three. A fourth, `backend/convex.config.ts`, mounts the `backend` component that holds the auth tables ([How it works](/docs/start/concepts/how-it-works#the-scaffolded-convexconfigts)).

```ts [backend/auth.config.ts]
export { default } from 'nuxt-backend/auth.config'
```

```ts [backend/auth.ts]
import { setupAuth } from 'nuxt-backend/auth'
import { components, internal } from './_generated/api'
import { query } from './_generated/server'
import { account } from './account'
import { audit } from './audit'
import { email } from './email'
import { rateLimiter } from './rateLimiter'
import { workflow } from './workflows'

export const {
  authComponent,
  createAuth,
  getAuthUser,
  authConfig,
  updateProfile,
  listSessions,
  revokeSession,
} = setupAuth(components, query, {
  email,
  rateLimiter,
  audit,
  account,
  onUserCreated: async (ctx, user) => {
    await workflow.start(ctx, internal.workflows.onSignup, {
      userId: user.id,
      email: user.email,
      name: user.name,
    })
  },
})
```

```ts [backend/http.ts]
import { registerBackendRoutes } from 'nuxt-backend/http'
import { httpRouter } from 'convex/server'
import { ai } from './ai'
import { authComponent, createAuth } from './auth'
import { billing } from './billing'
import { email } from './email'

const http = httpRouter()
registerBackendRoutes(http, { auth: { authComponent, createAuth }, billing, email, ai })

export default http
```

`registerBackendRoutes` mounts the auth routes beside the billing and email webhooks and the AI stream route. Every webhook delivery is signature-verified and refused until its secret is set ([Register webhooks](/docs/ship/security/webhooks)).

## `setupAuth(components, query, options)`

It takes your generated `components`, your `query` builder and the options below, and returns:

| Name | What it is |
|---|---|
| `authComponent` | The auth component client, for `registerBackendRoutes`. |
| `createAuth(ctx)` | The Better Auth instance for one request. |
| `getAuthUser` | A query: the signed-in account, or an `unauthenticated` refusal. |
| `authConfig` | A query: the paths the deployment serves on and links to, which `doctor` compares with `nuxt.config` ([`page-paths`](/docs/reference/cli/diagnostics#page-paths)). |
| `updateProfile` | A mutation: the caller's `name`, `image` and `locale`. Never the email address ([Profile](/docs/build/auth/accounts/profile)). |
| `listSessions`, `revokeSession` | The caller's devices and signing one out, behind `useSessions()` ([Security](/docs/build/auth/accounts/security)). |

`listSessions` reads the session table, so it works for a sign-in of any age, and returns ids, never session tokens. `revokeSession` signs out one of the caller's own sessions through Better Auth's route, so your session hooks still run.

### Codes, not links

Every proof of a mailbox is a one-time code: sign-in, and both halves of an email change. No link signs anyone in or moves an account, so a forwarded email or a scanner that opens every link changes nothing. Better Auth's link routes are off. The database keeps only a hash of each code, keyed by `AUTH_SECRET`, so reading the table yields no code. [Security model](/docs/ship/security#passwordless-sign-in-and-its-rate-limits) has the limits on guessing.

Each code is bound to the browser that asked for it, and every code, cookie and recovery code is tagged with its purpose: a sign-in code never confirms an email change, and a recovery code never signs in as a code ([Codes work only where they were asked for](/docs/build/auth/sign-in#codes-work-only-where-they-were-asked-for)).

## Cross-component wiring

Each option connects auth to another part of your backend. All are optional but `email`:

| Option | What it connects | Home |
|---|---|---|
| `paths` | The `paths` of the generated `paths.generated.ts`: the auth route, and the pages the auth emails link to (an invitation, a recovered passkey-only account, a waitlist place). The module writes the file from `nuxt.config`, so you never write a path here. | [The paths file](/docs/reference/configuration/module-options#the-paths-file) |
| `email` (required) | Your `setupEmail` instance. Every auth email goes out through it: codes, the welcome email, the email-change notice and invitations. | [Templates](/docs/build/email/templates) |
| `rateLimiter` | Limits on sending codes per address and for the whole deployment, on checking them, on email changes, and on the privileged routes. A closed limit answers `rate_limited` with the wait. | [Tune rate limits](/docs/ship/security/rate-limits) |
| `audit` | Your `setupAudit` instance, so the `auth` capability's events reach its `onEvent`. | [Record and review activity](/docs/build/auth/admin/audit-log) |
| `account` | Your `setupAccount` instance, so a deletion erases everything of the account. | [Export and delete an account](/docs/build/auth/accounts/data) |
| `access` | Your `setupAccess` instance: the launch phase and the tickets that admit a new address. | [Launch in phases](/docs/build/growth/launch) |
| `workspaces` | How long an invitation lasts (`invitationExpiresIn`, in seconds), a veto on invitations (`canInvite`), and the workspace hooks `onCreate`, `onMemberAdded` and `onMemberRemoved`. Only these: the organization plugin behind workspaces takes no other option from here, and any other key (a 0.1 `organizationHooks`, say) throws when `setupAuth` runs, so a guard you kept never fails open. | [Invite people to a workspace](/docs/build/auth/workspaces/invitations) |
| `canSignIn` | Your own gate on sign-in, sign-up, new sessions and email changes. | [Gate who signs in](/docs/build/auth/sign-in/hooks#gate-who-signs-in) |
| `onUserCreated`, `onUserDeleted` | Your code once an account exists, or once it is deleted. | [Sign-in hooks](/docs/build/auth/sign-in/hooks) |

Billing links provider customers to accounts, and keeps its feature and credit cache inside the `backend` component, so subscriptions and credits need nothing in your schema.

::note
Until `EMAIL_API_KEY` is set, a code request is refused with a message the form shows, and Resend's test addresses still get theirs. In development (`BACKEND_ENVIRONMENT=development`), every code also prints in the `convex dev` console ([Develop with real sandboxes](/docs/develop/sandboxes)).
::

## Auth route and options

The auth routes answer under `/api/auth` on your app's origin. The Nuxt module proxies them to the deployment.

### Extend Better Auth options

Better Auth's own options pass through: `admin` for the admin plugin, and `authOptions` for the rest. They merge with the package's defaults. `workspaces` takes the package's own options only, which it maps onto the organization plugin: an upstream option of that plugin is reachable only by ejecting `backend/auth.ts`.

```ts [backend/auth.ts]
export const { authComponent, createAuth, getAuthUser } = setupAuth(components, query, {
  email,
  authOptions: {
    appName: 'Panels',
    session: { expiresIn: 60 * 60 * 24 * 30 },
  },
  workspaces: { invitationExpiresIn: 60 * 60 * 24 * 7 },
})
```

`databaseHooks` you pass in `authOptions` compose with the package's ([Add Better Auth hooks of your own](/docs/build/auth/sign-in/hooks#add-better-auth-hooks-of-your-own)).

::warning
The package runs Better Auth 1.6 until Convex's Better Auth component accepts 1.7 ([Roadmap](/docs/start/roadmap)). Three 1.6 advisories, fixed only in 1.7, sit in plugins the package leaves off: magic links together with social sign-in ([GHSA-965c-763c-88jm](https://github.com/better-auth/better-auth/security/advisories/GHSA-965c-763c-88jm)), the OAuth proxy ([GHSA-r4xp-prcw-77qf](https://github.com/advisories/GHSA-r4xp-prcw-77qf)) and the device authorization grant ([GHSA-q84f-53jg-9ppm](https://github.com/advisories/GHSA-q84f-53jg-9ppm)). Don't add those plugins in `authOptions.plugins` until then.
::

::note
The `backend` component owns the auth schema. Keep data of your own in app tables keyed by the user id, not in extra fields on `user`. Leave out Better Auth plugins that add tables or fields: the packaged schema has no room for them.
::

### Change the auth route

Set the module's `authRoute`. It is the one place the path lives: the module writes it to `backend/paths.generated.ts`, where the auth routes, the Convex auth config and the proxy read it ([The paths file](/docs/reference/configuration/module-options#the-paths-file)).

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-backend'],
  backend: { authRoute: '/internal/auth' },
})
```

The next `nuxt prepare` or `dev` rewrites the paths file, and the scaffolded `auth.config.ts` and `auth.ts` pass it on:

```ts [backend/auth.config.ts]
import { defineBackendAuthConfig } from 'nuxt-backend/auth.config'
import { paths } from './paths.generated'

export default defineBackendAuthConfig({ paths })
```

Push the functions with the new file: until the deployment serves the new route, the proxy forwards to one it does not, and sign-in fails. `npx nuxt-backend doctor` says so ([`page-paths`](/docs/reference/cli/diagnostics#page-paths)).
