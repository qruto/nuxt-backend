Two kinds of role decide what a person may do. An **app-wide role** holds everywhere in your app: `user` for everyone, `admin` for the people who run it, and names of your own such as `editor`. A **workspace role** holds inside one workspace: `owner`, `admin` or `member`. Better Auth's admin plugin keeps the first, and its organization plugin the second. The package puts both on the session token, checks them in your pages and functions, and reads them fresh where a stale answer would matter.

## App-wide roles

Every account starts as `user`. The role decides what the app lets a person do anywhere:

| Role | Gives |
|---|---|
| `user` | The app, as every signed-in person sees it. |
| `admin` | The [admin console](/docs/build/auth/admin) at `/admin`, the `admin` function tier, and your own pages guarded by `role: 'admin'`. |
| A name of yours, such as `editor` | What your own pages and functions grant it, through `withRole('editor')` and `role: 'editor'`. |

### Make the first administrator

A new deployment has none. Sign in once with your own address, then run `doctor --fix` and enter that address when it asks:

```bash
npx nuxt-backend doctor --fix
```

In CI or a script, call the scaffold's internal `setUserRole`, which no browser can reach:

```bash
npx convex run functions:setUserRole '{"email":"you@example.com","role":"admin"}'
```

Both record the change on the [activity trail](/docs/build/auth/admin/audit-log), as the app's.

### Give a role of your own

Administrators set roles from the Users tab of the admin console. List the roles it offers with `<AdminUsers>`'s `roles` prop, on your own admin page:

```vue [app/pages/admin/people.vue]
<script setup lang="ts">
definePageMeta({ auth: { role: 'admin' } })
</script>

<template>
  <AdminUsers :roles="['user', 'editor', 'admin']" />
</template>
```

A role is a name: there are no permission lists to define. Then check it wherever it grants something:

```ts [backend/strips.ts]
import { v } from 'convex/values'
import { withRole } from './functions'

export const feature = withRole('editor').mutation({
  args: { stripId: v.id('strips') },
  handler: async (ctx, { stripId }) => {
    await ctx.db.patch('strips', stripId, { featured: true })
  },
})
```

## Workspace roles

Every member of a workspace has one built-in role in it. The person who creates a workspace is its `owner`, and the people they invite join as `member` or `admin`:

| Role | May |
|---|---|
| `owner` | Everything an admin may, and keep the workspace: Better Auth refuses to leave a workspace without an owner. |
| `admin` | Invite people, cancel invitations, remove members and change their roles. Manage the workspace's plan and credits. |
| `member` | Work in the workspace, and see its members and usage. |

[Manage members](/docs/build/auth/workspaces/members) changes them. Roles an owner defines, and billing as a permission inside a role, wait for the next release ([Roadmap](/docs/start/roadmap#service-app-features)).

## Check a role

| Where | App-wide role | Workspace role |
|---|---|---|
| A page | `definePageMeta({ auth: { role: 'admin' } })` | `workspace: 'owner'` in the same rules ([Protect pages](/docs/build/auth/access/pages)) |
| A part of a page | `<Gate role="editor">` | `<Gate workspace="owner">` |
| A function | the `admin` tier, or `withRole('editor')` | the `workspace` tier, then `ctx.workspace.role` |
| Your own markup | `useAuth().hasRole('editor')`, or `useAuth().role` | `useWorkspace().role` |

`<Gate>` and page rules decide what the screen shows. The function checks are the ones that protect data, so every function a page calls keeps its tier ([Protect backend functions](/docs/build/auth/access/functions)).

## How fresh a role is

The app-wide role rides on the session token, so a check costs no read. A token can lag a change by up to fifteen minutes, its lifetime. Where that matters, the package reads the account instead:

- The `admin` tier reads the role fresh on every call, so a demoted administrator is refused at once.
- Writes of `authed` and `withRole` read the account fresh, so a ban lands on the next write.
- A workspace role is always read fresh from the member table.

A role you give in the console reaches the person's own token at their next refresh. Their pages catch up then, and their calls are checked right away.
