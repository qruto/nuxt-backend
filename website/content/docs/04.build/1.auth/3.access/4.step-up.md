A session can outlive the person who opened it: a laptop left open, a cookie copied off a machine. Most of what an account does is fine for such a session. A few actions are not, so they take a **recent sign-in**, one from the last ten minutes. Saving or removing a passkey takes one. So do deleting the account, inviting people to a workspace or changing who belongs to it, and an administrator's writes. An older session is refused with [`reauthentication_required`](/docs/reference/backend/errors#reauthentication_required). The person confirms it's them with a passkey or a code, and the action runs again.

Better Auth's own `session.freshAge` covers its passkey routes. The package extends the same window to every sensitive route and function, and adds the dialog that asks.

## How it works

- **Every session knows when its sign-in happened.** The session token carries the time, which no field of your user table can write.
- **One window.** A sensitive action compares that time with ten minutes, `RECENT_SIGN_IN_SECONDS` (600) from `nuxt-backend/functions`. Better Auth's `session.freshAge` is set to the same value, so its own checks agree.
- **Confirming is an ordinary sign-in.** It is held to the account it replaces: another account's passkey is refused (`forbidden`, reason `other_account`). The new session keeps the active workspace, and the old one is signed out. The client waits for the live connection to take the new token, so the retried action carries it.
- **It fails closed.** An administrator's visit to the account never passes (`forbidden`, reason `impersonating`): the administrator can't sign in as the person. A session that carries no sign-in time is refused as `reauthentication_required`.

Signing devices out never asks. Revoking a session is how a person defends an account they fear for, and it must work the first time.

## Ask in the UI

`useReauthentication().withReauthentication(action)` runs the action. When the server refuses it as `reauthentication_required`, it opens `<ReauthenticateDialog>`, waits for the person to confirm, and runs the action once more. A cancelled dialog rejects with the first refusal, so the error your page shows says why nothing happened.

```vue [app/pages/team.vue]
<script setup lang="ts">
const { members, removeMember } = useWorkspace()
const { withReauthentication } = useReauthentication()

async function remove(memberId: string) {
  await withReauthentication(() => removeMember(memberId))
}
</script>

<template>
  <ul>
    <li v-for="member in members" :key="member.id">
      {{ member.user.name }}
      <button type="button" @click="remove(member.id)">Remove {{ member.user.name }}</button>
    </li>
  </ul>
</template>
```

`<SecuritySettings>`, `<AccountData>` and the admin console already do this, and render the dialog themselves. For your own pages, mount the dialog once in your layout. Of every dialog on a page, only the oldest opens:

```vue [app/app.vue]
<template>
  <NuxtLayout>
    <NuxtPage />
  </NuxtLayout>
  <ReauthenticateDialog />
</template>
```

The dialog offers the passkey first, and a code to the account's own address beside it. The code request passes the [bot check](/docs/build/auth/sign-in/bots) like the sign-in form's. Its words are the `reauthenticate` label group.

To build your own dialog, call `useReauthentication({ prompt: true })` in the component that renders it. It returns `isRequired`, `step` (`choose`, then `verify-code`), `email`, `otp`, `isPending`, `error`, and the step actions `withPasskey`, `sendCode`, `verifyCode`, `back` and `cancel`, which never reject. With no prompt on the page, `withReauthentication` rejects with the refusal as it came, and a development build warns that the dialog is missing.

## Ask in your own functions

A function built from the [tiers](/docs/build/auth/access/functions) declares it beside `args`: `recentSignIn: true` for ten minutes, or a number of seconds. The `admin` tier's mutations and actions ask by default, and a routine one says `recentSignIn: false`:

```ts [backend/strips.ts]
import { admin, workspace } from './functions'

export const archiveAll = workspace.mutation({
  recentSignIn: true,
  args: {},
  handler: async (ctx) => {
    const strips = await ctx.db.query('strips')
      .withIndex('workspaceId', q => q.eq('workspaceId', ctx.workspace.id))
      .take(500)
    for (const strip of strips) await ctx.db.patch('strips', strip._id, { archived: true })
  },
})

export const reindex = admin.action({
  recentSignIn: false, // an admin write, but a routine one
  args: {},
  handler: async () => {},
})
```

Only a mutation or an action asks. A query is not rerun as time passes, so its window would not hold, and defining one with `recentSignIn` throws. Ask in the mutation or action the sensitive step runs in.

A function checks the recent sign-in last, after roles and membership. Someone who may not act at all is told so, and never asked to sign in again first.

## In tests

`asUser(t, { signedInAt })` from `nuxt-backend/test` opens the session at that time, so a test can call as a sign-in older than the window:

```ts [backend/strips.test.ts]
const stale = await asUser(t, { signedInAt: Date.now() - 11 * 60_000 })
await expect(stale.mutation(api.strips.archiveAll, {})).rejects.toThrow()
```

By default, every caller signed in a moment ago.
