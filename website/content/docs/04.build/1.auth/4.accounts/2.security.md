A person who fears for their account needs one place to act: see every device signed in, sign the strange one out, and add a passkey. The module mounts `/security` (module option `pages.security`), guarded for signed-in people. It renders `<SecuritySettings>` in sections you pick with `sections`: `passkeys`, `sessions` and `danger` (signing this browser out). Below it, `<AccountData>` exports and deletes the account ([Export and delete an account](/docs/build/auth/accounts/data)).

Better Auth keeps the passkeys and the sessions. The package adds the page, a session list that works at any age, the recent activity, and the "Confirm it's you" step before a passkey changes. It also keeps the browser's passkey list in step, and lets a person turn sign-in codes off.

```vue [app/pages/security.vue]
<script setup lang="ts">
definePageMeta({ auth: true })
</script>

<template>
  <SecuritySettings :sections="['passkeys', 'sessions']" />
</template>
```

## Passkeys

`usePasskeys()` lists the person's passkeys and adds, renames and removes them:

```vue [app/components/PasskeyList.vue]
<script setup lang="ts">
const { passkeys, add, remove, isPending, error } = usePasskeys()
const { withReauthentication } = useReauthentication()
</script>

<template>
  <ul>
    <li v-for="passkey in passkeys" :key="passkey.id">
      {{ passkey.name }}
      <button type="button" @click="withReauthentication(() => remove(passkey.id))">Remove {{ passkey.name }}</button>
    </li>
  </ul>
  <button type="button" :aria-disabled="isPending || undefined" @click="withReauthentication(() => add({ name: 'Laptop' }))">Add a passkey</button>
  <p v-if="error" role="alert">{{ error.message }}</p>
</template>
```

- **Adding and removing take a [recent sign-in](/docs/build/auth/access/step-up).** `<SecuritySettings>` asks with the dialog it renders. Your page wraps the call in `withReauthentication`, as above. Renaming never asks.
- **Failures.** The list loads in the browser, and a failed load lands in `error`. `add`, `rename` and `remove` reload the list, and reject on failure, a cancelled passkey prompt included.
- **An administrator's visit** sees the passkeys and can change none of them: a passkey would let them back in after the visit.
- **The device follows.** Loading the list, which a removal reloads, tells the browser which passkeys the account still holds (`signalAllAcceptedCredentials`), so a removed one stops showing in the device's prompt. A name or address change updates the passkey's label (`signalCurrentUserDetails`) ([Keep the browser's passkey list in step](/docs/build/auth/sign-in#keep-the-browsers-passkey-list-in-step)).

### What this browser supports

`usePasskeys().capabilities` holds what the browser's `getClientCapabilities()` reported, or `null` before it answers or in a browser without it. Read it to hide a button that can't work:

```vue [app/components/AddPasskey.vue]
<script setup lang="ts">
const { add, capabilities } = usePasskeys()
const { withReauthentication } = useReauthentication()
</script>

<template>
  <button
    v-if="capabilities?.passkeyPlatformAuthenticator !== false"
    type="button"
    @click="withReauthentication(() => add({ name: 'This device' }))"
  >
    Add a passkey
  </button>
</template>
```

The keys are the browser's own, such as `conditionalGet`, `hybridTransport` and `passkeyPlatformAuthenticator` ([WebAuthn client capabilities](https://web.dev/articles/webauthn-client-capabilities)). `useLoginFlow` reads the same answer before it offers a passkey.

## Passkey-only

A person with a passkey can turn sign-in codes off, so a stolen mailbox can't sign in to the account. `<SecuritySettings>` shows the switch in its `passkeys` section, labeled "Sign in with passkeys only", once the account has a passkey; while it is on, "Make a new recovery code" issues a new one.

```vue [app/components/PasskeyOnly.vue]
<script setup lang="ts">
const { passkeyOnly, setPasskeyOnly, passkeys } = usePasskeys()
const { withReauthentication } = useReauthentication()
const recoveryCode = ref<string | null>(null)

async function turnOn() {
  const answer = await withReauthentication(() => setPasskeyOnly(true))
  recoveryCode.value = answer.recoveryCode
}
</script>

<template>
  <button v-if="!passkeyOnly" type="button" :aria-disabled="!passkeys?.length || undefined" @click="turnOn">
    Sign in with passkeys only
  </button>
  <button v-else type="button" @click="withReauthentication(() => setPasskeyOnly(false))">
    Allow sign-in codes again
  </button>
  <p v-if="recoveryCode">
    Your recovery code: <code>{{ recoveryCode }}</code>. Keep it somewhere safe. It is shown once.
  </p>
</template>
```

- **`passkeyOnly`** is `true` while the account refuses sign-in codes.
- **`setPasskeyOnly(on)`** takes a recent sign-in, and refuses an administrator's visit. Turning it on needs at least one passkey, and resolves with `{ recoveryCode }`. Turning it on again issues a new code, and the old one stops working.
- **Removing the last passkey** of a passkey-only account is refused, so the account can't lock itself out. Allow codes again first.
- **Recovery.** "Lost your passkey?" on the sign-in page takes the address and the recovery code, then asks for a new passkey before anything else ([Passkey-only accounts](/docs/build/auth/sign-in#passkey-only-accounts)). The person gets an email saying so, and the sign-in page shows the new recovery code that replaced the used one, once. "Make a new recovery code" here replaces it again.

Store the recovery code as a person would store a password: in a password manager, or on paper. The package keeps only its SHA-256 hash, tagged for recovery and bound to the account, so it can't be used as a sign-in code or an email-change code. The hash takes no key, so rotating the auth secret never stops a code working. The account's session and `getAuthUser` never return it.

## Signed-in devices

`useSessions()` is a live list of the person's unexpired sessions, the latest expiry first, with `current` marking this browser. Each session carries `device`, a readable label such as `Chrome · macOS`, or `null` when the browser said nothing useful.

- `revoke(id)` signs one session out, and `revokeOthers()` every other one. Each rejects with what the call threw.
- While the session itself is still being read, server rendering included, `sessions` is `undefined` and `isLoading` is `true`, never an empty list.
- A failed read lands in `listError`, apart from an action's failure in `error`.
- It works for sessions of any age. Better Auth's own session list refuses a sign-in older than ten minutes, so the package reads the session table instead, and returns ids, never session tokens.

In `0.2.0`, a sign-in from a new device also tells the person, in the app and by email, with a link back here ([Alert people to new sign-ins](/docs/build/auth/accounts/alerts)).

## Recent activity

Below the sections, the page lists what happened to the account, newest first, ten at a time. It shows sign-ins and sign-outs, passkeys, email changes, devices signed out, workspaces joined or left, and what an administrator did to the account. It is `<AuditLog>` over the [activity trail](/docs/build/auth/admin/audit-log), which keeps a year of it.

## Deletion and sign-out

`<AccountData>`, below the sections, deletes the account. The person types their address and confirms it's them, and the account is deleted after a grace period ([Delete an account](/docs/build/auth/accounts/data#delete-an-account)). Removing a passkey asks first: in the component's own styled dialog, or through the `confirm` prop when you pass one.

Signing out here goes to the sign-in page. A sign-out in another tab, or this session revoked from another device, ends the session under the open page. The module then sends the person to sign in, with `?redirect=` back to `/security` ([When the session ends](/docs/build/auth/access/pages#when-the-session-ends)).

## Its props, events and slots

`<SecuritySettings>` takes `sections`, `confirm` and `labels`. It emits `passkey-added`, `passkey-removed(id)`, `session-revoked(id)`, `sessions-revoked`, `signed-out` and `error(message)`. Its slots are `passkeys`, `passkey`, `sessions`, `session`, `danger` and `footer`. Its words are the `security` label group ([Translate the UI](/docs/build/ui/customize/translation)). Each row's buttons are named after the passkey or the session they act on.

To restyle it, the customization ladder applies: tokens, labels, slots, then swapping a part such as `SecurityPasskeys` with a component of yours of the same name ([Customization ladder](/docs/build/ui/customize)).

## What happens when…

| Refused with | When |
|---|---|
| [`reauthentication_required`](/docs/reference/backend/errors#reauthentication_required) | Adding or removing a passkey, or switching passkey-only, with a sign-in older than ten minutes. The dialog asks, then the action runs again. |
| [`forbidden`](/docs/reference/backend/errors#forbidden), reason `impersonating` | An administrator's visit tries to change a passkey or passkey-only. |
| [`invalid_input`](/docs/reference/backend/errors#invalid_input), field `passkeys` | Passkey-only is turned on without a passkey, or the last passkey of a passkey-only account is removed. |
| [`unavailable`](/docs/reference/backend/errors#unavailable) | The browser cancelled the passkey prompt, or has no passkey provider. |

## Limits

- **Signals and capabilities** need Chrome or Edge 132, or Safari 26. Elsewhere the page works the same, and a removed passkey stays on the device until the person deletes it there.
- **One recovery code** per passkey-only account. Without it and without a passkey, only an administrator can turn passkey-only off.
- **Sessions** list the first 100 per account.

## Test it

A function test calls the same routes as the page. `asUser` opens a fresh session, so the recent sign-in passes ([Test backend functions](/docs/develop/testing/functions)):

```ts [backend/security.test.ts]
import { asUser, defineBackendTestApp } from 'nuxt-backend/test'
import { expect, test } from 'vitest'
import { api } from './_generated/api'
import schema from './schema'

const testApp = defineBackendTestApp(schema, import.meta.glob('./**/*.ts'))

test('lists the caller\'s sessions, never their tokens', async () => {
  const ada = await asUser(testApp(), { email: 'ada@example.com' })
  const sessions = await ada.query(api.auth.listSessions, {})
  expect(sessions).toHaveLength(1)
  expect(sessions[0]).not.toHaveProperty('token')
})
```
