- **You get:** an undeliverable step at sign-in in place of a code that never arrives, and a way for administrators to lift a suppression.
- **Powered by:** Resend's suppression list, which it fills after a hard bounce or a complaint, and its `suppression.added` and `suppression.removed` events.
- **The package adds:** a copy of the list on your deployment, read before a code is sent, the sign-in step, and the admin console's list with a lift action.

Tell a person at sign-in when their address can't receive your mail, instead of leaving them waiting for a code. When an email hard-bounces, or its reader marks it as spam, Resend adds the address to its suppression list and drops every later email to it, sign-in codes included. The package keeps a copy of that list on your deployment and checks it before a code is sent.

## How it works

1. **The provider decides.** Resend's suppression list stays the source of truth: the package never suppresses an address on its own.
2. **The deployment keeps a copy.** Resend's `suppression.added` and `suppression.removed` events reach `/email/events` with its delivery events, verified the same way, and so does `email.suppressed` for a send it dropped. The `backend` component records each suppressed address, and drops it once the suppression is lifted.
3. **Sign-in reads the copy first.** Before a code is sent, the request looks the address up in that copy, one indexed read with no provider call. A suppressed address gets an undeliverable step in place of a code. Its words are the same whether or not an account holds the address, so the step tells no one who has signed up. No code is minted, and none of the address's code budget is spent.
4. **An administrator lifts it.** The admin console's **Suppressions** tab lists the suppressed addresses and lifts one through Resend's suppressions API, and the next code goes out.

## Subscribe the webhook to suppressions

Point the Resend webhook at `/email/events` as [Track delivery](/docs/build/email/delivery#point-the-provider-at-the-route) shows, and subscribe it to `suppression.added` and `suppression.removed` beside the email events. `npx nuxt-backend doctor` reports a webhook that misses them (`email-webhook-events`). Until the events arrive, the copy is empty and sign-in sends codes as it does without it.

## What a person sees at sign-in

`useLoginFlow()` moves to an `undeliverable` step instead of the code step, and `<AuthForm>` shows it (the `AuthFormUndeliverable` part, the `undeliverable` slot): the app can't send mail to that address right now, so use another one, or ask for help, with a button back to the email field. A sign-in page of your own on the composable renders it like the other steps ([Build a custom sign-in page](/docs/build/auth/sign-in/custom-page)). Its words are labels, translated with the rest: `auth.undeliverable` and `auth.tryAnotherEmail`.

The code request answers `unavailable` with service `email` and reason `suppressed`, the step's cause. Any other place that asks for a code, an email change to a new address included, reads it as the `errors.unavailable_suppressed` sentence.

A workspace invitation, a gift and your own `email.send` to a suppressed address go to Resend, which drops them and reports `email.suppressed` to your handlers ([React to events](/docs/build/email/delivery#reacting-to-events)).

## Try it on your dev deployment

Send any email to `suppressed@resend.dev`, Resend's test address for an address that bounced before. Resend drops it and posts `email.suppressed`, and the deployment records the address. Ask for a sign-in code with it on `/login`: the flow moves to the undeliverable step.

## Lift a suppression

Lift one when the cause is gone: a typo corrected, a mailbox that works again. A complaint means the person asked not to get your mail, so lift that one only when they ask you to. Lifting is an administrator's write: it asks for a [recent sign-in](/docs/build/auth/access/step-up), and the activity trail records `email.suppression_lifted`, with why it was suppressed and the account that holds the address, never the address.

The tab calls two functions the scaffold's `backend/email.ts` re-exports from `email.api`:

```ts [backend/email.ts]
export const { getSuppressions, liftSuppression } = email.api
```

- `getSuppressions({ paginationOpts })` pages through the suppressed addresses, newest first, with why each one is (`bounce`, `complaint`, `manual`, or `dropped` when only a dropped send told of it). Anyone but an administrator reads `null`.
- `liftSuppression({ email })` lifts one at Resend, then in the copy, and answers `{ lifted }`: `false` for an address the copy does not hold.

## Privacy

A suppressed address is personal data. The copy takes part in [account erasure](/docs/build/auth/accounts/data), and in erasure by address for people without an account. The [Privacy and data inventory](/docs/ship/compliance/privacy) page lists it with the other tables.

## Limits

- **The copy lags by one webhook.** A suppression Resend added a moment ago reaches the deployment with its event, so the first code after a bounce can still go out and be dropped.
- **Resend decides what is suppressed.** The package never adds an address itself, and cannot keep Resend from suppressing one.
- **Not on a sandbox.** A deployment with `BACKEND_ENVIRONMENT=sandbox`, such as the public playground, refuses a lift as `not_ready`, reason `sandbox`: it would change the provider's list for real. A lift runs on `production` and `development` alone: a preview, or a deployment whose `BACKEND_ENVIRONMENT` is unset or mistyped, refuses it as reason `environment` ([Deploy a demo or staging app](/docs/ship/deploy/staging#what-a-demo-refuses)).
- **Lifting needs a full-access key.** A key restricted to sending can't call Resend's suppressions API.
