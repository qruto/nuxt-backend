- **You get:** your own events in the inbox, by email and as push, with each person's choices and the channel matrix applied.
- **Powered by:** the shared event path the activity trail records, and the package's notifications component.
- **The package adds:** the `notify` option that turns an event type into a notification, its words as translated labels, and its place on each person's profile.

Tell someone their strip was shared with them, the way the package tells them they were given a role. Your own events take the path the package's take: you record the event, and the notifications capability delivers it in the inbox, by email and as a push notification. It uses only the channels the kind allows and the person has not turned off.

## Before you start

- The event path: recording your own events on the activity trail works today ([Record your own events](/docs/build/auth/admin/audit-log#record-your-own-events)).
- The inbox in your layout ([Show the inbox](/docs/build/email/notifications#show-the-inbox)).
- `backend/notifications.ts`, and `backend/audit.ts` passing it to `setupAudit({ notifications })`: the scaffold does both, so the events you record reach `notify`.

## Record the event

Record it where it happens, about the person who should hear of it:

```ts [backend/strips.ts]
import { v } from 'convex/values'
import { audit } from './audit'
import { workspace } from './functions'

export const share = workspace.mutation({
  args: { stripId: v.id('strips'), userId: v.string() },
  handler: async (ctx, { stripId, userId }) => {
    await ctx.db.insert('stripShares', { stripId, userId })
    await audit.recordBackendEvent(ctx, {
      type: 'app.strip_shared',
      subjectId: userId,
      entityId: ctx.workspace.id,
      targetId: stripId,
    })
  },
})
```

`subjectId` names who the event is about, and so who is notified; the actor is the caller. The event lands on the activity trail and reaches your `onEvent`. On its own it becomes nothing more: you say what it becomes.

## Turn it into a notification

The `notify` option of `setupNotifications` says what each event type of yours becomes: the channels it may use and where it links:

```ts [backend/notifications.ts]
export const notifications = setupNotifications(components, {
  notify: {
    'app.strip_shared': {
      channels: ['app', 'email', 'push'],
      link: event => `/strips/${event.targetId}`,
    },
  },
})
```

A type without an entry stays a row on the trail. The channels are `app`, `email` and `push`, narrowed by the [channel matrix](/docs/build/email/notifications#the-channel-matrix) and by each person's choices. Email and push go out through `deliverNotification`, once `setupNotifications` has the email instance ([Set it up](/docs/build/email/notifications#set-it-up)). `link` returns a path of your app, read from the event as it is recorded; a link to another site is dropped, and one that throws is logged (`notifications.deliver_failed`) while the notification goes out without it. `setupNotifications` refuses a type that is not under `app.`, a channel that does not exist, and words that would replace a package kind's. Like every hook, `notify` declares when it runs and how often ([Hooks](/docs/reference/backend/hooks)).

Two rules hold for your kinds as for the package's:

- **No personal data in the event.** The row keeps ids and the few flat values you pass, for a year. The notification reads names when it is shown, so a renamed strip shows its new name.
- **The person decides.** Each kind of yours appears on the profile's email preferences with the channels it allows, and a person can turn any of them off ([Notification channels](/docs/build/email/preferences#notification-channels)).

## Give it words

A notification's words are labels, so they read in the person's language. Each kind takes a `title` and a `body` under `backend.notifications`, keyed by its type without the `app.` prefix. Placeholders fill from the event: `{actor}` is who did it, `{workspace}` the workspace it happened in, and the rest are its values (`{amount}` is an `amount` and its `currency` written as the person's currency writes them). A kind with no words reads "New activity".

```json [i18n/locales/en.json]
{
  "backend": {
    "notifications": {
      "strip_shared": { "title": "{actor} shared a strip with you", "body": "Open it to read and comment." }
    }
  }
}
```

Your messages sit beside the package's, in your i18n files or in app config ([Change copy and labels](/docs/build/ui/customize/labels)). The inbox reads either. Email and push are worded on the deployment, which never reads app config: they read the messages `setupEmail` takes, so pass your i18n files there, English included (`messages: { en, de }`). The email channel renders the words in the package's [layout](/docs/build/email/templates/theme), with your brand, and a kind with no words there reads "New activity".

## Forget them with what they point at

A notification links to its target for as long as it is kept, a year when unread. When you delete the target, delete its notifications in the same mutation with `notifications.forget`, so no inbox keeps a link to a page that is gone:

```ts [backend/strips.ts]
import { notifications } from './notifications'

export const remove = workspace.mutation({
  args: { stripId: v.id('strips') },
  handler: async (ctx, { stripId }) => {
    await ctx.db.delete('strips', stripId)
    await notifications.forget(ctx, { kind: 'app.strip_shared', target: stripId })
  },
})
```

`kind` is a type `notify` names, and `target` the `targetId` you recorded the events with. It deletes that kind's notifications about that target for everyone they reached, read or not, through an index, and rolls back with your mutation. The events stay on the activity trail. One call deletes up to 200 and answers `{ deleted, done }`: `done` is `false` while more are left, so a target that notified more people than that is forgotten by calling again, or from a scheduled function, until it is `true`. A kind `notify` does not name, a package kind among them, is refused with a `TypeError`.

## Check it works

Run the mutation on your dev deployment, and the notification appears live in the inbox of the person it names. The DevTools **Account** tab lists it with the channels it went out on. When the person's address is a Resend test address, the email reaches the [dev inbox](/docs/develop/dev-inbox), and a browser that subscribed on the dev app gets the push.
