You get billing from one call in one scaffolded file. `setupBilling` in `backend/billing.ts` mounts billing on the `backend` component and on Polar's Convex component, reads the `BILLING_*` variables, and resolves who pays from the session.

- **Polar does natively:** customers (individual or team, with members), products, hosted checkout, the customer portal, tax as the merchant of record, and signed webhooks (checked on 2026-10-25).
- **The package adds:** one customer per workspace or account, keyed by its id; who may buy for a workspace, checked fresh on every call; the entitlement cache your functions read; and billing's part of an account's export and erasure.

This page walks through the file, the choices it leaves you, and what a deployment needs to go live. Polar's account, tokens and sandbox are on the [Polar](/docs/services/polar) page.

## Before you start

- **The scaffold**: `backend/billing.ts`, `billing.catalog.ts` and `billing.generated.ts`, next to `auth.ts`, `email.ts` and `audit.ts`. `npx nuxt-backend upgrade` restores a scaffold file that is gone.
- **A catalog**, declared and synced: [Define and sync your catalog](/docs/build/billing/catalog). Without one, billing reads work and a checkout is refused as `not_ready` (reason `no_catalog`).
- **A sandbox token** for development: a Polar sandbox organization's access token in `.env.local` as `BILLING_ACCESS_TOKEN` ([Develop with real sandboxes](/docs/develop/sandboxes#billing-on-polars-sandbox)).

## Wire it

::steps{level="3"}

### Keep the scaffolded instance

`setupBilling(components, options)` takes the app's components and one required option, `email`: the `setupEmail` instance that sends a gift's notice. The scaffold also passes the catalog's id map; `audit`, so billing's events reach the [activity trail](/docs/build/billing/events#on-the-activity-trail); and `paths`, the settings page its emails link to ([The paths file](/docs/reference/configuration/module-options#the-paths-file)). It returns its helpers and `api`, the functions your composables call:

```ts [backend/billing.ts]
import { setupBilling } from 'nuxt-backend/billing'
import { components } from './_generated/api'
import { audit } from './audit'
import { catalog } from './billing.generated'
import { email } from './email'
import { paths } from './paths.generated'

export const billing = setupBilling(components, { catalog, email, audit, paths })

export const {
  getPricing, getConfiguredProducts, getBillingAccess, getFeatures, getCredits,
  getCurrentSubscription, listAllSubscriptions, syncEntitlements, syncProducts, startFreePlan,
  generateCheckoutLink, generateCustomerPortalUrl,
  updateSubscription, cancelSubscription, uncancelSubscription,
  cancelPendingChange, pauseSubscription, resumeSubscription,
  getOrders, getInvoiceUrl, getUsageHistory, refundOrder,
  giftCheckout, getReceivedGifts, claimGift, getWebhookDeliveries, getRevenue,
} = billing.api
```

Keep every export. The composables call them by name: `usePricing` calls `getPricing`, `useBilling` calls `getCurrentSubscription`, `generateCheckoutLink` and the lifecycle actions, and so on. A trimmed export leaves its composable reading `undefined`, and `npx nuxt-backend doctor` names the missing function.

`setupBilling` checks `email` as it runs. An import cycle through `email.ts` can hand it over as `undefined` despite its type. That fails the deploy rather than the first paid gift.

### Hand billing to your functions

`backend/functions.ts` builds every function tier in one `createFunctions` call, and `billing` is one of its inputs. The `withFeature` tier comes from that call: the `workspace` tier plus a plan's feature ([Gate features by plan](/docs/build/billing/subscriptions/feature-gating)).

```ts [backend/functions.ts]
import { createFunctions } from 'nuxt-backend/functions'
import { billing } from './billing'
import { rateLimiter } from './rateLimiter'
import { components } from './_generated/api'
import { action, mutation, query } from './_generated/server'

export const { authed, workspace, admin, withRole, withFeature, setUserRole } = createFunctions(
  { query, mutation, action },
  { components, billing, rateLimiter },
)
```

`billing.ts` imports nothing from `functions.ts`, so the two files never import each other.

### Choose who pays

The default, `billTo: 'workspace'`, bills the active workspace. `billTo: 'user'` bills each account on its own. `resolveEntity` replaces both with a resolver of your own, for an entity your tables define. See [Who pays](#who-pays) and [Bill each person](#bill-each-person) below.

```ts [backend/billing.ts]
export const billing = setupBilling(components, { catalog, email, audit, billTo: 'user' })
```

### Throttle the provider calls

Pass your `setupRateLimiter` instance as `rateLimiter`. Every client-callable function that reaches the live provider then counts against the `billingSync` limit, ten a minute per workspace or user. That covers `syncEntitlements`, checkout, the plan's lifecycle, orders and invoices, so a caller can't loop one to fan out provider requests. `giftCheckout` counts against it too, keyed by the purchaser.

```ts [backend/billing.ts]
import { rateLimiter } from './rateLimiter'

export const billing = setupBilling(components, { catalog, email, audit, rateLimiter })
```

### Leave the routes to `http.ts`

The scaffolded `backend/http.ts` hands `billing` to `registerBackendRoutes`, which mounts the signed webhook endpoint at `/billing/events`. `backend/account.ts` hands it to `setupAccount`, so an account's export and erasure reach the provider. Neither needs more from you. [Register webhooks](/docs/ship/security/webhooks) lists every route and its secret.

## The options

Every option but `email` overrides a default. [Hooks and guarantees](/docs/reference/backend/hooks) says when each callback runs and what a throw does.

| Option | Effect |
|---|---|
| `email` | Required. The app's `setupEmail` instance: a paid gift's recipient hears of it through its `gift` [template](/docs/build/email/templates). |
| `audit` | The app's `setupAudit` instance. Checkouts, plan changes, refunds, gifts, low balances and the provider's subscription, order and benefit deliveries are recorded through it and reach its `onEvent`. Without it they are recorded on the component's own trail. |
| `catalog` | The id map in `billing.generated.ts`. The deployment reads its `production` entry when `BACKEND_ENVIRONMENT` is `production`, and its `sandbox` entry everywhere else. |
| `products` · `credits` | An explicit product map (catalog key to product id) and named credit meters. `products` replaces the catalog's map, and `credits` entries win over its meters. |
| `billTo` | `'workspace'` (the default: the active workspace pays and its members share the plan) or `'user'` (each account pays for itself). |
| `resolveEntity` | `(ctx, rule?) => Promise<{ userId, email } \| null>`: the billing entity, resolved your way, for every read, checkout, spend and lifecycle call. Return `null` without an identity, and throw to refuse a caller the `rule` does not allow. See [Billing a user instead](#billing-a-user-instead). |
| `trustedOrigins` | Origins besides `SITE_URL`'s that a checkout, a gift checkout or the portal may return to (`['https://app.example.com']`). |
| `rateLimiter` | Your `setupRateLimiter` instance: throttles every client-callable function that reaches the provider, against `billingSync`. |
| `multipleSubscriptions` | Let one entity hold several live subscriptions at once. `getCurrentSubscription` then leads with a `subscriptions` array, and the lifecycle actions take a `subscriptionId`. |
| `requireAdmin` | Your gate for the admin functions, `refundOrder`, the webhook log and `getRevenue`. The default requires the `admin` role on the caller's account, read fresh. |
| `canGift` · `giftLimit` | Who may receive a gift, on top of the package's own rules, and how many gifts one purchaser may buy in a window (10 in 30 days by default). See [Send and receive gifts](/docs/build/growth/offers/gifts#who-can-receive-a-gift). |
| `checkoutDiscount` | Pick a catalog promotion for a plan's checkout that names none, such as founder pricing for an early cohort. See [Run a promotion](/docs/build/growth/offers#pick-one-per-customer). |
| `events` · `onUnknownEvent` | Your handlers for the provider's events, after the package's own work, and for a verified event too new for the installed SDK. See [React to billing events](/docs/build/billing/events). |
| `accessToken` · `webhookSecret` | Override `BILLING_ACCESS_TOKEN` and `BILLING_WEBHOOK_SECRET`. |

In `0.2.0` the `environment` option is gone: `BACKEND_ENVIRONMENT` decides. The billing lifecycle adds `lifecycle`, each part off until named, with `saveOffers` for the [cancel flow](/docs/build/growth/engage/cancel-flow), `abandonedCheckout`, `renewalReminders` and `withdrawal` ([React to billing events](/docs/build/billing/events#lifecycle-events)).

## Who pays

The billing entity is what owns a subscription and a credit balance. Every billing call resolves it on the server, from the session, never from an id the browser sends:

- **A workspace**, with the default `billTo: 'workspace'`: the session's active workspace. Its members share its plan, features and credits. Its owner and admins manage them, and every call checks the caller's membership and role fresh ([Who may buy for a workspace](#who-may-buy-for-a-workspace)).
- **A user**, with `billTo: 'user'`: the signed-in account, which manages its own billing ([Bill each person](#bill-each-person)).
- **Your own entity**, with `resolveEntity` beside `billTo: 'user'`: a studio in your own tables, say, where your resolver decides who acts for it ([Billing a user instead](#billing-a-user-instead)).

### One customer per billing entity

Every billing entity pays through a Polar customer of its own, keyed by the entity's id as the customer's external id. With a [free plan](/docs/build/billing/catalog#the-free-plan) in the catalog, the free plan's start creates the customer as the entity is made, so the owner's email (or the user's) reaches the provider at sign-up. Without one, the first checkout creates it. Every live call after that finds the customer by that id: customer state, usage events, orders and the portal. Webhooks resolve the entity from the customer's external id first, then from the entity tag in its metadata, then from the cache.

- **A workspace** is a team customer named after it, with the workspace's owner as its owner member. One person can own several workspaces, and each still bills through its own customer, with its own plan, credits and orders. Members are never seats: the customer pays, and its billing managers act for it.
- **A user** (`billTo: 'user'`) is an individual customer with the user's email. The provider keeps an individual customer's email unique, so an email it already holds for another account is refused with `forbidden` (reason `customer_taken`).
- **An earlier customer** of the owner's verified email that no entity keyed becomes the entity's own for a personal workspace or a user. An example is one the provider made from a checkout that named no customer. It never does for a shared workspace, for a customer another entity holds, or for an email its owner has not proved with a sign-in code.
- **A customer from before 0.2**, mapped by the old email lookup and carrying no external id, gets the entity's id on its first checkout or entitlement read. Production billing from 0.1 carries over with nothing to run. A customer that two entities shared is refused for the second as `forbidden` (reason `customer_taken`), and the deployment logs `billing.customer_mapping_shared` until its billing data is reset.

Trials run once per owner. A checkout for a workspace whose owner already had a trial starts without one, whatever the product or the server offers. The package records a trial by the owner's user id when a subscription starts one, so deleting the workspace that trialed changes nothing. A checkout that offers a trial holds it for its workspace for an hour, so two first checkouts of one owner's workspaces at once can't both start one.

## Who may buy for a workspace

A workspace pays for everyone in it, but only its owner and admins spend its money. They are its billing managers: they check out, open the portal, change or cancel the plan, and read the orders and invoices. Every other member reads the plan, the features and the balance, and spends the credits. The server reads the member table on every call, so a removed or demoted member loses access on their next call. With `billTo: 'user'` there is no workspace to manage: each account buys for itself.

### Who can do what

Each function the scaffolded `backend/billing.ts` re-exports, who may call it, and whether an administrator [impersonating](/docs/build/auth/admin/impersonation) that person may:

| Function | Who | Impersonating admin |
|---|---|---|
| `getConfiguredProducts` · `getPricing` | Anyone, signed out included | Yes |
| `getCurrentSubscription` · `listAllSubscriptions` · `getFeatures` · `getCredits` · `getBillingAccess` · `syncEntitlements` · `getUsageHistory` | Any member of the workspace | Yes |
| `spendCredits` · `reserveCredits` · `refundCredits` from your own function, and the [metered AI actions](/docs/build/ai/metered-actions) | Any member of the workspace | No |
| `generateCheckoutLink` · `generateCustomerPortalUrl` | Its owner and admins | No |
| `updateSubscription` · `cancelSubscription` · `uncancelSubscription` · `cancelPendingChange` · `pauseSubscription` · `resumeSubscription` | Its owner and admins | No |
| `getOrders` · `getInvoiceUrl` | Its owner and admins | Yes |
| `giftCheckout` | Any signed-in account, paying from a billing entity it manages | No |
| `getReceivedGifts` | Any signed-in account, for its own verified address | Yes |
| `claimGift` | The gift's recipient, into a billing entity they manage | No |
| `getBillingConsole` | App admins | Yes |
| `refundOrder` | App admins, signed in within the last ten minutes | No |
| `getRevenue` | App admins ([Read revenue and usage](/docs/build/growth/measure/revenue)) | No |

An impersonating administrator may look but not spend. Reading a workspace's billing helps them support it, and its money stays its own. Each refusal is listed under [What happens when…](#what-happens-when).

### Checked fresh, not from the token

The session token names the active workspace and the app-wide role, and it lives for up to 15 minutes. Billing reads neither from it. Every call reads the account, the caller's membership and the caller's role from the user and member tables, and an admin function reads the account's role. Each change takes effect on the next call, without waiting for a token to expire:

- A member you remove is refused.
- A member you demote stops managing billing.
- An account you ban is refused.
- An admin you demote loses `refundOrder`, the webhook log and the admin console's Billing tab.

Each read happens once per function call, and a second check in the same call reuses it. A function of yours that changes the caller's membership or role and then checks again passes `reread: true` to [`requireEntity`](#in-your-own-functions).

### Hide what a member can't do

`useBilling().canManage` says whether the caller manages the billing, as the server decides it. The scaffolded `getBillingAccess` runs the same check the portal does, so `canManage` is `true` for every account with `billTo: 'user'`, and `false` for an impersonating administrator. While the answer isn't known yet (signed out, or still loading), it reads `true`, so a pricing page still shows its plans to a visitor.

The package's own components read it. `<PricingTable>`, `<WorkspaceSettings>`, `<BillingCheckoutLink>` and `<BillingPortalLink>` show a member who doesn't manage billing the plans without their buttons. A note takes their place (the `pricing.managed` label), with no checkout or portal link. A page of your own does the same:

```vue [app/pages/studio/billing.vue]
<script setup lang="ts">
const { canManage, portal } = useBilling()
</script>

<template>
  <button v-if="canManage" type="button" @click="portal()">
    Manage billing
  </button>
  <p v-else>
    Ask your workspace's owner to change the plan.
  </p>
</template>
```

Hiding a button is a courtesy: the server refuses the call either way.

### In your own functions

`billing.requireEntity(ctx, rule)` checks a caller the way the package's functions do, and returns the billing entity it may act for. The rule takes:

- **`access`**: `'member'` for any member, `'manage'` for the owner and admins. Any other value is refused (`forbidden`, reason `permission`).
- **`impersonation`**: `'allowed'` by default; `'refused'` keeps an impersonating administrator out.
- **`recentSignIn`**: in a mutation or an action, how recent a sign-in it takes, in seconds.
- **`reread`**: read the member table again after the same call changed the caller's membership or role.

Only a workspace's billing managers set where its invoices go, and only in person:

```ts [backend/invoicing.ts]
import { v } from 'convex/values'
import { mutation } from './_generated/server'
import { billing } from './billing'

export const setInvoiceAddress = mutation({
  args: { address: v.string() },
  handler: async (ctx, { address }) => {
    const { userId: workspaceId } = await billing.requireEntity(ctx, {
      access: 'manage',
      impersonation: 'refused',
    })
    await ctx.db.insert('invoiceAddresses', { workspaceId, address })
  },
})
```

The entity comes back as `userId`, the name every billing call gives it: a workspace's id with `billTo: 'workspace'`, an account's with `billTo: 'user'`. To spend credits for that entity from the same function, pass it on: `billing.spendCredits(ctx, { userId, meter: 'credits' })` ([Spend credits in your functions](/docs/build/billing/credits/spending)).

### The billing portal

The portal opens as the caller's own member of the workspace's customer at Polar, so it shows who is signed in. The plan, the payment method and the invoices change there, so only a billing manager opens it, and only in person.

The member is found by the caller's user id. An adopted customer's owner member has none (the provider sets it only at creation), so it is matched by the caller's verified email instead, and only a member no account is keyed to. That owner loses the portal if they change their email, until you update the member at the provider.

Workspace admins pass the server's check, but the package registers only the workspace's owner as a billing manager of its team customer at the provider. An admin's portal is therefore refused with `forbidden` (reason `provider_owner_only`). Admins still check out, change or cancel the plan, and read orders and invoices: the portal is the one thing the owner opens for them. Registering every admin as a billing manager at the provider comes with workspace billing permissions, after `0.2.0` ([Roadmap](/docs/start/roadmap)).

### Billing a user instead

With `billTo: 'user'`, each account pays for itself and manages its own billing, so `canManage` is `true`. The impersonation rules and the ban still hold. [Bill each person](#bill-each-person) sets it up.

To bill something else, such as a studio in your own tables, keep `billTo: 'user'` and add a `resolveEntity`. Your resolver then decides who acts for the entity:

- A call that checks its caller hands the resolver its rule as the second argument, so the resolver can refuse a caller who may only read.
- Treat a missing rule as the strictest case.
- Refuse by throwing: a read then answers `null`, and `canManage` reads `false`.

```ts [backend/billing.ts]
import { setupBilling } from 'nuxt-backend/billing'
import { backendError } from 'nuxt-backend/functions'
import { components, internal } from './_generated/api'
import { audit } from './audit'
import { catalog } from './billing.generated'
import { email } from './email'

export const billing = setupBilling(components, {
  catalog,
  email,
  audit,
  billTo: 'user',
  // Bill the studio the caller picked; only its owners buy for it.
  resolveEntity: async (ctx, rule) => {
    const membership = await ctx.runQuery(internal.studios.currentMembership, {})
    if (!membership) return null
    if (rule?.access !== 'member' && membership.role !== 'owner') {
      throw backendError('forbidden', { reason: 'not_billing_manager' })
    }
    return { userId: membership.studioId, email: membership.billingEmail }
  },
})
```

`internal.studios.currentMembership` is your own query.

## Bill each person

For a product people buy for themselves, such as Panels, a writing tool or a course, a shared workspace bill is in the way. With `billTo: 'user'`, every account is its own billing entity: its own Polar customer, plan, features and credit balance, managed by the person alone. Workspaces still exist for sharing strips; they don't pay.

::steps{level="3"}

### Bill the account

Pass `billTo: 'user'` in `backend/billing.ts`. Every billing call now resolves the signed-in account instead of the active workspace.

You should see: after `nuxt-backend dev` redeploys, a second account in the same workspace reads its own plan and balance, not the first account's.

### Declare a free plan and a paid one

A plan priced `{ month: 0 }` is the free plan. With `billTo: 'user'`, each new account starts on it at its first sign-in, as a Polar customer with the person's email. Run `npx nuxt-backend billing sync` after you edit the catalog.

You should see: a new account's `/pricing` marks Free as the current plan, and the DevTools Billing tab shows its 20 credits.

### Gate a feature on the person's plan

The `withFeature` tier is built on the `workspace` tier and asks for a workspace member. With `billTo: 'user'`, gate a function with the `authed` tier and `billing.requireFeature` instead, which checks the caller's own plan. A refusal carries the plans that include the feature, for `<UpgradePrompt>`.

You should see: on Free, `exportMine` is refused as `feature_required` with `plans: ['creator']`. After a checkout of Creator with the test card, it runs.

### Show the plan where the person looks

`/pricing` works as it is. The billing and credits sections of `<WorkspaceSettings>` read the caller's billing entity, so they show the person's own plan wherever they render. Put them on an account page of yours, and keep `/settings` for workspaces.

You should see: `/account/billing` shows the plan, its state and the credit balance, and Cancel plan works.

::

`exportStrips` is your own code. What changes with it:

- **Gifts.** A purchaser pays for a gift on their own account, and the recipient claims it into theirs: no workspace is involved on either side ([Send, receive and manage gifts](/docs/build/growth/offers/gifts)).
- **Erasure.** Deleting an account deletes and anonymizes its own customer at the provider, which keeps its orders for its books ([When an account or a workspace is deleted](#when-an-account-or-a-workspace-is-deleted)).
- **One email, one customer.** The provider keeps an individual customer's email unique, so an address it already holds for another customer is refused as `forbidden` (reason `customer_taken`).
- **Credits only, no plans.** Drop the paid plan and sell packs. The free plan still gives every account a monthly allowance.

Don't switch an app that already bills workspaces to `billTo: 'user'` in place. Each workspace's customer, plan and credits stay with the workspace's id, and the accounts start from nothing.

## When an account or a workspace is deleted

Deleting an account erases what billing holds of it, as one participant of the account's [erasure](/docs/build/auth/accounts/data#what-an-erasure-removes):

- **The entities that go with it** are its personal workspace, every workspace it was the only member of, or the account itself with `billTo: 'user'`. They are marked as deleting before anything else. Their customers are then deleted and anonymized at the provider, which keeps their orders for its books. Their cached plans, balances, reservations and quota counts are forgotten. The mark means the subscription that ends with a customer starts no free plan again, and the provider's later deliveries about it map, cache and record nothing.
- **A workspace it leaves** keeps its customer and its plan. Only the account's member of that team customer is removed.
- **Its export** lists the subscriptions and the newest orders (up to 100 each) of every entity it owns alone.

One thing stays for now. Polar's Convex component keeps the subscriptions it synced and the link from the entity's id to its deleted customer, since it has no way to delete them yet. They name the entity's id, never an address or a name, and a cancellation keeps the reason and comment the customer gave. [Privacy and data inventory](/docs/ship/compliance/privacy) lists it.

For a workspace your own code dissolves, call `billing.forgetEntity(ctx, workspaceId)`. It drops the entity's cache and quota counts, and leaves the provider's customer as it is.

## Environment

Two variables configure billing, and `BACKEND_ENVIRONMENT` picks which Polar they talk to: `production` bills live, and every other value bills in Polar's sandbox ([Environments and deployments](/docs/start/concepts/environments#sandbox-and-production-providers)).

| Variable | Purpose |
|---|---|
| `BILLING_ACCESS_TOKEN` | The Polar organization's access token: a sandbox one outside production, a live one in production. Unset, billing reads answer empty and provider calls are refused as `unavailable` (reason `not_configured`). Workspaces need its `members:write` and `customer_sessions:write` scopes too, for team customers and the member's portal. |
| `BILLING_WEBHOOK_SECRET` | Verifies deliveries to `/billing/events`. Unset, the endpoint answers `503`, and entitlements refresh only on demand (`syncEntitlements`). `billing sync` stores it when it creates the endpoint. |

`npx nuxt-backend env push` forwards both from `.env.local` to the deployment, and derives `BACKEND_ENVIRONMENT` from `CONVEX_DEPLOYMENT`. They live on the Convex deployment, not in the Nuxt app: see [Environment variables](/docs/reference/configuration/environment-variables#convex-deployment-variables). `BACKEND_ENVIRONMENT` replaces the `BILLING_ENVIRONMENT` of earlier previews.

## Go live

::steps{level="3"}

### Create the production organization

Create an organization on Polar's production server, and an access token there with the scopes above. A sandbox token does not work in production.

### Set the token on the production deployment

Set `BILLING_ACCESS_TOKEN` on the production deployment. Its `BACKEND_ENVIRONMENT` is `production`, which `env push` derives from a `prod:` deployment.

### Sync the catalog to production

With the production deployment's `CONVEX_DEPLOY_KEY` in the shell and the production token as `BILLING_ACCESS_TOKEN`, run `npx nuxt-backend billing sync --env production`. The sync writes the `production` entry of `billing.generated.ts`, creates the webhook endpoint at the deployment's HTTP origin (or the URL `--webhook` names), and stores its secret there. Commit the file and deploy it with the backend.

### Check it

Run `npx nuxt-backend doctor --prod`, and fix what it reports for billing: the catalog's production ids, the webhook route, the token's access, and the organization settings the catalog relies on, such as trial-abuse prevention for a plan with a trial.

::

The [Production checklist](/docs/ship/checklist) has the whole list across capabilities.

## What happens when…

A refused call throws a [refusal](/docs/reference/backend/errors) you can branch on, and a reactive read answers `null` instead:

| Refusal | When |
|---|---|
| `unauthenticated` | Nobody is signed in. |
| `no_workspace` | The session has no active workspace. |
| `forbidden`, reason `banned` | The account was banned after its token was minted. |
| `forbidden`, reason `not_member` | The caller is no longer a member of the workspace. |
| `forbidden`, reason `not_billing_manager` | A member who is neither its owner nor an admin. |
| `forbidden`, reason `impersonating` | A call the table refuses to an impersonating administrator. |
| `forbidden`, reason `admin_only` | An admin function, and the account is no admin. |
| `forbidden`, reason `provider_owner_only` | A workspace admin opened the portal ([The billing portal](#the-billing-portal)). |
| `forbidden`, reason `customer_taken` | An individual customer's email belongs to another customer at Polar. |
| `reauthentication_required` | `refundOrder` with a sign-in older than ten minutes ([Require a recent sign-in](/docs/build/auth/access/step-up)). |
| `unavailable`, reason `not_configured` | No `BILLING_ACCESS_TOKEN` on the deployment ([`deployment-billing-access-token`](/docs/reference/cli/diagnostics#deployment-billing-access-token)). |
| `not_ready`, reason `no_catalog` | No catalog for this environment: run `npx nuxt-backend billing sync` for it, and deploy `billing.generated.ts`. |

And when a symptom shows instead of a refusal:

| Symptom | Fix |
|---|---|
| `/pricing` shows no plans | The deployment's products table is empty: run `npx convex run billing:syncProducts` once, or `billing sync` again. |
| Plans don't update after a purchase | The webhook is not reaching the deployment: see [`billing-webhook-secret`](/docs/reference/cli/diagnostics#billing-webhook-secret) and [`billing-webhook-route`](/docs/reference/cli/diagnostics#billing-webhook-route). A local deployment gets no webhooks: [Develop with real sandboxes](/docs/develop/sandboxes#billing-on-polars-sandbox) says what to do. |
| A workspace admin can't open the portal | The package registers only the owner as a billing manager at Polar: see [The billing portal](#the-billing-portal). |

## Limits

- **No seats.** A plan here never counts people, and a workspace is never billed per member ([Principles](/docs/start/concepts/principles#what-it-never-does)). Polar's seat-based pricing is beta and stays out of the catalog.
- **Built-in roles only.** The owner and admins manage billing, and every other member reads and spends. Billing as a permission you grant to a role of your own, and acting for another workspace than the active one, wait for the release after `0.2.0` with custom workspace roles ([Roadmap](/docs/start/roadmap)).
- **The portal is the owner's.** Polar's team customer has one billing manager the package registers: the workspace's owner.
- **One provider.** The catalog, the cache and the customer mapping are built on Polar's customers, products, benefits and meters.

## Test it

`asUser` from `nuxt-backend/test` signs a test caller in the way a real session does, so `requireEntity` reads the member table as in production:

```ts [backend/invoicing.test.ts]
import { getBackendError } from 'nuxt-backend/functions'
import { asUser, defineBackendTestApp, seedWorkspace } from 'nuxt-backend/test'
import { expect, test } from 'vitest'
import { api } from './_generated/api'
import schema from './schema'

const testApp = defineBackendTestApp(schema, import.meta.glob('./**/*.ts'))

test('only a billing manager sets the invoice address', async () => {
  const t = testApp()
  const workspace = await seedWorkspace(t)
  const owner = await asUser(t, { workspace, workspaceRole: 'owner' })
  const member = await asUser(t, { workspace })

  await owner.mutation(api.invoicing.setInvoiceAddress, { address: '1 Panel Street' })
  const refusal = await member.mutation(api.invoicing.setInvoiceAddress, { address: '2 Gutter Lane' }).catch(getBackendError)
  expect(refusal).toMatchObject({ code: 'forbidden', data: { reason: 'not_billing_manager' } })
})
```

Then check the deployment itself:

- `npx nuxt-backend status` shows the billing capability as `live`, or `test` while it runs in Polar's sandbox.
- `npx nuxt-backend doctor --only billing` runs every billing finding. Each one's id opens its entry on [Diagnostics](/docs/reference/cli/diagnostics#billing).
- The DevTools [Billing tab](/docs/develop/devtools#billing) shows the entity's plans, entitlements, quotas and webhook deliveries. The demo's [pricing page](/playground/pricing) runs checkout on Polar's sandbox, and its [settings page](/playground/settings) the plan, the portal and the credits.
