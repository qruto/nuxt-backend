When a package function refuses a call (signed out, out of credits, rate limited), it throws a
`ConvexError` with a stable code: `{ code: 'insufficient_credits', balance: 0, need: 1 }`. Convex
sends that data to the client in production as well. A plain `Error` arrives there as "Server
Error", whatever its message said. The [Errors](/docs/reference/backend/errors) reference lists
every code and its fields. The package adds the stable codes, `getBackendError` to read them anywhere, and `backendError` to throw them from your own functions.

## Where a failure shows up

| You call | A failure |
|---|---|
| A data composable of the package: `useSearch`, `useWorkflowStatus`, `useEmailStatus` and the others | Lands in its `error`, already read: `{ code, data, message }`. A read never throws ([Composable conventions](/docs/reference/nuxt/conventions)) |
| An action of a package composable (`useBilling().checkout()`, `useWorkspace().invite()`) | Rejects: catch it and read it with `getBackendError` |
| `useMutation`, `useAction` | Rejects, the same way |
| `useAsyncQuery`, `useQuery_experimental` | Lands in the result's `error`, as the thrown error: read it with `getBackendError` |
| `useQuery`, `usePaginatedQuery` | Throws during render: wrap the part that reads it in an error boundary, or use one of the forms above |

## Read a refusal

`getBackendError(error)` is auto-imported. It returns `{ code, data, message }` for a refusal and
`null` for anything else, such as a crash or an error of your own:

```vue
<script setup lang="ts">
import { api } from '#backend/api'

const transform = useAction(api.ai.transform)
const notice = ref<string | null>(null)
const outOfCredits = ref(false)

async function run(text: string) {
  notice.value = null
  try {
    await transform({ text })
  }
  catch (error) {
    const refusal = getBackendError(error)
    outOfCredits.value = refusal?.code === 'insufficient_credits'
    notice.value = refusal?.message ?? 'Something went wrong. Try again.'
  }
}
</script>
```

`message` is the sentence to show: the throw site's own sentence for the person when it wrote one
(an app's `canSignIn` refusal, say), else the code's English label. The data is typed by code, so
after `refusal.code === 'rate_limited'` you can read `refusal.data.retryAfter`, the wait in
milliseconds. Every field may be absent on this side, so check the one you use: the reader keeps
only what fits the catalog.

It reads the same codes from every source:

- a package function's refusal, and one you throw with `backendError`;
- the rate limiter's own error, from any limit called with `throws: true`, as `rate_limited` with
  the limit's name;
- an auth client result (`{ data, error }`) or its `error`: the package's auth refusals carry the
  same codes, and Better Auth's own 401, 403 and 429 map to `unauthenticated`, `forbidden` and
  `rate_limited`. A banned account's refusal reads as `forbidden` with reason `banned`, the same
  reason the package's own ban checks give, and Better Auth's 400s for a wrong or expired code,
  an invalid address and a taken workspace slug read as `invalid_input` on `otp`, `email` or
  `slug`;
- any of these as an `Error`'s `cause`, which is how the rejections of the auth composables
  (`useLoginFlow()`, `useWorkspace()`, `usePasskeys()`, `useSessions()`) pass them on.

`useAiStream()` keeps the refusal of its last `start` in `error`, and its `status` ends in
`'error'`.

## Branch on the code

| Code | What to offer |
|---|---|
| `unauthenticated` | Sign in, then retry. On a sign-in form it can also be refused credentials: show the message. |
| `reauthentication_required` | A fresh sign-in, then the same call: `useReauthentication().withReauthentication(() => call())` does both. |
| `no_workspace` | Choose or create a workspace. |
| `insufficient_credits` | A credit pack or a bigger plan. `data.need` and `data.balance`, when present, say how far off it is. |
| `feature_required` | The plans in `data.plans`, which include `data.feature`: `<UpgradePrompt :plans="refusal.data.plans" />`. |
| `quota_exceeded` | The plans in `data.plans`, which allow more of `data.quota` than `data.limit`; `data.used` says how many there are. |
| `rate_limited` | A countdown from `data.retryAfter`, when present. |
| `forbidden` | The message. `data.reason` says why, `banned` or `role` for example. |
| `invalid_input` | The message beside the input `data.field` names. |
| `not_ready` | No retry: the first purchase (`no_customer`) or a credit pack (`not_synced`) is what changes it. |
| `unavailable` | A retry later for `provider_refused`. The other reasons need the deployment fixed; the log says what. |

## Refuse from your own functions

`backendError(code, data?, detail?)` from `nuxt-backend/functions` builds the error. The data is
checked against the code's fields, and `detail` is the English the deployment log shows:

```ts [backend/strips.ts]
import { backendError } from 'nuxt-backend/functions'
import { v } from 'convex/values'
import { workspace } from './functions'

export const rename = workspace.mutation({
  args: { id: v.id('strips'), title: v.string() },
  handler: async (ctx, { id, title }) => {
    const strip = await ctx.db.get('strips', id)
    if (strip?.workspaceId !== ctx.workspace.id) {
      throw backendError('forbidden', { reason: 'other_workspace' })
    }
    if (!title.trim()) {
      throw backendError('invalid_input', { field: 'title', message: 'Give the strip a title.' })
    }
    await ctx.db.patch('strips', id, { title: title.trim() })
  },
})
```

The `authed`, `workspace` and `admin` builders from `createFunctions` already throw `unauthenticated`,
`no_workspace` and `forbidden`. A limit of your own refuses as `rate_limited` when you call it with
`throws: true`, but the limiter throws only when it knows the wait. Keep the result, and refuse
yourself when it says no:

```ts
const { ok, retryAfter } = await rateLimiter.limit(ctx, 'sendMessage', { key: ctx.user.id, throws: true })
if (!ok) throw backendError('rate_limited', { limit: 'sendMessage', retryAfter: retryAfter || undefined })
```

In an auth hook, throw the auth library's `APIError` with the code and its fields in the body, and
the client reads it the same way:

```ts
import { APIError } from 'nuxt-backend/auth'

throw new APIError('BAD_REQUEST', { code: 'invalid_input', field: 'email', message: 'Invite a company address.' })
```

## Test it

```ts [backend/strips.test.ts]
import { asUser, defineBackendTestApp } from 'nuxt-backend/test'
import { expect, test } from 'vitest'
import { api } from './_generated/api'
import schema from './schema'

const testApp = defineBackendTestApp(schema, import.meta.glob('./**/*.ts'))

test('a blank title is refused on its field', async () => {
  const author = await asUser(testApp())
  const id = await author.mutation(api.strips.create, { title: 'Monday' })
  await expect(author.mutation(api.strips.rename, { id, title: ' ' }))
    .rejects.toMatchObject({ data: { code: 'invalid_input', field: 'title' } })
})
```
