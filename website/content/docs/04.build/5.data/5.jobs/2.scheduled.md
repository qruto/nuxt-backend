Send a weekly digest every Monday, refresh exchange rates every six hours, or remind each reader at the hour they picked. Fixed schedules go in `backend/crons.ts` with Convex's own `cronJobs()`. Schedules that are data, one per person or per row, go through the official [`@convex-dev/crons`](https://www.convex.dev/components/crons) component. The `backend` component's own maintenance needs nothing from you.

## Your own jobs

`backend/crons.ts` is Convex's file for jobs that are the same on every deployment. Create it with your first job:

```ts [backend/crons.ts]
import { cronJobs } from 'convex/server'
import { internal } from './_generated/api'

const crons = cronJobs()

crons.cron('send weekly digest', '15 8 * * 1', internal.digest.send, {})
crons.interval('refresh rates', { hours: 6 }, internal.rates.refresh, { currency: 'eur' })

export default crons
```

- **`crons.cron(name, expression, fn, args)`** runs on a cron expression, in UTC. Pick a minute other than `0`, so your job does not start with everyone else's.
- **`crons.interval(name, { hours, minutes, seconds }, fn, args)`** runs on an interval from the first deploy.
- **The function** is an internal one, referenced through `internal`, with the arguments its validator asks for.

A job with a lot to do works in batches: one transaction each, scheduling the next until nothing is left. For rows that pass an age, a [retention rule](/docs/build/data/retention) writes that loop for you. The Convex guide to [cron jobs](https://docs.convex.dev/scheduling/cron-jobs) has the rest.

## Jobs your code schedules

Some schedules are data: a digest at the hour each reader picked, a reminder that repeats until someone answers. The crons component keeps them by name, each with its own time zone. Install and mount it:

```bash
npm install @convex-dev/crons
```

::code-tree{defaultValue="backend/digest.ts"}

```ts [backend/convex.config.ts]
import crons from '@convex-dev/crons/convex.config'

// …after the package's components
app.use(crons)
```

```ts [backend/digest.ts]
import { Crons } from '@convex-dev/crons'
import { v } from 'convex/values'
import { components, internal } from './_generated/api'
import { authed } from './functions'

const schedules = new Crons(components.crons)

export const setDigestHour = authed.mutation({
  args: { hour: v.number(), timeZone: v.string() },
  handler: async (ctx, { hour, timeZone }) => {
    const name = `digest:${ctx.user.id}`
    if (await schedules.get(ctx, { name })) await schedules.delete(ctx, { name })
    await schedules.register(
      ctx,
      { kind: 'cron', cronspec: `20 ${hour} * * *`, tz: timeZone },
      internal.digest.sendTo,
      { userId: ctx.user.id },
      name,
    )
  },
})
```

::

A component's functions are never public on their own: wrap them in your own functions, behind a tier, as above. `register` takes a cron or an interval, `get` and `list` read what is scheduled, and `delete` stops a job. The component's [README](https://www.convex.dev/components/crons) lists every method.

## The maintenance the component runs

The `backend` component's own cron starts a pass every hour. Each task deletes what is past its window, a few hundred rows per transaction, and schedules its next batch until nothing is left. A pass fixes its cutoff when it starts, so it always ends. A batch that throws rolls back, ends its task's pass and logs `maintenance.task_failed`; the next pass tries again.

| Task | Deletes |
|---|---|
| `sessions` | Sessions that expired |
| `verifications` | Expired sign-in codes and email-change tokens |
| `rateLimits` | Rate-limit counters that went idle, when an app turns that limiter on |
| `aiRequests` | The records of metered AI requests that settled or were released, and of one stuck as reserved for a week |
| `invitations` | Invitations nobody answered, well after they expired |
| `auditEvents` | Activity rows past their year |
| `accountExports` | An account's data export a day after it was made, with its file |
| `failedErasures` | An [erasure](/docs/build/auth/accounts/data) that stopped at a failing source and was not run again within 30 days |
| `billingDeletions` | A billing entity's deletion mark, 30 days after the erasure that set it |
| `billingConsents` | A renewing checkout's consent proof three years after the consent, or two days after a checkout that started nothing ([Follow subscription law](/docs/ship/compliance/subscriptions)) |
| `billingWithdrawals` | An EU withdrawal's record, three years after it |
| `billingSaveOffers` | The cancel flow's save offers, two years after they were made |
| `billingLifecycleMarks` | What the billing lifecycle did once (an annual reminder, an abandoned checkout's record), two years on |
| `secretOutbox` | A secret email still waiting after its code expired |
| `emailRecords` | Email records with a final status, by the windows [`setupEmail({ retention })`](/docs/build/email/sending) sets |
| `storageOrphans` | Uploads nobody claimed, a day after they arrived ([Keep storage clean](/docs/build/data/files/cleanup)) |

`storageOrphans` arrives with FILES. The sandbox inbox's copies are gone: the dev inbox reads sent mail back from Resend instead of keeping copies.

DevTools shows each task's last pass and the rows it deleted on the [Overview tab](/docs/develop/devtools#overview). `npx convex run --component backend maintenance:status` prints the same. [Limits and retention](/docs/reference/backend/limits#windows-and-lifetimes) gives each window.

::note
On a deployment that already holds data, the first pass deletes the backlog. It works through it a batch at a time, so it may take a few minutes, and it never deletes anything still in use.
::
