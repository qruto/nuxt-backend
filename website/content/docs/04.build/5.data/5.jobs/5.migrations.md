Give every existing strip a `status` before you make the field required. A schema change that existing documents do not satisfy yet is made in three steps: deploy the field as optional, migrate every document, then make it required. The official [`@convex-dev/migrations`](https://www.convex.dev/components/migrations) component does the middle step online, a batch per transaction, while the app keeps serving, and resumes where it stopped. Your app imports it directly.

## Fill in a new field

```bash
npm install @convex-dev/migrations
```

::code-tree{defaultValue="backend/migrations.ts"}

```ts [backend/convex.config.ts]
import migrations from '@convex-dev/migrations/convex.config'

// …after the package's components
app.use(migrations)
```

```ts [backend/migrations.ts]
import { Migrations } from '@convex-dev/migrations'
import { components } from './_generated/api'
import schema from './schema'

export const migrations = new Migrations(components.migrations, { schema })

// Runs any migration below by name.
export const run = migrations.runner()

export const setDefaultStatus = migrations.define({
  table: 'strips',
  migrateOne: strip => (strip.status === undefined ? { status: 'draft' } : undefined),
})
```

::

`migrateOne` runs inside a mutation, one document at a time, a batch per transaction. Return a partial document and the component patches it, or write through `ctx.db` yourself. `schema` types `strip` and lets a migration narrow its pass to an index range with `customRange`.

## Run it

```bash
# Dry run: one batch, then roll back. See what it would do.
npx convex run migrations:run '{ "fn": "migrations:setDefaultStatus", "dryRun": true }'

# Start, or resume where it stopped. A finished migration does nothing.
npx convex run migrations:run '{ "fn": "migrations:setDefaultStatus" }'

# Several, one after another.
npx convex run migrations:run '{ "fn": "migrations:setDefaultStatus", "next": ["migrations:backfillStripCount"] }'
```

Add `--prod` to run on production, after the deploy that defines the migration. From code, `migrations.runOne(ctx, internal.migrations.setDefaultStatus)` starts one from a mutation or an action, `migrations.runSerially(ctx, [...])` runs a series, and `migrations.getStatus(ctx, {})` reads where each stands. A query can return that status to a page.

A migration is also how you backfill an [aggregate](/docs/build/data/read-write/aggregates) over rows that predate its trigger: `migrateOne: (ctx, strip) => stripsPerWorkspace.insertIfDoesNotExist(ctx, strip)`.

## The package's own migrations

The `backend` component migrates its own tables the same way, on a migrations component nested inside it, so their record stays beside the tables they change and apart from yours. A release that changes data an earlier one wrote ships a migration for it. [`npx nuxt-backend upgrade`](/docs/reference/cli#upgrade) runs the ones a deployment has not finished, on the dev deployment, or on production with `--prod --yes` after its deploy. Each changes a document only while it still needs the change, so running one again changes nothing.

| Migration | Since | What it does |
|---|---|---|
| `personalWorkspaces` | 0.2.0 | Gives each signed-in user (one with a live session) without a workspace the personal one their sign-in would have made. Anyone else gets it at their next sign-in, which asks your `canSignIn` first: the migration runs in the component and cannot ask it. A banned user gets it at their first sign-in once the ban ends |
| `activeWorkspaces` | 0.2.0 | Activates the user's first workspace on each live session that has none, so nobody signs in again for it |

`upgrade` repairs the scaffold and runs these, and nothing else: there is no codemod from `0.1` ([Upgrade](/docs/ship/releases/upgrade)).
