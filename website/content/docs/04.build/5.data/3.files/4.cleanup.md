Files pile up quietly: a cover replaced, a strip deleted, an upload from a tab someone closed. Convex keeps every stored file until code deletes it, with no reference counting. The package keeps one owner record per file: release the file when your row lets go of it and both go together, while the `backend` component's maintenance deletes what nobody claimed, with no cron of yours.

## Release a file your row lets go of

Call `storage.release(ctx, storageId)` in the same mutation that drops the reference, so the row and the file go together:

```ts [backend/strips.ts]
import { backendError } from 'nuxt-backend/functions'
import { v } from 'convex/values'
import { workspace } from './functions'
import { storage } from './storage'

export const remove = workspace.mutation({
  args: { id: v.id('strips') },
  handler: async (ctx, { id }) => {
    const strip = await ctx.db.get('strips', id)
    if (strip?.workspaceId !== ctx.workspace.id) throw backendError('forbidden', { reason: 'other_workspace' })
    await storage.release(ctx, strip.photoId)
    await storage.release(ctx, strip.coverId)
    await storage.revokeShareLink(ctx, 'strips', id)
    await ctx.db.delete('strips', id)
  },
})
```

`release` takes a storage id, or `null` or `undefined` and does nothing. It deletes the owner record and the file, gives the bytes back to the quota, and calling it twice is safe. A row deleted in batches by a [retention rule](/docs/build/data/retention) releases its files in the rule's `onDelete`.

## Show it in a page

A delete that takes files with it deserves a confirmation that says so:

```vue [app/components/DeleteStrip.vue]
<script setup lang="ts">
import { api } from '#backend/api'

import type { Id } from '#backend/dataModel'

const props = defineProps<{ stripId: Id<'strips'>, title: string }>()
const remove = useMutation(api.strips.remove)
const dialog = ref<HTMLDialogElement>()
</script>

<template>
  <button type="button" @click="dialog?.showModal()">Delete strip</button>
  <dialog ref="dialog" aria-labelledby="delete-heading">
    <h2 id="delete-heading">Delete "{{ title }}"?</h2>
    <p>The strip, its photo and its cover are deleted, and its share link stops working.</p>
    <button type="button" @click="remove({ id: props.stripId }).then(() => dialog?.close())">Delete strip</button>
    <button type="button" @click="dialog?.close()">Cancel</button>
  </dialog>
</template>
```

## What the sweep deletes

| A file in storage | What happens |
|---|---|
| Claimed or stored, with an owner record | Kept until `release`, or the owner's erasure |
| Never claimed, under a day old | Kept: the person may still be on the page that uploads it |
| Never claimed, a day old or more | Deleted by the next maintenance pass |
| Claimed, then refused by its type check | Deleted at once |

The sweep runs inside the `backend` component, where the files and their records live. It reads storage a page at a time and keeps its place between passes, so a large backlog never fills one transaction. A refused claim rolls its mutation back, so a rejected upload is an unclaimed one, and the sweep deletes it too. A file stored in one mutation is never an orphan.

DevTools shows the sweep's last pass and how many files it deleted on the [Overview tab](/docs/develop/devtools#overview), beside the component's other [maintenance tasks](/docs/build/data/jobs/scheduled#the-maintenance-the-component-runs).

## A person's files in export and erasure

- **Export.** A person's data export lists their files, each with its type, size and a link to its bytes: every file they own, and every file of a workspace that goes with their account, beside the share links they turned on. The files also come as zip parts, behind links that end with the export's own, and each file in the export names the part and the entry it is in. [Export and delete an account](/docs/build/auth/accounts/data) shows the export.
- **Erasure.** Deleting an account deletes the files it owns, and those of its personal workspace and of any workspace it was the only member of. Files of a shared workspace stay with the workspace.
- **Your rows.** A row of yours that points at a deleted file reads `null` from `getFileUrl` and `storage.fileUrl`. Clear the field in your account source if the row stays.

## What happens when…

| Situation | Result |
|---|---|
| `release` gets an id with no owner record | Nothing: it returns without an error |
| A row still points at a released file | `getFileUrl` and `storage.fileUrl` return `null`, and `<StorageImage>` shows `missing` |

## Limits

- **`release` checks no owner.** Pass it an id read from your own row, never one from a client's arguments.
- **Files stored outside `setupStorage`.** Files your app stored with `ctx.storage` directly live in the app's own storage, which the component cannot see: the sweep, export and erasure leave them alone. Keep deleting them with your own code, and send new uploads through `setupStorage`.
- **Cached copies.** An optimizer's resized copy can outlive the file until its cache expires ([Show images](/docs/build/data/files/images#limits)).

## Test it

```ts [backend/strips.test.ts]
import { readFile } from 'node:fs/promises'
import { asUser, defineBackendTestApp } from 'nuxt-backend/test'
import { expect, test } from 'vitest'
import { api } from './_generated/api'
import schema from './schema'

const testApp = defineBackendTestApp(schema, import.meta.glob('./**/*.ts'))

test('deleting a strip releases its photo', async () => {
  const author = await asUser(testApp())
  const id = await author.mutation(api.strips.create, { title: 'Monday' })
  const png = new Uint8Array(await readFile(new URL('./fixtures/panel.png', import.meta.url))).buffer
  await author.mutation(api.strips.addPhoto, { id, photo: png })
  const { photoId } = (await author.query(api.strips.get, { id }))!
  await author.mutation(api.strips.remove, { id })
  expect(await author.query(api.storage.getFileUrl, { storageId: photoId! })).toBeNull()
})
```
