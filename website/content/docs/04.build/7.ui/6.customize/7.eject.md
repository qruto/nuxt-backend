Take the packaged plan card's source into your app, change anything in it, and still learn what the package changed when you upgrade. This is the copy-in pattern that shadcn-vue's registry made common: the source becomes yours. `npx nuxt-backend eject` copies a part, a page or an email, its `.vue` file and its CSS, and stamps it with the package version; `npx nuxt-backend upgrade` later diffs your copy against the new version.

## Eject a part

```bash
npx nuxt-backend eject PricingPlanCard
```

```text
✔ app/components/PricingPlanCard.vue      from nuxt-backend 0.2.0
✔ app/components/PricingPlanCard.css      from nuxt-backend 0.2.0
```

The CSS keeps the part's rules inside `@layer nuxt-backend`, and the `.vue` file loads it with `<style src>`. The copy has the part's name, so it [swaps the part](/docs/build/ui/customize/parts) everywhere at once, packaged pages included. Its first line is the stamp:

```vue [app/components/PricingPlanCard.vue]
<!-- nuxt-backend eject: PricingPlanCard@0.2.0 -->
<script setup lang="ts">
import type { PricingPlanCardProps } from '#backend/parts'

const props = defineProps<PricingPlanCardProps>()
const { t } = useLabels('pricing')
</script>
```

The copy keeps using the composables, labels and bindings, so the state and the accessibility attributes still come from the package: its imports point at `#backend/parts`, `#backend/a11y` and `#backend/runtime`, the package's own code, instead of relative paths. Only the markup and the CSS are now yours.

## Eject a page or an email

| You eject | Command | Written to |
|---|---|---|
| A part | `npx nuxt-backend eject PricingPlanCard` | `app/components/PricingPlanCard.vue` and its CSS |
| A page | `npx nuxt-backend eject page:pricing` | `app/pages/pricing.vue`, with its guard in `definePageMeta`, at the path `pages.pricing` gives it |
| A component | `npx nuxt-backend eject AuthForm` | `app/components/AuthForm.vue` and its CSS; its parts stay packaged |
| An email | `npx nuxt-backend eject email:otp` | `backend/emails/otp.ts`, added to `templates` in `backend/email.ts` |

`npx nuxt-backend eject --list` prints every part, component, page key and email you can eject, with the ones already ejected marked. The emails are `email:otp`, `email:passkeyRecovered`, `email:emailChanged`, `email:deletionScheduled`, `email:deletionCanceled`, `email:welcome`, `email:invite`, `email:gift`, `email:waitlistConfirmation` and `email:waitlistAdmitted`, each written to a kebab-case file (`email:emailChanged` to `backend/emails/email-changed.ts`). When `setupEmail` in `backend/email.ts` has a shape `eject` cannot edit, it writes the template and prints the line to add.

An ejected page replaces the packaged one at its path, as any page of yours would. It composes the packaged parts, so each part inside it still upgrades unless you eject that part too. An ejected email is the template's own source: the blocks it builds, every word read from its labels through `t`, and its plain-text part, with the helpers it uses (`linkBlocks`, `describeOrigin`, `plainName`) imported from `nuxt-backend/email` ([Customize email templates](/docs/build/email/templates#eject-an-email)).

## Show it in a page

Nothing to wire: a part's copy swaps the part, a page's copy serves its path, an email's copy is sent in place of the packaged one, since `eject` adds it to `templates`. Open `/pricing` to see your copy of the plan card.

## Upgrade an ejected file

```bash
npx nuxt-backend upgrade
```

```text
Ejected files
  PricingPlanCard      0.2.0 → 0.3.0      2 upstream changes
                       npx nuxt-backend upgrade --diff PricingPlanCard
```

`upgrade` reads each stamp, compares the packaged source at that version with the installed one, and counts the changed hunks; `upgrade --diff PricingPlanCard` prints them as a unified diff for you to apply by hand, and writes nothing. It never rewrites an ejected file. Once you have carried the changes over, set the version in the stamp to the installed one, and `upgrade` stops listing the file. The older source comes from the published package on the jsDelivr CDN, so this step needs the network.

## What happens when…

| Situation | Result |
|---|---|
| The name is not a part, page key or email | `eject` lists the close matches and writes nothing |
| The target file exists | `eject` stops; pass `--force` to overwrite |
| A part was removed upstream | `upgrade` says it is no longer shipped; the [Upgrade page](/docs/ship/releases/upgrade) names what replaces it |
| The older source cannot be fetched | `upgrade` says so beside the file, and the rest of the run goes on |
| You delete the copy | The packaged part, page or email comes back on the next build |

## Limits

- **Eject is the last rung.** Every upstream fix to an ejected file now needs your hand. Try a [token](/docs/build/ui/customize/tokens), a [slot](/docs/build/ui/customize/slots) or a [swapped part](/docs/build/ui/customize/parts) first.
- **Markup and CSS only.** Composables, server functions and the component contract are never ejected.
- **Accessibility is yours.** Keep the bindings in the copy, and what the region promised ([Accessibility](/docs/build/ui/accessibility#what-a-replacement-must-keep)).

## Test it

Run your component tests and the axe check in your end-to-end suite after each eject and each upgrade ([Test pages over a mock backend](/docs/develop/testing/pages)).
