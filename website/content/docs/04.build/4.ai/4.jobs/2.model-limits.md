- **You get:** jobs that slow down when a provider throttles them, instead of failing.
- **Powered by:** Convex's rate limiter component, and the `429` and `Retry-After` answers the gateway passes on.
- **The package adds:** a token bucket per model that halves on a `429` and grows back after clean calls, retries with backoff and jitter, and error classification inside the step.

Every model has a rate limit at its provider, and a gateway reports none of it in advance. The only signal is a `429` once the limit is passed. So the job queue learns each model's limit from those answers. It halves a model's rate the moment one comes back, then earns the rate back one call per minute while calls succeed. A job whose call was throttled waits and tries again, so a burst of `429`s slows jobs down before it fails any. Metered actions and streams make one call each and are not throttled this way: this is the queue's.

## The limit per model

Each model a step names gets a token bucket, counted in calls per minute, on Convex's rate limiter component. A step takes a turn from its model's bucket before your handler runs. When the bucket is empty, the step returns at once with the time the next turn frees up, and `job.run` schedules it again for then: no action sleeps while it waits.

The bucket's rate adapts. The pattern is additive increase, multiplicative decrease, the one TCP uses for congestion control:

| What happens | What the rate does |
|---|---|
| A call comes back `429` | Halves at once, never below `min`, and at most once a minute: a burst of `429`s from jobs running together halves it once |
| Five calls in a row succeed, a minute or more after the last `429` | Grows by one call a minute, never above `max` |
| Any other error | Stays, and the run of clean calls starts over |

The burst a bucket allows is a third of a minute's rate, one call at least. Set where each model starts on `defineJobQueue`:

```ts [backend/jobs.ts]
export const jobs = defineJobQueue(components, {
  ai,
  models: {
    'google/gemini-3.1-flash-image-preview': { perMinute: 6, min: 1, max: 30 },
    'anthropic/claude-sonnet-4.5': { perMinute: 20, min: 2, max: 60 },
  },
})
```

A model you do not list starts at 6 calls a minute, between 1 and 30. The rate the queue has learned is kept, so a deploy does not start it over, and the admin console can retune it by hand ([Operate the queue](/docs/build/ai/jobs/operate)). A step without `model` runs without a bucket.

## Retries

`job.run` tries a step up to 4 times, a throttled attempt included, so a model that answers `429` four times in a row fails the job. A step that found no free turn never ran, and does not count. Between attempts it waits:

1. The time the provider asked for, when its answer carries `Retry-After`. The Convex AI Gateway documents forwarding it on chat completions (checked on 2026-10-27), and the Vercel AI Gateway sends `retry-after` on some `429`s. A wait longer than 5 minutes counts as 5.
2. Otherwise 5 seconds, doubled on each attempt.
3. Plus up to 2 seconds of jitter, the same for the same job and step, so jobs throttled together do not retry together.

The wait is a scheduled step, and it extends the job's lease, so the queue never mistakes a waiting job for a stalled one.

## Which errors fail a job

The step classifies its own error, inside the action, where the error object, its status code and its headers still exist. It hands `job.run` the outcome as data, never the error's message:

| The step's error | What `job.run` does | If it fails the job |
|---|---|---|
| `429`, or the gateway's rate-limit error | Halves the model's rate, waits, tries again | `unavailable`, reason `provider_refused` |
| A timeout, or an error the provider marks retryable (a `502`, a `503`) | Waits, tries again | `unavailable`, reason `provider_refused` |
| The model refuses the content, such as a `content-filter` finish | Fails the job at once | `invalid_input`, reason `content_blocked` |
| A catalog error your step throws (`backendError(...)`) | Fails the job at once | That error, as it is |
| Anything else | Fails the job at once | `unavailable`, reason `job_failed` |

A failed job gets its credits back ([Charge for a queued job](/docs/build/ai/jobs/credits)). The person sees the catalog error's message in their language. The provider's own error goes to your logs with the job's id, and never to the page.

## What this means for you

- **List the models your steps use, with a rate you know is safe.** The queue only lowers a rate on a `429`, so a start far above the provider's limit costs a few failed calls before it settles.
- **A slot in the queue is not a turn at the model.** Every running job shares each model's bucket, whatever its tier, so dedicated slots ([Keep slots for paid plans](/docs/build/ai/jobs/priority#keep-slots-for-paid-plans)) guarantee a running place, not calls. Route a paid kind to a model of its own when it must not share.
- **Make each step one model call.** A retry repeats the whole step, so two calls in one step pay for the first one twice when the second is throttled.
- **Throw a catalog error for what a retry cannot fix**, such as an input your step rejects. The queue fails the job at once instead of trying three more times.
- **Watch the Queue tab after a launch.** A model whose rate keeps sitting at `min` is under-provisioned at its provider: ask for a higher limit, or move the step to another model.
