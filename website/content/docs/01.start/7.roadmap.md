`0.2.0` is the backend for client apps: products people sign in to, pay for and create things in. The features a service platform needs wait for the next release, and so do a few upstream upgrades. Each line below says why it waits. Nothing here has a date yet: the service-app release follows `0.2.0`, and the order of its work follows what apps ask for, so [open a discussion](https://github.com/qruto/nuxt-backend/discussions) with your case. The [Feature map](/docs/start/feature-map) lists everything that ships in `0.2.0`.

## Service-app features

A service app sells to developers and other systems: they call it with keys, subscribe to its events and run teams inside it. These features serve that kind of app, and arrive together in the service-app release:

| Feature | Why it waits |
|---|---|
| API keys | Keys only matter when other systems call your app. Their scopes, rotation and per-key limits ship together, beside outgoing webhooks. |
| Outgoing webhooks | Telling other systems about your app's events needs signing, retries and a delivery log of its own, for the same customers who ask for keys. |
| An MCP endpoint for your users' agents | Your app as tools your users' agents sign in to, with connected agents and MCP Apps widgets. It waits for Better Auth 1.7's native MCP plugin, so it runs on Better Auth's own OAuth flow. |
| Custom workspace roles | Roles that workspace owners define from your permissions. A client app's workspaces are personal or small, and the built-in roles cover them. |
| Workspace ownership transfer | Moving a workspace, and its billing customer, to another owner matters once teams buy on behalf of a company. |
| Workspace billing permissions | Billing as a permission inside workspace roles builds on custom roles. Until then only a workspace's owner opens its billing portal, and its admins are refused ([Decide who manages billing](/docs/build/billing/setup#the-billing-portal)). |
| The full workspace API | Typed workspace metadata, every native read, and rules for who creates workspaces. `0.2.0` keeps members, invitations, the built-in roles and switching. |
| Workspace invite links | Shareable links into a workspace, with an expiry and a use limit. In `0.2.0` an invitation goes to one address, and access links admit people to the app itself. |

## Smaller follow-ups

These are planned for a release after `0.2.0` and need nothing upstream:

| Feature | What it adds |
|---|---|
| A warning about the provider's own checkout links | `doctor` names a catalog product the billing provider also sells through a checkout link of its own, which skips the package's checks on the price, the return address and the buyer. |
| Re-sync every entitlement at once | One command that rebuilds every billing entity's plan, features and credits from the billing provider, for a deployment restored from a backup or filled by an import. |
| A template per notification kind | An email template for each kind of in-app notification, in place of the one shared notification email. |

Presence, who is online in a room, is a collaboration feature and no part of either release. An app that needs it uses Convex's [presence component](https://www.convex.dev/components/presence) beside the package.

## Upstream releases the package holds for

The package moves to each of these as soon as the projects it builds on support them. `.github/upstream.json` in the repository tracks each one, and a weekly check reports when one is ready.

- **Better Auth 1.7.** It waits for Convex's Better Auth component to accept it ([get-convex/better-auth#444](https://github.com/get-convex/better-auth/pull/444)). It also brings the native MCP plugin the endpoint above needs, and the OAuth device grant, client ID metadata documents and DPoP that programmatic access will prefer over API keys. The package will require 1.7.7 or later, the release that fixes advisory [GHSA-965c-763c-88jm](https://github.com/better-auth/better-auth/security/advisories/GHSA-965c-763c-88jm). That advisory needs magic links plus social sign-in, and `0.2.0` uses neither.
- **Polar SDK 1.0.** It waits for Convex's Polar component to build against it ([get-convex/polar#100](https://github.com/get-convex/polar/pull/100)).
- **Nuxt 5.** The package requires Nuxt 4.6.2 or later, and moves to Nuxt 5 once Nuxt's server runs on h3 2 and the release is out. `nuxt-security` 2.6, which supplies the security headers, still imports h3 1, so it has to move first.

## Watched, not planned

These would change how the package works, and none is ready to build on. Each is checked again before every release.

| What | Why it waits |
|---|---|
| Device Bound Session Credentials | Sessions bound to the device's key would make a stolen cookie useless. Chrome ships them on Windows only, and the spec is still a W3C draft. |
| Vercel Workflow and Queues | Both overlap the Convex workflows and workpool the package already runs on, and Queues is in beta. |
| Vercel Flags | It has no Nuxt adapter. The package's own flags are read inside your functions ([Principles](/docs/start/concepts/principles#native-first)). |
