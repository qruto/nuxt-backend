The package is the backend for client apps: products people sign in to, pay for and create things in. The features a service platform needs wait for a later release, and so do a few upstream upgrades. Each line below says why it waits. Nothing here has a date yet: the order of the work follows what apps ask for, so [open a discussion](https://github.com/qruto/nuxt-backend/discussions) with your case. The [Feature map](/docs/start/feature-map) lists everything the package has today.

## Service-app features

A service app sells to developers and other systems: they call it with keys, subscribe to its events and run teams inside it. These features serve that kind of app, and arrive together in the service-app release:

| Feature | Why it waits |
|---|---|
| API keys | Keys only matter when other systems call your app. Their scopes, rotation and per-key limits ship together, beside outgoing webhooks. |
| Outgoing webhooks | Telling other systems about your app's events needs signing, retries and a delivery log of its own, for the same customers who ask for keys. |
| An MCP endpoint for your users' agents | Your app as tools your users' agents sign in to, with connected agents and MCP Apps widgets. It will run on Better Auth's own OAuth flow, which the package can build on now that it runs Better Auth 1.7. |
| Custom workspace roles | Roles that workspace owners define from your permissions. A client app's workspaces are personal or small, and the built-in roles cover them. |
| Workspace ownership transfer | Moving a workspace, and its billing customer, to another owner matters once teams buy on behalf of a company. |
| Workspace billing permissions | Billing as a permission inside workspace roles builds on custom roles. Until then only a workspace's owner opens its billing portal, and its admins are refused ([Decide who manages billing](/docs/build/billing/setup#the-billing-portal)). |
| The full workspace API | Typed workspace metadata, every native read, and rules for who creates workspaces. Today the package has members, invitations, the built-in roles and switching. |
| Workspace invite links | Shareable links into a workspace, with an expiry and a use limit. Today an invitation goes to one address, and access links admit people to the app itself. |

## Smaller follow-ups

This one is planned for `0.3.0` and needs nothing upstream:

| Feature | What it adds |
|---|---|
| A template per notification kind | An email template for each kind of in-app notification, in place of the one shared notification email. |

Presence, who is online in a room, is a collaboration feature and no part of the package. An app that needs it uses Convex's [presence component](https://www.convex.dev/components/presence) beside the package.

## Upstream releases the package holds for

The package moves to each of these as soon as the projects it builds on support them. `.github/upstream.json` in the repository tracks each one, and a weekly check reports when one is ready.

- **Polar SDK 1.0.** It waits for Convex's Polar component to build against it ([get-convex/polar#100](https://github.com/get-convex/polar/pull/100)).
- **Nuxt 5.** The package requires Nuxt 4.6.2 or later, and moves to Nuxt 5 once Nuxt's server runs on h3 2 and the release is out. `nuxt-security` 2.7, which supplies the security headers, still reads h3 1's `event.node`, so it has to move first.

## Watched, not planned

These would change how the package works, and none is ready to build on. Each is checked again before every release.

| What | Why it waits |
|---|---|
| Device Bound Session Credentials | Sessions bound to the device's key would make a stolen cookie useless. Chrome ships them on Windows only, and the spec is still a W3C draft. |
| Vercel Workflow and Queues | Both overlap the Convex workflows and workpool the package already runs on, and Queues is in beta. |
| Vercel Flags | It has no Nuxt adapter. The package's own flags are read inside your functions ([Principles](/docs/start/concepts/principles#native-first)). |
