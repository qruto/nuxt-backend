The package composes its services into twelve **capabilities**, each named for what it gives your app rather than the service underneath. You never turn a capability on: it starts working when its env or catalog exists, and `npx nuxt-backend status` shows where each one stands.

A capability owns everything that belongs to that part of the app:

- its setup API and its env names, which say what they do (`BILLING_*`, never a provider's name);
- the service it runs on, and that service's test mode in development;
- the `doctor` findings that check it, and the DevTools tab that shows it;
- its Services page, its Build pages and its playground pages.

One registry holds them, so every place that talks about a part of the app uses the same name for it. [Capabilities](/docs/reference/capabilities) in the reference lists each one with everything it owns, and the [Feature map](/docs/start/feature-map) lists the features of each.

::note
Earlier previews called these "app layers". In Nuxt, a layer is something you `extends`, and nuxt-backend is not one: it is a single module ([One module, not a Nuxt layer](/docs/start/concepts/principles#one-module-not-a-nuxt-layer)). The twelve names did not change, and neither did `doctor --only <name>`. The CLI and DevTools say capability too.
::

## The twelve capabilities

`0.2.0` has twelve capabilities. `analytics` reads revenue from Polar, and counts the growth funnel and experiments inside your deployment. The end-user MCP endpoint, and with it the `agents` capability, waits for the next release ([Roadmap](/docs/start/roadmap)).

| Capability | What it gives your app | Powered by | In development | Docs |
|---|---|---|---|---|
| `auth` | Sign-in by passkey and sign-in code, launch phases, invites and the waitlist, workspaces with invitations, consents, the admin console with impersonation, the activity trail, and an account's export and deletion | Better Auth, running inside your deployment | Codes print in the terminal, or reach Resend's test addresses | [Auth](/docs/build/auth) |
| `data` | The database with realtime queries, server rendering, full-text search, checked uploads, share links and retention | [Convex](/docs/services/convex) | A local or cloud dev deployment | [Data](/docs/build/data) |
| `jobs` | Scheduled jobs, durable workflows, queued work and the backend's own maintenance | Convex and its official components | The same deployment's scheduler | [Background work](/docs/build/data/jobs) |
| `billing` | Plans with monthly and yearly prices, prepaid credits, the pricing page, feature gates, the cancel flow, gifts, referrals and promotions, from a catalog in code | [Polar](/docs/services/polar), as the merchant of record | Polar's sandbox | [Billing](/docs/build/billing) |
| `email` | Transactional and lifecycle email from one template registry, themed, localized and tracked, with preferences and inbound mail | [Resend](/docs/services/resend) | Resend's test addresses, read back in the dev inbox | [Email](/docs/build/email) |
| `notifications` | An in-app inbox fed by backend events, and web push, each kind opted into | The package's own component, and the browsers' push services | The same code, on your dev deployment | [Notifications](/docs/build/email/notifications) |
| `ai` | Metered model calls and streams, generation jobs with credits held until they run, chat, and labels on generated content | The AI SDK, through the [AI gateway](/docs/services/ai-gateway) | The same gateway, on a paid Convex plan, or a Vercel AI Gateway key | [AI](/docs/build/ai) |
| `protection` | Bot checks before a code is sent or an account created, on your own guarded calls, and moderation of uploads and prompts | [Bot protection](/docs/services/bot-protection): Vercel BotID on Vercel, a Cloudflare Turnstile challenge elsewhere | The dev server's bot check answers human | [Stop bots](/docs/build/auth/sign-in/bots) |
| `monitoring` | Error reports from the browser, the Nuxt server and the backend, logs, cron check-ins and a health endpoint | [Sentry](/docs/services/sentry) | A local error log, listed in DevTools | [Monitoring](/docs/ship/operate/monitoring) |
| `flags` | Feature flags read inside your functions, experiments, targeting, kill switches and a maintenance notice | The package's own code, on Convex | The same code everywhere | [Flags](/docs/ship/operate/flags) |
| `analytics` | Revenue metrics, growth funnels and experiment results with attribution, in the admin console | Polar's metrics, and first-party counts in your deployment | Polar's sandbox metrics | [Measure growth](/docs/build/growth/measure) |
| `hosting` | The deploy, the app's env and its domains: one-command production and a deploy template | [Vercel](/docs/services/vercel) first; any host that runs Nuxt keeps working | The Nuxt dev server | [Deploy](/docs/ship/deploy) |

The [Service map](/docs/services) turns this table around: each service, the capabilities it powers, whether you need it, and the order to connect them in.

## A capability's state is detected

There is no option that turns a capability on or off, and no key for one in `nuxt.config`: every capability is always there. What changes is what it runs on. The package reads that from the env, `BACKEND_ENVIRONMENT` and `doctor`'s checks, and a capability is in one of four states:

| State | Light | Means |
|---|---|---|
| `live` | green | The real service is configured on a production deployment, and the capability acts for real. |
| `test` | amber | The capability runs in its service's test mode: Polar's sandbox, Resend's test addresses, a deployment that is not production, a challenge's test keys. |
| `missing` | grey | What it needs is not configured, so it does less, the way its env names describe. |
| `failing` | red | A check of the capability failed, whatever else holds. |

`test` takes the place of the `simulated` state of earlier previews: development runs on the providers' own test modes, so nothing is simulated. What decides the state, capability by capability:

| Capability | Live | Test | Missing |
|---|---|---|---|
| `auth` | Email is live, so codes reach real inboxes | Codes reach Resend's test addresses, or print in the dev console | `AUTH_SECRET` or `SITE_URL` is not set |
| `data`, `jobs` | A production or self-hosted deployment | A dev, local or preview deployment | No deployment |
| `billing` | `BILLING_ACCESS_TOKEN` on a `production` environment | A token on any other environment, which bills in Polar's sandbox | No `BILLING_ACCESS_TOKEN` |
| `email` | `EMAIL_API_KEY` on a `production` environment | A key on any other environment, in test mode | No `EMAIL_API_KEY` |
| `notifications` | `production`, with `PUSH_PUBLIC_KEY` and `PUSH_PRIVATE_KEY` set | Any other environment | No push keys: the in-app inbox works, web push does not |
| `ai` | `production`, with a route to the models (the Convex AI Gateway or `AI_GATEWAY_API_KEY`) and live billing | The same route, outside production | No route to a model, or billing is missing |
| `protection` | The deployment takes proofs (`PROTECTION_PROOF_SECRET`, BotID on Vercel) or challenge answers (`PROTECTION_CHALLENGE_SECRET_KEY`) | Outside production, where the dev server's bot check answers human, or a challenge on its test keys | Neither secret on production |
| `monitoring` | `MONITORING_DSN`, or the `NEXT_PUBLIC_SENTRY_DSN` Sentry's Vercel integration sets | No DSN outside production: the local error log stands in | No DSN on production |
| `flags` | Always: the package's own code, with nothing to configure | Never | Never |
| `analytics` | Billing is live | Billing runs in Polar's sandbox | Billing is missing |
| `hosting` | A production deployment whose app has its env | A preview or `sandbox` deployment | No production deployment yet |

A capability fails as soon as one of its findings fails, whatever the env says. A webhook route that is not mounted fails `billing` or `email`. A function the composables call that the deployment lacks fails `data`.

The backend reads its env on the deployment, so the deployment decides. A key that is in `.env.local` but was never pushed leaves its capability missing, and the reason says to run `npx nuxt-backend env push`. Under `--prod`, only production's names count. Values are read only to tell a mode apart, and the one mode value is `BACKEND_ENVIRONMENT`. No value is ever printed or sent anywhere.

## Where you see a capability's state

- **`npx nuxt-backend status`** prints a console of the capabilities: a light for each, what it runs on, the env it lacks and its most pressing finding. `--prod` checks production's, and `--json` gives the same as one document ([CLI](/docs/reference/cli#status)).
- **`npx nuxt-backend doctor --only <capability>`** runs one capability's checks, and every finding names its capability ([Diagnose your setup](/docs/develop/doctor)).
- **The DevTools Overview** lights one channel per capability, with links to its own tab and its docs ([DevTools](/docs/develop/devtools)).
- **The health endpoint**, `/api/backend/health`, answers each capability's state for an uptime check, and the detail for an administrator ([Monitor errors and uptime](/docs/ship/operate/monitoring#the-health-endpoint)).
- **`.env.example`** groups its names by purpose, with the platform's own names last ([Environment variables](/docs/reference/configuration/environment-variables)).
- **The docs** follow the same split. Each service has a [Services](/docs/services) page, each feature a [Build](/docs/build) page, and the Feature map has a section per capability.

## Why it works this way

- **One word per part of the app.** The CLI, DevTools, the health endpoint, `.env.example` and the docs all say `billing`, so a finding in one place leads to the page in another.
- **Named for what it gives, not who runs it.** Your code and your env say `BILLING_*`. Polar appears in prose, on its Services page and in the "Powered by" column.
- **Detected, never switched.** A switch can disagree with what is configured. The env and a check cannot ([Principles](/docs/start/concepts/principles#capabilities-are-detected-never-switched)).

## What it is not

- **Not a Nuxt layer.** You never `extends` a capability. They all ship inside the one module you add to `modules`.
- **Not a plugin you install.** Every capability is in the package from the first run. One without its key reads `missing` and does less.
- **Not a provider switch.** Each capability runs on one service's own features. [Replacing a provider](/docs/start/concepts/choosing#replacing-a-provider) says what a change would take.
- **Not the end of the list.** The `agents` capability, the MCP endpoint for your users' agents, waits for the service-app release ([Roadmap](/docs/start/roadmap)).

## What this means for you

You never configure a capability: you configure the service under it. Put a provider's key in `.env.local`, run `npx nuxt-backend env push`, and the capability turns from missing to test, or to live on production. `npx nuxt-backend status` shows the change. In development, test is the healthy state. Before a release, run `npx nuxt-backend status --prod`: production should show every capability you use as live, and `doctor --prod` gives the fix for any that is not.
