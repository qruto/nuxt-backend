The package ships two halves in one install: a Nuxt module for your app, and one Convex component for your backend. The [capabilities](/docs/start/concepts/capabilities) are what they give your app. This page is how the halves fit together, and which request takes which path. It is one module in `modules`, never a Nuxt layer in `extends` ([Principles](/docs/start/concepts/principles#one-module-not-a-nuxt-layer)).

| Half | What it does |
|---|---|
| **Nuxt module** (`nuxt-backend`) | Registers plugins, composables, components, server utilities and the auth proxy, mounts the ready-made pages, and loads the CSS of the capabilities it detects |
| **Convex component** (`nuxt-backend/convex.config`) | Defines the all-in-one `backend` component: the Better Auth adapter and auth tables, transactional email (Resend's component nested inside), the billing entitlement cache, gifts, AI metering records, the webhook delivery log, the activity trail and feature flags |

The scaffolded `convex.config.ts` mounts the `backend` component and the official `@convex-dev/*` components its setup helpers use, one explicit `app.use` each. A component your own code needs, such as an aggregate, your app mounts beside them ([the component tree](#one-backend-component-beside-the-official-ones)).

## Request flows

Three transports run side by side, each with its own path through the stack:

::card-group
  :::card{icon="i-lucide-zap" title="Real-time"}
  `Browser ⇄ Convex deployment` over a WebSocket (`ConvexVueClient`): queries subscribe, and the deployment pushes live updates.
  :::

  :::card{icon="i-lucide-server" title="SSR"}
  `Browser → Nuxt → Convex` over HTTP (`ConvexHttpClient`): the server renders the HTML and ships a hydration payload.
  :::

  :::card{icon="i-lucide-shield-check" title="Auth"}
  `Browser → /api/auth/* → Nuxt proxy → Better Auth → Convex`: the session token and `Set-Cookie` come back same-origin.
  :::
::

### Real-time data

The client, `ConvexVueClient`, keeps one WebSocket open to the deployment. `useQuery`, `useMutation`, `useAction` and pagination go through it, and every subscribed query updates live, in every open tab ([Query and update data](/docs/build/data/read-write)).

::demo-connection
::

### SSR

During the server render, `useAsyncQuery` fetches a query over HTTP as the signed-in person and hands the result to the browser, which goes live without fetching it again. Nuxt server routes call the deployment with `fetchQuery`, `fetchMutation` and `fetchAction`, or as the signed-in person through `backendAuth(event)` ([Render data on the server](/docs/build/data/read-write/server-rendering)).

### Authentication

`/api/auth/*` is proxied from Nuxt to the deployment's site URL, so cookies stay on your domain. Better Auth keeps users and sessions through the adapter inside the `backend` component, and issues a session token the client authenticates its WebSocket with ([Auth](/docs/build/auth)).

### Inbound webhooks

One more path ends in the backend without a browser in front: `Provider → <site URL>/billing/events | /email/events → Convex HTTP router`. `registerBackendRoutes` in the scaffolded `http.ts` mounts both, beside the metered AI stream at `/ai/stream` and the health check. Every delivery is verified once with Standard Webhooks, deduplicated and logged, and the route answers `503` until its secret is set ([Register webhooks](/docs/ship/security/webhooks)).

::note
This mirrors the official Convex and Better Auth integration: realtime over a WebSocket, server rendering over HTTP, and a same-origin auth proxy that keeps cookies on your domain.
::

## What it mounts

`nuxt-backend` ships one [Convex component](https://www.convex.dev/components) of its own, the all-in-one `backend` component, and sets up the official components its helpers build on. Each capability is set up by one helper in one scaffold file: [Setup helpers](/docs/reference/backend) lists every helper with its file, and [Ecosystem](/docs/reference/ecosystem) the components that work beside these.

| Capability | Component | Entrypoint | Setup helper |
|---|---|---|---|
| Auth | `backend` (the Better Auth tables and adapter) | `nuxt-backend/auth` | `setupAuth` |
| Access tiers and errors | None: function builders over your own `query`, `mutation` and `action` | `nuxt-backend/functions` | `createFunctions` |
| Launch access and the waitlist | `backend` | `nuxt-backend/access` | `setupAccess`, `setupWaitlist` |
| Account export, deletion and consents | `backend` | `nuxt-backend/account` | `setupAccount` |
| Admin console | `backend` | `nuxt-backend/admin` | `setupAdmin` |
| Activity trail | `backend` | `nuxt-backend/audit` | `setupAudit` |
| Feature flags | `backend` | `nuxt-backend/flags` | `defineFlags`, `setupFlags` |
| Email | `backend` (nests [`@convex-dev/resend`](https://www.convex.dev/components/resend)) | `nuxt-backend/email` | `setupEmail` |
| Notifications | `backend` | `nuxt-backend/notifications` | `setupNotifications` |
| Billing | [`@convex-dev/polar`](https://www.convex.dev/components/polar), [`@convex-dev/sharded-counter`](https://www.convex.dev/components/sharded-counter) (plan quotas) and `backend` (the entitlement and credit cache, gifts) | `nuxt-backend/billing` | `setupBilling`, `defineBillingCatalog` |
| Files | `backend`, over Convex file storage | `nuxt-backend/storage` | `setupStorage` |
| Webhooks and routes | None: HTTP routes over auth, billing, email and AI | `nuxt-backend/http` | `registerBackendRoutes` |
| Monitoring | None: actions post to the DSN | `nuxt-backend/monitoring` | `reportError`, `checkIn` |
| Rate limiting | [`@convex-dev/rate-limiter`](https://www.convex.dev/components/rate-limiter) | `nuxt-backend/rate-limit` | `setupRateLimiter` |
| Metered AI and generation jobs | [`@convex-dev/persistent-text-streaming`](https://www.convex.dev/components/persistent-text-streaming), [`@convex-dev/workpool`](https://www.convex.dev/components/workpool) and `backend` (the request records) | `nuxt-backend/ai` | `setupAi`, `defineJobQueue` |
| Workflows and email sequences | [`@convex-dev/workflow`](https://www.convex.dev/components/workflow) | `nuxt-backend/workflows` | `setupWorkflows`, `defineEmailSequence` |
| Search | Convex's native full-text search | `nuxt-backend/search` | `defineSearch` |

Your own counters, aggregates, cached actions, queues and migrations come straight from their official components: [`@convex-dev/sharded-counter`](https://www.convex.dev/components/sharded-counter) (the scaffold already mounts it for plan quotas), [`@convex-dev/aggregate`](https://www.convex.dev/components/aggregate), [`@convex-dev/action-cache`](https://www.convex.dev/components/action-cache), [`@convex-dev/workpool`](https://www.convex.dev/components/workpool) and [`@convex-dev/migrations`](https://www.convex.dev/components/migrations). Your app mounts the one it needs and imports it directly, as the [Data](/docs/build/data) recipes show. The package's own maintenance runs inside its component, so your app registers no cron for it.

### The scaffolded `convex.config.ts`

`npx nuxt-backend init` writes `backend/convex.config.ts`. It mounts the `backend` component and the official components the setup helpers use, and declares the typed env contract (`backendEnv` from `nuxt-backend/app`: `AUTH_SECRET` and `SITE_URL` required, the rest optional). It also forwards the variables the `backend` component reads, so setting them on the deployment is all the sign-in codes, invitations and cron check-ins need:

```ts [backend/convex.config.ts]
import { defineApp } from 'convex/server'
import { backendEnv } from 'nuxt-backend/app'
import backend from 'nuxt-backend/convex.config'
import persistentTextStreaming from '@convex-dev/persistent-text-streaming/convex.config'
import polar from '@convex-dev/polar/convex.config'
import rateLimiter from '@convex-dev/rate-limiter/convex.config'
import shardedCounter from '@convex-dev/sharded-counter/convex.config'
import workflow from '@convex-dev/workflow/convex.config'
import workpool from '@convex-dev/workpool/convex.config'

const app = defineApp({ env: backendEnv })

// Components are isolated from the app's env: forward what backend reads.
app.use(backend, {
  env: {
    BACKEND_ENVIRONMENT: app.env.BACKEND_ENVIRONMENT,
    EMAIL_API_KEY: app.env.EMAIL_API_KEY,
    EMAIL_FROM: app.env.EMAIL_FROM,
    EMAIL_WEBHOOK_SECRET: app.env.EMAIL_WEBHOOK_SECRET,
    MONITORING_DSN: app.env.MONITORING_DSN,
  },
})
app.use(persistentTextStreaming)
app.use(polar)
app.use(rateLimiter)
app.use(shardedCounter)
app.use(workflow)
app.use(workpool)

export default app
```

::note
**Why not a one-call helper?** Convex discovers components from the `convex.config` imports it meets while bundling this file. Current Convex backends refuse the push (`start_push 500`) when such an import is reached through an intermediate module, or when `app.use` runs in a loop. So the definition is explicit on purpose: every component imported and mounted in the root file, one `app.use` each, which also keeps the component tree in plain sight.
::

To read an env var of your own, extend the contract, and mount a component of your own after the package's:

```ts [backend/convex.config.ts]
import aggregate from '@convex-dev/aggregate/convex.config'
import { v } from 'convex/values'

const app = defineApp({
  env: { ...backendEnv, STORY_STYLE: v.optional(v.string()) },
})
// … the package's components, as above
app.use(aggregate)
```

`backend` is the package's core: keep it mounted, with the official components its helpers name. `setupAuth` uses `rateLimiter`, `setupAi` needs `persistentTextStreaming` and `rateLimiter`, `setupBilling` needs `polar`, plus `shardedCounter` for plan quotas, and `setupWorkflows` needs `workflow`. The env proxy throws on an undeclared variable, so declare every one you read.

### One `backend` component, beside the official ones

The package ships one Convex component of its own, its functions split into modules by concern. Your code reaches them through the setup helpers; [The backend component](/docs/reference/backend/component) lists every function and table:

| Module | What it holds |
|---|---|
| `adapter` | The Better Auth tables and adapter. Better Auth itself runs as app-level code over it, not as a component |
| `account` | An account's export and its erasure across every participant |
| `audit` | The activity trail: one row per event, and the hand-off to your `onEvent` |
| `email` | Transactional email, with [`@convex-dev/resend`](https://www.convex.dev/components/resend) nested inside; it owns the `EMAIL_*` env |
| `billing` and `gifts` | The live entitlement and credit cache, and gift purchases |
| `ai` | The records of metered AI requests, from the reservation to settlement or release |
| `flags` | The overrides an administrator set; a flag without one holds its default from code |
| `webhooks` | The delivery log of `/billing/events` and `/email/events`, which dedupes redeliveries and feeds DevTools ([the delivery log](/docs/ship/security/webhooks#the-delivery-log)) |
| `maintenance` and `monitoring` | The hourly housekeeping of every table above, and its cron check-ins ([Background work](/docs/build/data/jobs#what-the-component-already-runs)) |
| `migrations` and `posture` | Internal: the package's own data migrations, which [`nuxt-backend upgrade`](/docs/reference/cli#upgrade) runs, and what the deployment reports of its email to `doctor --prod` |

Two components are nested **inside** `backend`: Resend's, which is self-contained, so `backend` re-exposes it through its `email` functions, and a migrations component of its own, which runs the package's data migrations over `backend`'s tables when `nuxt-backend upgrade` asks. The official components mount at the app level: a nested component is sandboxed from the parent app, and Polar's, the rate limiter, the sharded counter, workflows and the workpool all work over your own tables, functions, auth and HTTP routes.

The dashboard component tree looks like this:

```text
app
├─ backend
│  ├─ backend/resend
│  └─ backend/migrations
├─ persistentTextStreaming
├─ polar
├─ rateLimiter
├─ shardedCounter
├─ workflow
│  └─ workflow/workpool
└─ workpool
```

### Server helpers and composables, two halves of one feature

The `nuxt-backend/*` entrypoints are server code: you import them inside your Convex functions to set up each capability with the package's defaults, such as the auth rate limits or the workflow retries. The auto-imported composables, such as `useSearch`, `useBilling` and `useWorkflowStatus`, are client code: reactive wrappers over `useQuery` that subscribe to the queries those functions expose. The helper builds the server endpoint, and the composable reads it reactively in your components.

::note
Each helper lives on its own entrypoint rather than one barrel, so a Convex function bundles only what it imports: the reason the official `@convex-dev/*` packages are split too, and what keeps `better-auth` out of a file that only does rate limiting.
::

## Who owns what

| | Owns |
|---|---|
| The `backend` component | Its own tables (accounts, sessions, passkeys, workspaces, the billing cache, gifts, AI requests, email records, the webhook log, the activity trail and flags), the operations on them, their hourly maintenance, and erasing what it holds about an account |
| Your app's `backend/` | Identity and authorization (Better Auth runs there, over the component's tables, and `functions.ts` decides who may call what), every call to a provider, made by the setup helpers, and your own tables and files |
| The providers | Money (Polar's customers, orders, invoices and meters), delivery (Resend's messages and events) and model calls |

The split is why the component can be upgraded and migrated on its own (`npx nuxt-backend upgrade`), while nothing it does needs a provider key: those stay in your app's functions.

## One path for what happens

A sign-in, a workspace change, a subscription or order, or an administrator's action is a [backend event](/docs/reference/backend/events#backend-events), written once to the activity trail by the code that made it happen. Everything that reacts reads it there: the [activity](/docs/build/auth/admin/audit-log) the account, its workspace and administrators see, your own `onEvent` hook, and the [in-app notifications](/docs/build/email/notifications) an event derives in the same transaction, for the people it is about. An administrator acts inside someone else's account only by [impersonating](/docs/build/auth/admin/impersonation) it, which is an event of its own.
