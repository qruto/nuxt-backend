An app has one deployment per stage: a dev deployment for each developer, a preview per branch, and one production. One variable, `BACKEND_ENVIRONMENT`, tells the backend which kind it runs on, and every mode follows from it: email test mode, Polar's sandbox, trusted local origins and sign-in codes in the logs. You never flip those one by one.

## The deployments

| Deployment | `CONVEX_DEPLOYMENT` | Made by | `BACKEND_ENVIRONMENT` |
|---|---|---|---|
| Account-free local | `anonymous:…` | `npx nuxt-backend dev --anonymous`, on any OS, with no account | `development` |
| Local | `local:…` | `convex dev` in an account's project, on this machine | `development` |
| Cloud dev | `dev:…` | `convex dev` in an account's project, one per developer | `development` |
| Preview | Named by the branch | `convex deploy` with a preview deploy key | `preview` |
| Demo or staging | `prod:…`, in a project of its own | `convex deploy` with that project's production key, as the [Panels demo](/docs/start/tutorial) runs | `sandbox`, set on purpose |
| Production | `prod:…` | `convex deploy` with a production deploy key | `production` |
| Self-hosted | None: `CONVEX_SELF_HOSTED_URL` names it | Your own Convex backend | What you set |

## `BACKEND_ENVIRONMENT`

`BACKEND_ENVIRONMENT` takes `development`, `preview`, `sandbox` or `production`. `npx nuxt-backend env push` derives it from `CONVEX_DEPLOYMENT`: a dev deployment is `development`, a preview is `preview`, and production is `production`. Each value decides four things at once:

| `BACKEND_ENVIRONMENT` | Email | Billing | Local origins trusted | Sign-in codes logged |
|---|---|---|---|---|
| `development` | Test mode | Polar's sandbox | Yes | Yes |
| `preview` | Test mode | Polar's sandbox | No | No |
| `sandbox` | Test mode | Polar's sandbox | No | No |
| `production` | Live | Live | No | No |

`sandbox` is the one value you set by hand. It is for a deployed demo or a staging app: the deployment runs in production mode, with production's checks and no code logging, while every provider stays in its test mode. The monitoring environment name equals `BACKEND_ENVIRONMENT` too, so Sentry groups a demo's errors apart from production's. A `sandbox` deployment also refuses the admin actions that reach a provider for real: a broadcast, a webhook replay and lifting an email suppression ([What a demo refuses](/docs/ship/deploy/staging#what-a-demo-refuses)). The replay and the lift run on `production` and `development` alone, so a preview, or a deployment whose value is unset or mistyped, refuses them too.

`BACKEND_ENVIRONMENT` replaces five variables of earlier previews, each of which said one part of the same thing: `EMAIL_TEST_MODE`, `BILLING_ENVIRONMENT`, `MONITORING_ENVIRONMENT`, `AUTH_TRUST_LOCAL_ORIGINS` and `NUXT_BACKEND_LOG_OTP`.

## Sandbox and production providers

Every provider starts in its test mode, and only `production` takes it out:

- **Email** in test mode delivers only to Resend's test addresses, such as `delivered@resend.dev`. Any other address is refused on the request, with a message that says why.
- **Billing** outside production calls Polar's sandbox, with a sandbox token, a sandbox catalog and the test card `4242 4242 4242 4242`.
- **AI** calls the same models everywhere, through the Convex AI Gateway or `AI_GATEWAY_API_KEY`, and charges credits from whichever billing the environment uses.

`npx nuxt-backend doctor --prod` fails a production deployment whose `BACKEND_ENVIRONMENT` is unset, `development` or `preview`. It only warns on `sandbox`, which you set on purpose for a demo or staging app ([Prepare for launch](/docs/ship/checklist)). [Develop on real sandboxes](/docs/develop/sandboxes) covers each test mode in development.

## The app's env and the deployment's

Most values live on the deployment, and the package forwards them there for you:

| Where | What lives there | Who puts it there |
|---|---|---|
| The deployment | `AUTH_SECRET`, `SITE_URL`, `BACKEND_ENVIRONMENT`, and the email, billing, AI, push and monitoring keys | `npx nuxt-backend env push` from `.env.local`, or the dashboard |
| The Nuxt app | The backend's URL, `NUXT_PUBLIC_BACKEND_URL`, and the bot challenge's public site key | The URL derives from `CONVEX_DEPLOYMENT` in development, and the deploy sets it on a host. The site key is yours to set |
| Both | The few values the app's server and the backend must agree on, such as the bot-check proof secret | `env push`, and your host's env |

Write every value once in `.env.local`. The Nuxt app reads its part, and `env push` forwards the deployment's part, never replacing a value already set unless you pass `--force`. The app needs no second URL for the deployment's HTTP routes: it derives that origin from `NUXT_PUBLIC_BACKEND_URL`. [Environment variables](/docs/reference/configuration/environment-variables#every-variable) says where each name lives, grouped as Backend, Email, Billing, AI, Protection, Notifications and Monitoring, with the platform's names last.

## Regions

Where each deployment runs is chosen when it is created, and each service decides it in its own way:

- **Convex** picks the deployment's region at creation: the US, the EU in Dublin, Canada or Australia. Moving a deployment means a backup and a restore ([Convex](/docs/services/convex)).
- **Resend** sends from the region `EMAIL_REGION` names, while the account's data stays in the US ([Resend](/docs/services/resend)).
- **The AI gateway** can pin inference to the EU ([AI gateway](/docs/services/ai-gateway)).

Pick the same region for every deployment of an app, so a preview behaves like production. [Privacy, GDPR and cookies](/docs/ship/compliance/privacy) says what each region means for the data you hold.

## The platform's own variables

`CONVEX_DEPLOYMENT`, `CONVEX_DEPLOY_KEY`, `CONVEX_SITE_URL` and `CONVEX_SELF_HOSTED_URL` belong to the Convex CLI and runtime. The package reads them to find the deployment and derive its URLs, and never asks you to write or rename one: `convex dev` writes `CONVEX_DEPLOYMENT`, your host holds the deploy key, and the runtime sets `CONVEX_SITE_URL` itself.

## What this means for you

- In development: write values into `.env.local` and run `npx nuxt-backend env push` ([Run the dev loop](/docs/develop/dev-loop)).
- Connecting a service: its [Services](/docs/services) page lists its keys for dev and production.
- For previews and production: [Preview environments](/docs/ship/deploy/previews) and [Deploy to production](/docs/ship/deploy#the-env-split) set the env per stage, and [Self-host and add domains](/docs/ship/deploy/self-hosting#self-host-the-backend) covers your own backend.
- Before launch: pass `npx nuxt-backend doctor --prod` ([Diagnose your setup](/docs/develop/doctor)).
