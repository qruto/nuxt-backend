The install and the first `npx nuxt-backend dev` left your app with a deployment that mounts the `backend` component, and a `backend/` folder of setup files that are yours to edit. Pages and HTTP routes already answer, every composable and component is auto-imported, and a maintenance pass keeps the backend's own tables small. None of it needs a line of your code.

## The inventory

The list below is generated from the package's registries, so whatever a later release adds shows up here, each name linked to its reference entry. The scaffold writes only the files the package calls into: you add a file when you use what it sets up.

## Who owns what

| | Who writes it after the first run |
|---|---|
| Your files | You. They were written once, `npx nuxt-backend init --force` is the only thing that rewrites them, and `init` or `doctor --fix` restores one that is gone. Commit them. |
| `backend/billing.generated.ts` | `npx nuxt-backend billing sync`: the provider ids, one entry for the sandbox and one for production. Commit it too. |
| `backend/_generated/` | The platform's codegen, on every push of `convex dev`. |
| Pages and routes | The module mounts them. A page of yours at the same path replaces the module's, a path in `backend.pages` moves one, and `false` turns one off ([Packaged pages](/docs/build/ui/pages)). |
| The deployment's env | `dev` set `AUTH_SECRET`, `SITE_URL` and `BACKEND_ENVIRONMENT`, and never replaces a value. `npx nuxt-backend env push` forwards what you add to `.env.local` ([Environment variables](/docs/reference/configuration/environment-variables)). |
| The backend's tables | The `backend` component: it owns its tables and their maintenance, and your schema never lists them ([How it works](/docs/start/concepts/how-it-works)). |

[Project files](/docs/reference/configuration/project-files) lists what each file exports and which exports `doctor` holds it to.

## What is live, and what turns the rest on

Each part of the app is a [capability](/docs/start/concepts/capabilities), and each capability reads `live`, `test`, `missing` or `failing` from what is configured, never from a switch. On the local deployment the Quickstart made, data, jobs and auth read `test`, with codes in the terminal, and flags are live. Billing, email and AI read `missing` until you add their keys: [Develop on real sandboxes](/docs/develop/sandboxes) adds each one.

```bash
npx nuxt-backend status
```

The command prints each capability's state, the env names it lacks and the `doctor --only` run that shows the fix. [Capabilities](/docs/reference/capabilities) says what turns each one live, the [Service map](/docs/services) connects each service, and [Run the dev loop](/docs/develop/dev-loop) what changes on a cloud deployment.
