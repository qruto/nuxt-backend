`npx nuxt-backend doctor`, the dev-server preflight and the DevTools tab report the same findings, and this page has an entry for each. An entry says what the finding checks, when it warns or fails in development and under `--prod`, why it matters, and how to fix it.

Each finding has an id, the [capability](/docs/reference/capabilities) that `doctor --only` selects it by, and a `docsUrl`, `https://nuxt-backend.dev/d/<id>`, that lands on its entry below. The entries are generated from the findings registry. In `0.x` a minor release may rename a finding or move it to another capability, and any release may change a message's wording ([Stability](/docs/ship/releases/stability)).

A finding that **fails** breaks the app or a deploy, and `doctor` exits `1`. One that **warns** is a designed degradation, or a check that could not run. Under `--prod`, a warning of a finding production cannot run without fails too. `doctor --fix` repairs the findings marked so: it restores missing scaffold files and pushes env, never with `--force`, and changes provider settings only once you confirm them.

```bash
npx nuxt-backend doctor --only billing   # one capability's findings
npx nuxt-backend doctor --prod --json    # production posture, as JSON
```

## What changes

`0.2.0` changes the findings with the variables and the capabilities they check. One variable, `BACKEND_ENVIRONMENT`, replaces the five that each said what kind of deployment this is, so `deployment-auth-trust-local-origins`, `deployment-email-test-mode`, `deployment-billing-environment` and `deployment-monitoring-environment` gave way to `deployment-backend-environment`, and `deployment-removed-env` names any of the variables `0.2.0` removed that a deployment still holds. `backend-site-url` checks the site origin derived from `NUXT_PUBLIC_BACKEND_URL`. The billing simulator and the MCP endpoint for your users' agents are gone, and their findings with them. The live site's probes (`site-https`, `site-csp`, `site-backend-url` and `agent-docs`) moved from `data` to `hosting`. `nuxt.config` is the one place a path is written, so `invitation-path` gave way to `page-paths`, which compares every path the deployment uses with it, and `paths-file` checks the generated file that carries them to the backend ([The paths file](/docs/reference/configuration/module-options#the-paths-file)). `deployment-email-dev-inbox` warns when the dev inbox's opt-in is left set on production. `name-collisions`, in `data`, is informational: it names each app component or composable that shares a name with one of the package's, since a same-named component is how you swap a [part](/docs/reference/components/parts). Two changes are still to come:

| Finding | In `0.2.0` | Unit |
|---|---|---|
| `agent-files` | Checks that `.mcp.json` holds the `nuxt-backend` server in place of the Convex one | DEVMCP |
| `bundle-duplicates` | New, in `data`: warns when the last `analyze` run found a package bundled more than once in the Convex bundle, and names the fix. There is no finding until a run exists | ANALYZE |

`doctor --only` takes the twelve capabilities of `0.2.0`. `agents` is not one of them ([Capabilities](/docs/start/concepts/capabilities)). With OPS2, `doctor --fix` also applies the settings the warn-only billing findings recommend at the provider, such as [`billing-trial-abuse`](#billing-trial-abuse), after you confirm them at a terminal ([Apply the provider settings](/docs/services#recommended-settings)).

The entries below are generated from the findings registry as it stands, and keep the previous findings until each unit lands.

## `auth`

### `auth-secret`

`AUTH_SECRET` is set on the deployment, or visible locally, at least 32 characters and not a placeholder.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `auth` | Auth secret | Fails when it is too short or a placeholder; otherwise warns | As in dev | Applies the fix |

**Why it matters:** It signs sessions and encrypts the keys the session tokens are signed with; a weak one makes them guessable. **Fix:** Generate one (`openssl rand -base64 32`) and push it: `npx nuxt-backend env push`, or `doctor --fix` on a dev deployment. Check it again with `npx nuxt-backend doctor --only auth`.

### `site-url`

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `auth` | App site URL | Fails when it is malformed; otherwise warns | As in dev | Applies the fix |

**Why it matters:** Auth trusts it as the app origin, and invitation and gift emails link to it. **Fix:** Set `SITE_URL` to the app's origin, such as `https://app.example.com`. Check it again with `npx nuxt-backend doctor --only auth`.

|---|---|---|---|---|
| `auth` | Deployment SITE_URL | Fails when it is not set; otherwise warns | As in dev | Applies the fix |

### `site-url-origin`

Production's `SITE_URL`, its origin read off the deployment (`convex env get --prod SITE_URL`; the app's public origin, no secret, so the findings print it): an `https` origin passes; one on this machine (`localhost`, a `.localhost` name, a loopback address), a plain `http` one or no URL at all fails. An `https` origin of its own is the site the live probes below check; nothing is probed over plain HTTP, so this finding alone reports it. No finding when `SITE_URL` is not set (`deployment-site-url` fails).

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `auth` | Production site URL | Not checked | Fails when it is a local origin, plain HTTP, or not a URL; otherwise warns | No |

**Why it matters:** Auth trusts it as the one browser origin, and every emailed link starts with it: left at the dev default, links point at the developer's machine; over plain HTTP, browsers keep passkeys and secure cookies away. **Fix:** Set the app's public origin on production: `npx convex env set --prod SITE_URL https://app.example.com`. Check it again with `npx nuxt-backend doctor --only auth --prod`.

### `site-gated-page`

An anonymous request to a page behind the sign-in gate (`backend.pages.settings`, `/settings` by default) on production's site: a redirect to the sign-in page (`backend.pages.login`) passes; a `200` that carries a cache's mark (`x-vercel-cache` `HIT`, `STALE` or `PRERENDER`, `cf-cache-status: HIT`, `x-nitro-prerender`, an `age`) fails; any other `200`, a redirect elsewhere, a `404` or no answer warns.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `auth` | Gated pages | Not checked | Fails when the page is served to an anonymous visitor from a cache; otherwise warns | No |

**Why it matters:** A private page rendered once and cached is served to everyone, with the data of whoever it was rendered for; one rendered only in the browser sends its shell before the gate runs. **Fix:** Drop the `swr`, `isr`, `cache` or `prerender` route rule that reaches the page (the module exempts private pages at their exact paths only), and keep server rendering on for it. Check it again with `npx nuxt-backend doctor --only auth --prod`.

### `site-auth-proxy`

An anonymous `GET <authRoute>/ok` (`/api/auth/ok` by default) on production's site, Better Auth's own health answer through the sign-in proxy: `{ ok: true }` passes; a `5xx` fails; a `404`, another answer or none warns.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `auth` | Sign-in proxy | Not checked | Fails when the proxy answers `5xx`: it cannot reach the deployment; otherwise warns | No |

**Why it matters:** The proxy forwards to the HTTP routes' origin the build baked in, derived from the backend URL the build knew. A build that knew none (`NUXT_PUBLIC_BACKEND_URL` set for the runtime only) leaves it empty, and every sign-in request fails. **Fix:** Set `NUXT_PUBLIC_BACKEND_URL` where the app builds, or set `NUXT_PUBLIC_CONVEX_SITE_URL` on the app's host to the deployment's `https://<name>.convex.site` URL, then redeploy ([Deploy to Vercel](/docs/ship/deploy/vercel#the-backends-url-at-build)). Check it again with `npx nuxt-backend doctor --only auth --prod`.

### `consent-urls`

Whether each required consent that `setupAccount({ consents })` declares in `backend/account.ts` has a `url`. It reads the declaration from the source, so a `consents` that is not an object literal in the call is left alone. It runs under `--prod` only.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `auth` | Consent documents | Not checked | Warns, never fails | No |

**Why it matters:** The agreement line on the sign-up form and the prompt that asks again after a change link each kind to its `url`: a required kind without one points nowhere, and a person cannot read what they agree to. **Fix:** Add the page of the document as the kind's `url`, such as `/terms` ([Record consents](/docs/build/auth/accounts/consents#declare-your-consents)). Check it again with `npx nuxt-backend doctor --only auth --prod`.

### `admin-bootstrap`

Whether an account on the deployment holds the `admin` role, read off the auth tables of the `backend` component (`convex run --component backend --inline-query`, which answers `true` or `false` and reads no address). An account whose roles include `admin` passes (`admin,support` too); none warns. Only the `admin` role itself is looked for: administrators who hold only a role of the app's own read as none, so give them `admin` as well. No finding when the deployment cannot be read, or when it holds more than 8,000 accounts and none of the first 8,000 is an administrator.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `auth` | First administrator | Warns, never fails | Still a warning | Applies the fix |

**Why it matters:** Until an account holds the role, nobody can open the admin console at `/admin`, ban an account, sign its devices out or act as it to help. **Fix:** Sign in once with your address, then run `npx nuxt-backend doctor --fix` at a terminal and enter it: the scaffold's `setUserRole` makes that account an administrator and records the change on the activity trail. Without a terminal: `npx convex run functions:setUserRole '{"email":"you@example.com","role":"admin"}'` ([Run the admin console](/docs/build/auth/admin)). Check it again with `npx nuxt-backend doctor --only auth`.

### `page-paths`

The paths the deployment serves on and links to (`paths` from the deployed `auth:authConfig`: the auth route, and the invitation, keep-account, security, waitlist, login, unsubscribe, report, settings and privacy pages) against the ones `nuxt.config` declares (`backend.authRoute` and `backend.pages`). They differ when the deployed code predates the generated `paths.generated.ts`, or does not pass its `paths` to `defineBackendAuthConfig`, `setupAuth` and `setupAccount`. No finding when the deployment or `nuxt.config` cannot be read.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `auth` | Page paths | Fails when any path differs; otherwise warns | As in dev | No |

**Why it matters:** A different auth route sends the proxy to routes the deployment does not serve, so nobody signs in; a different page path sends the email that links to it to a 404. **Fix:** Pass the generated `paths` on as the scaffold does, then let `npx convex dev` push, or deploy. Check it again with `npx nuxt-backend doctor --only auth`.

## `data`

### `backend-site-url`

A backend site URL is configured: the site origin derived from `NUXT_PUBLIC_BACKEND_URL` (or the `url` module option, or `CONVEX_DEPLOYMENT`), or `NUXT_PUBLIC_CONVEX_SITE_URL`, the base module's own variable, for a custom domain.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `data` | Backend site URL | Warns, never fails | Still a warning | No |

**Why it matters:** Without it the `/api/auth` proxy has no target, so nobody can sign in. **Fix:** Normally derived for you; set `NUXT_PUBLIC_BACKEND_URL` to point at another deployment, or `NUXT_PUBLIC_CONVEX_SITE_URL` for a custom domain or a self-hosted backend. Check it again with `npx nuxt-backend doctor --only data`.

### `deployment-env`

The deployment env could be read at all (`npx convex env list`).

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `data` | Deployment env | Warns, never fails | Still a warning | No |

**Why it matters:** Every `deployment-*` check reads it; without it they cannot run. **Fix:** Run `npx convex dev` once to provision a deployment, then run `doctor` again. Check it again with `npx nuxt-backend doctor --only data`.

### `deployment-backend-environment`

`BACKEND_ENVIRONMENT` is set on the deployment: the kind of deployment, which decides email's test mode, the billing sandbox, the local origins auth trusts, the sign-in codes in the logs and the environment reports name. Under `--prod` its value is read (`convex env get`, compared and never printed): `production` passes; unset, `development` and `preview` fail; `sandbox`, a demo or staging app on purpose, warns, and so does a value that is none of the four.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `data` | Deployment BACKEND_ENVIRONMENT | Warns, never fails | A warning fails | Applies the fix |

**Why it matters:** Without it every provider stays in its test mode: mail reaches only the email provider's test addresses, checkout takes test cards, and nobody pays. A `development` value on production also trusts local origins and logs sign-in codes. **Fix:** Run `npx nuxt-backend env push` (`--prod` for production): it derives the value from the deployment's kind, and `doctor --fix` does the same. A demo or staging app sets `sandbox` by hand (`npx convex env set --prod BACKEND_ENVIRONMENT sandbox`). Check it again with `npx nuxt-backend doctor --only data --prod`.

### `paths-file`

`<functions dir>/paths.generated.ts` exists and holds the paths `nuxt.config` declares (`backend.authRoute`, and `backend.pages` for the invitation, keep-account, security, waitlist, login, unsubscribe, report, settings and privacy pages), read as the module reads them: options written inline in `modules` over the `backend` key. Missing or out of date warns, naming each path that differs. So does a backend file that does not import it while `nuxt.config` moves a path its helper reads: `auth.config.ts` (the auth route), `auth.ts`, `account.ts` (the keep-account page), `waitlist.ts` (the sign-in page) or `access.ts` (the sign-in and privacy pages). No finding before there is a functions directory, or when `nuxt.config` cannot be loaded.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `data` | Paths file | Warns, never fails | Still a warning | Applies the fix |

**Why it matters:** The backend reads its paths from that file: without it, with an old one, or in a file that does not pass it on, the auth routes and the links in its emails point at the default paths, or at pages that moved. An `auth.config.ts` kept from `0.1` serves the token keys under `/api/auth` while the proxy moves, and nobody signs in. **Fix:** Run `npx nuxt-backend doctor --fix` (any `nuxt prepare`, `dev` or `build` writes it too), commit the file and push the functions. In a file that does not pass it on, import `paths` from `./paths.generated` and pass it as the scaffold does. Check it again with `npx nuxt-backend doctor --only data`.

### `convex-config`

`convex.config.ts` mounts every component the scaffold's own mounts, plus each component the scaffold leaves out once a file of the functions directory imports it directly (the action cache, an aggregate, migrations, or `Crons` from `@convex-dev/crons`), and forwards every env name the scaffold forwards to the `backend` component (`MONITORING_DSN` among them) when it forwards an `env` object at all, and forwards none of the names `0.2.0` removed (`EMAIL_TEST_MODE`, `MONITORING_ENVIRONMENT` and the rest), and `http.ts` passes every route group the scaffold's passes to `registerBackendRoutes`. Both lists are read from the scaffold of the installed version. A mount anywhere in the file counts, a branch included; a component marked `// nuxt-backend-unmounted: <name>` is left out on purpose. A file that does not parse warns.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `data` | Mounts and routes | Fails when a missing component is already needed by a backend file (`components.<name>`, a helper that reads it such as `setupRateLimiter`, or a direct import of one the scaffold leaves out), or the mount forwards a name `0.2.0` removed, which the deployment no longer declares, so the push fails; otherwise warns | As in dev | Applies the fix |

**Why it matters:** A project scaffolded by an earlier release lacks what later ones added, and the features that need it stay off; a component the code needs but nothing mounts fails the push. **Fix:** `doctor --fix` adds each missing import and `app.use(…)`, each missing forwarded env name, and each missing route group with its import after the ones the scaffold lists before it, and deletes a forward `0.2.0` removed when it is the scaffold's own line (`NAME: app.env.NAME`, a comment ending the line going with it; one written another way stays, and it says so), keeping a BOM, CRLF line ends and comments. It mounts only on a top-level `defineApp()` variable, re-parses the result before writing it, and leaves alone, saying why: a file that does not parse, an app built in a function, an import it cannot match to a mount, a scaffold name mounted from another file, and an optional mount while its package is not installed. Check it again with `npx nuxt-backend doctor --only data`.

### `agent-files`

`AGENTS.md` holds the `nuxt-backend` section the app's installed version writes (or the version-free one the templates ship), with its markers paired, `.mcp.json` has the `nuxt-backend` server (the developer MCP server), and every skill copy in `.agents/skills/` (and every copy of its own in `.claude/skills/`) is one the installed version ships, as it ships it: line endings and dotfiles aside. A project with no `AGENTS.md`, or with none or only some of the skills, passes with a note.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `data` | Agent files | Warns, never fails | Still a warning | No |

**Why it matters:** The section points coding agents at the skills in `node_modules`, which match the installed version, and agents read the copies in `.agents/skills/` on their own; a stale copy, or one of a skill the version no longer ships, sends them to names another version had. **Fix:** Run `npx nuxt-backend init --agents`: it rewrites only the section, adds the developer MCP server, and replaces the stale skill copies or removes them. A skill the project's `skills-lock.json` lists belongs to the skills CLI, which `init` leaves it to: `npx skills add ./node_modules/nuxt-backend/skills --skill '*' -y` reinstalls the installed version's. When the markers don't pair up, keep one start and one end marker around the section, or delete every marker, first. Check it again with `npx nuxt-backend doctor --only data`.

### `name-collisions`

The app's own components (`app/components/`, named as Nuxt names them) and composables (the top level of `app/composables/` and `app/utils/`), against the names the installed package and the Convex module under it register. It always passes: the message names each shared name and the file it is in.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `data` | Name collisions | Warns, never fails | Still a warning | No |

**Why it matters:** A same-named component is how an app swaps a [part](/docs/reference/components/parts), so sharing a name is often meant. One shared by accident hides the package's from that app. **Fix:** Nothing, when you meant it. Otherwise rename yours. Check it again with `npx nuxt-backend doctor --only data`.

### `bundle-duplicates`

The last `npx nuxt-backend analyze` run, kept in `node_modules/.cache/nuxt-backend/analyze.json`: a package the Convex bundle holds more than once (the analyzer's `duplicate-package` insight) warns, and names each package with what removing the extra copies would save. A package that every component bundles again is not one, since Convex bundles each component on its own. `doctor` never runs the analyzer: there is no finding until a run exists, nor once a lockfile is newer than the run, since the install it measured has changed.

| Capability | Title | In dev | Under `--prod` | `--fix` |
|---|---|---|---|---|
| `data` | Duplicate packages in the Convex bundle | Warns, never fails | Still a warning | No |

**Why it matters:** Each copy is code the deployment pushes and loads: two versions of one package, installed under different dependencies, are bundled twice. **Fix:** Dedupe the install (`pnpm dedupe`), or align the version your code asks for with the one a dependency uses, then run `npx nuxt-backend analyze --only convex` again: it names each copy and what imports it ([See what is inside your bundles](/docs/develop/analyze)). Check it again with `npx nuxt-backend doctor --only data`.
