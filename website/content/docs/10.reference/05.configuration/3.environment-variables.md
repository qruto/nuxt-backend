This page lists every variable the package reads, once: where it is read, what it takes, and what degrades without it. `0.2.0` reads eighteen, named after what they do and grouped by purpose. One of them, `BACKEND_ENVIRONMENT`, says what kind of deployment the backend runs on, and every mode follows from it. [Environments and deployments](/docs/start/concepts/environments) explains the split between the app's env and the deployment's.

## Every variable

Write each value you set in `.env.local`, once. The Nuxt app reads the ones marked **Nuxt app**, and [`npx nuxt-backend env push`](/docs/reference/cli#env-push) forwards the rest to the deployment. **Set by** says who writes each one, and **Without it** what stops working:

| Variable | Group | Read on | Set by | Takes | Without it |
|---|---|---|---|---|---|
| `NUXT_PUBLIC_BACKEND_URL` | Backend | Nuxt app | Derived. You, to point at another deployment | The deployment's URL, such as `https://happy-otter-123.convex.cloud` | Derived from the deployment the platform CLI names in `.env.local`. Set it to point the app at another deployment |
| `SITE_URL` | Backend | Deployment | `dev` in development, you elsewhere. Required. `env push` takes the origin of `NUXT_SITE_URL` when `SITE_URL` is not set | The app's http(s) origin, without a path, such as `https://app.example.com` | A deploy fails: auth trusts it as the app's origin, and every emailed link names it |
| `AUTH_SECRET` | Backend | Deployment | `dev` in development, you elsewhere. Required | A random secret of at least 32 characters (`openssl rand -base64 32` prints one) | A deploy fails: it signs sessions. [`env rotate`](/docs/reference/cli#env-rotate) replaces it with no downtime: the new value beside the old, as `<version>:<new>,<version>:<old>`, until the old retires |
| `BACKEND_ENVIRONMENT` | Backend | Deployment | `env push`, from the deployment. You, for `sandbox` | `development`, `preview`, `sandbox` or `production` | Every provider stays in its test mode, and `doctor --prod` fails on production |
| `EMAIL_API_KEY` | Email | Deployment | You. Needed to send outside `development` | Resend's API key | Sends no-op. On `development` the sign-in codes print in the dev console, and elsewhere a code to a real address is refused |
| `EMAIL_FROM` | Email | Deployment | You | An address on a verified sending domain, alone or as `Name <address>`: the sender of transactional mail | Resend's onboarding sender is used |
| `EMAIL_MARKETING_FROM` | Email | Deployment | You (ENGAGE) | The sender of marketing and lifecycle mail, on a subdomain apart from `EMAIL_FROM`'s | Marketing and lifecycle mail goes from `EMAIL_FROM` |
| `EMAIL_REGION` | Email | Deployment | You | The region Resend sends from: `us-east-1`, `eu-west-1`, `sa-east-1` or `ap-northeast-1`. Account data stays in the US | Resend's default region |
| `EMAIL_WEBHOOK_SECRET` | Email | Deployment | You, from Resend's webhook settings | The signing secret of Resend's webhook endpoint, which verifies `/email/events` | Delivery and inbound events are refused, so `useEmailStatus` stays at `sent` |
| `BILLING_ACCESS_TOKEN` | Billing | Deployment | You. Needed to sell | A Polar organization access token: a sandbox token outside `production`, a live one on it | Billing reads return empty, and checkout fails when called |
| `BILLING_WEBHOOK_SECRET` | Billing | Deployment | `billing sync` | The signing secret of Polar's webhook endpoint, which verifies `/billing/events`. `billing sync` stores it | Billing events are refused, so entitlements refresh only on demand |
| `AI_GATEWAY_API_KEY` | AI | Deployment | You, where the Convex AI Gateway is unavailable | A Vercel AI Gateway key: the route a `provider/model` id takes where the Convex AI Gateway does not answer it | Model ids go through the Convex AI Gateway alone, on a paid Convex plan. On a free plan or a self-hosted deployment a model call is refused |
| `PROTECTION_PROOF_SECRET` | Protection | Deployment and the app's server | You | A random secret of at least 32 characters, the same value on both. A comma-separated `new,old` on the deployment passes proofs signed with either while you rotate it | The routes that send a code take no proof of a bot check. On Vercel, BotID still refuses the bots that come through the app |
| `PROTECTION_CHALLENGE_SECRET_KEY` | Protection | Deployment | You | Cloudflare Turnstile's secret key. Its documented test keys pass or refuse everyone | The deployment verifies no challenge answer, so off Vercel nothing checks for bots |
| `NUXT_PUBLIC_BACKEND_CHALLENGE_SITE_KEY` | Protection | Nuxt app | You | Turnstile's site key, which is public | No challenge renders, so a deployment with the secret key refuses every code request |
| `PUSH_PUBLIC_KEY` | Notifications | Deployment | `env push`, which generates the pair | The public half of the web push key pair, which [`env push`](/docs/reference/cli#env-push) generates: production's never copied from `.env.local` | The in-app inbox works, but web push does not |
| `PUSH_PRIVATE_KEY` | Notifications | Deployment | `env push`, which generates the pair | The private half of the same pair, never derived from another secret | The in-app inbox works, but web push does not |
| `MONITORING_DSN` | Monitoring | Deployment | You, or Sentry's Vercel integration | A Sentry DSN. The Nuxt app reads it too. Sentry's Vercel integration sets the DSN as `NEXT_PUBLIC_SENTRY_DSN`: the app reports to it when `MONITORING_DSN` is unset, and `env push` forwards it to the deployment as `MONITORING_DSN`, so the integration alone is enough | The backend reports nothing. In development a local error log in DevTools stands in |

The platform's own names, `CONVEX_DEPLOYMENT`, `CONVEX_SITE_URL` and `CONVEX_SELF_HOSTED_URL`, are not here: the Convex CLI and runtime own them. The package reads them and never asks you to write one. For an account-free local deployment, `npx nuxt-backend dev --anonymous` gives the Convex CLI what it reads (`CONVEX_AGENT_MODE=anonymous`) itself, on every OS.

### `BACKEND_ENVIRONMENT`

`BACKEND_ENVIRONMENT` decides four modes at once, so you never set one by hand:

| `BACKEND_ENVIRONMENT` | Email | Billing | Local origins trusted | Sign-in codes logged |
|---|---|---|---|---|
| `development` | Test mode | Polar's sandbox | Yes | Yes |
| `preview` | Test mode | Polar's sandbox | No | No |
| `sandbox` | Test mode | Polar's sandbox | No | No |
| `production` | Live | Live | No | No |

`env push` derives it from `CONVEX_DEPLOYMENT`: a dev deployment is `development`, a preview is `preview`, and production is `production`. You set `sandbox` on purpose, for a deployed demo or staging app that runs in production mode on the providers' test modes. It also names the monitoring environment, so Sentry keeps a demo's errors apart from production's.

### Removed variables

`0.2.0` removes eight variables. `env push` never forwards one, and `doctor` names any still set on a deployment:

| Variable | Replaced by |
|---|---|
| `EMAIL_TEST_MODE` | `BACKEND_ENVIRONMENT`: test mode everywhere but `production` |
| `BILLING_ENVIRONMENT` | `BACKEND_ENVIRONMENT`: Polar's sandbox everywhere but `production` |
| `MONITORING_ENVIRONMENT` | `BACKEND_ENVIRONMENT`, which names the monitoring environment |
| `AUTH_TRUST_LOCAL_ORIGINS` | `BACKEND_ENVIRONMENT=development`, which trusts the local origins |
| `NUXT_BACKEND_LOG_OTP` | `BACKEND_ENVIRONMENT=development`, which logs the sign-in codes |
| `NUXT_PUBLIC_BACKEND_SITE_URL` | Derived from `NUXT_PUBLIC_BACKEND_URL`. A custom domain sets `NUXT_PUBLIC_CONVEX_SITE_URL`, the base module's own variable |
| `BILLING_SIMULATOR_URL` | Nothing: development bills in Polar's sandbox |
| `NUXT_BACKEND_SIMULATE_MODELS` | Nothing: development calls the same models through the Convex AI Gateway or `AI_GATEWAY_API_KEY` |

## App variables

`npx nuxt-backend init` writes `.env.example`, grouped by purpose with the platform's names last. Nothing in it is required in development:

<!-- generated:env-example (pnpm docs:lookups, from src/capabilities/env-example.ts) -->

```dotenv [.env.example]
# Nothing here is required in development: the backend URL derives from the
# deployment the Convex CLI writes, and AUTH_SECRET, SITE_URL and
# BACKEND_ENVIRONMENT are provisioned on the first run. Add keys as you
# connect services, then run `npx nuxt-backend env push`.

# ── Backend ──
# NUXT_PUBLIC_BACKEND_URL=

# ── Email ──
# EMAIL_API_KEY=
# EMAIL_FROM=
# EMAIL_MARKETING_FROM=
# EMAIL_REGION=
# EMAIL_WEBHOOK_SECRET=

# ── Billing ──
# BILLING_ACCESS_TOKEN=
# BILLING_WEBHOOK_SECRET=

# ── AI ──
# AI_GATEWAY_API_KEY=

# ── Protection ──
# PROTECTION_PROOF_SECRET=
# PROTECTION_CHALLENGE_SECRET_KEY=
# NUXT_PUBLIC_BACKEND_CHALLENGE_SITE_KEY=

# ── Monitoring ──
# MONITORING_DSN=

# ── Dev only ──
# `nuxt-backend dev` sets these on a dev deployment, and `env push` never
# carries them to a preview or production.
# EMAIL_DEV_INBOX=1

# ── Platform ──
# The Convex CLI appends CONVEX_DEPLOYMENT here. Read it; never rename it.
```

<!-- /generated:env-example -->
The push key pair is not in it: `env push` generates the pair on the deployment the first time it runs. `npx convex dev` then appends the deployment it set up:

```dotenv [.env.local]
# Deployment used by `npx convex dev`
CONVEX_DEPLOYMENT=dev:your-deployment # team: your-team, project: your-project
```

The Nuxt process reads `NUXT_PUBLIC_BACKEND_URL` and `NUXT_PUBLIC_BACKEND_CHALLENGE_SITE_KEY`, and `PROTECTION_PROOF_SECRET` on its server. Its error reports read the DSN (`MONITORING_DSN`, else Sentry's `NEXT_PUBLIC_SENTRY_DSN`), and name their environment `BACKEND_ENVIRONMENT` when the app's host sets it too (a `sandbox` demo does), else Vercel's own. The rest are staged here for `env push` to forward. Of `CONVEX_DEPLOYMENT` the module reads only the slug, to derive the deployment's URLs.

::note
The platform's own names still work. The base module reads `NUXT_PUBLIC_CONVEX_URL` and `NUXT_PUBLIC_CONVEX_SITE_URL` directly, and an explicit one wins over the derived default: `NUXT_PUBLIC_BACKEND_URL` is this package's own name for the first, and the `.convex.site` origin the app's server talks to derives from it, at runtime too. Set `NUXT_PUBLIC_CONVEX_SITE_URL` only for a custom domain in front of the HTTP routes, a self-hosted backend, or a build that does not know the backend's URL: the `/api/auth` proxy reads the origin the build baked in, so a host that sets `NUXT_PUBLIC_BACKEND_URL` for the runtime alone sets `NUXT_PUBLIC_CONVEX_SITE_URL` there too ([`site-auth-proxy`](/docs/reference/cli/diagnostics#site-auth-proxy)).
::

## Convex deployment variables

The scaffolded `convex.config.ts` declares the deployment's variables with Convex's typed [`defineApp({ env })`](https://docs.convex.dev/production/environment-variables), through `backendEnv` from `nuxt-backend/app`. A deploy validates them, and your functions read them type-safely through `env` from `_generated/server`. `AUTH_SECRET` and `SITE_URL` are required: a push fails until both are set. Every other one is optional: the deploy succeeds, and the feature degrades in the way the table above describes until you set it. `npx nuxt-backend doctor` reports each one.

### Setting them

On a dev deployment, `npx nuxt-backend dev` (or `env push`) provisions the required values and `BACKEND_ENVIRONMENT`, and forwards whatever `.env.local` holds. To set one by hand, pipe the secret in so it never lands in your shell history:

```bash
# Production: every command takes --prod
openssl rand -base64 32 | npx convex env set --prod AUTH_SECRET
npx convex env set --prod SITE_URL https://app.example.com
npx convex env set --prod BACKEND_ENVIRONMENT production
npx convex env set --prod EMAIL_API_KEY           # asks for the key
npx convex env set --prod BILLING_ACCESS_TOKEN    # asks for the token
```

[`npx nuxt-backend env push --prod`](/docs/reference/cli#env-push) does the same from `.env.local`, and refuses a deploy key for another deployment.

::note
The `EMAIL_*` variables reach the `backend` component by reference, since [components can't read the app's env directly](https://docs.convex.dev/components). The scaffolded `convex.config.ts` handles it ([How it works](/docs/start/concepts/how-it-works)).
::
