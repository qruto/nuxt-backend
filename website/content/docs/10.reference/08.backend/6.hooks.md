A hook is a function your `backend/` files pass to a setup helper, which the package calls at a point of its own. This page lists every hook with where it runs, how often, in which order, what a throw does and the idempotency it needs, so you can write one the package calls safely. Each one runs with a Convex ctx, so it can read your tables and schedule work. The list is generated from the helpers' option types, and a hook added to an option type cannot ship without its promises.

Two rules hold for every hook. A webhook handler can run twice for one event, so key what it writes on the event's id. A gate (`canSignIn`, `canGift`, `resolveEntity`, `requireAdmin`) is a read: it can run more than once for one request.

When an account is created, `canSignIn` runs after the launch rules of `setupAccess` (passed to `setupAuth` as `access`), as a veto of your own. On a code request it runs first, with `ticket: null`, and the launch phase's ticket check follows once the code checks. `setupAccount`'s sources erase their rows when an account's grace period ends, unless the account has become the only owner of a workspace others belong to: its deletion then moves a day on, until ownership moves or the others leave. An administrator's removal and `account.forget` start the erasure at once: a source that keeps failing is retried, then logged as `account.erasure_failed` and recorded for administrators, so an erasure is done only once every source finished.

### `setupAuth({ onUserCreated })`

Fired after an account is created, after its welcome email.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In the auth request that created the account (a mutation or action ctx), after its welcome email | Once, or twice when it throws: Better Auth runs a failed after-hook a second time | After the account is created | Run again once; a second throw fails the sign-up request, and the account stays created | Key what it starts on `user.id`, since it can run twice |

### `setupAuth({ canSignIn })`

Gate sign-in / sign-up (invite-only, allow-list, closed beta).

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In the auth request (a mutation or action ctx), before the write it guards | Every time the gate is asked: a code request, an account creation, each new session, and twice for an email change | Before any write, so a refusal leaves nothing behind | The error propagates as thrown and fails the request; return `{ allowed: false }` to refuse with `forbidden`, reason `sign_in_refused` | A read only: it runs several times for one sign-in |

### `setupAuth({ onUserDeleted })`

Fired after an account is deleted, after any consumer `afterDelete`.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In the deletion request (a mutation or action ctx), after the app's own `user.deleteUser.afterDelete` | Once per deletion | After the account is deleted | The deletion request fails; the account is already deleted | Make the erasure safe to run again, by `user.id` |

### `setupBilling({ resolveEntity })`

Resolve the billing entity yourself, in place of the identity claims `billTo` reads.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In every billing function's ctx: a query, a mutation or an action | On every billing call, the reads included | Before the call reads or writes anything | A refusal it throws answers the reads with `null` and refuses the rest | A read only; return `null` when there is no identity |

### `setupBilling({ requireAdmin })`

Gate the admin-tier billing functions (`refundOrder` — moving real money — and the webhook delivery log).

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In the admin-tier function's ctx (`refundOrder`, the webhook log) | On every admin-tier call | After the impersonation refusal, before the call | The call is refused | A read only |

### `setupBilling({ events })`

React to billing webhook events, keyed by the provider's own event names (`'order.paid'`, `'subscription.active'`, …).

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In the webhook's HTTP action, after the built-in entitlement refresh and gift fulfilment | At least once: a delivery already processed answers 200 without running it again, but one that threw is redelivered | As the provider delivers: no order across events | Logged as `handler_error`, answered 500, and the provider retries | Key what it writes on the event's id |

### `setupBilling({ canGift })`

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In `giftCheckout`'s action ctx, after the package's own gift rules | Once per gift checkout | Before the purchaser's checkout opens | The error fails the gift checkout; return a refusal instead, whose message reaches the purchaser as `forbidden`, reason `gift_refused` | A read only |

### `setupBilling({ checkoutDiscount })`

### `setupAudit({ onEvent })`

Hear of every event once it is recorded, the package's own and yours: an internal action of yours, by its reference, taking `{ event: vBackendEvent }`.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In an action of its own, scheduled by the transaction that recorded the event, once it commits | Once per event, fire and forget: nothing retries a run that fails, and the event stays recorded | Scheduled in the order events are recorded; runs may overlap, so order across events is not kept | The failure is the action's own, in the deployment's logs; the event and what recorded it stand | Key what it writes on `event.id` |

### `access.memberTickets({ enabled })`

Whether the program runs now, for a switch of the app's own (a flag, say): `false` answers `off`, issues nothing, and the links already shared admit nobody (`revoked`) until it is on again.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In the query or mutation that reads or mints a member's ticket, and in each code check and sign-up that brings a code or link (nobody signed in), in its transaction | Once per read, per mint and per code checked; a live read runs it again whenever what it read changes | A read or a mint asks it after the phase (a public app answers `open` without asking), before the member's ticket; a code check or a sign-up, before the code's row is read | The read, the mint, the check or the sign-up fails with its error, and nothing is minted or taken | A read: it may run many times for one member or code, and writes nothing |

### `storage.shareable({ canShare })`

Whether the signed-in caller may turn the row's link on or rotate it.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In `enableShareLink`'s and `revokeShareLink`'s mutations and in `getShareLink`'s query, in their transaction, with the signed-in caller as `ctx.user` | Once per `enableShareLink`; in `revokeShareLink` and `getShareLink` only when the row has a live link and the caller is not the one who shared it. A live `getShareLink` runs it again whenever what it read changes | `enableShareLink` asks it after the caller is checked (signed in, account present, not banned) and the row is found (a missing row fails `invalid_input` first), before the link is written; `revokeShareLink` after the same caller check and the link read; `getShareLink` after the link read, with only the signed-in identity checked | `enableShareLink` and `revokeShareLink` fail with its error and change nothing; `getShareLink` reads a throw, a missing row included, as `false` and answers `null` | A check: it may run many times for one row and caller, and writes nothing |

### `storage.shareable({ ogImage })`

The storage id of the image the preview card shows, or `null` for none.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In `resolveShareLink`, inside the query or mutation of yours that calls it, once the token matched a live link and its row was found; never from an action | Once per resolve; a live query that resolves the link runs it again whenever what it read changes | After the link and its row are read, before the image's expiring URL is signed | `resolveShareLink` throws, and with it the function of yours that called it | Synchronous and given only the row: it may run many times for one row, and should read nothing else |

### `storage.shareable({ onEnable })`

Runs in `enableShareLink`'s mutation once the link is on, a new one replacing an earlier one included: record an event, tick off a checklist step, stamp the row.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In `enableShareLink`'s mutation, in its transaction, with the caller who turned the link on as `ctx.user` | Once per `enableShareLink` that succeeds; each rotation is a call of its own, with `link.rotated` set | After `canShare` agreed and the new link replaced any earlier one, before the mutation returns the link | The mutation fails with its error and rolls back with it: no new link, and an earlier one stays live | Its writes commit with the link or not at all; a conflict reruns the whole mutation, never this hook alone |

### `storage.acceptUpload({ check })`

Your check that the upload may go where it is headed, before the content check reads it: the caller's row, room on it, not a file kept already.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In the action that calls `acceptUpload`, through the `ctx` your callback closed over (an internal query of yours, a rate limit) | Once per `acceptUpload`; a person's retry calls `acceptUpload` again, and with it this | First, before the content check and `keep` | `acceptUpload` throws its error, and neither the content check nor `keep` runs; an `invalid_input` or `quota_exceeded` refusal discards the upload, any other error keeps it for a retry | A check: it may run again for the same upload, so it should write nothing a second run would trip over |

### `storage.acceptUpload({ keep })`

Keep the upload: your internal mutation that claims it with `storage.claim` and writes your row, in one transaction.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| In the action that calls `acceptUpload`, through the `ctx` your callback closed over (`ctx.runMutation` of your mutation) | Once per `acceptUpload` whose check and content check passed | Last, after `check` and the content check passed | `acceptUpload` throws its error; your mutation rolled back, the claim with it, so an `invalid_input` or `quota_exceeded` refusal (the claim's own, the type or the size, the quota) discards the upload, and any other error keeps it for a retry | Your mutation's transaction: its claim and your row commit together or not at all, and a second keep of a claimed upload is refused `upload_claimed` |

### `defineJobQueue({ onJobEnd })`

Hear of every job's end: done, failed, stalled, or canceled while it waited or ran, with its id, kind, args, error, run (`retries`) and `endedAt`.

| Runs | Delivery | Order | When it throws | Idempotency |
|---|---|---|---|---|
| As its own function, scheduled by the transaction that ended the job, once it commits | Once per run of a job, whichever way it ended, except a job erased with its owner's account, which ends unheard; a mutation runs exactly once, an action at most once | After the job's row reads its end; a retried job's runs are heard in turn, `retries` counting up; ends of different jobs run in no set order | The failure is the hook's own, in the deployment's logs; the job's end and the queue's handling of its credits stand | An administrator's retry runs a failed job again, and it ends again: compare `retries` with the run you last recorded, and let a later run's end win |
