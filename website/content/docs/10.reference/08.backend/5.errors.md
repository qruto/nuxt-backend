This page lists every code the package refuses with, the fields it carries, its English label, the status an auth route answers with, and what to do about it. Branch on a code in your UI, and look up a reason here when a refusal surprises you.

## What changes

The codes stay the same in `0.2.0`. The reasons change where the features do:

- **A new address without a ticket gets `ticket_required`:** while the app is in early access or invite only, the code check refuses it as `forbidden`, reason `ticket_required`, with `phase` and, when an invite code came along that admits nobody, `invite`. In early access the check also records the address on the [waitlist](/docs/build/growth/launch/waitlist), and the refusal carries its `waitlist` place (`position`, `total` and the status link's `token`). The code is not used up, and `useLoginFlow` moves to its `waitlisted` or `invite-code` step. `sign_in_refused` stays your own `canSignIn`'s.
- **Test mode follows `BACKEND_ENVIRONMENT`:** `email` `test_mode` applies on every deployment but `production`.
- **No stand-in model (NOSIM):** `ai` `not_configured` means the deployment has no route to a model, the Convex AI Gateway or `AI_GATEWAY_API_KEY`.
- **Content safety adds reasons:** `invalid_input` with `content_blocked` on `prompt` or `images` when the safety classifier flags content ([Keep content safe](/docs/build/ai/content-safety)), `removed_copy` on `file` for the bytes of a removed intimate image, and the notice form's and the appeal's fields ([Moderate user content](/docs/ship/compliance/moderation)).

## How a refusal reaches you

A refusal from a package function is a `ConvexError` whose data is `{ code, ...fields }`. Convex sends that data to the client in production too, where any other error arrives as "Server Error". An auth route refuses with the same code and fields in its error body, at the status below. [`getBackendError(error)`](/docs/build/data/read-write/errors) reads both and returns `{ code, data, message }`. `BACKEND_ERRORS` in `nuxt-backend/functions` holds the catalog, and `pnpm docs:lookups` writes this page's codes from it. `/e/<code>` links to the code's entry below.

`message` is the sentence to show: the throw site's own sentence for the person when it wrote one (`data.message`), else the code's label from the `errors` group. Some reasons have a label of their own (`errors.<code>_<reason>`), and a label with numbers in it is used only when the numbers are there. The English the deployment log shows is the error's `message` property, which production never sends to the client.

The package's own auth refusals write no `data.message`, so a person always reads them in their language. An auth route's error body still carries a `message`, for a client that reads the body raw: the code's English label, which `getBackendError` recognizes as the label and leaves out of `data`. Only a sentence an app wrote, such as its `canSignIn` refusal, travels as written. A few billing refusals still write an English sentence of their own in `data.message`, shown as written in every language: `customer_taken`, `already_subscribed`, `not_billing_manager`, `provider_owner_only` and `gift_refused` (where a `canGift` message of yours goes too).

Every field in `data` is optional on the read side, the required ones too: the reader keeps only the fields that fit the catalog, so check the one you use before you rely on it.

## Codes

Each entry is generated from the catalog: its data fields and status from `BACKEND_ERRORS`, its label from the `errors` group of the [labels](/docs/reference/configuration/labels#errors).

### `unauthenticated`

| Data | Label | Status | Handling |
|---|---|---|---|
| `message?` | Sign in to continue. | 401 | Show the message. If nobody is signed in, send the person to sign in, then retry. |

Better Auth answers some of its own refusals with 401 too, and the reader maps them here with Better Auth's message: a wrong password on a sign-in form, for one, where the person is already on the sign-in page and only needs the message.

### `forbidden`

| Data | Label | Status | Handling |
|---|---|---|---|
| `reason`, `message?`, `phase?`, `invite?`, `kind?`, `waitlist?` | You don't have access to this. | 403 | Show the message; `reason` says what would change the answer. |

### `reauthentication_required`

| Data | Label | Status | Handling |
|---|---|---|---|
| `message?` | Confirm it's you to continue: this needs a recent sign-in. | 403 | Ask the person to sign in again, then retry: `useReauthentication().withReauthentication(action)` does both. |

A sensitive action, refused because the session's sign-in is older than it takes (ten minutes for the package's own): an auth route of the [sensitive-action table](/docs/build/auth/access/step-up#which-actions-ask), an admin write, or a function of yours with `recentSignIn` or `requireRecentSignIn`. Signing in again opens a new session; an agent's token and an administrator's visit never pass, and are refused as `forbidden` instead.

### `no_workspace`

| Data | Label | Status | Handling |
|---|---|---|---|
| `message?` | Create or choose a workspace first. | 409 | Offer the workspace switcher, or create one. |

### `rate_limited`

| Data | Label | Status | Handling |
|---|---|---|---|
| `retryAfter?` (ms), `limit?`, `plans?`, `message?` | Too many requests. Try again in a moment. | 429 | Wait `retryAfter`, then retry. `limit` names the spent limit. |

### `insufficient_credits`

| Data | Label | Status | Handling |
|---|---|---|---|
| `meter?`, `balance`, `need`, `message?` | Not enough credits. Top up to continue. | 402 | Offer a credit pack or a plan with more credits. |

With both amounts, the label reads "Not enough credits: {balance} left, {need} needed. Top up to continue." (`errors.insufficient_credits_amounts`).

### `feature_required`

| Data | Label | Status | Handling |
|---|---|---|---|
| `feature`, `plans`, `message?` | Your plan doesn't include this. Upgrade to use it. | 402 | Offer the plans in `plans`: `<UpgradePrompt :plans>` links to the first on the pricing page. |

Thrown by `billing.requireFeature` and the `withFeature` tier of `createFunctions` when the billing entity's plan does not grant the feature, read from the entitlement cache. `feature` is the catalog key asked for; `plans` the catalog keys of the plans on sale that include it, in pricing order, empty when none does. A caller who may not read the entity's billing at all is refused for that first. See [Feature gating](/docs/build/billing/subscriptions/feature-gating#the-refusal).

### `quota_exceeded`

| Data | Label | Status | Handling |
|---|---|---|---|
| `quota`, `limit`, `used`, `amount`, `plans`, `message?` | Your plan's limit is reached. Upgrade for more. | 402 | Say how many are used of how many, and offer the plans in `plans`, or ask the person to remove one first. |

Experimental. Thrown by `billing.requireQuota`, and by `storage.store` and `storage.claim` for `setupStorage`'s `quota` (`quota` is the catalog key, or `files` or `bytes` for a number), when `amount` more of the `quota` do not fit what the billing entity's plan allows: `limit` is the most any grant allows (`0` when none names the quota), `used` how many are counted, and `plans` the catalog keys of the plans on sale that allow `used + amount`, in pricing order, empty when none does. Nothing is counted for a refused call. See [Limit resources per plan](/docs/build/billing/subscriptions/quotas#the-refusal).

### `invalid_input`

| Data | Label | Status | Handling |
|---|---|---|---|
| `field`, `reason?`, `need?`, `units?`, `message?` | That input isn't valid. Check it and try again. | 400 | Mark `field` and show the message. |

A checkout, a gift checkout, a plan change and the portal refuse what only the server may choose with this code: `productIds`, `productId` or `pack` outside the catalog (a plan change to a credit pack too), an `origin`, `successUrl` or `returnUrl` off the site, reserved `metadata` keys, a client's `trialInterval`, `trialIntervalCount` or `discountId`, a `trial` from server code that is not 1 to 30 days in days or weeks, a `discountCode` the provider does not accept, and a `discount` that names no catalog promotion a client may name (one with a code), applies to none of the checkout's products or is no longer redeemed (`field: 'discount'`; `billing.applyDiscount` refuses the same way, and a checkout naming two discounts too). See [What the server decides](/docs/build/billing/subscriptions/checkout#what-the-server-decides). `billing.requireFeature` refuses an empty feature with it (`field: 'feature'`), and `billing.requireQuota` and `releaseQuota` an empty quota (`field: 'quota'`) or an `amount` that is not a whole number above zero (`field: 'amount'`).

### `not_ready`

| Data | Label | Status | Handling |
|---|---|---|---|
| `reason`, `message?` | Nothing to show yet. | 409 | Don't offer a retry: something has to happen first. `reason` says what (below). |

### `unavailable`

| Data | Label | Status | Handling |
|---|---|---|---|
| `service`, `reason`, `message?` | This isn't available right now. Try again shortly. | 503 | Retry later only for `provider_refused`; the other reasons need the deployment fixed, and `reason` tells an operator what. |

## Reasons

The `forbidden` reasons the package throws:

| Reason | When |
|---|---|
| `banned` | The account is banned: a call it makes, or its sign-in (Better Auth's `BANNED_USER`). |
| `role` · `permission` | The account's role lacks the role or the permission statement the call requires. |
| `not_member` · `workspace_role` | The caller is not a member of the workspace, or lacks the workspace role: read fresh from the member table, so someone removed is refused on their next call, a billing call or a spend included. |
| `admin_only` | A billing admin function (`refundOrder`, the webhook log) and the account is no admin, its role read fresh. |
| `not_owner` | The order or subscription belongs to another account, or the order does not exist: the two answer alike. |
| `impersonating` | An administrator acting as this account tried something only its owner may do: spending its credits, changing its billing, signing its devices out, an admin function's write, or anything that takes a recent sign-in, which only the owner's own sign-in gives. |
| `admin_target` | A caller who may impersonate tried to impersonate an administrator's account, their own included: an administrator's account is never visited, whoever asks and whatever the app's roles grant ([Impersonation](/docs/build/auth/admin/impersonation)). Better Auth's own refusal of one reads the same. |
| `passkey_only_admin` | On a `sandbox` deployment, an administrator whose account is not passkey-only, or whose session no passkey signed in to, called an admin gate: the `admin` tier, the admin console, billing's admin functions, `listAllActivity` or one of Better Auth's `/admin/*` routes. The console's reads answer `null`, the rest refuse. A public demo's dev inbox shows sign-in codes, so its administrators sign in with a passkey, on a passkey-only account ([What a demo refuses](/docs/ship/deploy/staging#what-a-demo-refuses)). Label: "On this demo, administrators sign in with a passkey, on an account that signs in with passkeys only. Turn on passkey-only sign-in in your security settings, then sign in again with your passkey." |
| `other_account` | A [re-authentication](/docs/build/auth/access/step-up) signed in as another account (another account's passkey, or a code to another address), or one the server could not tie to the session it confirms: the browser keeps the session it was confirming. Label: "That sign-in belongs to another account. Confirm with this account's passkey or code." |
| `sign_in_refused` | `canSignIn` said no: its message is the one shown, and without one the label "Sign-in is by invitation right now." |
| `ticket_required` | A new address checked its sign-in code while the app is in early access or invite only, with no ticket ([Launch in phases](/docs/build/growth/launch)): `phase` names the phase, and `invite` how an invite code that came along checked (`expired`, `used-up`, `revoked`, `unknown`). The code is not used up; `useLoginFlow` moves to its `waitlisted` or `invite-code` step rather than showing an error. Label: "Signing up needs an invite right now." |
| `consent_required` | A function asked [`account.requireConsent`](/docs/build/auth/accounts/consents#check-one-in-a-function) about an account that has not accepted a required consent at its latest version: `kind` names it. `<ConsentPrompt>` asks for it. Label: "Accept the updated terms to continue." |
| `age_required` | A new address checked its sign-in code while the app sets a [minimum age](/docs/build/auth/accounts/consents#set-a-minimum-age), and sent no age. The code is not used up; `useLoginFlow` moves to its `age` step rather than showing an error. Label: "Tell us how old you are to continue." |
| `under_age` | The age typed at sign-up is under `minimumAge`, or this browser answered under it in the last day. No account is created. Label: "We can't create an account for you." |
| `waitlist_closed` | A join while the app is not in early access ([Run a waitlist](/docs/build/growth/launch/waitlist)): `phase` names the phase it is in. Entries already on the list keep their place. |
| `invitation_refused` | `workspaces.canInvite` said no to a workspace invitation: its message is the one shown, and without one the label "This invitation can't be sent." |
| `customer_taken` | With `billTo: 'user'`, the account's email already pays for another account (the provider keeps an individual customer's email unique); or the entity is mapped onto a customer from before 0.2 that another entity is keyed to. |
| `already_subscribed` | A checkout for a plan while the billing entity holds a subscription: switch plans with `changePlan` (`updateSubscription`), or turn on `multipleSubscriptions`. Also a plan pass claimed into a workspace on a paid plan or on a pass already ([Gift a plan as a pass](/docs/build/growth/offers/plan-passes#what-the-claim-does)). |
| `not_billing_manager` | A checkout, the portal, a plan change, orders or an invoice of a workspace, by a member who is neither its owner nor an admin. See [Decide who manages billing](/docs/build/billing/setup#who-may-buy-for-a-workspace). |
| `provider_owner_only` | The billing portal of a workspace, opened by one of its admins: the server lets them in, but the billing provider lists only the owner as a member who manages the customer for now. |
| `gift_refused` · `not_recipient` · `no_email` | A gift was refused (to the purchaser's own address, before their first paid order, or by `canGift`, whose message is the one shown), the gift is addressed to another email or does not exist, or the session has no verified email. |
| `gift_refunded` | The gift's purchase was refunded before its claim, so there is nothing to receive. |
| `gift_claimed` · `gift_delivered` | A change to a gift its recipient has claimed or started to claim (a notice again, a new address, a cancel), or a new date for a gift already delivered ([Send, receive and manage gifts](/docs/build/growth/offers/gifts#manage-gifts)). |
| `sole_owner` | Deleting an account (`/delete-user`, or an administrator's `/admin/remove-user`) that is the only owner of a workspace others belong to: another member becomes an owner first, or the others leave ([Export and erase account data](/docs/build/auth/accounts/data)). Label: "You're the only owner of a workspace others belong to. Make another member an owner first." |
| `flag_off` | `flags.requireFlag(ctx, key)` and the flag is off for the caller: its default, an administrator's override, its targets and its rollout all said no ([Roll out features and pause services](/docs/ship/operate/flags)). Label: "This isn't available to you yet." |
| `passkey_required` | A session opened with a passkey-only account's recovery code, on any route but saving a passkey, reading the session and signing out: the person saves a new passkey before anything else, and no Convex function runs as the account until then ([Passkey-only accounts](/docs/build/auth/sign-in#passkey-only-accounts)). Label: "Save a new passkey to finish signing in." |
| `not_allowed` | `cancelJob` by someone who neither started the job, nor owns or administers its workspace, nor administers the app. |
| `cannot_share` | `enableShareLink` for a row the table's `canShare` refuses the caller, or `revokeShareLink` by someone it refuses who did not turn the link on ([Share by link](/docs/build/data/files/share-links)). Label: "You can't share this." |
| `bot_check` | The request or call passed no bot check: a sign-in code request, sign-up or password sign-in that BotID calls a bot, or that reached the deployment without a proof that passes (for its route, its address and that deployment) or a challenge answer the provider accepts, and a `verifyHuman` call without a token that passes (Better Auth's captcha `VERIFICATION_FAILED` reads the same). Label: "We couldn't confirm you're a person. Try again." See [Turn on bot protection](/docs/build/auth/sign-in/bots). |

Better Auth's own refusals of a sign-in too old for the route, `SESSION_NOT_FRESH` (registering a passkey, its session list) and `SESSION_EXPIRED` (deleting an account), read as `reauthentication_required`, like the package's own.

A `forbidden` the reader maps from Better Auth's own 403 carries Better Auth's error code, lower-cased, as its `reason` (`you_are_not_allowed_to_ban_users`, say), except `BANNED_USER`, which reads as `banned`, and the captcha plugin's `VERIFICATION_FAILED`, which reads as `bot_check`. Those reasons pass through as Better Auth names them: they are not in the table above and not covered by the stability promise. One has a label of its own: `too_many_attempts` (`TOO_MANY_ATTEMPTS`, too many wrong sign-in codes) reads "Too many wrong codes. Ask for a new one."

Better Auth's own refusals never carry its English sentence: a composable keeps the auth client's error as the failure's `cause`, and the person reads the label, in their language. Its 401 reads as `unauthenticated`. Its 400s for one input read as `invalid_input` on that field, with a reason where the field alone says too little:

| Better Auth code | `field` | `reason` | Label |
|---|---|---|---|
| `INVALID_OTP` | `otp` | | That code isn't right. Check it, or ask for a new one. |
| `OTP_EXPIRED` | `otp` | `otp_expired` | That code has expired. Ask for a new one. |
| `INVALID_EMAIL` | `email` | | Enter a valid email address. |
| `ORGANIZATION_ALREADY_EXISTS` · `ORGANIZATION_SLUG_ALREADY_TAKEN` | `slug` | | That name is taken. Try another one. |
| `AUTH_CANCELLED` · `ERROR_CEREMONY_ABORTED` | `passkey` | `passkey_cancelled` | The passkey prompt was closed. Try again, or continue with an email code. |
| Any other passkey code (`PASSKEY_NOT_FOUND`, a WebAuthn `ERROR_*`) | `passkey` | | That passkey didn't work. Try again, or continue with an email code. |

A label for one field or reason is `errors.invalid_input_<field>` or `errors.invalid_input_<reason>`, used over the code's own.
