`nuxt-backend` is built from community packages, and it works with more of them than it installs. This page says where each one stands, so you know what you get, what you install yourself and what you import directly. The package's CI reads the tables below: a component that ships without its row, or a row that claims a package the manifest does not have, fails the build. So the **Status** column is the manifest as it stands, and the **Notes** column says what `0.2.0` changes.

| Status | Meaning |
|---|---|
| **Shipped** | Installed and wired by this package. You add nothing. |
| **Optional peer** | Wired by this package once you install it yourself: an optional peer dependency, never installed for you. |
| **Bundled** | Arrives through a shipped package or an optional peer. It works, but this package exposes no options of its own for it. |
| **Supported** | Works when you add it: the package already sets what it needs. |
| **Planned** | On the roadmap for the release named in the notes. |
| **Recipe** | Works beside the package with a little code of your own. There is no wrapper. |
| **Not planned** | Left out on purpose, for the reason given. |

## What changes

`0.2.0` keeps the packages that carry a feature and drops the thin wrappers around the rest:

- **Direct imports (SIMPLIFY).** The `counter`, `cache`, `workpool`, `migrations`, `aggregate` and `crons` subpaths go. Your app imports `@convex-dev/sharded-counter`, `@convex-dev/action-cache`, `@convex-dev/workpool`, `@convex-dev/migrations`, `@convex-dev/aggregate` and `@convex-dev/crons` itself, as their own docs show, and mounts the ones it uses. The package's own maintenance runs inside its component.
- **Optional peers.** `botid` is an optional peer like `@sentry/nuxt`: install it for the bot check on Vercel.
- **Left for the next release (DEFER).** `@nuxtjs/mcp-toolkit` is no dependency of the package: it went with the end-user MCP endpoint ([Roadmap](/docs/start/roadmap)).
- **An image provider.** With `@nuxt/image` in your modules, `<NuxtImg provider="backend">` resizes files from storage through your host's optimizer.
- **Chat and knowledge search.** `@convex-dev/agent` and `@convex-dev/rag` are optional peers: install and mount them for [chat](/docs/build/ai/chat) and [knowledge search](/docs/build/ai/chat/knowledge-search).
- **Not planned any more.** Presence is a collaboration feature: an app that needs it mounts `@convex-dev/presence` itself.
- **One webhook verifier.** Both webhooks verify with `standardwebhooks`, and `svix` leaves the dependencies (SIMPLIFY).

| `@nuxtjs/seo` · `nuxt-schema-org` · `nuxt-seo-utils` | Supported | With any of them, the [pricing page](/docs/build/billing/pricing-page#meta-tags-and-search) adds Open Graph tags and its plans and packs as schema.org `Product` / `Offer` data | Without one it keeps to its meta description. | `@nuxt/image` | Supported | The `backend` [image provider](/docs/build/data/files/images#resize-with-the-image-provider): a file URL from storage, resized and converted by your host's optimizer | Add it to your modules: the module registers the provider and adds the deployment's file hosts to `image.domains` |
| `@nuxt/test-utils` | Supported | [`nuxt-backend/test-utils`](/docs/develop/testing/pages): `createBackendMock` and `backendTestAliases` put a fake backend and session under your pages and components | Install it yourself as a dev dependency; the entry is experimental |
| `@nuxtjs/i18n` | Supported | `backend.*` messages [translate](/docs/build/ui/customize/translation) every packaged page and component; the pages follow its routing. | `@sidebase/nuxt-auth` | Not planned | | Same reason |
| `@clerk/nuxt` | Not planned | | A hosted identity provider replaces what the package owns |
| `@nuxthub/core` | Not planned | | A different platform: the backend here is Convex |
| `convex-nuxt` | Not planned | | A thinner, client-only Convex module; use it instead when you want bindings without the SaaS layer |

## Convex tooling

| Package | Status | Surface | Notes |
|---|---|---|---|
| `convex` | Shipped | The peer dependency and the CLI | `npx nuxt-backend dev` runs it for you |
| `convex-helpers` | Shipped | The custom functions behind [`createFunctions`](/docs/build/auth/access/functions), and the triggers behind [aggregates](/docs/build/data/read-write/aggregates) | |
| `convex-test` | Optional peer | [`nuxt-backend/test`](/docs/develop/testing) registers the component | Install it to run the test helpers |
| `@convex-dev/eslint-plugin` | Optional peer | [`nuxt-backend/eslint`](/docs/develop/testing/linting) | Install it beside the preset |

The rest of Convex's tooling works as it does anywhere:

- **The dashboard.** The DevTools tab links to it for a cloud deployment.
- **The MCP server.** `npx convex mcp start` lets an agent read the deployment. The [developer MCP server](/docs/develop/agents/developer-mcp) `init` writes into `.mcp.json` runs it for the project and passes its tools through, so the project needs no `convex` server of its own.
- **The AI guidelines.** `npx convex ai-files install` writes Convex's own rules for agents.
- **Local and self-hosted backends.** An anonymous local deployment is enough for development, and a self-hosted URL works through the Convex CLI's own variables.

## Bot protection

| Package | Status | Surface | Notes |
|---|---|---|---|
| `botid` | Optional peer | Vercel BotID: the invisible [bot check](/docs/build/auth/sign-in/bots) on the app's server, which then signs a proof the deployment checks | Runs only on Vercel, where its Basic check is free on every plan; in development it answers human. An optional peer: install it for Vercel (`npm install botid`) |

Wherever the app has a site key (the way off Vercel), the bot check is a Cloudflare Turnstile challenge verified through Better Auth's own captcha plugin, which ships with `better-auth`: no package of its own.

## Monitoring

| Package | Status | Surface | Notes |
|---|---|---|---|
| `@sentry/nuxt` | Optional peer | [Error reports, traces, log lines, replays after consent and feedback](/docs/ship/operate/monitoring) from the browser and the Nuxt server, tagged with the backend function and its error code, personal data scrubbed | Install it and set `MONITORING_DSN`, or let its Vercel integration set `NEXT_PUBLIC_SENTRY_DSN`: the module wires it with its own config files and preset; an app without it never imports it |

## Agent tooling

| Package | Status | Surface | Notes |
|---|---|---|---|
| `skills` | Supported | The [`nuxt-backend` skills](/docs/develop/agents): the core and a task skill per feature | `npx skills add https://nuxt-backend.dev --skill '*'` lists and installs them all; in an app, `init` copies the installed version's into `.agents/skills/` the way the CLI lays them out |

Beyond the skills, `init` writes an `AGENTS.md` section and `.mcp.json` for coding agents. `.mcp.json` holds one server, `nuxt-backend mcp`, which reads the project's state and docs and passes through to Convex, Polar, Resend and Vercel. This site publishes [`llms.txt`](/llms.txt) and a read-only [docs MCP](/docs/develop/agents/docs-mcp).

## Templates

Apps start from Nuxt's own `create nuxt` with a [template](/docs/start/templates): the starter, Panels or the advanced example. Once the package is listed on [nuxt.com/modules](https://nuxt.com/modules), `create nuxt` and `npx nuxt module add backend` offer it by name.
