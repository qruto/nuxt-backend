The package's composables are shaped like [VueUse](https://vueuse.org)'s: learn the shape once and
every composable reads the same. This page is that shape. [Composables](/docs/reference/nuxt/composables)
lists each one's signature.

## Calling one

```ts
const delivery = useEmailStatus({ emailId })                          // options only
const { results } = useSearch(api.search.searchMessages, { term })     // the query it reads, then options
```

- **Options come in one object**, typed `Use<Name>Options`. A composable that reads a query you
  wrote takes that query first, the way `useQuery` does, and its options second. `useAggregate`
  is the exception: after the query it takes the query's own arguments, positionally, exactly as
  `useQuery` does (`'skip'` included).
- **Inputs are `MaybeRefOrGetter`.** Pass a plain value, a ref, a computed or a getter
  (`() => route.params.id`); the composable reads it reactively and follows every change.
- **An empty input pauses a read.** An `undefined`, `null`, empty or whitespace-only id, address
  or term skips the query: nothing is sent, and nothing is loading.
- **A call in the old shape warns.** In development, passing a bare value, ref or getter where
  the options object goes logs a warning naming the new call.

## What it returns

A plain object, typed `Use<Name>Return`, of refs and functions. Destructure it freely: every value
in it is a ref, so destructuring keeps it reactive.

| Name | For | Means |
|---|---|---|
| `data`, or a name for what it holds (`results`, `messages`, `sessions`) | reads | The value. `undefined` until the first read lands, while paused, and after a failed read. `null` when the server answered that there is nothing (no such email). A list that is empty while loading says so in its own doc |
| `isLoading` | reads | `true` until the first read for the current inputs lands. `false` while paused, and once a read has failed |
| `isPending` | actions | `true` while an action runs |
| `error` | both | `null`, or why the last read or action failed: `{ code, data, message }` |

### `error`

`error` is the same `{ code, data, message }` that [`getBackendError`](/docs/data/errors) reads,
so one reader handles a composable's failure and a failure you caught yourself:

- **A refusal** carries its catalog code and fields: `unauthenticated`, `rate_limited` with
  `retryAfter`, `insufficient_credits` with `balance` and `need`, … [Errors](/docs/reference/backend/errors)
  lists them.
- **Anything else** (a function that crashed, which production words as "Server Error", or an
  app's own `ConvexError('…')`) reads as `unavailable` with service `backend` and reason
  `unexpected`. That does not mean a service is down: it means the failure carried no code. Its
  `message` is the sentence the app wrote, or "Something went wrong."; never the platform's
  wrapper. In development the original error is also logged to the console, and it rides along
  as the value's non-enumerable `cause`.
- **`message`** is a sentence to show a person. Branch on `code`, never on `message`.

A composable with both a read and actions holds the last action's failure first, and the read's
when no action has failed. An action clears its own failure when the next one starts.

```vue
<script setup lang="ts">
const { sessions, revoke, isPending, error } = useSessions()
</script>

<template>
  <p v-if="error?.code === 'rate_limited'">Too many tries. Wait a moment.</p>
  <p v-else-if="error">{{ error.message }}</p>
  <button v-for="session in sessions" :key="session.id" :disabled="isPending" @click="revoke(session.id)">
    Sign out {{ describeUserAgent(session.userAgent) ?? 'an unknown device' }}
  </button>
</template>
```

## Reads never throw, actions reject

- **A read never throws.** A refused or crashed query lands in `error`, and the page keeps
  rendering. Nothing to wrap in `try`.
- **An action resolves or rejects.** It resolves with its result, or rejects with the error the
  call threw, as the call threw it, and mirrors it into `error`. Await it in a `try` when the next
  step depends on it; otherwise let `error` show the failure.

```ts
try {
  await revoke(id)
  toast('Signed out.')
}
catch (cause) {
  // `error` already holds getBackendError(cause) ?? unavailable/unexpected.
}
```

## Step machines never reject

`useLoginFlow` and `useEmailChange` drive a form through steps (`request-code`, `verify-code`, …).
Their actions never reject: a failed step stays where it is, with the reason in `error` and a
`retryAfter` after a rate limit, so a form never needs a `try`.

## Which composables follow them

`useSearch`, `useAggregate`, `useWorkflowStatus`, `useEmailStatus`, `useSandboxInbox` and
`useSessions` follow every rule on this page. The [Composables](/docs/reference/nuxt/composables)
reference gives each other composable's shape as it is.
