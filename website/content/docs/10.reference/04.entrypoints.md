This page lists every import path the package publishes, where its code runs, and what you take from it. Use it to find the subpath a name comes from. You consume the package two ways:

- **Explicit imports** from `nuxt-backend/<subpath>`, declared in the package `exports` map. Every subpath but the module, `test`, `test-utils` and `eslint` runs in your Convex backend (`backend/`), not in the Vue app.
- **Auto-imports** the module registers, with no `import` statement: composables and components in app code ([Composables](/docs/reference/nuxt/composables), [Components](/docs/reference/components)), and `backendAuth` in `server/` ([Server utilities](/docs/reference/nuxt/server-utilities)).

## Every subpath

The import tree and the exports map below are generated from `package.json` and the module's registry. The package re-exports none of the Convex components it builds on: an app that uses `@convex-dev/sharded-counter`, `@convex-dev/action-cache`, `@convex-dev/workpool`, `@convex-dev/migrations`, `@convex-dev/aggregate` or `@convex-dev/crons` imports it directly ([Ecosystem](/docs/reference/ecosystem)). The package's own maintenance runs inside its component, so your app registers no cron for it.

One more import path is a Nuxt alias rather than a subpath: `#backend/a11y`, in app code, exports the helpers the headless bindings are built on, `useActionState`, `useFocusReturn` and `useLiveRegion` ([Headless bindings](/docs/reference/nuxt/composables#headless-bindings)).

## Selected entrypoint signatures

### `nuxt-backend/auth.config`

```ts
import defineBackendAuthConfig, {
  type DefineBackendAuthConfigOptions,
} from 'nuxt-backend/auth.config'

function defineBackendAuthConfig(options?: DefineBackendAuthConfigOptions): AuthConfig
interface DefineBackendAuthConfigOptions {
  paths?: Partial<BackendPaths>  // the paths.generated.ts the module writes;
                                 // reads authRoute (default '/api/auth')
  jwks?: string
}
```

### `setupAuth` options

`setupAuth` in `backend/auth.ts` takes these options:

```ts
interface SetupAuthOptions<DM> {
  authConfig?: AuthConfig          // replaces the default Convex auth config
  authOptions?: BetterAuthOptions  // merged with the package's defaults
  paths?: Partial<BackendPaths>    // paths.generated.ts: the auth route and the
                                   // pages its emails link to
  admin?: AdminPluginOptions       // roles, bans and impersonation
  workspaces?: WorkspaceOptions    // invitationExpiresIn, canInvite and the
                                   // onCreate / onMemberAdded / onMemberRemoved hooks
  email: AuthEmail                 // the setupEmail result every auth email uses
  rateLimiter?: AuthRateLimiter    // code sends and privileged routes
  access?: AuthAccess              // setupAccess(...): the launch phases
  canSignIn?: CanSignIn<DM>        // a veto of your own, after the phases
  onUserCreated?: OnUserCreated<DM>
  onUserDeleted?: OnUserDeleted<DM>
  audit?: AuthAudit                // setupAudit(...): auth events reach its onEvent
  account?: AuthAccount            // setupAccount(...): a deletion erases everything
                                   // of the account through it
}
```

You pass the result of `setupAccess` as `access`: the launch phases, invite codes and access links decide who may sign up, and your own `canSignIn` can still refuse after them. [Hooks and guarantees](/docs/reference/backend/hooks) says when the package calls each hook.
