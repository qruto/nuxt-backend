The components that sell and show billing. They read the billing entity of the session: the active workspace, or the user with `billTo: 'user'`. Each one keeps the [component contract](/docs/reference/components#the-component-contract): its props, slots, events, states and accessibility are listed in its section.

## What changes

`0.2.0` keeps six billing components, adds three, and folds the rest into the one gate and the one notice region:

| Component | In `0.2.0` |
|---|---|
| `<PricingTable>`, `<BillingCheckoutLink>`, `<BillingPortalLink>`, `<BillingHistory>`, `<UsageHistory>`, `<UpgradePrompt>` | Kept, with their props, slots and events |
| `<CancelFlow>`, `<WithdrawalButton>`, `<ReferralCard>` | New: the cancel flow, the EU withdrawal button and a person's referral link |
| The low-credits banner | The `low-credits` notice of [`<BackendNotices>`](/docs/reference/components/shell#backendnotices): no longer a public component |
| The gift-claim banner | The `gift` notice of `<BackendNotices>`: no longer a public component |
| The quota and feature boundaries | The `quota` and `feature` props of [`<Gate>`](/docs/reference/components/shell#gate) |

The [Upgrade](/docs/ship/releases/upgrade) page names each one 0.1 had.

`<UpgradePrompt>` is what a gate's `fallback` slot shows when a plan lacks a feature. With `cooldown` (ms) it offers "Not now", and a person who dismissed it doesn't see it again for that long ([Wait before asking again](/docs/build/billing/subscriptions/feature-gating#wait-before-asking-again)).

Three components are new:

- **`<CancelFlow>`** cancels in one step. Where save offers are on, it first asks one optional question and makes the one offer `useBilling().cancel({ reason })` answers with (a pause, a downgrade or a win-back promotion), with "Cancel my plan" on every screen ([Handle cancellations](/docs/build/growth/engage/cancel-flow)).
- **`<ReferralCard>`** shows a person's referral link with copy and share buttons, and says beside it what both sides get ([Run a referral program](/docs/build/growth/offers/referrals)). The page a referral link opens, `/r/:code` (`pages.referral`), is not a component of the list: it is built on `useReferrals()` and `claimReferral`.
- **`<WithdrawalButton>`** is the EU withdrawal button, with a confirm step and an email receipt, for where Polar doesn't provide one ([Follow subscription law](/docs/ship/compliance/subscriptions)). The gifts page is not a component of the list: `/gifts` (`pages.gifts`) is built on `useGifts()`, and a page of your own gets the same ([Send, receive and manage gifts](/docs/build/growth/offers/gifts#manage-gifts)).

## `<BillingCheckoutLink>`

A link that opens a checkout for the caller's billing entity. The session is created on click, through the app's `generateCheckoutLink`, so the server checks every input then — never on render, where each page view would open a checkout nobody uses. It returns to the current page unless `success-url` says otherwise, and opens in the same tab unless `redirect` is `false`. A refusal (an off-catalog product, a signed-out visitor) is emitted as `error`; read it with `getBackendError`. It renders nothing for a caller the server says manages none of the billing (`useBilling().canManage`). While a topic of the app's takes the EU soft opt-in (`useBilling().softOptIn`), the soft opt-in's notice and its "Don't email me" box (`PricingEmailOptOut`) follow the link, and its checkout says whether the box was ticked.

## `<BillingPortalLink>`

A link that opens the billing customer portal for the caller's billing entity, through the app's `generateCustomerPortalUrl`, on click. With workspaces the portal is the caller's own member of the workspace's billing customer: anyone but its owner or an admin is refused (`forbidden`, reason `not_billing_manager`), and an entity that never paid has no portal yet (`not_ready`, reason `no_customer`) — both emitted as `error`. It renders nothing for a caller the server says manages none of the billing (`useBilling().canManage`).

## `<CancelFlow>`

Cancelling takes one step; a save offer is one optional step (LIFECYCLE). The flow asks one optional question, the main reason with a comment, and shows at most the one offer the server answers for it (a pause, a cheaper plan or a discount, by its real terms), then the end: the date the plan ends and a "Keep my plan" button until then. "Cancel my plan" is on every screen and finishes at once, a button of the same size and style as the offer's. Which offer, and whether one may be made at all (none in the withdrawal period, on a past-due plan or a trial, one per customer in 12 months), is the server's: `setupBilling({ lifecycle: { saveOffers } })`.

## `<WithdrawalButton>`
