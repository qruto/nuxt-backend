These components frame an app rather than fill a page. `<Gate>` shows its content only to the people a rule admits, `<BackendNotices>` holds every notice that applies to the whole session, `<AppShell>` is the frame your layout renders, and `<NotificationInbox>` lists what the app told a person. `<AccessDenied>` is what the [page guard's](/docs/build/auth/access/pages) 403 shows in your error page, and `<ConnectionStatus>` says when the live connection drops. Each section lists the component's props, slots, events, states and accessibility, as the [component contract](/docs/reference/components#the-component-contract) asks of every one.

## What changes

`0.2.0` keeps one gate and one notice region, so a template has one way to do each:

- **One gate (SIMPLIFY).** `<Gate>` replaces `<RoleBoundary>`, `<OrganizationBoundary>`, `<FeatureBoundary>` and `<QuotaBoundary>`: each boundary's check is now one prop of it.
- **One notice region (SIMPLIFY).** `<BackendNotices>` replaces `<ImpersonationBanner>`, `<MaintenanceBanner>`, `<CreditsLowBanner>` and `<GiftClaimBanner>`. Those banners stop being public components, and each lives on as a notice of the region, overridden through its slot.
- **The app shell.** `<AppShell>` makes the frame of the ready-made pages a component your own layout renders. It has a section of its own at the end of this page.
- **A past-due notice.** `<BackendNotices>` gains the `past-due` slot, shown to the billing managers while a payment has failed and the provider retries it; it receives `{ message, portal, isPending }`.
- **The page guard (SIMPLIFY).** `<AccessDenied>` answers the one page guard, `definePageMeta({ auth })`, and words its `role`, `workspace` and `feature` rules. A rule with `hidden: true` answers 404 instead, so the page never says it exists.

`<AccessDenied>` and `<ConnectionStatus>` keep their props, slots and events.

## `<Gate>`

Renders its default slot only when the session passes every check its props name, and its `fallback` slot when one refuses. It has no markup, labels or family of its own, but for the refusal it renders for `quota`. Naming any check also asks for a sign-in, so a signed-out visitor gets the fallback. [Show parts of a page to the right people](/docs/build/ui/gate) shows how to use it.

| At a glance |  |
|---|---|
| Replaces | `<RoleBoundary>`, `<OrganizationBoundary>`, `<FeatureBoundary>`, `<QuotaBoundary>` |
| Rendered by | no ready-made page: place it yourself |
| Family | none: it renders only your slots, but for the quota refusal, which keeps the `quota` family |
| Labels | [`quota`](/docs/reference/configuration/labels#quota), for the quota refusal |
| Slots | `default`, `fallback`, `placeholder`, `error` |
| Events | none |
| States | loading, ready, refused, error |
| Status | Built |

**Props**

| Prop | Type | Default | Passes when | Replaces |
|---|---|---|---|---|
| `signed-in` | `boolean` | `false` | A signed-in account that is not banned | The session check every boundary made |
| `role` | `string \| string[]` | none | The account holds one of these app-wide roles, such as `admin` | `<RoleBoundary role>` |
| `workspace` | `boolean \| string \| string[]` | `false` | `true`: the session has an active workspace. A role or a list: the person holds one of them there, as the page rule reads it | `<OrganizationBoundary>` |
| `feature` | `string \| string[]` | none | The active workspace's plan grants one of these features, by catalog key | `<FeatureBoundary feature>` |
| `quota` | `string` | none | The plan has room for `amount` more of this quota | `<QuotaBoundary quota>` |
| `amount` | `number` | `1` | How many the content needs room for, with `quota` | `<QuotaBoundary amount>` |

`<RoleBoundary permission>` has no counterpart: custom permissions wait for the next release ([Roadmap](/docs/start/roadmap)), so check an app-wide role instead. `<FeatureBoundary plan>` has none either: a gate asks for a feature a plan includes, never for a plan by name ([Feature gating](/docs/build/billing/subscriptions/feature-gating)).

**Slots**

| Slot | Renders | Receives |
|---|---|---|
| `default` | Every check passed | `workspace` with `workspace`; `limit`, `used` and `remaining` with `quota` |
| `fallback` | A check failed | With `quota`: the plans that allow more, and the link to the first |
| `placeholder` | The checks are loading, on the server render and until the page has hydrated | Nothing |
| `error` | The plan's features or quotas could not be read | `{ error }`, as `{ code, data, message }` |

Without a `fallback`, a failed check renders nothing, except `quota`: it says how many are used of how many, names the plans that allow more and links to the first. A member who manages no billing reads who to ask instead of a link. The server render shows the `placeholder`, never the content.

```vue [app/pages/stories/index.vue]
<template>
  <Gate feature="illustrations">
    <NuxtLink to="/stories/new">New story</NuxtLink>
    <template #fallback>
      <UpgradePrompt feature="illustrations" />
    </template>
  </Gate>
</template>
```

A gate hides what a person should not see; it secures nothing. The server makes the same checks with the `authed`, `workspace`, `withRole` and `withFeature` tiers and `billing.requireQuota` ([Protect backend functions](/docs/build/auth/access/functions)), and a whole page with `definePageMeta({ auth })` ([Protect pages and routes](/docs/build/auth/access/pages)).

**Accessibility:** Renders exactly one slot, so each state is as accessible as what you put in it. Loading is the `placeholder`, or nothing. With `quota`, the packaged refusal is a polite status whose one stop is a real link, and a failed read is an alert.

## `<BackendNotices>`

The one region for every notice that holds for the whole session: an administrator's visit, maintenance, a scheduled deletion, low credits, a gift to claim and announcements. Every ready-made page renders it in its frame, and so does `<AppShell>`. Place it once in your layout otherwise. It renders nothing while no notice applies: what stays is an empty live region the notices appear in. [Show app-wide notices](/docs/build/ui/notices) shows how to use it.

| At a glance |  |
|---|---|
| Replaces | `<ImpersonationBanner>`, `<MaintenanceBanner>`, `<CreditsLowBanner>`, `<GiftClaimBanner>` as public components |
| Rendered by | every ready-made page, in its frame, and `<AppShell>` |
| Family | each notice keeps the family of the banner it was: `data-impersonation`, `data-maintenance`, `data-deletion`, `data-credits`, `data-gift`, and `data-announcement` |
| Labels | each notice its own group: [`impersonation`](/docs/reference/configuration/labels#impersonation), [`maintenance`](/docs/reference/configuration/labels#maintenance), [`credits`](/docs/reference/configuration/labels#credits), [`gift`](/docs/reference/configuration/labels#gift), [`deletion`](/docs/reference/configuration/labels#deletion), [`announcement`](/docs/reference/configuration/labels#announcement) |
| Slots | `impersonation`, `maintenance`, `deletion`, `low-credits`, `gift`, `announcement` |
| Events | none: each notice's actions are in its slot's props |
| States | empty, ready |
| Status | Built |

**Props**

| Prop | Type | Default | What it does |
|---|---|---|---|
| `threshold` | `number` | `appConfig.backend.billing.lowCreditsThreshold`, `10` | The balance under which the low-credits notice shows |

**Notices**, most important first, the order they stack in when several apply:

| Notice | Shows while | Slot | Arrives with |
|---|---|---|---|
| An administrator's visit | An administrator acts as the account: whose account, when the visit ends, and a way out | `impersonation` | Built, as `<ImpersonationBanner>` |
| Maintenance | The maintenance switch is on ([Kill switches](/docs/ship/operate/flags#kill-switches)), with the administrator's message | `maintenance` | Built, as `<MaintenanceBanner>` |
| Deletion scheduled | The account's deletion waits out its grace period: when it happens, and a **Keep my account** button; its slot receives `{ deletion, message, keep, isPending, error }` | `deletion` | Built |
| Low credits | The balance is under `threshold`, with a top-up | `low-credits` | Built, as `<CreditsLowBanner>` |
| A gift to claim | A gift addressed to the person waits, with a claim button | `gift` | Built, as `<GiftClaimBanner>` |
| Announcements | An announcement you published is live and not dismissed, the three newest, each with a **Dismiss** button; its slot receives `{ announcements, dismiss, isPending }` | `announcement` | Built |

**Slots.** A named slot replaces that notice and receives its state and actions, such as `{ balance, topUp, dismiss }` for `low-credits`. An empty slot turns that notice off. A slot never renders while its notice does not apply.

```vue [app/layouts/default.vue]
<template>
  <div>
    <BackendNotices>
      <template #low-credits="{ balance, topUp, dismiss }">
        <p>Only {{ balance }} credits left for new stories.</p>
        <button type="button" @click="topUp()">Add credits</button>
        <button type="button" @click="dismiss()">Not now</button>
      </template>
      <template #gift />
    </BackendNotices>
    <slot />
  </div>
</template>
```

**Accessibility:** One polite live region stays mounted, and each notice appears inside it, so a screen reader announces it. Each notice is a region named in words, never by colour alone. A dismissed notice leaves focus where it was, and a page shows each notice once, however many regions are mounted.
