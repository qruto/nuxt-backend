Better Auth is wired in by the module. App code talks to it through a single composable — `useAuth()` — plus an opt-in route middleware and three auth-state components.

## `useAuth()`

`useAuth()` is the single Better Auth service. It exposes the Better Auth client, the reactive session wrapper, the computed auth state used by the Convex integration, and the passwordless calls the packaged pages use:

```vue
<script setup lang="ts">
const { client, session, isAuthenticated, isLoading, sendOtp, signInWithOtp, signOut } = useAuth()

await sendOtp('user@example.com')                              // emails a one-time code
await signInWithOtp({ email: 'user@example.com', otp: '123456' }) // signs in, or signs up on first use
const user = computed(() => session.value.data?.user)
</script>
```

Sign-in is passwordless by default: an emailed one-time code, with an optional passkey saved afterwards. Better Auth client calls **resolve** `{ data, error }` instead of throwing — check `error`, or wrap the call in `unwrapAuth()` (auto-imported) to turn it into an exception.

::callout{icon="i-lucide-key-round"}
Email + password is off (`emailAndPassword.enabled: false`). To offer it as well, pass `authOptions: { emailAndPassword: { enabled: true } }` to `setupAuth` in `backend/auth.ts` ([customizing auth](/platform/auth/customizing)) — after which `client.signIn.email({ email, password })` and `client.signUp.email(...)` work as in the Better Auth docs.
::

## Signing in

The shipped `/login` page and the `<AuthForm>` component are built on `useLoginFlow()`. For your own page, use the same composable — it owns the step state (`choose` → `request-code` → `verify-code` → `add-passkey`), validation, the pending flag and the error message:

```vue [pages/login.vue]
<script setup lang="ts">
const { step, email, otp, pending, error, sendCode, verifyCode, skipPasskey, signInWithPasskey, goTo } = useLoginFlow({
  onSuccess: () => navigateTo('/account'),
})
</script>

<template>
  <form v-if="step === 'choose' || step === 'request-code'" @submit.prevent="sendCode">
    <input v-model="email" type="email" placeholder="Email" autocomplete="email">
    <button :disabled="pending" type="submit">Email me a code</button>
    <button type="button" @click="signInWithPasskey">Use a passkey</button>
  </form>

  <form v-else-if="step === 'verify-code'" @submit.prevent="verifyCode">
    <input v-model="otp" inputmode="numeric" autocomplete="one-time-code" placeholder="6-digit code">
    <button :disabled="pending" type="submit">Sign in</button>
    <button type="button" @click="goTo('request-code')">Use another email</button>
  </form>

  <div v-else-if="step === 'add-passkey'">
    <p>Signed in. Save a passkey for next time?</p>
    <button type="button" @click="skipPasskey">Not now</button>
  </div>

  <p v-if="error">{{ error }}</p>
</template>
```

Pass `offerPasskey: false` to finish right after the code is verified. Every step is also available one level down on `useAuth()` — `sendOtp`, `signInWithOtp`, `signInWithPasskey`, `registerPasskey` — when a page needs a shape the composable does not model.

## Reading session state

```vue [pages/account.vue]
<script setup lang="ts">
import { api } from '#backend/api'

definePageMeta({ middleware: 'auth' })

const { session } = useAuth()
const currentUser = useQuery(api.auth.getAuthUser, {})
const email = computed(() => session.value.data?.user.email)
</script>

<template>
  <section>
    <p>Signed in as {{ email }}</p>
    <pre>{{ currentUser }}</pre>
  </section>
</template>
```

`useAuth().session` exposes the Better Auth session, and `useQuery(...)` keeps Convex data live after hydration.

## Protecting routes

Guard a page with the built-in `auth` middleware — it's registered **non-global**, so installing the module never guards routes by surprise:

```vue
<script setup lang="ts">
definePageMeta({ middleware: 'auth' })
</script>
```

Unauthenticated users are redirected to `/login` (the [`loginPath`](/api-reference/module-options) option, when the built-in page is replaced) with the original destination in `?redirect=`. The guard runs on the server for direct loads and in the browser for client-side navigation.

`auth` is this package's name for the guard `nuxt-convex-module` registers as `convex-auth` — both stay registered and point at the same middleware, so code written against the base module keeps working.

## Auth-state components

Three components render their slot based on auth state — useful for headers, menus, and loading skeletons:

```vue
<template>
  <Authenticated>Signed in — show the dashboard</Authenticated>
  <Unauthenticated>Show a sign-in button</Unauthenticated>
  <AuthLoading>Resolving auth…</AuthLoading>
</template>
```

| Component | Renders its slot when |
|---|---|
| `<Authenticated>` | the user is authenticated |
| `<Unauthenticated>` | the user is unauthenticated |
| `<AuthLoading>` | auth state is still resolving |

## Workspace invitations

Workspaces (the organization plugin) ship a complete invitation flow, end-to-end:

1. A member calls `useOrganization().invite({ email, role })`.
2. The invitee receives an email with an accept link — `{SITE_URL}{invitationPath}?id=<invitationId>`, where `invitationPath` defaults to `/accept-invitation`.
3. The link lands on the built-in `/accept-invitation` page (auto-registered by the module behind the `auth` middleware, so signing in first is enforced), which renders `<AcceptInvitation>` — workspace + inviter details with accept/decline buttons.
4. Accepting joins the workspace (and can activate it); declining rejects the invitation.

```vue
<script setup lang="ts">
const org = useOrganization()

await org.invite({ email: 'teammate@example.com', role: 'member' })
</script>
```

Beyond `invite`, `useOrganization()` covers both sides of the flow:

```ts
const {
  acceptInvitation,        // (invitationId, { activate? }) — join, optionally set active
  declineInvitation,       // (invitationId)
  cancelInvitation,        // (invitationId) — inviter side, revoke a pending invite
  getInvitation,           // (invitationId) — details for a custom accept page
  listReceivedInvitations, // invitations addressed to the signed-in user
} = useOrganization()
```

### Customizing the flow

- **Email template** — override `invite` in `integrations.emailTemplates` on `setupAuth` to restyle the invitation email without replacing the transport, or supply your own `organization.sendInvitationEmail` to take over delivery entirely.
- **Link path** — set `organization: { invitationPath: '/join' }` in `setupAuth` to change where emailed links point.
- **Page** — the module option `pages.acceptInvitation` controls the built-in page: `true` (default) mounts `/accept-invitation`, a string mounts a custom path (keep it in sync with `invitationPath`), `false` disables it.

A custom accept page is just the component behind the `auth` middleware — it reads `?id=` from the URL itself:

```vue [app/pages/join.vue]
<script setup lang="ts">
definePageMeta({ middleware: 'auth' })
</script>

<template>
  <AcceptInvitation />
</template>
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-backend'],
  backend: { pages: { acceptInvitation: false } }, // bring your own page
})
```

```ts [backend/auth.ts]
setupAuth(components, query, {
  organization: { invitationPath: '/join' },
})
```

## Advanced: low-level auth helpers

The package also exports low-level Convex auth helpers for custom auth integrations: `provideConvexAuth`, `useAuthState`, and the components above. These are building blocks for custom auth providers and are **not required** for the default Better Auth setup scaffolded by the module.

```ts
function useAuthState(): { isLoading: boolean, isAuthenticated: boolean }
function provideConvexAuth(options: ConvexAuthProviderOptions): ConvexAuthState
```
