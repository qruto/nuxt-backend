Install the module and these routes exist — no files, no config:

| Route | Page | Access | Built on |
|---|---|---|---|
| `/login` | Passwordless sign-in (passkeys + email OTP) | public | `<AuthForm>` · `useLoginFlow` |
| `/pricing` | Plan cards + credit packs, live from billing | public | `<PricingTable>` · `useBilling`, `useCredits` |
| `/settings` | Workspaces, plan summary, credits | auth | `<WorkspaceSettings>` · `useOrganization` |
| `/profile` | Identity, display name, change email | auth | `<ProfileSettings>` · `useAuth` |
| `/security` | Verification, passkeys, sessions, deletion | auth | `<SecuritySettings>` · `usePasskeys`, `useSessions` |
| `/accept-invitation` | Workspace invitation accept links | auth | `<AcceptInvitation>` |

Each page is a thin wrapper around one auto-imported component, styled by the
neutral `ui.css` the module adds. The `/login` path doubles as the `auth`
middleware's redirect target, and the original destination rides along as
`?redirect=` so sign-in returns the visitor where they were headed.

Configure the set with the [`pages` module option](/api-reference/module-options):

```ts
export default defineNuxtConfig({
  modules: ['nuxt-backend'],
  backend: {
    pages: {
      pricing: '/plans',   // custom path
      profile: false,      // bring your own
    },
  },
})
```

## Search engines

The four `auth` pages redirect a signed-out visitor to sign-in, so the module keeps them out of search indexes and sitemaps. For each one mounted, at its resolved path, it adds a route rule:

```ts
routeRules: {
  '/settings': { robots: false, sitemap: false },
  // …the same for /profile, /security and /accept-invitation
}
```

[`@nuxtjs/robots`](https://nuxtseo.com/docs/robots/getting-started/introduction) answers `robots: false` with a `noindex, nofollow` header and meta tag, and [`@nuxtjs/sitemap`](https://nuxtseo.com/docs/sitemap/getting-started/introduction) leaves the URL out; both come with `@nuxtjs/seo`. Without those modules the rules do nothing. `/login` and `/pricing` stay indexable, and `robots.txt` is not changed: `noindex` is the signal for a page that exists but has nothing public on it.

The rules follow the path, so an app page that shadows one of these gets them too. A rule you set for the same path wins key by key: `routeRules: { '/security': { robots: true } }` indexes that page again. A page disabled with `pages.<key>: false` gets no rule.

## The customization ladder

The neutral stylesheet (`nuxt-backend/ui.css`) makes every page work and
look intentional out of the box — see it live in the playground's
[Vanilla section](/playground/vanilla/pricing). When a page no longer fits,
climb one rung. Every rung keeps the packaged behavior, you only replace what
you outgrow, and there is nothing to eject. [Customization](/guide/customization)
is the reference for each rung; this is the map.

1. **[CSS tokens](/guide/customization#_1-css-tokens)** — every component
   reads the shared `--bk-*` custom properties, so one override re-themes
   everything at once. The `data-*` hooks on every element are there for
   direct styling, with or without the neutral stylesheet
   (`backend: { css: false }`).
2. **[`app.config` content](/guide/customization#_2-appconfig-content)** —
   the plan catalog, copy and brand live in `appConfig.backend`: reactive,
   HMR-friendly, typed. Plan `key`s match your `setupBilling` products
   map; names and prices always resolve live from billing, so the catalog
   can't drift.
3. **[Slots](/guide/customization#_3-slots)** — keep the packaged component
   and replace only the regions you care about. Every slot receives the full
   composable state the component runs on.
4. **[Route shadowing](/guide/customization#_4-route-shadowing)** — an app
   page at the same path always wins: the module detects it, skips its own
   and logs the override.
5. **[Composables](/guide/customization#_5-composables)** — for a fully
   custom page, drop the component and build on the same composables the
   packaged one uses. The playground's own [/login](/login) page is a worked
   example: full custom markup on `useLoginFlow`, shadowing the module's
   login page.
