`npx nuxt-backend <command>` ships with the package. Every command takes `--cwd <dir>` (default `.`, the project directory) and reads `.env` + `.env.local` from it; deployment env **values** are never read — only names, via `npx convex env list`.

## `init`

Scaffold the backend files, `.env.example`, and the `nuxt.config` wiring. Re-run any time to restore missing files — existing files are never touched unless you `--force`.

```bash
npx nuxt-backend init
npx nuxt-backend init --installation local   # scaffold the whole `backend` component locally
npx nuxt-backend init --force                # overwrite existing scaffold files
```

| Flag | Effect |
|---|---|
| `--installation default\|local` | Scaffold mode (default `default`). `local` installs the component under `backend/components/backend/` — see [Local installation](/tooling/local-installation). |
| `--force` | Overwrite existing scaffold files (and `.env.example`). |

What it does: writes every missing file from the [scaffold](/platform/auth/setup#the-scaffolded-files) into the Convex functions directory (`convex.json`'s `functions`, else an existing `backend/` or `convex/`, else `backend/`), writes `.env.example`, and adds `'nuxt-backend'` to `modules` in `nuxt.config.{ts,js,mjs}` via magicast (or tells you to). With `--installation local` it reminds you to `pnpm add @convex-dev/resend`. It ends with the next steps:

```text
Next steps:
  1. npx convex dev        # provisions the deployment + codegen (terminal 1)
  2. npm run dev           # derives URLs, provisions dev env, mounts /login (terminal 2)
  3. Sign in — with no EMAIL_API_KEY yet, the OTP code prints in the convex dev console.
```

The dev server runs the same scaffold on startup (`backend.scaffold: 'auto'`); set `scaffold: false` when you prefer `init` explicitly.

## `doctor`

Check the project and the deployment configuration. Exit code `1` when any finding fails.

```bash
npx nuxt-backend doctor
npx nuxt-backend doctor --prod     # production posture
npx nuxt-backend doctor --fix      # restore missing scaffold files + push env
npx nuxt-backend doctor --json     # machine-readable { findings, summary }
```

| Flag | Effect |
|---|---|
| `--prod` | Production posture: the optional tier's designed degradations become failures (see below). |
| `--fix` | Repair what doctor can: restore missing scaffold files (existing files untouched; local install auto-detected), then run the `env push` engine. |
| `--json` | Machine-readable output. |

### Findings

Each finding has an `id`, a status (`pass` / `warn` / `fail`), a message, and a fix hint:

| Id | Checks | Fails when |
|---|---|---|
| `backend-site-url` | A backend site URL is configured (module option, env, or derived from `CONVEX_DEPLOYMENT`) | — (warn) |
| `auth-secret` | `AUTH_SECRET` visible locally, ≥ 32 chars, not a placeholder | too short / placeholder |
| `site-url` | `SITE_URL` is a valid http(s) URL | malformed |
| `email-transport` / `email-webhook-secret` / `billing-access` / `billing-webhook-secret` | `EMAIL_API_KEY` / `EMAIL_WEBHOOK_SECRET` / `BILLING_ACCESS_TOKEN` / `BILLING_WEBHOOK_SECRET` visible locally | — (warn; **fail with `--prod`**) |
| `convex-codegen` | `<functions dir>/_generated` exists | — (warn) |
| `deployment-auth-secret`, `deployment-site-url` | The required pair is set on the deployment | not set |
| `deployment-email-api-key`, `deployment-email-from`, `deployment-email-test-mode`, `deployment-email-webhook-secret`, `deployment-billing-access-token`, `deployment-billing-webhook-secret`, `deployment-billing-environment` | Each optional var's presence on the deployment, with its designed degradation | — (warn; the key/secret ones **fail with `--prod`**) |
| `deployment-auth-trust-local-origins` | Dev-only: unset is healthy; set on a **non-dev** deployment is a leak | — (warn; **fail with `--prod`**) |
| `deployment-env` | The deployment env could be read at all | — (warn) |
| `mcp` | Reports the OAuth-protected agent endpoint's route; omitted when `backend.mcp: false` | — (always pass) |
| `billing-meter-usage` | Every meter in `billing.catalog.ts` is funded by a plan or pack credit grant, or billed by a usage price | — (warn: an orphan meter) |
| `billing-organization` | `BILLING_ACCESS_TOKEN` is visible locally and the provider answers with it for the active `BILLING_ENVIRONMENT` | — (warn: expired / wrong environment — the cross-checks below are skipped) |
| `billing-multiple-subscriptions`, `billing-proration`, `billing-benefit-grace`, `billing-trial-abuse`, `billing-portal`, `billing-feature-benefits` | The provider organization's settings against the catalog: one active subscription per customer when several plans exist, plan-change proration, benefit revocation grace, trial-abuse prevention when a plan has a trial, portal plan changes, native feature-flag benefits | — (warn) |
| `billing-webhook-route`, `email-webhook-route`, `ai-stream-route` | An unsigned empty POST probe of `/billing/events`, `/email/events`, `/ai/stream` on the site URL: `404` = not mounted, `503` = mounted but fail-closed (secret unset), other 4xx = mounted (probe rejected as expected) | 404; `503` warns (**fails with `--prod`**) |
| `function-contract` | Every function the composables bind to (`auth:getAuthUser`, `billing:getCredits`, `email:getEmailStatus`, …) exists in `npx convex function-spec` | any missing |
| `invitation-path` | `organization.invitationPath` (deployed `auth:authConfig`) matches `backend.pages.acceptInvitation` (nuxt.config) | mismatch — invitees would 404 |

The route probes, `function-contract` and `invitation-path` need the deployment (and `nuxt.config`) to be reachable and produce no finding otherwise; the `billing-*` catalog checks need a `billing.catalog.ts` and run the provider half only with a token visible locally. The same preflight (`backend-site-url` … `billing-webhook-secret`) runs on every dev-server start and in the [DevTools tab](/tooling/devtools).

## `env push`

Sync the backend env contract from `.env(.local)` onto the Convex deployment. On **dev** deployments (`dev:` and `local:`) it also fills the required gaps so onboarding needs no manual `convex env set`.

```bash
npx nuxt-backend env push
npx nuxt-backend env push --dry-run
npx nuxt-backend env push --prod
npx nuxt-backend env push --json
```

| Flag | Effect |
|---|---|
| `--prod` | Never invent values; fail (exit 1) on missing required env. Also treats the deployment as non-dev regardless of its slug. |
| `--dry-run` | Print the plan without setting anything. |
| `--json` | Machine-readable output. |

The plan, per variable of the contract (`AUTH_SECRET`, `SITE_URL`, `AUTH_TRUST_LOCAL_ORIGINS`, `EMAIL_*`, `BILLING_*`):

| Action | When |
|---|---|
| `skipped` | Already set on the deployment — **existing values are never overwritten** |
| `set` (forward) | Present in `.env(.local)` — forwarded |
| `set` (provision, dev only) | Required and missing: `AUTH_SECRET` is generated (32 random bytes, base64), `SITE_URL` defaults to `http://localhost:3000`; and `NUXT_BACKEND_LOG_OTP=1` is set while no `EMAIL_API_KEY` exists anywhere, so OTP codes print in the `convex dev` console |
| `MISSING` | Required and missing on a non-dev push — blocks with exit 1 |
| `unset` | Optional and absent — informational, with the designed degradation; dev-only vars are never forwarded to a non-dev deployment |

Values pass to `npx convex env set` as argv (never through a shell). The deployment is whatever the Convex CLI targets — `CONVEX_DEPLOYMENT` from `.env.local` in dev, or a `CONVEX_DEPLOY_KEY` in the environment for production. Without a reachable deployment the command exits 1 (`run npx convex dev once, then push again`).

::note
`backend.autoEnv` (default `true`) runs this same engine once per dev deployment on dev-server startup, stamped under `node_modules/.cache/nuxt-backend`, and watches `.env.local` for `CONVEX_DEPLOYMENT` to appear so the two first-run terminals can start in any order. It never touches non-dev deployments.
::

## `billing sync`

Push `backend/billing.catalog.ts` to the billing provider and write `backend/billing.generated.ts` — find-or-create, never deletes.

```bash
npx nuxt-backend billing sync
npx nuxt-backend billing sync --env production
npx nuxt-backend billing sync --dry-run
npx nuxt-backend billing sync --webhook off
npx nuxt-backend billing sync --adopt pro=prod_123,credits=meter_456
```

| Flag | Effect |
|---|---|
| `--env sandbox\|production` | Target environment (default `BILLING_ENVIRONMENT`, else `sandbox`). |
| `--dry-run` | Print the plan without creating anything. |
| `--webhook <url>` | Provision the webhook endpoint at this URL (default: derived `<site>/billing/events`; `off` to skip). |
| `--adopt key=<id>[,…]` | Record existing provider objects under catalog keys — recorded as-is, benefits untouched. |

Needs `BILLING_ACCESS_TOKEN` (env or `.env.local`) and a `billing.catalog.ts`. The full semantics — tagging, drift, adopted products, the generated map — are in [Catalog as code](/platform/billing/catalog-as-code).
