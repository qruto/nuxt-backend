## Content Security Policy

`nuxt-security` is a dependency of this package, and the module installs it in every app (ahead of `nuxt-convex-module`, which then finds it registered), so every app gets its security headers — and a CSP the Convex integration tightens for you: a Nitro plugin hooked into `nuxt-security:routeRules` extends **`connect-src`** (production only), **`img-src`**, and **`media-src`** with the deployment origins at runtime, on top of whatever the app configured, regardless of module order. Configure the rest through nuxt-security's own `security` key:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['nuxt-backend'],
  security: {
    headers: {
      contentSecurityPolicy: {
        // extend, e.g. an analytics origin; the Convex origins are added for you
        'connect-src': ['\'self\'', 'https://analytics.example.com'],
      },
    },
  },
})
```

Two route groups carry their own rules, merged over the global config (your `routeRules` can override them in turn):

- **The auth proxy** (`/api/auth/**`): `xssValidator: false` — the validator HTML-escapes JSON bodies and rejects anything that changed, which would break a display name containing `<`; these are opaque credentials forwarded to Better Auth, never rendered HTML. `allowedMethodsRestricter` limits it to `GET`, `HEAD`, `POST`, `OPTIONS`.
- **The agent surface** (`/mcp`, `/mcp/**`): nuxt-security's IP `rateLimiter`, `xssValidator`, and `corsHandler` are off — long agent sessions would trip the limiter, tool args can legitimately look like markup, and the MCP surface has its own guards (OAuth + the deployment's `mcp` limit). The `/.well-known/oauth-*` documents only relax `corsHandler` (they are fetched cross-origin by browser-based clients and answer with their own CORS headers).

`convex.security: false` opts out of the Convex CSP additions; `security: false` disables nuxt-security entirely (not recommended).

## Webhooks: fail closed

Both inbound webhooks (`/billing/events`, `/email/events`) share one policy, enforced before any handler runs:

| Condition | Status | Logged outcome |
|---|---|---|
| Secret env missing / empty | `503` | `missing_secret` |
| Invalid or stale signature (±5 min replay tolerance) | `403` | `invalid_signature` |
| Body over 1 MiB | `413` | `oversized` |
| Authentic, type unknown to this package | `202` | `unknown_type` |
| Handler threw | `500` (provider retries) | `handler_error` |
| Redelivery of a fully-processed id | `200` | `duplicate` |
| Success | `2xx` | `ok` |

Throw ⇒ 5xx ⇒ the provider retries against idempotent built-ins; dedupe short-circuits only `ok` outcomes; nothing is silently swallowed. There is deliberately **no rate limiting** on these routes — signature verification is the gate, and a limiter would drop the legitimate retry bursts after an incident. Every outcome lands in the component's delivery log (DevTools, playground, `getWebhookDeliveries`). `doctor` probes both routes and fails on `404` (not mounted) and `503` (mounted, unconfigured).

## Secret rotation

- **Webhook secrets** — `BILLING_WEBHOOK_SECRET` and `EMAIL_WEBHOOK_SECRET` accept a comma-separated accept-list (`whsec_new,whsec_old`; first entry primary). Add the new secret in front, rotate it in the provider dashboard, then drop the old one — zero downtime.
- **`AUTH_SECRET`** — signs sessions and encrypts the JWKS private keys. Rotating it invalidates every session and breaks the stored signing keys; treat it as an incident-response step, not routine, and follow [Troubleshooting](/production/troubleshooting#sessions-or-agent-tokens-fail-after-rotating-auth_secret).
- **Provider tokens** (`BILLING_ACCESS_TOKEN`, `EMAIL_API_KEY`) — rotate in the dashboard, set the new value, redeploy nothing: the functions read env at call time.

`env push` never prints values, never overwrites what is set (rotate with `npx convex env set` explicitly), and passes values as argv rather than through a shell.

## Privileged operations stay internal

The scaffold ships `createDiscount` and the marketing actions (`createAudience`, `addContact`, `createBroadcast`, `sendBroadcast`) as **`internalAction`s** — a public action would be a 100%-off coupon mint or an open relay on your verified domain. Expose one to an admin UI only by re-declaring it with the `admin.action` builder from [`functions.ts`](/platform/authorization). `setUserRole` is an `internalMutation` for the same reason.

Identity-gated reads: `getEmailStatus` (recipient and error detail), `getWebhookDeliveries` (event types and provider ids), and every billing read return `null` for anonymous callers.

## OAuth consent: what an agent can do

The agent surface is on by default because everything the built-in tools expose is already reachable through the product UI under the same user auth — OAuth adds **per-client consent** on top. The scopes are minimal by design:

| Scope | Grants |
|---|---|
| `openid` `profile` `email` | Identity — always granted by the provider |
| `profile:write` | Display **name** only. Email changes stay in the verified web flow, so an agent can never move an account to an unproven address |
| `billing:read` | Plans, the subscription, credit balances — reads |
| `billing:checkout` | Checkout and portal **links only**. The human opens them in a browser; no tool executes a payment. Success/return paths must be app-relative, so a prompt-injected agent can't bounce the paying user to another origin |
| `workspace:read` | Workspace list and members |

Beyond scopes: a tool is hidden without its scope and refused on a direct call; the minted Convex JWT lives 5 minutes and the Nitro cache expires with it, so revoking an agent's OAuth token cuts Convex access within minutes with no distributed invalidation; the exchange is throttled per client + user (`DEFAULT_LIMITS.mcp`); a deleted or banned account fails the exchange like an invalid token; `trustedClients` (`skipConsent`) should list first-party agents only. Or turn the whole surface off: `backend.mcp: false`. Details in [OAuth & consent](/agents/oauth-and-consent).

## Origins and dev flags

`SITE_URL` is the only trusted browser origin for auth. `AUTH_TRUST_LOCAL_ORIGINS=1` additionally trusts `http://localhost:*` / `http://127.0.0.1:*` — `env push` forwards it to dev deployments only, and `doctor` warns (fails with `--prod`) when it is present on a non-dev deployment. Nothing in the DevTools panel carries env values: only presence booleans cross the RPC.

## Reporting a vulnerability

Privately, through [GitHub Security Advisories](https://github.com/qruto/nuxt-backend/security/advisories/new) — not a public issue.
